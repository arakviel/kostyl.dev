# Скіл: Створення лекцій для коледжу (College Lectures Creator)

Цей скіл призначений для написання структурованих, зрозумілих та методично вивірених лекційних матеріалів у доступному інженерному стилі для студентів коледжів (рівень: фаховий молодший бакалавр / бакалавр за спеціальностями 121 «Інженерія програмного забезпечення», 122 «Комп'ютерні науки» тощо).

---

## 1. Фундаментальні мовні та стилістичні стандарти

### 1.1. Мова та термінологія
- **Виключно українська мова** для всього навчального матеріалу, пояснень, заголовків, коментарів до коду та підписів діаграм.
- **Перше згадування англійських термінів:** обов'язково вказуйте оригінальний англійський термін у круглих дужках при першому введенні поняття.
  - *Приклади:* покажчики (*pointers*), аналіз втечі (*escape analysis*), зрізи (*slices*), качина типізація (*duck typing*), конвеєр обробки (*middleware pipeline*), взаємна автентифікація (*mutual TLS / mTLS*).
- **Пріоритет індустріальних англіцизмів:** уникайте штучних або застарілих кальок, які не вживаються в реальній інженерній практиці.
  - **Правильно:** фреймворк, роутер / маршрутизатор, хендлер / обробник, мідлвар, патерн, пул з'єднань, десеріалізація, вебсокет, репозиторій.
  - **Неправильно:** каркас (замість фреймворку), павутиння (замість веб), перехоплювач (де стандартно вживається middleware/interceptor).
- **Термінологія ООП:** Використовувати термін **«наслідування»** (_inheritance_), а не «спадкування».
- **Жодних штучних кальок.** Якщо розробники вголос кажуть англійське слово, у тексті теж англійське. Правило «мікс»: **назви речей** — англійською латиницею (так їх студент бачить у виводі, IDE й документації), **дії** — звичайними українськими дієсловами без віддієслівних іменників: «зберіть проєкт», але «після build», а не «після збирання».

  | Не пишемо | Пишемо |
  |---|---|
  | збирання, система збирання, сервер збирання | build, build-система, CI-сервер |
  | збірка (файл `.dll`) | assembly |
  | середовище виконання | runtime |
  | запускач | apphost (нативний файл програми), muxer (`dotnet`) |
  | навантаження (Visual Studio) | workload |
  | залежна від фреймворку / самодостатня | framework-dependent / self-contained |
  | цільова платформа | target framework |
  | референсні збірки | reference assemblies |
  | заглушка | stub |
  | гаряче перезавантаження | hot reload |
  | відновлення пакетів | restore пакетів |
  | налагоджувач, налагодження, символи налагодження | дебагер, дебаг, debug-символи |
  | точка зупинки | breakpoint |
  | простір імен | namespace |
  | конвеєр | pipeline |
  | однофайлові програми | file-based програми |
  | ключ (опція команди) | опція: «опція `-c Release`» |
  | розкладка клавіш (у налаштуваннях IDE) | keymap |
  | оболонка | shell |
  | «у папці встановлення» | «у папці, куди встановлено .NET» |

  Назви, які в IDE стоять англійською (Step Over, Watch, Locals, Call Stack), лишаються англійськими. Англійське слово в латиниці не відмінюється: «з assembly», «у runtime», «до наступного breakpoint». Дублі на кшталт «**runtime** (*runtime*)» не пишуться: англійський термін у дужках потрібен лише після українського. Усталені українські терміни лишаються: метадані, маніфест, точка входу, код виходу, змінна середовища, методи розширення, збирач сміття (GC).

### 1.2. Тон викладення: сухо, по суті, без заумності
- **Пишіть як інженер, що пояснює колезі:** прямо, конкретно, з фактами й прикладами. Без академічних зворотів і без усної мови лектора.
- **Сувора заборона псевдонаукових та «заумних» слів** (зліва — як не писати, справа — як писати):
  - *«інтерпретабельність»* → *«зрозумілість / прозорість логіки»*
  - *«предикат»* → *«умова перевірки / правило (if)»*
  - *«ациклічний орієнтований граф»* → *«деревоподібна схема / структура»*
  - *«мажоритарне голосування»* → *«голосування більшості»*
  - *«декорельовані»* → *«незалежні / різноманітні (не повторюють одне одного)»*
  - *«консиліум»* → *«спільне голосування / команда моделей»*
  - *«розрив генералізації»* → *«різниця між навчанням і тестом (перенавчання)»*
  - *«термінальні листки»* → *«кінцеві листки з відповідями»*
  - *«нездатність до екстраполяції»* → *«не вміє прогнозувати поза відомим діапазоном»*
  - *«інференс»* (без пояснення) → *«отримання прогнозу / відповіді (інференс)»*
  - надмірна філософія чи канцеляризми (*«іманентна дихотомія»*, *«трансцендентний»*) → конкретні факти і логіка.
- **Повні речення та закінчені думки:** категорично уникайте уривчастих тез чи списків без пояснень, але й не наливайте води. Кожна теза має бути змістовною і показувати «як це працює на практиці».
- **Сухо і по суті.** Кожне речення або повідомляє факт, або ставить питання, на яке відповідає наступний текст. Визначення й пояснення подавайте прямо, без вступних фраз.
- **Заборонені заповнювачі** (вони нічого не повідомляють і звучать як усна мова лектора):
  - «поговоримо за хвилину», «настав час», «зробимо крок углиб», «перейдемо до», «тепер зрозуміло»;
  - «найчесніша / чесна / справжня відповідь», «справжній компілятор», «чудове нагадування», «цікаво, що», «несподіванка»;
  - «ментальна модель», «під капотом», «магія», «просто», «всього лише» (якщо це не точна кількісна характеристика);
  - риторичне «Здається, що…» як зачин, а також вигуки й похвала студенту.
- **Місток між розділами** — це або конкретний зв'язок із названим попереднім поняттям («У RAM лежать числа. Як записується саме число?»), або питання-проблема. Не пишіть порожніх переходів.
- **Приклад замість оцінки.** Замість «чудовий приклад, що…» напишіть сам факт: «Компілятор обчислив `2 + 3` заздалегідь, тому в байт-коді лише `5`».
- **Звертання до аудиторії** («розглянемо», «зверніть увагу», «зауважте») допустимі, але рідко: не більше одного-двох разів на розділ, і лише там, де треба привернути увагу до пастки або винятку.

### 1.3. Жодних емодзі — лише іконки

> **СУВОРА ЗАБОРОНА ЕМОДЗІ.** У лекціях, практичних і домашніх завданнях не використовуються емодзі (🎯 🛠️ 📋 ✅ ❌ ❓ 💡 ⚠️ 🚀 тощо). Емодзі поруч з іконкою компонента дублюють одне одне, на різних ОС виглядають по-різному і засмічують текст.

- **Заголовки (`##`, `###`)** — лише текст: `## Питання для самоперевірки`, а не `## ❓ Питання…`.
- **`title` карток і `label` акордеонів** — лише текст, візуальний знак дає атрибут `icon`: `::card{title="Навчальні цілі" icon="i-lucide-graduation-cap"}`, `:::accordion-item{label="Спробуйте: псевдоніми типів" icon="i-lucide-clipboard-list"}`.
- **«Так / ні» у тексті і списках** — рядкова іконка Lucide на початку пункту (обов'язково з класом `inline-block`, інакше вона має нульовий розмір і не видна):

  ```markdown
  - :icon{name="i-lucide-circle-check" class="inline-block text-green-500"} **Варто:** …
  - :icon{name="i-lucide-circle-x" class="inline-block text-red-500"} **Не потрібно:** …
  ```

- **Коментарі в коді** — словами: `// правильно`, `// помилка компіляції`, `// краще так`.
- **Картинки matplotlib** — без емодзі (шрифт DejaVu їх не має, замість символу буде квадрат).

Типові іконки: цілі — `i-lucide-graduation-cap`, стек — `i-lucide-cpu`, завдання — `i-lucide-clipboard-list`, розв'язок — `i-lucide-check-circle`, питання — `i-lucide-help-circle`, порада «коли що» — `i-lucide-lightbulb`, переваги / вади — `i-lucide-thumbs-up` / `i-lucide-thumbs-down`.

## 2. Педагогічні та методичні принципи

### 2.1. Текст — основа статті, код — лише ілюстрація
Лекція — це не шпаргалка з кодом і короткими коментарями. Це **розгорнуте концептуальне пояснення**.
- Код ніколи не подається «голим». Кожен лістинг коду має спиратися на попередній текст, який пояснює задачу, та супроводжуватися наступним покроковим аналізом рядків.
- Код покликаний підкріпити сформульовану теоретичну тезу, а не замінити її.

### 2.2. Розкриття суті без «води»
Кожне ключове поняття чи механізм повинні містити зрозуміле пояснення: навіщо це потрібно, яка фізична чи алгоритмічна логіка стоїть за цим, і як це застосовується в коді. Глибина «чому так зроблено» обов'язкова: рішення мови чи платформи пояснюється через проблему, яку воно закриває.

### 2.3. Плавні концептуальні мости (Bridge Building)
Починайте новий підрозділ із короткого зв'язку з тим, що студент уже знає. Якщо студенти пройшли попередній курс (наприклад, C++ перед C#), спирайтесь на ці знання і не пояснюйте з нуля, але без явних посилань на лекції іншого курсу.

**«Так само, як у C++» — не привід пропустити основу.** Навіть якщо конструкція пишеться так само, як у знайомій мові, розділ починається з плавного вступу: що це і навіщо, анатомія синтаксису (схема з підписаними частинами), програма з **усіма формами запису** і пояснення кожної форми (`::field-group`). Лише після цього — відмінності від C++ і пастки. Не можна відкривати розділ фразою «пишеться так само, як у C++» і одразу переходити до відмінностей. Еталон — розділ «Змінна: ім'я, тип і значення» в `content/01.csharp/01.fundamentals/04.variables-types-literals.md`; так само побудовані «Будова виразу» і «Групи операторів» у лекції 08, «Будова if», «Будова умовного оператора», «Будова switch» у лекції 09.

### 2.4. Передбачення запитань («А що, якщо...?»)
Випереджайте типові запитання та помилки студентів до того, як вони сформулюються:
- *«А що станеться, якщо клієнт раптово розірве TCP-з'єднання під час запису в сокет?»*
- *«Чому ми повертаємо покажчик на структуру, а не копію значення?»*
Виділяйте такі відповіді через `::note`, `::warning` або `::accordion`.

### 2.5. Усі способи і «коли що»
- Якщо одну задачу можна розв'язати кількома способами (оголошення змінної, публікація програми, перетворення типів), показуйте **усі способи** поруч — через `::field-group` / `::field` або `::code-group`.
- Після переліку способів додавайте блок «коли що»: `::callout{icon="i-lucide-lightbulb"}` із заголовком і списком з іконками «так / ні» (розділ 1.3, формат — розділ 4.2).
- Для нового синтаксису давайте **анатомію конструкції**: схема matplotlib, де кожна частина виразу підписана.

### 2.6. Реальні виводи
Будь-який вивід програми, число в тексті чи на картинці, розмір файлу, час виконання береться з **реального запуску** на заявленій версії платформи. Приклади зберігаються в репозиторії (`samples/<курс>/<розділ>/NN-тема/`), щоб їх можна було перезапустити скриптом. Якщо результат залежить від машини, вкажіть, на чому його отримано (ОС, процесор, версія).

### 2.7. Міні-завдання «Спробуйте» всередині матеріалу
Після кожного нового поняття — маленьке самодостатнє завдання на 2–5 хвилин, яке студент виконує майже за інструкцією, щоб звикнути до концепції.
- **Не копіпаст** коду з тексту вище: завдання змінює умову (інші типи, інше значення, інший прапорець), щоб студент повторив дію сам.
- Містить: інструкцію по кроках, очікуваний вивід (`::terminal-preview`) і схований розв'язок із поясненням, чому вийшло саме так.
- Формат — два елементи акордеона: `Спробуйте: …` і `Розв'язок` (приклад у 4.9).

### 2.7.1. Поглиблений матеріал: рамка «Поглиблено»
Матеріал поза програмою модуля (у плані курсу позначений `[+]`) обгортається компонентом `deep-dive` — фіолетова рамка з міткою «Поглиблено». Рамка завжди розгорнута. Студентам не пишемо, що поглиблене не входить у тести й домашні: це правило для автора.

- **Рівнів два:** основне (без позначки) і поглиблене (у рамці). Інших позначок обов'язковості немає.
- **Що можна обгорнути:** цілий підрозділ разом із заголовком (`###` або `##`) або окрему вставку всередині основного розділу (абзац, таблиця, схема, анімація). Заголовки всередині рамки потрапляють у зміст сторінки.
- **Рамка завжди з п'ятьма двокрапками**, бо всередині можуть бути акордеони (4) з елементами (3) і вкладеними компонентами (2):

  ```markdown
  :::::deep-dive

  ### Багаторівнева компіляція

  Текст, схеми, ::::accordion з міні-завданням…

  :::::
  ```

- **Основний текст не спирається на поглиблений.** Якщо приклад потрібен і основному матеріалу (як програма `CsHello` для розділу про IL), він лишається поза рамкою, а в рамку йде лише поглиблене порівняння.
- **Міні-завдання «Спробуйте»** до поглибленого розділу лежать усередині його рамки.
- **Самоперевірка, шпаргалка і практичні завдання в кінці лекції — лише з основного матеріалу.** Поглиблене ніколи не потрапляє в тести Wayground і домашні завдання.
- **Огляд на початку лекції:** третя картка в `::card-group` після «Навчальних цілей» і «Технологічного стеку» — `::card{title="Поглиблено" icon="i-lucide-telescope"}` з реченням «Розділи поза програмою модуля. У тексті вони позначені фіолетовою рамкою.» і списком посилань на поглиблені розділи (`[Назва](#slug-заголовка)`). Якщо рамка — вставка без власного заголовка, посилання веде на заголовок розділу, в якому вона стоїть. Навчальні цілі формулюються лише з основного матеріалу.

### 2.8. Структура лекції
1. `# Заголовок` і `::card-group` з картками: «Навчальні цілі» (`i-lucide-graduation-cap`), «Технологічний стек» (`i-lucide-cpu`: версії, інструменти, папка прикладів) і, якщо в лекції є поглиблений матеріал, «Поглиблено» (`i-lucide-telescope`, розділ 2.7.1).
2. Основний матеріал: розділи `##` / `###`, схеми, міні-завдання «Спробуйте» після кожного поняття, блоки «коли що».
3. `## Питання для самоперевірки` — акордеон із 6–10 питаннями на розуміння (не на пам'ять) і відповідями.
4. `## Шпаргалка` — таблиця «термін / що це / де побачити або як записати».
5. `## Практичні завдання` — 3–5 нескладних завдань на 5–15 хвилин, кожне з прихованим розв'язком. Вони відрізняються від міні-завдань: поєднують кілька понять лекції, вимагають письмової відповді «чому» і, де доречно, скріншота результату.
6. `## Домашнє завдання` — лише якщо курс його передбачає для цієї лекції (зазвичай остання лекція модуля).

### 2.9. Домашні та практичні завдання, які не розв'язує ШІ за студента
- Завдання нескладні: рівень складності не має штовхати до генерації коду.

> **КРИТИЧНЕ ПРАВИЛО ФОРМАТУВАННЯ DOCUS:**

- Запустіть локальний сервер (`pnpm dev`) і відкрийте сторінку: немає сирих `::` у тексті, усі картинки завантажуються, акордеони й вкладки відкриваються, рядкові іконки видно.
- `grep -nP "[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]" <файл>.md` не знаходить жодного емодзі.
- Усі виводи в лекції збігаються з повторним запуском прикладів.

> **ЗАБОРОНА ЧИСЛОВОЇ НУМЕРАЦІЇ В ЗАГОЛОВКАХ:**
> Ніколи не використовуйте штучні числові префікси в заголовках (`## 1. `, `### 1.1. `, `### 1.2. ` тощо).
> Заголовки (H2 `##`, H3 `###`) мають бути природними, змістовними та описовими (наприклад: `## Архітектурний контекст та еволюція систем`, `### Проблема монолітів минулого`).
