## Чому .dll читається майже як вихідний код

У першій лекції assembly описано як файл з IL-кодом і метаданими. Метадані — це повний опис усіх типів і методів з їхніми іменами, а IL — інструкції рівня мови, а не процесора: «виклич метод `Console.WriteLine`», «порівняй два значення», «перейди на мітку». З такого опису можна відновити програму, дуже схожу на ту, з якої його отримали.

У C++ інакше. Компілятор перетворює код на машинні команди, а лінкер викидає імена всього, що не потрібне для запуску. Від функції `IsValidKey` у Release `.exe` лишається адреса й набір команд процесора. Інструменти для C++ (наприклад, Ghidra чи IDA) відновлюють з цього приблизний C-подібний код з іменами на кшталт `FUN_00401a30`.

![Що лишається у файлі після компіляції: у C++ .exe — рядки і частково імена, у .NET .dll — імена типів, методів, параметрів, рядки і структура коду, з .pdb — ще й імена локальних змінних; коментарів немає ніде](/images/csharp/fundamentals/decompilers-and-obfuscators/01-what-survives.png){.diagram-img}

### Програма, яку будемо розбирати

Розберемо маленьку програму, яка перевіряє ключ ліцензії. Ключ зашито прямо в код, як це часто роблять у навчальних і не тільки проєктах:

```csharp [License/Program.cs]
Console.Write("Ключ ліцензії: ");
string? key = Console.ReadLine();

if (IsValidKey(key))
{
    Console.WriteLine("Ліцензію активовано.");
}
else
{
    Console.WriteLine("Невірний ключ.");
}

static bool IsValidKey(string? key)
{
    string secret = "KOSTYL-2026-PRO";
    return key == secret;
}
```

Зберемо її в Release і передамо готову `License.dll` декомпілятору (*decompiler*). `ilspycmd` — консольна версія декомпілятора ILSpy, встановлена в першій лекції (`dotnet tool install -g ilspycmd`):

```bash
dotnet build -c Release
ilspycmd bin/Release/net10.0/License.dll
```

::terminal-preview{title="ilspycmd bin/Release/net10.0/License.dll (фрагмент)"}
```text
[assembly: AssemblyConfiguration("Release")]
[assembly: AssemblyInformationalVersion("1.0.0+ee6f39df218b473f9b8a91990da374bafc20212c")]
[assembly: AssemblyProduct("License")]
[CompilerGenerated]
internal class Program
{
	private static void Main(string[] args)
	{
		Console.Write("Ключ ліцензії: ");
		if (IsValidKey(Console.ReadLine()))
		{
			Console.WriteLine("Ліцензію активовано.");
		}
		else
		{
			Console.WriteLine("Невірний ключ.");
		}
		static bool IsValidKey(string? key)
		{
			string text = "KOSTYL-2026-PRO";
			return key == text;
		}
	}
}
```
::

Ключ `KOSTYL-2026-PRO` видно одразу, без жодних зусиль. Видно й ім'я методу `IsValidKey`, ім'я параметра `key` і всю логіку перевірки. Є ще одна деталь: у `AssemblyInformationalVersion` після `+` стоїть хеш коміту git, з якого зібрано програму. SDK дописує його автоматично, коли проєкт лежить у git-репозиторії.

::warning
Усе, що записано в коді програми, яку отримує користувач, можна прочитати: рядки, ключі API, паролі до бази даних, адреси внутрішніх серверів. Перевірку ліцензії, яку не можна обійти, робить сервер, а не клієнтська програма.
::

::::accordion

:::accordion-item{label="Спробуйте: що бачить декомпілятор у вашій програмі" icon="i-lucide-clipboard-list"}

1. Створіть файл `greet.cs`:

```csharp [greet.cs]
Console.WriteLine(Greeting("Олена", 19));

static string Greeting(string name, int age)
{
    string prefix = age >= 18 ? "Вітаю" : "Привіт";
    return prefix + ", " + name + "!";
}
```

2. Зберіть його двічі, в Debug і в Release, у різні папки: `dotnet build greet.cs -c Debug -o debug` і `dotnet build greet.cs -c Release -o release`.
3. Декомпілюйте обидві версії: `ilspycmd debug/greet.dll` і `ilspycmd release/greet.dll`. Знайдіть метод `Greeting`.
4. Повторіть для Debug з опцією `-usepdb`: `ilspycmd -usepdb debug/greet.dll`.
5. Що сталося зі змінною `prefix` у кожному з трьох випадків?

:::

:::accordion-item{label="Розв'язок" icon="i-lucide-check-circle"}

::code-group

```csharp [Debug]
static string Greeting(string name, int age)
{
	string text = ((age >= 18) ? "Вітаю" : "Привіт");
	return text + ", " + name + "!";
}
```

```csharp [Debug з -usepdb]
static string Greeting(string name, int age)
{
	string prefix = ((age >= 18) ? "Вітаю" : "Привіт");
	return prefix + ", " + name + "!";
}
```

```csharp [Release]
static string Greeting(string name, int age)
{
	return ((age >= 18) ? "Вітаю" : "Привіт") + ", " + name + "!";
}
```

::

- **Debug без pdb.** Локальна змінна в IL є, але її ім'я в assembly не записується: у метаданих є лише номер слота і тип. Декомпілятор вигадує ім'я за типом: `string` — `text`, `int` — `num`.
- **Debug з `-usepdb`.** Імена локальних змінних лежать у файлі `.pdb` поруч з `.dll`. Декомпілятор бере їх звідти, і повертається `prefix`.
- **Release.** Компілятор помітив, що `prefix` використовується один раз, і прибрав змінну: значення лишається на стеку обчислень. Відновлювати нічого, тож `-usepdb` тут уже не допоможе.

Імена параметрів `name` і `age` видно в усіх трьох випадках: вони записані в метадані, бо є частиною сигнатури методу.

:::

## Декомпілятор: як він працює

**Декомпілятор** — програма, яка перетворює скомпільований код назад на код мовою програмування. У програмі курсу такі інструменти називаються **рефлекторами**: першим популярним декомпілятором для .NET був .NET Reflector Лутца Редера. У 2008 році його купила компанія Red Gate, а в 2011 оголосила, що інструмент стане платним. Того ж року команда SharpDevelop почала безкоштовний ILSpy, який сьогодні є основним відкритим декомпілятором .NET.

Декомпілятор працює в кілька етапів:

![Етапи роботи декомпілятора: читає метадані, розбирає IL на блоки й переходи, впізнає шаблони (цикли, if, top-level, інтерполяцію), друкує C# обраної версії мови](/images/csharp/fundamentals/decompilers-and-obfuscators/02-decompiler-pipeline.png){.diagram-img}

::steps

### Читає метадані

З таблиць метаданих беруться імена типів і методів, сигнатури, параметри і рядкові літерали. Ця частина відновлюється точно.

### Розбирає IL

Інструкції кожного методу діляться на блоки без переходів усередині (*basic blocks*), а переходи між блоками утворюють граф. Цикл у такому графі — це перехід назад, `if` — розгалуження на два блоки, які потім сходяться.

### Впізнає шаблони

Компілятор C# перетворює багато конструкцій мови на простіші: інтерполяцію рядків — на виклики `DefaultInterpolatedStringHandler`, `foreach` — на цикл з лічильником чи енумератором, top-level statements — на метод `<Main>$`. Декомпілятор знає ці шаблони і збирає з них назад зручний C#.

### Друкує C#

Результат друкується в синтаксисі обраної версії мови. За замовчуванням — найновішої, тому код виходить коротким. Ім'я `<Main>$` недопустиме в C#, тож декомпілятор показує його як `Main`.

::

### Чого декомпілятор не відновить

Декомпільований код **еквівалентний** оригіналу, але не збігається з ним. У прикладі `License` це видно в кількох місцях:

| Що було в коді | Що показав декомпілятор | Чому |
|---|---|---|
| `string? key = Console.ReadLine();` | `IsValidKey(Console.ReadLine())` | у Release компілятор прибрав змінну, значення пішло одразу в аргумент |
| `string secret = ...` | `string text = ...` | ім'я локальної змінної є лише в `.pdb` |
| top-level statements | метод `Main` у класі `Program` | так їх насправді зібрав компілятор, а `<Main>$` — недопустиме ім'я |
| коментар над програмою | нічого | коментарі не потрапляють ні в IL, ні в метадані |
| `IsValidKey` після коду програми | `IsValidKey` усередині `Main` | локальна функція технічно належить методу `<Main>$` |

### Код без синтаксичного цукру

Опція `-lv` (*language version*) обирає, у синтаксисі якої версії C# друкувати результат. Зі старою версією декомпілятор не може скористатися новими конструкціями мови і показує код таким, яким його згенерував компілятор. Так видно, у що насправді перетворюється інтерполяція рядків:

```csharp [interpolation.cs]
string name = "Олена";
int age = 19;
Console.WriteLine($"{name} має {age} років");
```

::code-group

```csharp [ilspycmd interpolation.dll]
string value = "Олена";
int value2 = 19;
Console.WriteLine($"{value} має {value2} років");
```

```csharp [ilspycmd -lv CSharp1 interpolation.dll]
string value = "Олена";
int value2 = 19;
DefaultInterpolatedStringHandler defaultInterpolatedStringHandler = new DefaultInterpolatedStringHandler(11, 2);
defaultInterpolatedStringHandler.AppendFormatted(value);
defaultInterpolatedStringHandler.AppendLiteral(" має ");
defaultInterpolatedStringHandler.AppendFormatted(value2);
defaultInterpolatedStringHandler.AppendLiteral(" років");
Console.WriteLine(defaultInterpolatedStringHandler.ToStringAndClear());
```

::

Інтерполяція `$"..."` не склеює рядки оператором `+`. Компілятор створює структуру `DefaultInterpolatedStringHandler`, наперед повідомляє їй довжину сталого тексту (11 символів) і кількість вставок (2), а потім додає частини по черзі. Так рядок будується в одному буфері без проміжних копій. Детально про це — в лекції про рядки.

::::accordion

:::accordion-item{label="Спробуйте: знайдіть синтаксичний цукор" icon="i-lucide-clipboard-list"}

1. Створіть файл `sugar.cs`, у якому оголошено дві змінні `a = 7` і `b = 5` і виведено рядок `$"{a} + {b} = {a + b}"`.
2. Зберіть його: `dotnet build sugar.cs -c Release -o out`.
3. Декомпілюйте двічі: без опцій і з `-lv CSharp1`.
4. Яку довжину сталого тексту і скільки вставок компілятор передав у конструктор `DefaultInterpolatedStringHandler`? Порахуйте самі й порівняйте.

Очікуваний вивід програми:

::terminal-preview{title="dotnet run sugar.cs"}
```text

```
::

:::

:::accordion-item{label="Розв'язок" icon="i-lucide-check-circle"}

```text

int num2 = 5;
```

## Навіщо декомпілятор розробнику

Декомпілятор найчастіше асоціюється зі зломом програм, але в щоденній роботі його використовують для інших речей.

::field-group

::field{name="Вивчити, як працює бібліотека" type="BCL, NuGet"}
Що робить метод усередині, які винятки кидає, чи копіює він дані. Вихідний код .NET відкритий (source.dot.net), але декомпілятор показує саме ту версію, яка встановлена на вашій машині.
::

::field{name="Дебаг чужої бібліотеки" type="без вихідного коду"}
Коли закрита бібліотека поводиться не так, як описано в документації, декомпільований код показує, чому. Rider і Visual Studio вміють ставити breakpoint прямо в декомпільований код.
::

::field{name="Перевірка пакета" type="аудит"}
Що насправді робить пакет із NuGet: чи не надсилає дані на сторонні сервери, чи не читає файли, які не мав би.
::

::field{name="Відновлення коду" type="втрачений проєкт"}
`ilspycmd -p -o папка License.dll` створює проєкт `.csproj` з файлами `.cs`, який збирається знову. Імена локальних змінних і коментарі не повернуться, але логіка — так.
::

::field{name="Навчання" type="що генерує компілятор"}
Як компілятор перетворює top-level statements, інтерполяцію, `foreach`, локальні функції. Це допомагає зрозуміти, скільки коштує та чи інша конструкція.
::

::

Декомпіляція методу з BCL. Опція `-m` обирає один член класу за ідентифікатором XML-документації: `M:` — метод, далі повне ім'я з типами параметрів. Файл `System.Private.CoreLib.dll` лежить у папці runtime. Шлях і номер версії у вас можуть бути іншими: візьміть їх з виводу `dotnet --list-runtimes`.

::tabs

::tabs-item{label="PowerShell (Windows)"}

```powershell
$lib = "C:\Program Files\dotnet\shared\Microsoft.NETCore.App\10.0.15"
ilspycmd -m "M:System.String.IsNullOrWhiteSpace(System.String)" "$lib\System.Private.CoreLib.dll"
```

::

::tabs-item{label="bash / zsh (macOS, Linux)"}

```bash
lib=/usr/local/share/dotnet/shared/Microsoft.NETCore.App/10.0.15
ilspycmd -m "M:System.String.IsNullOrWhiteSpace(System.String)" $lib/System.Private.CoreLib.dll
```

::

::

::terminal-preview{title="ilspycmd -m M:System.String.IsNullOrWhiteSpace(System.String) (без XML-коментаря)"}
```text
public static bool IsNullOrWhiteSpace([NotNullWhen(false)] string? value)
{
	if ((object)value == null)
	{
		return true;
	}
	for (int i = 0; i < value.Length; i++)
	{
		if (!char.IsWhiteSpace(value[i]))
		{
			return false;
		}
	}
	return true;
}
```
::

Метод перебирає символи рядка і повертає `false` на першому, який не є пробільним. Над методом ilspycmd друкує ще й XML-коментар з документацією. Його немає в самій `.dll`: декомпілятор знаходить файл `.xml` поруч із reference assemblies у папці SDK.

::::accordion

:::accordion-item{label="Спробуйте: подивіться всередину Math.Abs" icon="i-lucide-clipboard-list"}

1. Декомпілюйте метод `Math.Abs` для `int`: ідентифікатор `M:System.Math.Abs(System.Int32)`, файл той самий — `System.Private.CoreLib.dll`.
2. Знайдіть у тілі методу дві перевірки `value < 0`. Навіщо друга, якщо після першої `value` стало додатним?
3. Перевірте свою відповідь програмою: `Console.WriteLine(Math.Abs(int.MinValue));`.

:::

:::accordion-item{label="Розв'язок" icon="i-lucide-check-circle"}

::terminal-preview{title="ilspycmd -m M:System.Math.Abs(System.Int32) (без XML-коментаря)"}
```text
[MethodImpl(MethodImplOptions.AggressiveInlining)]
public static int Abs(int value)
{
	if (value < 0)
	{
		value = -value;
		if (value < 0)
		{
			ThrowNegateTwosCompOverflow();
		}
	}
	return value;
}
```
::

::terminal-preview{title="dotnet run abs-min.cs"}
```text
Unhandled exception. System.OverflowException: Negating the minimum value of a twos complement number is invalid.
```
::

Діапазон `int` — від −2 147 483 648 до 2 147 483 647: від'ємних чисел на одне більше. Число `int.MinValue` не має додатної пари, і `-int.MinValue` при переповненні знову дає `int.MinValue`. Друга перевірка ловить саме цей випадок, і програма падає з `OverflowException` замість того, щоб повернути від'ємний «модуль». Атрибут `AggressiveInlining` просить JIT вставляти тіло методу в місце виклику.

## Читаємо IL власної програми

У першій лекції IL розглядався на прикладі констант і виклику методу. Справжні методи мають локальні змінні, цикли й умови. Ось як вони виглядають в IL.

```csharp [sum-loop.cs]
Console.WriteLine(SumTo(3));

static int SumTo(int n)
{
    int sum = 0;
    for (int i = 1; i <= n; i++)
    {
        sum += i;
    }
    return sum;
}
```

::terminal-preview{title="ilspycmd -il sum-loop.dll (метод SumTo)"}
```text
.maxstack 2
.locals init (
	[0] int32,
	[1] int32
)

IL_0000: ldc.i4.0
IL_0001: stloc.0
IL_0002: ldc.i4.1
IL_0003: stloc.1
IL_0004: br.s IL_000e
// loop start (head: IL_000e)
	IL_0006: ldloc.0
	IL_0007: ldloc.1
	IL_0008: add
	IL_0009: stloc.0
	IL_000a: ldloc.1
	IL_000b: ldc.i4.1
	IL_000c: add
	IL_000d: stloc.1

	IL_000e: ldloc.1
	IL_000f: ldarg.0
	IL_0010: ble.s IL_0006
// end loop

IL_0012: ldloc.0
IL_0013: ret
```
::

::field-group

::field{name=".locals init" type="оголошення"}
Перелік локальних змінних методу: лише номери слотів і типи. Слот `[0]` — `sum`, `[1]` — `i`. Слово `init` означає, що CLR обнулить їх перед першим виконанням.
::

::field{name=".maxstack 2" type="оголошення"}
Найбільша кількість значень, які одночасно лежать на стеку обчислень у цьому методі. CLR перевіряє IL на відповідність цьому числу під час JIT-компіляції.
::

::field{name="stloc.N / ldloc.N" type="store / load local"}
Зняти значення зі стеку і записати в локальну змінну N / покласти значення змінної N на стек.
::

::field{name="ldarg.N" type="load argument"}
Покласти на стек аргумент методу N. У статичному методі `ldarg.0` — перший параметр, тут `n`.
::

::field{name="br.s мітка" type="branch"}
Безумовний перехід. Суфікс `.s` (*short*) означає, що зсув до мітки вміщується в один байт.
::

::field{name="ble.s мітка" type="branch if less or equal"}
Зняти два значення і перейти, якщо перше менше або дорівнює другому. Так само працюють `blt` (<), `bgt` (>), `bge` (>=), `beq` (==).
::

::

Компілятор розташував перевірку умови `i <= n` **після** тіла циклу і на початку робить перехід `br.s` прямо до неї. Так у кожній ітерації виконується лише один умовний перехід `ble.s` назад, а не два переходи (на перевірку і назад). Коментарі `// loop start` і `// end loop` дописує ilspycmd, у файлі їх немає.

Виконання `SumTo(3)` покроково: зліва IL, у центрі рядок C#, якому відповідає інструкція, і стек обчислень, справа локальні змінні.

### Метадані: імена, які згенерував компілятор

Метадані — це набір таблиць. ilspycmd вміє друкувати їх напряму опцією `--dump-table`. Таблиця `MethodDef` містить усі методи assembly:

::terminal-preview{title="ilspycmd --dump-table MethodDef License.dll (стовпці скорочено)"}
```text
RID  Token       Attributes                                     Name
---  ----------  ---------------------------------------------  --------------------------
1    0x06000001  Private, Static, HideBySig                     <Main>$
2    0x06000002  Public, HideBySig, SpecialName, RTSpecialName  .ctor
3    0x06000003  Assembly, Static, HideBySig                    <<Main>$>g__IsValidKey|0_0
```
::

- `<Main>$` — метод, у який компілятор зібрав top-level statements.
- `.ctor` — конструктор класу `Program`, який компілятор додав автоматично.
- `<<Main>$>g__IsValidKey|0_0` — локальна функція `IsValidKey`. Ім'я складається з методу-власника `<Main>$`, позначки `g__` (*generated*) і номера. Символи `<`, `>` і `|` недопустимі в C#, тож з коду цей метод напряму не викликати.
- Стовпець `Token` — номер рядка в таблиці. Саме за такими номерами IL посилається на методи: інструкція `call` містить токен, а не ім'я.

:::accordion-item{label="Спробуйте: знайдіть цикл while в IL" icon="i-lucide-clipboard-list"}

1. Створіть файл `digits.cs` з методом, який рахує кількість цифр числа:

```csharp [digits.cs]
Console.WriteLine(CountDigits(2026));

static int CountDigits(int value)
{
    int count = 0;
    while (value > 0)
    {
        value /= 10;
        count++;
    }
    return count;
}
```

2. Зберіть Release і виведіть IL: `dotnet build digits.cs -c Release -o out`, `ilspycmd -il out/digits.dll`.
3. Знайдіть метод `CountDigits`. Скільки в ньому локальних змінних і чому? Яка інструкція перевіряє умову `value > 0`? Яка інструкція записує нове значення у `value`?

Очікуваний вивід програми:

::terminal-preview{title="dotnet run digits.cs"}
```text

```

::terminal-preview{title="ilspycmd -il out/digits.dll (метод CountDigits)"}
```text
.locals init (
	[0] int32
)
IL_0000: ldc.i4.0
IL_0001: stloc.0
IL_0002: br.s IL_000e
// loop start (head: IL_000e)
	IL_0004: ldarg.0
	IL_0005: ldc.i4.s 10
	IL_0007: div
	IL_0008: starg.s 'value'
	IL_000a: ldloc.0
	IL_000b: ldc.i4.1
	IL_000c: add
	IL_000d: stloc.0
	IL_000e: ldarg.0
	IL_000f: ldc.i4.0
	IL_0010: bgt.s IL_0004
// end loop
IL_0012: ldloc.0
IL_0013: ret
```
::

- Локальна змінна одна — `count` (`[0]`). `value` — параметр, і змінюється він на місці: `starg.s 'value'` знімає значення зі стеку і записує його в аргумент.
- Умову перевіряє `bgt.s IL_0004` (*branch if greater than*): якщо `value > 0`, перехід на початок тіла.
- `ldc.i4.s 10` — константа 10. Для чисел від −1 до 8 є окремі однобайтові інструкції `ldc.i4.m1`…`ldc.i4.8`, а 10 вже потребує форми `.s` з байтом значення.
- Цикл `while` у IL має ту саму форму, що й `for`: перехід на умову в кінці, умовний перехід назад.

## Обфускатор

Декомпілятор показав ключ і всю логіку програми `License`. Якщо програма комерційна, автор хоче, щоб її було важче прочитати. Для цього існують **обфускатори** (*obfuscators*): програми, які змінюють assembly так, щоб вона працювала так само, але її декомпільований код став незрозумілим. У програмі курсу їх названо **дотфускаторами**, за назвою Dotfuscator — обфускатора компанії PreEmptive, безкоштовна версія якого довгий час постачалася разом з Visual Studio.

### Прийоми обфускації

![Прийоми обфускації: перейменування (Program і IsValidKey стають A), приховування рядків (ключ стає викликом b() з байтами під XOR), заплутування потоку (if стає циклом із switch, спрощена ілюстрація)](/images/csharp/fundamentals/decompilers-and-obfuscators/03-obfuscation-techniques.png){.diagram-img}

::field-group

::field{name="Перейменування" type="renaming"}
Класи, методи, параметри й поля отримують короткі безглузді імена: `A`, `a`, `B`, `P_0`. Метаданим усе одно, як називається метод, а людині без імен значно важче зрозуміти, що робить код.
::

::field{name="Приховування рядків" type="string encryption"}
Рядкові літерали прибираються з коду і зберігаються закодованими, наприклад як масив байтів. Під час роботи програми спеціальний метод декодує їх назад.
::

::field{name="Заплутування потоку керування" type="control flow obfuscation"}
Прості `if` і цикли перебудовуються в заплутану машину станів зі `switch` і переходами, яку декомпілятор не може зібрати назад у читабельний вигляд.
::

::field{name="Захист від змін і дебагера" type="anti-tamper, anti-debug"}
Програма перевіряє, чи не змінено її файл, і чи не запущена вона під дебагером, і в такому разі завершується.
::

::field{name="Віртуалізація коду" type="code virtualization"}
Частина методів перекладається на власний набір інструкцій, який виконує вбудований у програму інтерпретатор. Найсильніший і найповільніший прийом, є лише в платних продуктах.
::

::

### Obfuscar на практиці

**Obfuscar** — обфускатор з відкритим кодом, який працює на всіх ОС як інструмент `dotnet`. Він уміє перейменування і приховування рядків.

```bash
dotnet tool install -g Obfuscar.GlobalTool
```

Налаштування записуються в XML-файл поруч із проєктом:

```xml [License/obfuscar.xml]
<?xml version="1.0"?>
<Obfuscator>
  <Var name="InPath" value="bin/Release/net10.0" />
  <Var name="OutPath" value="obfuscated" />
  <Var name="HideStrings" value="true" />
  <Var name="KeepPublicApi" value="false" />
  <Var name="HidePrivateApi" value="true" />
  <Module file="$(InPath)/License.dll" />
</Obfuscator>
```

- `InPath` і `OutPath` — звідки брати assembly і куди класти результат.
- `HideStrings` — приховувати рядкові літерали.
- `KeepPublicApi` / `HidePrivateApi` — чи перейменовувати публічні та приватні члени.
- `Module` — яку assembly обфускувати.

```bash
dotnet build -c Release
obfuscar.console obfuscar.xml
cp bin/Release/net10.0/License.runtimeconfig.json obfuscated/
dotnet obfuscated/License.dll
```

Obfuscar кладе в `obfuscated/` нову `License.dll` і файл `Mapping.txt`. Файл `runtimeconfig.json` він не копіює, тому його додають вручну, інакше програма не запуститься. Обфускована програма працює так само:

::terminal-preview{title="dotnet obfuscated/License.dll"}
```text
Ключ ліцензії: KOSTYL-2026-PRO
Ліцензію активовано.
```
::

А от декомпільований код змінився:

::terminal-preview{title="ilspycmd obfuscated/License.dll (фрагмент)"}
```text
namespace A
{
	[CompilerGenerated]
	internal class A
	{
		private static void A(string[] P_0)
		{
			Console.Write(CBD7D892-71C6-4872-8D3F-DC6156F02490.A());
			if (A(Console.ReadLine()))
			{
				Console.WriteLine(CBD7D892-71C6-4872-8D3F-DC6156F02490.a());
			}
			else
			{
				Console.WriteLine(CBD7D892-71C6-4872-8D3F-DC6156F02490.B());
			}
		}

		[CompilerGenerated]
		internal static bool A(string? P_0)
		{
			string text = CBD7D892-71C6-4872-8D3F-DC6156F02490.b();
			return P_0 == text;
		}
	}
}
```
::

- Клас `Program`, метод `<Main>$` і локальна функція `IsValidKey` тепер усі називаються `A`. Метаданим це не заважає, а C# забороняє методу називатися так само, як клас, у якому він лежить (помилка CS0542). Тому такий код уже не збереться назад без ручних правок.
- Параметр `key` став `P_0`.
- Рядків у коді немає: замість `"KOSTYL-2026-PRO"` стоїть виклик `b()` з класу з ім'ям-GUID. Obfuscar обирає GUID випадково при кожному запуску, тож у вас ім'я буде іншим.

Файл `Mapping.txt` зберігає відповідність старих і нових імен:

::terminal-preview{title="obfuscated/Mapping.txt (початок)"}
```text
Renamed Types:

[License]Program -> [License]A.A
{
	[License]Program::<Main>$[1]( [System.Runtime]System.String[] ) -> A
	[License]Program::<<Main>$>g__IsValidKey|0_0[1]( [System.Runtime]System.String ) -> A
}
```
::

Без цього файлу помилку в обфускованій програмі не знайти: у тексті винятку буде «помилка в методі `A.A.A`». Тому `Mapping.txt` зберігають разом з кожним випуском, але не передають користувачам.

### Що обфускатор не може

Обфускація лише **ускладнює** читання. Вона не може зробити його неможливим, бо програма мусить працювати: логіка й дані мають лишатися в assembly.

- **Рядки декодуються під час роботи.** Щоб надрукувати «Ліцензію активовано.», програма мусить отримати цей рядок. У дебагері або в пам'яті процесу він видний у звичайному вигляді.
- **Спосіб декодування лежить поруч.** Метод, який відновлює рядки, теж в assembly, і декомпілятор його показує.
- **Існують деобфускатори.** Інструменти на кшталт de4dot впізнають популярні обфускатори і відкочують частину їхніх перетворень.
- **Публічні імена бібліотеки перейменувати не можна.** Інші програми викликають методи бібліотеки за іменами; якщо `Calculate` стане `A`, вони перестануть збиратися. Тому в бібліотеках обфускатор перейменовує лише приватні та внутрішні (`internal`) члени.
- **Рефлексія і серіалізація працюють за іменами.** Код, який шукає метод за рядком `"IsValidKey"` або перетворює об'єкт на JSON з іменами полів, після перейменування зламається. Такі члени доводиться виключати з обфускації в налаштуваннях.

:::::deep-dive

Ось як знімається приховування рядків у прикладі `License`. Декомпілятор показує весь допоміжний клас, який додав Obfuscar: масив зі 106 байтів і статичний конструктор, що їх декодує:

::terminal-preview{title="ilspycmd obfuscated/License.dll (допоміжний клас, фрагмент)"}
```text
internal static byte[] 4 = new byte[106] { 122, 49, 120, 18, 127, 33, ... };

private static string 6(int P_0, int P_1, int P_2)
{
	string text = Encoding.UTF8.GetString(4, P_1, P_2);
	5[P_0] = text;
	return text;
}

public static string b()
{
	return 5[3] ?? 6(3, 91, 15);
}

static CBD7D892-71C6-4872-8D3F-DC6156F02490()
{
	for (int i = 0; i < 4.Length; i++)
	{
		4[i] = (byte)(4[i] ^ i ^ 0xAA);
	}
}
```
::

«Шифр» — це XOR кожного байта з його номером і числом `0xAA`. Метод `b()` бере 15 байтів, починаючи з 91-го. Достатньо повторити ці дії в окремій програмі (`decode-strings.cs` у прикладах), щоб отримати всі рядки:

::terminal-preview{title="dotnet run decode-strings.cs"}
```text
Ключ ліцензії: 
Ліцензію активовано.
Невірний ключ.
KOSTYL-2026-PRO
```
::

На це пішло чотири рядки коду і числа, скопійовані з декомпілятора. Платні обфускатори використовують складніші алгоритми, але принцип той самий: ключ для декодування лежить у тій самій програмі.

**Коли обфускація має сенс**

- :icon{name="i-lucide-circle-check" class="inline-block text-green-500"} **Комерційна десктопна програма** з власним алгоритмом, який не хочеться віддавати конкурентам у вигляді готового C#.
- :icon{name="i-lucide-circle-check" class="inline-block text-green-500"} **Як додатковий шар** поруч з іншими заходами: перевіркою ліцензії на сервері, підписом коду.
- :icon{name="i-lucide-circle-x" class="inline-block text-red-500"} **Не для серверного коду**: користувач не має доступу до `.dll` на сервері, захищати нічого.
- :icon{name="i-lucide-circle-x" class="inline-block text-red-500"} **Не для секретів**: ключі API, паролі й рядки підключення до бази даних не можна зберігати в клієнтській програмі ні з обфускацією, ні без неї.
- :icon{name="i-lucide-circle-x" class="inline-block text-red-500"} **Не для навчальних і open source проєктів**: обфускація лише заважає дебагу та читанню стека викликів.

## Native AOT замість обфускації

У першій лекції Native AOT розглядався як спосіб швидкого старту: програма компілюється в машинний код ще під час публікації. Побічний ефект — у результаті немає IL і метаданих, тож декомпілятору .NET нічого читати:

```bash
dotnet publish -c Release -r osx-arm64 -p:PublishAot=true -o aot
ilspycmd aot/License
```

::terminal-preview{title="ilspycmd aot/License"}
```text
System.BadImageFormatException: Unknown file format.
   at System.Reflection.PortableExecutable.PEHeaders..ctor(Stream peStream, Int32 size, Boolean isLoadedImage)
```
::

Імен методів у файлі теж немає: пошук рядка `IsValidKey` нічого не знаходить. Але рядкові літерали нікуди не зникли. Програма `find-utf16.cs` з прикладів шукає текст у кодуванні UTF-16, у якому .NET зберігає рядки, у будь-якому файлі:

::terminal-preview{title="dotnet run find-utf16.cs -- aot/License KOSTYL"}
```text
зсув   1049921: KOSTYL-2026-PR....LA
Знайдено: 1
```
::

Ключ видно майже повністю: останній символ зливається зі службовими байтами, що йдуть одразу за рядком у файлі. Той самий пошук у звичайній `License.dll` знаходить ключ повністю, а в обфускованій — не знаходить нічого:

![Що видно з License у трьох варіантах: Release .dll — декомпілятор, імена й ключ видно; після Obfuscar — декомпілятор показує код з іменами A, рядків у файлі немає; Native AOT — декомпілятор не працює, імен немає, але ключ знаходиться пошуком у файлі](/images/csharp/fundamentals/decompilers-and-obfuscators/04-secret-visibility.png){.diagram-img}

Native AOT прибирає IL і метадані, і для дослідника програма стає схожою на C++ `.exe`: читати її доводиться інструментами для машинного коду. Це суттєво складніше за декомпіляцію .NET, але рядки й логіка в файлі лишаються. Обмеження Native AOT з першої лекції теж діють: рефлексія та динамічне завантаження коду працюють обмежено.

::warning
Разом з Native AOT-файлом публікація створює файл символів (`License.dSYM` на macOS, `License.pdb` на Windows). У ньому є імена всіх методів. Цей файл не передають користувачам.
::

## Правові та етичні межі декомпіляції

Програма захищена авторським правом так само, як книжка. Декомпіляція створює копію коду в іншій формі, тому вона дозволена не завжди.

- **Закон.** Закон України «Про авторське право і суміжні права» (2022, стаття 25) дозволяє законному користувачу декомпілювати програму без дозволу правовласника, якщо це потрібно, щоб незалежно створена програма могла з нею взаємодіяти. Декомпілювати можна лише потрібні для цього частини, а отриману інформацію не можна використовувати для створення схожої програми чи передавати іншим. Аналогічне правило діє в ЄС (директива 2009/24/ЄС, стаття 6).
- **Ліцензійна угода.** Багато комерційних програм прямо забороняють декомпіляцію в ліцензії (EULA), яку ви приймаєте під час встановлення.
- **Без обмежень:** власний код, програми з відкритим кодом (у межах їхньої ліцензії), навчальні приклади, як у цій лекції.
- **Етика.** Обхід перевірки ліцензії чужої програми — порушення закону, навіть якщо технічно це кілька хвилин роботи з декомпілятором. Якщо під час дослідження знайдено вразливість, про неї повідомляють розробнику (*responsible disclosure*), а не публікують.

## Питання для самоперевірки

::::accordion

:::accordion-item{label="Чому .NET assembly декомпілюється значно точніше, ніж C++ .exe?" icon="i-lucide-help-circle"}

У .NET assembly лежать метадані з іменами всіх типів, методів і параметрів, а також IL — інструкції рівня мови з викликами методів за іменами. У C++ `.exe` після компіляції і лінкування лишаються машинні команди процесора, а імена здебільшого викинуто. Відновити з них можна лише приблизний C-подібний код з вигаданими іменами.

:::

:::accordion-item{label="Що декомпілятор не може відновити і чому?" icon="i-lucide-help-circle"}

Коментарі, форматування та імена локальних змінних: їх немає ні в IL, ні в метаданих. Імена локальних змінних є лише в `.pdb`. Крім того, у Release компілятор прибирає змінні, які використовуються один раз, і такий код уже не повернеться у вихідну форму навіть з `.pdb`.

:::

:::accordion-item{label="Чому ilspycmd показує top-level код як метод Main, а в IL це <Main>$?" icon="i-lucide-help-circle"}

Компілятор зібрав top-level statements у метод з навмисно недопустимим для C# ім'ям `<Main>$`, щоб його не можна було викликати чи повторити з коду. Декомпілятор друкує C#, тому замінює недопустиме ім'я на найближче допустиме. Справжнє ім'я видно в IL (`-il`) і в таблиці `MethodDef`.

:::

:::accordion-item{label="Що робить опція -lv CSharp1 і навіщо вона?" icon="i-lucide-help-circle"}

Вона змушує декомпілятор друкувати код синтаксисом C# 1, без новіших конструкцій. Декомпілятор не може «зібрати назад» інтерполяцію рядків чи інший синтаксичний цукор і показує код таким, яким його згенерував компілятор. Так видно, наприклад, що `$"..."` перетворюється на виклики `DefaultInterpolatedStringHandler`.

:::

:::accordion-item{label="Як в IL записано цикл for?" icon="i-lucide-help-circle"}

Локальні змінні оголошено в `.locals init` слотами з типами, значення переносяться між ними і стеком інструкціями `stloc` і `ldloc`. Після ініціалізації стоїть безумовний перехід `br.s` на перевірку умови в кінці циклу, а умовний перехід (`ble.s`, `blt.s` тощо) повертає виконання на початок тіла, поки умова істинна.

:::

:::accordion-item{label="Які основні прийоми обфускації і що кожен ускладнює?" icon="i-lucide-help-circle"}

Перейменування прибирає змістовні імена класів, методів і параметрів. Приховування рядків прибирає з коду текстові літерали. Заплутування потоку керування перетворює прості `if` і цикли на машину станів, яку важко прочитати. Захист від змін і дебагера заважає модифікувати й досліджувати програму під час роботи.

:::

:::accordion-item{label="Чому обфускатор не може надійно сховати ключ ліцензії, зашитий у програму?" icon="i-lucide-help-circle"}

Програма мусить сама отримати ключ, щоб порівняти його з введеним. Отже, і закодований ключ, і спосіб його декодування лежать в assembly, а під час роботи ключ є в пам'яті у звичайному вигляді. Обфускація лише ускладнює пошук. Перевірку, яку не можна обійти, робить сервер.

:::

:::accordion-item{label="Навіщо зберігати файл Mapping.txt і чому його не передають користувачам?" icon="i-lucide-help-circle"}

`Mapping.txt` містить відповідність нових імен (`A`, `b`) старим (`Program`, `IsValidKey`). Без нього неможливо зрозуміти повідомлення про помилку з обфускованої програми: у стеку викликів будуть лише `A.A.A`. Користувачам його не дають, бо він повністю скасовує перейменування.

:::

## Практичні завдання

Чотири завдання на закріплення, кожне на 10–15 хвилин. У кожному є письмова відповідь і скріншот: результат має бути отриманий на вашій машині.

::::accordion

:::accordion-item{label="Завдання 1. Три погляди на одну програму" icon="i-lucide-clipboard-list"}

1. Візьміть програму `average.cs` з лекції про перший проєкт (середня оцінка) або будь-яку свою програму з методом, у якому є хоча б дві локальні змінні.
2. Зберіть її в Debug і в Release у різні папки.
3. Декомпілюйте три варіанти: Release, Debug, Debug з `-usepdb`.
4. Заповніть таблицю для кожної локальної змінної:

| Змінна в коді | Release | Debug | Debug + `-usepdb` |
|---|---|---|---|
| | | | |

5. Поясніть письмово, чому в Release деяких змінних немає зовсім і звідки беруться імена в Debug без pdb.

Додайте скріншот трьох виводів.

:::

:::accordion-item{label="Розв'язок завдання 1" icon="i-lucide-check-circle"}

Для `average.cs` (ilspycmd 11.2):

| Змінна в коді | Release | Debug | Debug + `-usepdb` |
|---|---|---|---|
| `grades` | `array` | `array` | `grades` |
| `sum` | `num` | `num` | `sum` |
| `i` | `i` | `i` | `i` |
| `average` | `value` | `value` | `average` |

- Без `.pdb` декомпілятор вигадує імена: масив — `array`, `int` — `num`, лічильник циклу `for` — `i`. Змінна `average` отримала ім'я `value`, бо далі передається в метод, параметр якого так називається.
- У цій програмі Release не прибрав жодної змінної: кожна використовується більше одного разу. Зникають змінні, значення яких використано лише раз, як `prefix` у `greet.cs`.
- Імена локальних змінних не потрапляють у метадані: там є лише слоти з типами (`.locals init`). Імена зберігає тільки `.pdb`.

:::

:::accordion-item{label="Завдання 2. Два декомпілятори" icon="i-lucide-clipboard-list"}

1. Оберіть метод з BCL: `Math.Clamp(int, int, int)` або `string.IsNullOrWhiteSpace(string)`.
2. Декомпілюйте його в ilspycmd.
3. Відкрийте той самий метод у своїй IDE: напишіть у будь-якій програмі виклик, наприклад `Math.Clamp(5, 0, 10)`, і перейдіть до визначення (F12 у Visual Studio і VS Code, Ctrl+клік або Cmd+клік у Rider).
4. Порівняйте два результати: чим відрізняються імена, форматування, атрибути, коментарі? Чи однакова логіка?

Додайте скріншоти з обох інструментів.

```csharp
public static int Clamp(int value, int min, int max)
{

		ThrowMinMaxException(min, max);
```

```csharp [even-sum.cs]
Console.WriteLine(EvenSum(10));

static int EvenSum(int n)
{
    int sum = 0;
    for (int i = 1; i <= n; i++)
    {
        if (i % 2 == 0)
        {
            sum += i;
        }
    }
    return sum;
}
```

Програма друкує `30`. В IL:

- `.locals init` з двома слотами `int32`: `[0]` — `sum`, `[1]` — `i`;
- умова циклу — `ble.s` на початок тіла в кінці циклу, як у `SumTo`;
- умова `if` — `rem` (остача від ділення) і умовний перехід `brtrue.s`, який обходить додавання, якщо остача не нуль;
- `return` — `ldloc.0` і `ret` після циклу.

За ітерацію виконуються два умовні переходи: один для `if`, один для умови циклу. Точні мітки й форма переходу залежать від версії компілятора, тому на скріншоті важливо позначити саме роль інструкцій.
