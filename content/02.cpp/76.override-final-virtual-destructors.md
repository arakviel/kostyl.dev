## Коли компілятор не бачить помилки: підступність сигнатур

Припустимо, ви розробляєте графічну систему з класом `Widget` та його нащадками. Базовий клас оголошує віртуальний метод `render()` для відображення віджета на екрані:

```cpp [WidgetSystem.cpp]
#include <iostream>

class Widget
{
public:
    virtual void render() const
    {
        std::cout << "Widget: базове відображення\n";
    }
};

class Button : public Widget
{
public:
    // Програміст забув const — це НЕ перевизначення!
    void render()
    {
        std::cout << "Button: малюю кнопку\n";
    }
};

int main()
{
    Button btn;
    Widget* ptr = &btn;
    
    ptr->render();  // Очікуємо: "Button: малюю кнопку"
    
    return 0;
}
```

Інтуїтивно ми очікуємо, що виклик `ptr->render()` виведе `"Button: малюю кнопку"`, адже `ptr` адресує об'єкт `Button`, а метод `Widget::render()` є віртуальним. Проте результат шокує:

::terminal-preview{title="./WidgetSystem"}
<div class="line">Widget: базове відображення</div>
::

Поліморфізм не спрацював! Метод `Button::render()` **не є перевизначенням** `Widget::render()`, адже сигнатури різні: `Widget::render()` є константним методом (має `const` після параметрів), а `Button::render()` — ні. Компілятор вважає їх **різними методами** і мовчки компілює код без жодних попереджень.

Це одна з найпідступніших проблем віртуальних функцій у C++: **випадкове перевантаження замість перевизначення**. Програміст мав намір перевизначити метод, але через дрібну помилку в сигнатурі (забутий `const`, інший тип параметра, додатковий `&`) створив незалежний метод. Код компілюється, виглядає правильним, але поводиться неочікувано.

У цій статті ми вивчимо інструменти C++11, які вирішують цю проблему (**специфікатори `override` і `final`**), а також розглянемо критично важливу тему **віртуальних деструкторів** — механізм, без якого робота з поліморфними об'єктами призводить до витоків пам'яті та Undefined Behavior.

::card-group

::card{title="🎯 Мета статті" icon="i-lucide-target"}

- Опанувати специфікатор `override` (C++11) як обов'язковий інженерний стандарт контролю компілятора
- Використовувати специфікатор `final` для заборони подальшого перевизначення методу або наслідування класу
- Дослідити смертельну небезпеку невіртуальних деструкторів при видаленні поліморфних об'єктів
- Засвоїти фундаментальне правило: базовий клас із віртуальними функціями зобов'язаний мати віртуальний деструктор
- Навчитися розрізняти сценарії, коли деструктор має бути публічним віртуальним, а коли — захищеним невіртуальним

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Специфікатор `override`** (*override specifier*): інструкція компілятору перевірити, що метод дійсно є перевизначенням віртуального методу базового класу
- **Специфікатор `final`** (*final specifier*): заборона подальшого перевизначення методу або заборона наслідування класу
- **Віртуальний деструктор** (*virtual destructor*): деструктор базового класу, позначений як `virtual`, що забезпечує каскадне виклик деструкторів при видаленні похідного об'єкта через покажчик на базовий клас
- **Витік ресурсів** (*resource leak*): ситуація, коли ресурси (пам'ять, файли, сокети) не звільняються через невірну логіку деструкції
- **Коваріантний тип повернення** (*covariant return type*): можливість перевизначеного методу повертати покажчик або посилання на більш похідний клас

## Специфікатор `override`: компілятор як перший рецензент коду

### Проблема: мовчазне перевантаження замість перевизначення

Як ми побачили у вступному прикладі, забута модифікація в сигнатурі методу призводить до того, що метод похідного класу **не є перевизначенням**, хоча програміст мав саме такий намір. Компілятор C++ не видає помилку, адже технічно можливо мати два методи з однаковим ім'ям, але різними сигнатурами — це перевантаження.

Розглянемо кілька типових сценаріїв такої помилки:

```cpp [CommonMistakes.cpp]
class Base
{
public:
    virtual void process(int x) const { /* ... */ }
    virtual int getValue() { return 0; }
    virtual void update() { /* ... */ }
};

class Derived : public Base
{
public:
    // ❌ Помилка 1: забули const
    void process(int x) { /* ... */ }
    
    // ❌ Помилка 2: інший тип параметра (double замість int)
    void process(double x) const { /* ... */ }
    
    // ❌ Помилка 3: інший тип повернення
    double getValue() { return 0.0; }
    
    // ❌ Помилка 4: додали параметр за замовчуванням (змінилася сигнатура)
    void update(bool force = false) { /* ... */ }
};
```

Жоден із методів `Derived` **не є перевизначенням** відповідних методів `Base`, адже сигнатури різні. Проте компілятор мовчить — код компілюється без попереджень. Поліморфізм не працює, а програміст може витратити години на налагодження, намагаючись зрозуміти, чому викликається базовий метод замість похідного.

### Рішення: специфікатор `override`

C++11 додав **специфікатор `override`** — спеціальну мітку, яку можна додати після сигнатури методу, щоб явно вказати компілятору: «цей метод **має бути** перевизначенням віртуального методу базового класу». Якщо компілятор не знайде відповідного віртуального методу в базовому класі (або сигнатури не збігаються), він видасть **помилку компіляції**:

```cpp [OverrideSpecifier.cpp]
class Base
{
public:
    virtual void process(int x) const { /* ... */ }
};

class Derived : public Base
{
public:
    // ✅ Компілятор перевірить, чи це дійсно перевизначення
    void process(int x) const override { /* ... */ }
};
```

Тепер компілятор гарантує, що `Derived::process()` дійсно є перевизначенням `Base::process()`. Якщо ми помилимося в сигнатурі, компілятор негайно повідомить:

```cpp [OverrideError.cpp]
class Base
{
public:
    virtual void process(int x) const { /* ... */ }
};

class Derived : public Base
{
public:
    // ❌ Помилка компіляції: метод не перевизначує жоден базовий метод
    void process(int x) override { /* ... */ }  // Забули const!
};
```

Компілятор видасть помилку на кшталт:

```
error: 'void Derived::process(int)' marked 'override', but does not override
```

Це змушує програміста виправити сигнатуру (додати `const`) або усвідомити, що метод не призначений для перевизначення.

::tip
**Обов'язкова практика сучасного C++**: використовуйте `override` для **кожного** методу, який призначений для перевизначення віртуального методу базового класу. Це безкоштовна перевірка на етапі компіляції, яка виявляє помилки, які інакше проявилися б лише під час виконання або тестування. Більшість корпоративних code style guides (Google, LLVM, Qt) вимагають обов'язкового використання `override`.

::

### Синтаксис та розміщення

Специфікатор `override` розміщується **після списку параметрів та специфікатора `const`** (якщо метод константний), але **перед тілом методу**:

```cpp
class Base
{
public:
    virtual void foo() const;
    virtual int bar(double x);
};

class Derived : public Base
{
public:
    void foo() const override;        // ✅ Правильне розміщення
    int bar(double x) override;       // ✅ Правильне розміщення
};
```

Ключове слово `virtual` у похідному класі **необов'язкове**, якщо використовується `override` — сам факт перевизначення робить метод віртуальним. Проте багато програмістів залишають `virtual` для ясності:

::code-group

```cpp [З явним virtual]
class Derived : public Base
{
public:
    virtual void process(int x) const override;
};
```

```cpp [Без явного virtual]
class Derived : public Base
{
public:
    void process(int x) const override;
};
```

::

Обидва варіанти коректні та еквівалентні. `override` сам по собі гарантує віртуальність. Вибір — питання стилю команди.

::note
**Технічний нюанс**: `override` та `final` — це **не ключові слова** (*keywords*) у класичному розумінні. Це **контекстні ідентифікатори** (*contextual identifiers*), які мають спеціальне значення лише в певних позиціях (після сигнатури методу). У будь-якому іншому контексті `override` та `final` — звичайні ідентифікатори, які можна використовувати як імена змінних або функцій. Це забезпечує зворотну сумісність із старим кодом, написаним до C++11.

::

### Практичний приклад: ієрархія фігур

Розглянемо повний приклад з використанням `override`:

```cpp [ShapeHierarchy.cpp]
#include <iostream>
#include <cmath>

class Shape
{
public:
    virtual ~Shape() = default;
    
    virtual double getArea() const = 0;  // Чисто віртуальна функція
    virtual void describe() const
    {
        std::cout << "Це базова фігура\n";
    }
};

class Circle : public Shape
{
private:
    double radius;

public:
    Circle(double r) : radius(r) {}
    
    double getArea() const override
    {
        return 3.14159 * radius * radius;
    }
    
    void describe() const override
    {
        std::cout << "Це коло з радіусом " << radius << "\n";
    }
};

class Rectangle : public Shape
{
private:
    double width, height;

public:
    Rectangle(double w, double h) : width(w), height(h) {}
    
    double getArea() const override
    {
        return width * height;
    }
    
    void describe() const override
    {
        std::cout << "Це прямокутник " << width << "x" << height << "\n";
    }
};

int main()
{
    Circle circle(5.0);
    Rectangle rect(4.0, 6.0);
    
    Shape* shapes[] = { &circle, &rect };
    
    for (Shape* shape : shapes) {
        shape->describe();
        std::cout << "  Площа: " << shape->getArea() << "\n\n";
    }
    
    return 0;
}
```

<div class="line"></div>
<div class="line">Це прямокутник 4x6</div>
<div class="line">  Площа: 24</div>
::

У цьому прикладі всі перевизначення позначені `override`. Якщо програміст випадково помилиться в сигнатурі (наприклад, забуде `const`), компілятор негайно повідомить про помилку.

## Специфікатор `final`: заборона подальших змін

### Мотивація: коли перевизначення небажане

Іноді потрібно **заборонити** подальше перевизначення віртуального методу або наслідування класу. Причини можуть бути різними:

1. **Безпека та коректність**: метод реалізує критично важливу логіку, зміна якої може порушити інваріанти системи
2. **Оптимізація**: компілятор може виконати **девіртуалізацію** (*devirtualization*) — замінити динамічний виклик на прямий, якщо точно відомо, що метод не буде перевизначено
3. **Архітектурні обмеження**: клас є фінальною реалізацією концепції, подальше наслідування не має сенсу

C++11 додав **специфікатор `final`** для цих сценаріїв. `final` може застосовуватися до:

- **Окремих методів** — заборона їх перевизначення в похідних класах
- **Цілих класів** — заборона наслідування

### Заборона перевизначення методу

Специфікатор `final` для методу вказується в тому ж місці, що й `override`:

```cpp [FinalMethod.cpp]
#include <iostream>

class Animal
{
public:
    virtual const char* speak() const
    {
        return "???";
    }
};

class Dog : public Animal
{
public:
    const char* speak() const override final  // ✅ Перевизначення, але заборонено далі змінювати
    {
        return "Woof";
    }
};

class Bulldog : public Dog
{
public:
    // ❌ Помилка компіляції: Dog::speak() позначено як final
    const char* speak() const override
    {
        return "Woof-woof";
    }
};
```

Компілятор видасть помилку:

```
error: virtual function 'virtual const char* Bulldog::speak() const' overrides final function
```

Метод `Dog::speak()` позначено як `final`, тому клас `Bulldog` не може його перевизначити.

::note
Можна використовувати `override` та `final` одночасно: `override final`. Це означає: «цей метод є перевизначенням базового методу, але подальше перевизначення заборонено». Порядок не має значення — можна писати `final override` або `override final`.

::

### Заборона наслідування класу

Щоб заборонити наслідування класу, `final` вказується **після імені класу** перед списком базових класів (якщо є):

```cpp [FinalClass.cpp]
class Animal
{
public:
    virtual const char* speak() const { return "???"; }
};

class Dog final : public Animal  // ✅ Dog не можна наслідувати
{
public:
    const char* speak() const override { return "Woof"; }
};

// ❌ Помилка компіляції: Dog позначено як final
class Bulldog : public Dog
{
public:
    const char* speak() const override { return "Woof-woof"; }
};
```

Компілятор видасть помилку:

```
error: cannot derive from 'final' base 'Dog' in derived type 'Bulldog'
```

Клас `Dog` позначено як `final`, тому неможливо створити похідний клас `Bulldog`.

### Коли використовувати `final`

::card-group

::card{title="✅ Використовуйте final, коли:" icon="i-lucide-check"}

- Клас є кінцевою конкретною реалізацією абстракції (наприклад, `std::string` — фінальна реалізація рядка)
- Метод реалізує критично важливу логіку, порушення якої призведе до некоректної поведінки системи
- Потрібна оптимізація: компілятор може виконати девіртуалізацію для `final` методів
- Архітектура системи чітко розмежовує абстракції та конкретні реалізації

::

::card{title="❌ Уникайте final, коли:" icon="i-lucide-x"}

- Клас є частиною публічного API бібліотеки — користувачі можуть захотіти розширити його
- Немає чіткого архітектурного обґрунтування заборони наслідування
- Використовуєте `final` «на всяк випадок» без конкретної причини
- Проєктуєте систему плагінів або розширень, де гнучкість важливіша за захист

::

::

::warning
**Надмірне використання `final`** може зробити архітектуру негнучкою. Застосовуйте `final` свідомо, лише коли є чітке розуміння, чому подальше наслідування або перевизначення небажане. У більшості випадків достатньо позначити методи як `virtual`, а вибір, чи перевизначувати їх, залишити розробникам похідних класів.

::

### Оптимізація через девіртуалізацію

Одна з переваг `final` — можливість компілятора виконати **девіртуалізацію**. Коли метод або клас позначено як `final`, компілятор знає, що подальших перевизначень не буде, тому може замінити динамічний виклик через vtable на прямий виклик функції за фіксованою адресою:

```cpp [Devirtualization.cpp]
class Base
{
public:
    virtual void process() const { /* ... */ }
};

class Derived final : public Base  // Клас позначено як final
{
public:
    void process() const override { /* ... */ }
};

void example(const Derived& obj)
{
    // Компілятор знає, що obj має тип Derived і клас final
    // Виклик може бути девіртуалізовано: замість непрямого виклику через vtable
    // компілятор генерує прямий виклик Derived::process()
    obj.process();
}
```

У сучасних компіляторах (GCC, Clang, MSVC) девіртуалізація відбувається автоматично для `final` класів та методів, що покращує продуктивність у критичних ділянках коду.

## Віртуальні деструктори: запобігання катастрофічним витокам

### Проблема: невіртуальний деструктор у базовому класі

Тепер розглянемо одну з найнебезпечніших проблем поліморфізму в C++ — **невіртуальні деструктори**. Припустимо, ми створюємо динамічний об'єкт похідного класу та зберігаємо його через покажчик на базовий клас, а потім видаляємо:

```cpp [NonVirtualDestructor.cpp]
#include <iostream>

class Base
{
public:
    Base() { std::cout << "Конструктор Base\n"; }
    ~Base() { std::cout << "Деструктор Base\n"; }  // ❌ НЕ віртуальний!
};

class Derived : public Base
{
private:
    int* data;

public:
    Derived()
    {
        data = new int[1000];  // Виділяємо динамічну пам'ять
        std::cout << "Конструктор Derived (виділено 1000 int)\n";
    }
    
    ~Derived()
    {
        delete[] data;  // Звільняємо пам'ять
        std::cout << "Деструктор Derived (звільнено пам'ять)\n";
    }
};

int main()
{
    Base* ptr = new Derived();  // Створюємо Derived, зберігаємо через Base*
    
    std::cout << "\nВидаляємо об'єкт...\n";
    delete ptr;  // ⚠️ Небезпека!
    
    return 0;
}
```

Інтуїтивно ми очікуємо, що `delete ptr` викличе деструктор `Derived`, який звільнить динамічну пам'ять, а потім деструктор `Base`. Проте результат виконання шокує:

::terminal-preview{title="./NonVirtualDestructor"}
<div class="line">Конструктор Base</div>
<div class="line">Конструктор Derived (виділено 1000 int)</div>
<div class="line"></div>
<div class="line">Видаляємо об'єкт...</div>
<div class="line">Деструктор Base</div>
::

**Деструктор `Derived` не викликався!** Виділена пам'ять (`data = new int[1000]`) не була звільнена. Це **витік пам'яті** (*memory leak*) — одна з найнебезпечніших помилок у C++.

### Чому так відбувається

Коли ми виконуємо `delete ptr`, компілятор аналізує **статичний тип покажчика** (`Base*`). Оскільки деструктор `Base::~Base()` **не віртуальний**, компілятор генерує код, що викликає **лише** `Base::~Base()`, ігноруючи факт, що `ptr` насправді адресує об'єкт `Derived`.

Це аналогічно статичному зв'язуванню для звичайних методів: без `virtual` компілятор орієнтується на тип покажчика, а не на реальний тип об'єкта в пам'яті.

::caution
**Undefined Behavior**: видалення похідного об'єкта через покажчик на базовий клас з невіртуальним деструктором призводить до **Undefined Behavior** за стандартом C++. Програма може:
- Витікати пам'ять (як у нашому прикладі)
- Не закрити файли, сокети, з'єднання з базами даних
- Залишити незавершені транзакції
- Призвести до краху через некоректну деструкцію об'єктів

Це не теоретична проблема — це реальна причина багатьох витоків пам'яті та крахів у виробничих системах.

::

### Рішення: віртуальний деструктор

Щоб вирішити цю проблему, достатньо позначити деструктор базового класу як `virtual`:

```cpp [VirtualDestructor.cpp]
#include <iostream>

class Base
{
public:
    Base() { std::cout << "Конструктор Base\n"; }
    virtual ~Base() { std::cout << "Деструктор Base\n"; }  // ✅ Віртуальний!
};

class Derived : public Base
{
private:
    int* data;

public:
    Derived()
    {
        data = new int[1000];
        std::cout << "Конструктор Derived (виділено 1000 int)\n";
    }
    
    ~Derived() override  // ✅ Перевизначення віртуального деструктора
    {
        delete[] data;
        std::cout << "Деструктор Derived (звільнено пам'ять)\n";
    }
};

int main()
{
    Base* ptr = new Derived();
    
    std::cout << "\nВидаляємо об'єкт...\n";
    delete ptr;  // ✅ Тепер коректно!
    
    return 0;
}
```

<div class="line">Конструктор Derived (виділено 1000 int)</div>
<div class="line"></div>
<div class="line">Видаляємо об'єкт...</div>
<div class="line">Деструктор Derived (звільнено пам'ять)</div>
<div class="line">Деструктор Base</div>
::

Тепер все працює коректно! Деструктор `Derived` викликається першим, звільняючи динамічну пам'ять, а потім викликається деструктор `Base`. Це **каскадна деструкція** — стандартна поведінка віртуальних деструкторів.

::tip
**Золоте правило віртуальних деструкторів**: якщо клас має хоча б один віртуальний метод (призначений для наслідування та поліморфізму), його деструктор **обов'язково** повинен бути віртуальним. Інакше видалення об'єктів похідних класів через покажчики на базовий клас призводить до витоків ресурсів і Undefined Behavior.

::

### Реалістичний приклад: система файлів

Розглянемо реалістичний приклад, де відсутність віртуального деструктора призводить до витоку файлових дескрипторів:

```cpp [FileSystem.cpp]
#include <iostream>
#include <fstream>
#include <string>

class FileHandler
{
public:
    virtual void write(const std::string& data) = 0;
    
    // ❌ ПОМИЛКА: деструктор не віртуальний!
    ~FileHandler()
    {
        std::cout << "Деструктор FileHandler\n";
    }
};

class TextFileHandler : public FileHandler
{
private:
    std::ofstream file;
    std::string filename;

public:
    TextFileHandler(const std::string& fname) : filename(fname)
    {
        file.open(filename);
        if (file.is_open()) {
            std::cout << "Відкрито файл: " << filename << "\n";
        }
    }
    
    void write(const std::string& data) override
    {
        if (file.is_open()) {
            file << data << "\n";
        }
    }
    
    ~TextFileHandler() override
    {
        if (file.is_open()) {
            file.close();
            std::cout << "Закрито файл: " << filename << "\n";
        }
    }
};

int main()
{
    FileHandler* handler = new TextFileHandler("log.txt");
    handler->write("Запис даних у файл");
    
    delete handler;  // ⚠️ Файл НЕ закриється, якщо ~FileHandler не віртуальний!
    
    return 0;
}
```

Якщо деструктор `FileHandler` не віртуальний, виклик `delete handler` викличе лише `~FileHandler()`, пропустивши `~TextFileHandler()`. Файл залишиться відкритим, дескриптор витече, а дані можуть не записатися на диск через буферизацію.

::code-group

```cpp [❌ Невіртуальний деструктор]
class FileHandler
{
public:
    ~FileHandler() { /* ... */ }  // Не віртуальний
};

// Результат: файл не закривається
// Витік файлового дескриптора
```

```cpp [✅ Віртуальний деструктор]
class FileHandler
{
public:
    virtual ~FileHandler() { /* ... */ }  // Віртуальний
};

// Результат: ~TextFileHandler() викликається
// Файл коректно закривається
```

## Синтаксис віртуального деструктора: default vs явна реалізація

### Використання `= default` (C++11)

Якщо деструктор базового класу не виконує жодної спеціальної логіки (не керує ресурсами безпосередньо), найкраща практика — оголосити його як віртуальний через `= default`:

```cpp
class Base
{
public:
    virtual ~Base() = default;  // ✅ Віртуальний деструктор за замовчуванням
};
```

Це явно вказує компілятору: «згенеруй стандартний деструктор, але зроби його віртуальним». Переваги цього підходу:

1. **Ясність наміру**: код явно вказує, що клас призначений для наслідування
2. **Оптимізація**: компілятор може згенерувати більш ефективний код, ніж для порожнього `~Base() {}`
3. **Сумісність із Rule of Zero**: якщо клас не керує ресурсами вручну, всі спеціальні члени можна залишити за замовчуванням

### Явна реалізація деструктора

Якщо базовий клас безпосередньо керує ресурсами (динамічна пам'ять, файли, мережеві з'єднання), деструктор потрібно реалізувати явно:

```cpp
class ResourceManager
{
private:
    int* data;

public:
    ResourceManager() : data(new int[100]) {}
    
    virtual ~ResourceManager()  // ✅ Віртуальний з явною реалізацією
    {
        delete[] data;
        std::cout << "Ресурси звільнено\n";
    }
};
```

::note
**Rule of Five** (Правило п'яти): якщо ви явно визначаєте деструктор, майже напевно вам потрібно також явно визначити або заборонити (`= delete`) конструктор копіювання, оператор присвоєння, конструктор переміщення та оператор переміщення. Це запобігає подвійному видаленню та іншим проблемам керування ресурсами. Ми детально розглянемо це в статтях про move-семантику.

::

### Захищений невіртуальний деструктор

Іноді клас призначений лише як базовий для інших класів, але **не призначений для видалення через покажчик на базовий клас**. У таких випадках деструктор має бути **захищеним та невіртуальним**:

```cpp
class NonPolymorphicBase
{
protected:
    ~NonPolymorphicBase() = default;  // ✅ Захищений невіртуальний деструктор

public:
    void sharedLogic() { /* ... */ }
};

class Derived : public NonPolymorphicBase
{
public:
    ~Derived() = default;  // Публічний невіртуальний деструктор
};

int main()
{
    Derived d;  // ✅ Можна створювати локальні об'єкти
    
    // NonPolymorphicBase* ptr = new Derived();
    // delete ptr;  // ❌ Помилка компіляції: ~NonPolymorphicBase() захищений
    
    return 0;
}
```

Захищений деструктор дозволяє похідним класам викликати його (під час каскадної деструкції), але забороняє видалення через покажчик на базовий клас, усуваючи саму можливість витоку ресурсів.

::tip
**Коли використовувати захищений невіртуальний деструктор**:
- Клас є утилітним або міксином, що додає функціональність через наслідування
- Клас не має віртуальних методів (не призначений для поліморфізму)
- Видалення через покажчик на базовий клас не передбачається архітектурою

У всіх інших випадках, якщо клас має віртуальні методи, деструктор має бути **публічним віртуальним**.

::

## Вартість віртуального деструктора

### Накладні витрати

Віртуальний деструктор має ті самі накладні витрати, що й будь-який віртуальний метод:

1. **Покажчик на vtable**: кожен об'єкт класу з віртуальними методами зберігає приховані 8 байт (64-бітна система) для покажчика на віртуальну таблицю
2. **Непрямий виклик**: замість прямого виклику за фіксованою адресою виконується непрямий виклик через vtable

Проте ці витрати мізерні порівняно з катастрофічними наслідками витоків ресурсів. Для класів, призначених для поліморфізму, віртуальний деструктор — **обов'язковий**, незалежно від накладних витрат.

### Коли віртуальний деструктор зайвий

Якщо клас:
- Не має віртуальних методів (не призначений для поліморфізму)
- Є простою структурою даних (POD — Plain Old Data)
- Ніколи не використовується як базовий клас

То віртуальний деструктор зайвий і навіть шкідливий (збільшує розмір об'єкта без потреби):

```cpp
// ❌ Не робіть це — Point не призначений для наслідування
struct Point
{
    double x, y;
    virtual ~Point() = default;  // Зайвий віртуальний деструктор
};

// sizeof(Point) стане 24 байти замість 16 байт
// (8 байт x + 8 байт y + 8 байт vptr)
```

::warning
**Не додавайте віртуальний деструктор «на всяк випадок»**. Робіть деструктор віртуальним, лише якщо клас має віртуальні методи або явно призначений для наслідування. Зайвий віртуальний деструктор збільшує розмір кожного об'єкта та блокує оптимізації.

::

## Порівняльна таблиця: віртуальний vs невіртуальний деструктор

| Аспект | Невіртуальний деструктор | Віртуальний деструктор |
|:-------|:-------------------------|:-----------------------|
| **Виклик через `Base*`** | Викликається лише `~Base()` | Викликається `~Derived()`, потім `~Base()` |
| **Звільнення ресурсів** | ❌ Ресурси `Derived` витікають | ✅ Ресурси коректно звільняються |
| **Undefined Behavior** | ⚠️ Так, при `delete basePtr` | ✅ Ні, поведінка визначена стандартом |
| **Розмір об'єкта** | Не збільшується | +8 байт (vptr) на кожен об'єкт |
| **Продуктивність** | Прямий виклик (швидко) | Непрямий виклик через vtable (незначно повільніше) |
| **Коли використовувати** | Клас не призначений для наслідування | Клас має віртуальні методи або є базовим |

## Коваріантні типи повернення: гнучкість перевизначення

### Спеціальний випадок: повернення покажчика на похідний клас

Раніше ми згадували, що тип повернення перевизначення має збігатися з типом повернення базового методу. Проте є важливий виняток: **коваріантні типи повернення** (*covariant return types*).

Якщо базовий віртуальний метод повертає **покажчик або посилання** на клас `Base`, перевизначення в похідному класі може повертати **покажчик або посилання** на клас `Derived`:

```cpp [CovariantReturn.cpp]
#include <iostream>

class Animal
{
public:
    virtual ~Animal() = default;
    
    // Повертає Animal*
    virtual Animal* clone() const
    {
        std::cout << "Клонування Animal\n";
        return new Animal(*this);
    }
};

class Dog : public Animal
{
public:
    // ✅ Коваріантний тип повернення: Dog* замість Animal*
    Dog* clone() const override
    {
        std::cout << "Клонування Dog\n";
        return new Dog(*this);
    }
};

class Cat : public Animal
{
public:
    Cat* clone() const override
    {
        std::cout << "Клонування Cat\n";
        return new Cat(*this);
    }
};

int main()
{
    Dog barsik;
    Cat murka;
    
    // Пряме звернення: отримуємо Dog* без приведення типів
    Dog* barsikClone = barsik.clone();
    
    // Через покажчик на базовий клас: повертається Animal*
    Animal* animalPtr = &murka;
    Animal* murkaClone = animalPtr->clone();  // Фактично створюється Cat
    
    delete barsikClone;
    delete murkaClone;
    
    return 0;
}
```

::terminal-preview{title="./CovariantReturn"}
<div class="line">Клонування Dog</div>
<div class="line">Клонування Cat</div>
::

Коваріантні типи повернення зручні для патернів проєктування, таких як **фабричний метод** (*Factory Method*) або **прототип** (*Prototype*), де метод створює та повертає копію об'єкта. Без коваріантних типів довелося б виконувати явне приведення типів:

::code-group

```cpp [З коваріантністю]
Dog barsik;
Dog* clone = barsik.clone();  // ✅ Природно
```

```cpp [Без коваріантності]
Dog barsik;
Dog* clone = static_cast<Dog*>(barsik.clone());  // ❌ Незручно
```

::

::note
**Обмеження коваріантних типів**:
1. Працює лише для **покажчиків або посилань**, не для повернення за значенням
2. Похідний тип має бути **доступним** (публічне або захищене наслідування)
3. Рівень кваліфікації (`const`, `volatile`) має збігатися

Приклад неправильного використання:
```cpp
class Base {
    virtual Base getValue();  // Повернення за значенням
};

class Derived : public Base {
    Derived getValue() override;  // ❌ Помилка: коваріантність працює лише для покажчиків/посилань
};
```
::

## Практичні рекомендації та чеклист

::card-group

::card{title="✅ Обов'язкові практики" icon="i-lucide-check-square"}

- **Завжди** використовуйте `override` для перевизначень — це безкоштовна перевірка компілятора
- **Завжди** робіть деструктор віртуальним, якщо клас має віртуальні методи
- Використовуйте `virtual ~ClassName() = default;` для класів без керування ресурсами
- Застосовуйте `final` свідомо, лише коли є чітке обґрунтування заборони наслідування

::

::card{title="❌ Типові помилки" icon="i-lucide-alert-triangle"}

- Забувати `const` у сигнатурі перевизначення
- Робити деструктор невіртуальним у базовому класі з віртуальними методами
- Використовувати `final` без причини, роблячи архітектуру негнучкою
- Додавати віртуальний деструктор до простих структур даних (POD)

::

::card{title="🔍 Діагностика проблем" icon="i-lucide-search"}

- Компілятор не бачить перевизначення → перевірте сигнатуру на `const`, типи параметрів
- Витоки пам'яті при `delete basePtr` → деструктор базового класу не віртуальний
- Помилка «cannot derive from final» → базовий клас або метод позначено `final`
- Неочікуваний виклик базового методу → забули `override`, створили перевантаження

::

- Публічний віртуальний деструктор → клас призначений для поліморфного видалення

## Резюме

У цій статті ми опанували інструменти C++11, які роблять роботу з поліморфізмом безпечнішою та зрозумілішою:

::card-group

::card{title="🛡️ override" icon="i-lucide-shield-check"}

Специфікатор `override` змушує компілятор перевірити, що метод дійсно є перевизначенням віртуального методу базового класу. Це запобігає підступним помилкам, коли забута модифікація сигнатури (відсутній `const`, інший тип параметра) перетворює перевизначення на незалежний метод.

::

::card{title="🔒 final" icon="i-lucide-lock"}

Специфікатор `final` дозволяє заборонити подальше перевизначення методу або наслідування класу. Це корисно для критично важливих методів, фінальних реалізацій або оптимізацій (девіртуалізація). Використовуйте свідомо, лише з чітким обґрунтуванням.

::

::card{title="⚠️ Віртуальні деструктори" icon="i-lucide-alert-octagon"}

Якщо клас має віртуальні методи, його деструктор **обов'язково** має бути віртуальним. Інакше видалення об'єкта похідного класу через покажчик на базовий клас призводить до витоків ресурсів і Undefined Behavior. Використовуйте `virtual ~ClassName() = default;` для класів без керування ресурсами.

::

::card{title="📐 Коваріантні типи" icon="i-lucide-git-branch-plus"}

Перевизначений метод може повертати покажчик або посилання на більш похідний клас замість точного збігу типу повернення з базовим методом. Це зручно для патернів клонування та фабричних методів.

::

::

**Ключове правило**, яке слід запам'ятати:

> **Якщо клас має хоча б один віртуальний метод, його деструктор має бути публічним віртуальним або захищеним невіртуальним (якщо поліморфне видалення не передбачається).**

У наступній статті ми заглибимося в внутрішні механізми поліморфізму: як компілятор реалізує динамічне зв'язування через **віртуальні таблиці** (vtable), що таке **покажчик на віртуальну таблицю** (vptr), і чому віртуальні функції не працюють у конструкторах та деструкторах.

::::accordion

:::accordion-item{label="📋 Завдання 1: Виправлення помилок перевизначення" icon="i-lucide-clipboard-list"}

Знайдіть і виправте помилки в наступному коді. Використайте `override` для перевірки коректності перевизначень:

```cpp
class Shape
{
public:
    virtual double getArea() const = 0;
    virtual void draw() const { /* ... */ }
    virtual ~Shape() = default;
};

class Circle : public Shape
{
private:
    double radius;

public:
    Circle(double r) : radius(r) {}
    
    // Намагаємося перевизначити getArea
    double getArea() { return 3.14159 * radius * radius; }
    
    // Намагаємося перевизначити draw
    void draw() { /* ... */ }
};
```

:::

:::accordion-item{label="📋 Завдання 2: Віртуальні деструктори та керування ресурсами" icon="i-lucide-clipboard-list"}

Реалізуйте ієрархію класів для керування файлами з коректним звільненням ресурсів:

1. Базовий клас `Logger` з віртуальним методом `log(const std::string& message)`
2. Похідний клас `FileLogger`, що відкриває файл у конструкторі та закриває в деструкторі
3. Переконайтеся, що файл коректно закривається при видаленні через `Logger*`

:::

:::accordion-item{label="❓ Чому override важливіший за явне virtual у похідних класах?" icon="i-lucide-help-circle"}

Хоча метод автоматично стає віртуальним, якщо він перевизначує віртуальний метод базового класу, `override` надає критично важливу перевірку компілятора. Якщо ви помилитеся в сигнатурі (забудете `const`, змініть тип параметра), код без `override` скомпілюється, але створить незалежний метод, а не перевизначення. З `override` компілятор видасть помилку, змусивши виправити сигнатуру. Це запобігає підступним багам, які важко виявити під час виконання.

:::

:::accordion-item{label="❓ Коли використовувати захищений невіртуальний деструктор?" icon="i-lucide-help-circle"}

Захищений невіртуальний деструктор використовується для класів, які призначені лише як **базові** для інших класів, але **не призначені для поліморфного видалення** через покажчик на базовий клас. Захищений деструктор дозволяє похідним класам викликати його (під час каскадної деструкції), але забороняє `delete basePtr` на етапі компіляції, усуваючи саму можливість витоку ресурсів. Це типово для міксинів та утилітних базових класів без віртуальних методів.

:::

:::accordion-item{label="❓ Чи можна поєднувати override та final?" icon="i-lucide-help-circle"}

Так, можна писати `override final` або `final override` (порядок не має значення). Це означає: «цей метод є перевизначенням базового віртуального методу (перевірка через `override`), але подальше перевизначення заборонено (`final`)». Це корисно, коли ви перевизначаєте метод у проміжному класі ієрархії та хочете зафіксувати його поведінку для всіх подальших нащадків.

:::

:::accordion-item{label="✅ Розв'язок: Завдання 1" icon="i-lucide-check-circle"}

```cpp
class Shape
{
public:
    virtual double getArea() const = 0;
    virtual void draw() const { /* ... */ }
    virtual ~Shape() = default;
};

class Circle : public Shape
{
private:
    double radius;

public:
    Circle(double r) : radius(r) {}
    
    // ✅ Виправлено: додано const та override
    double getArea() const override
    {
        return 3.14159 * radius * radius;
    }
    
    // ✅ Виправлено: додано const та override
    void draw() const override { /* ... */ }
};
```

**Помилки**:
1. `getArea()` у `Circle` не мав `const` — сигнатура не збігалася з `Shape::getArea() const`
2. `draw()` у `Circle` не мав `const` — сигнатура не збігалася з `Shape::draw() const`

Додавання `override` змусило б компілятор видати помилки для обох методів, негайно вказуючи на проблему.
