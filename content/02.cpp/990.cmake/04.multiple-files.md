# Проєкт із кількома файлами: перелік джерел і file(GLOB)

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Зібрати проєкт із кількох `.cpp` та `.h` файлів.
- Порівняти три способи вказати джерела: явний перелік, змінні, `file(GLOB)`.
- Пояснити, чому `file(GLOB)` без `CONFIGURE_DEPENDS` не помічає нових файлів.
- Обрати спосіб, який підходить для реальних проєктів.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Одиниця трансляції (*translation unit*):** окремий `.cpp` з усіма підключеними заголовками.
- **`file(GLOB)`:** команда, яка шукає файли за маскою під час конфігурації.
- **`CONFIGURE_DEPENDS`:** прапорець, який змушує систему збірки перевіряти маску знову при кожній збірці.

::

::

У лекції про перший проєкт збирався один `main.cpp`. Реальні програми розділені на модулі, і кожен модуль — це пара `.h` та `.cpp` (тема про багатофайлові програми). Тут розглянемо, як повідомити про всі ці файли CMake.

## Приклад проєкту

Програма складається з трьох одиниць трансляції: `main.cpp`, `math_utils.cpp` і `string_utils.cpp`. Заголовки до одиниць трансляції не додаються окремо, бо компілятор бере їх через `#include`.

::code-tree

```cpp [main.cpp]
#include <iostream>
#include "math_utils.h"
#include "string_utils.h"

int main() {
    std::cout << "5 + 3 = " << add(5, 3) << std::endl;
    std::cout << "10 * 2 = " << multiply(10, 2) << std::endl;

    std::string text = "hello";
    std::cout << "Uppercase: " << toUpperCase(text) << std::endl;

    return 0;
}
```

```cpp [math_utils.h]
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add(int a, int b);
int multiply(int a, int b);

#endif
```

```cpp [math_utils.cpp]
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b) {
    return a * b;
}
```

```cpp [string_utils.h]
#ifndef STRING_UTILS_H
#define STRING_UTILS_H

#include <string>

std::string toUpperCase(const std::string& str);
std::string toLowerCase(const std::string& str);

#endif
```

```cpp [string_utils.cpp]
#include "string_utils.h"
#include <algorithm>

std::string toUpperCase(const std::string& str) {
    std::string result = str;
    std::transform(result.begin(), result.end(), result.begin(), ::toupper);
    return result;
}

std::string toLowerCase(const std::string& str) {
    std::string result = str;
    std::transform(result.begin(), result.end(), result.begin(), ::tolower);
    return result;
}
```

::

Усі три `.cpp` компілюються окремо і лише потім лінкуються. Якщо якогось з них не буде в `add_executable`, компіляція пройде, а лінкер повідомить про невизначені символи (*undefined reference* або `LNK2019` у MSVC).

## Спосіб 1: явний перелік усіх файлів

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyProject)

set(CMAKE_CXX_STANDARD 17)

add_executable(MyProject
    main.cpp
    math_utils.cpp
    math_utils.h
    string_utils.cpp
    string_utils.h
)
```

Файли перелічені прямо в `add_executable`, по одному в рядку. Заголовки `.h` додавати не обов'язково для збірки, але корисно: IDE (Visual Studio, CLion) показує їх у дереві проєкту і не плутає з зайвими файлами.

Це найпростіший і найпрозоріший варіант. Під час код-рев'ю в `git diff` одразу видно, що додано новий файл.

## Спосіб 2: змінні SOURCES і HEADERS

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyProject)

set(CMAKE_CXX_STANDARD 17)

# Список вихідних файлів
set(SOURCES
    main.cpp
    math_utils.cpp
    string_utils.cpp
)

# Список заголовкових файлів (необов'язковий, для IDE)
set(HEADERS
    math_utils.h
    string_utils.h
)

add_executable(MyProject ${SOURCES} ${HEADERS})
```

Результат той самий, але списки винесені в змінні. Зручність у тому, що перелік можна використати в кількох місцях: наприклад, зібрати з тих самих `SOURCES` і виконуваний файл, і тестову програму, або додавати файли до списку умовно:

```cmake
if(WIN32)
    list(APPEND SOURCES windows_specific.cpp)
endif()
```

## Спосіб 3: автоматичний пошук через file(GLOB)

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyProject)

set(CMAKE_CXX_STANDARD 17)

# Знайти всі .cpp файли в поточній папці
file(GLOB SOURCES "*.cpp")

# Знайти всі .h файли
file(GLOB HEADERS "*.h")

add_executable(MyProject ${SOURCES} ${HEADERS})
```

Команда `file(GLOB ЗМІННА маска)` шукає файли за маскою і записує знайдений список у змінну. Додавати файл у `CMakeLists.txt` вручну не потрібно. Спокуслива зручність, але з нею пов'язана проблема.

### Чому GLOB ризикований

Пошук виконується **один раз**, під час конфігурації. Якщо після цього створити новий `.cpp`, система збірки про нього не дізнається: вона не знає, що список файлів міг змінитись. Перевіримо це на нашому проєкті:

<div class="line">[ 75%] Building CXX object CMakeFiles/MyProject.dir/string_utils.cpp.o</div>
<div class="line">[100%] Built target MyProject</div>

Тільки після ручної повторної конфігурації `logger.cpp` потрапив у збірку. Така поведінка дає плутанину в команді: колега додав файл, ви зробили `git pull`, зібрали проєкт, і лінкер видає помилку «undefined reference», хоча код правильний. Причина прихована в кеші.

::warning
Для вихідних файлів проєкту офіційна документація CMake радить **не** використовувати `file(GLOB)`. Додавання або видалення файлу має бути змінною в `CMakeLists.txt`, бо тоді CMake сам знає, що потрібно перегенерувати файли збірки.
::

### CONFIGURE_DEPENDS: компроміс

CMake 3.12 додав прапорець `CONFIGURE_DEPENDS`. З ним система збірки при кожній збірці повторно перевіряє маску і запускає конфігурацію, якщо список файлів змінився:

```cmake
file(GLOB SOURCES CONFIGURE_DEPENDS "*.cpp")
```

Результат на тому ж проєкті:

::terminal-preview{title="GLOB з CONFIGURE_DEPENDS"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">touch extra.cpp</strong></div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">cmake --build build</strong></div>
<div class="line">[ 16%] Building CXX object CMakeFiles/MyProject.dir/extra.cpp.o</div>
<div class="line">[100%] Built target MyProject</div>

::

Нові файли підхоплюються без ручної повторної конфігурації. Платою за це є додаткова перевірка файлової системи при кожній збірці. На великих проєктах і повільних мережевих дисках це помітно, а в документації CMake зазначено, що не всі генератори надійно її підтримують. Тому `CONFIGURE_DEPENDS` слід розглядати як пом'якшення проблеми, а не як її усунення.

::note
`file(GLOB ...)` не рекурсивний. Для пошуку у вкладених папках існує `file(GLOB_RECURSE SOURCES "src/*.cpp")`. Усі зауваження щодо ризиків діють і для нього.
::

## Порівняння способів

| Спосіб | Переваги | Недоліки |
|--------|----------|----------|
| Явний перелік | Прозорий `git diff`, надійна повторна конфігурація, IDE бачить усі файли | Новий файл доводиться дописувати вручну |
| Змінні `SOURCES`, `HEADERS` | Список використовується повторно, його можна збирати умовно | Те саме, що й у явного переліку |
| `file(GLOB)` | Нічого не треба дописувати | Новий файл не помічається без повторної конфігурації |
| `file(GLOB ... CONFIGURE_DEPENDS)` | Нові файли підхоплюються автоматично | Додаткова перевірка при кожній збірці, нестабільна на деяких генераторах |

**Рекомендація:** у реальних проєктах використовуйте способи 1 або 2. Спосіб 3 прийнятний для невеликих навчальних проєктів, де ви єдиний автор і готові перегенеровувати файли збірки.

## Питання для самоперевірки

::::accordion

:::accordion-item{label="❓ Чи обов'язково додавати .h файли в add_executable?" icon="i-lucide-help-circle"}

Для збірки ні, бо компілятор знаходить заголовки через `#include`. Додавати їх варто заради IDE: Visual Studio і CLion показують у дереві проєкту лише ті файли, про які знає CMake. Крім того, зміна заголовка, доданого в ціль, надійніше викликає повторну збірку залежних файлів у деяких генераторах.

:::

:::accordion-item{label="❓ Я додав новий .cpp у папку, а лінкер скаржиться на undefined reference. Що не так?" icon="i-lucide-help-circle"}

Ймовірно, у проєкті використано `file(GLOB)` без `CONFIGURE_DEPENDS`. Файл лежить у папці, але CMake про нього не знає, бо список складений під час попередньої конфігурації. Запустіть `cmake -S . -B build` повторно. Щоб виправити причину, замініть GLOB на явний перелік.

:::

:::accordion-item{label="❓ Чи можна змішувати явний перелік і GLOB?" icon="i-lucide-help-circle"}

Можна, і це типовий підхід у перехідний період. Але змішування ускладнює розуміння того, які файли беруть участь у збірці. Краще обрати один підхід на весь проєкт.

:::

## Практичне завдання

::::accordion

:::accordion-item{label="📋 Завдання: розширення проєкту" icon="i-lucide-clipboard-list"}

1. Створіть проєкт із `main.cpp`, `math_utils.cpp/.h` і `string_utils.cpp/.h` та зберіть його способом 1.
2. Перепишіть `CMakeLists.txt` на спосіб 2 (змінні `SOURCES` і `HEADERS`).
3. Додайте файл `logger.cpp/.h` з функцією `void logMessage(const std::string&)` та викличте її з `main`. Скільки місць у `CMakeLists.txt` довелося змінити?
4. Замініть перелік на `file(GLOB ...)` без `CONFIGURE_DEPENDS`, додайте ще один модуль і подивіться, на якому кроці виникне помилка.

:::

:::accordion-item{label="✅ Розв'язок (способи 1–2)" icon="i-lucide-check-circle"}

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyProject)

set(CMAKE_CXX_STANDARD 17)

set(SOURCES
    main.cpp
    math_utils.cpp
    string_utils.cpp
    logger.cpp
)

set(HEADERS
    math_utils.h
    string_utils.h
    logger.h
)

add_executable(MyProject ${SOURCES} ${HEADERS})
```

У варіантах 1 і 2 змінюється рівно один список: додаються два рядки (`logger.cpp` та `logger.h`). У пункті 4 збірка без повторної конфігурації закінчиться помилкою лінкера `undefined reference to logMessage(...)`.

## Резюме

::card-group

::card{title="📃 Явний перелік" icon="i-lucide-list-checks"}
Найнадійніший спосіб: усі файли названі у `CMakeLists.txt`, зміни видно в `git diff`, CMake завжди в курсі складу проєкту.
::

::card{title="🧺 Змінні списків" icon="i-lucide-variable"}
`SOURCES` і `HEADERS` дозволяють повторно використовувати списки та додавати файли за умовою.
::

::card{title="⚠️ GLOB" icon="i-lucide-triangle-alert"}
Шукає файли лише під час конфігурації, тому нові файли без повторної конфігурації не потрапляють у збірку.
::

::card{title="🔄 CONFIGURE_DEPENDS" icon="i-lucide-refresh-cw"}
Змушує перевіряти маску при кожній збірці. Пом'якшує проблему, але не рекомендований як основний спосіб.
::

::

::note
Тепер проєкт із одним виконуваним файлом збирається без труднощів. Далі код розділимо ще глибше: частину файлів оформимо як бібліотеку, яку використовує кілька програм.
::
