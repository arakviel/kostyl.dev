## Зовнішній тренер на C++: один код для трьох ОС

Тренер виконує три дії: отримує доступ до процесу, читає або пише байти, обходить області пам'яті. На кожній ОС вони виконуються різними викликами, тому код розділено: клас `Process` має однаковий інтерфейс, а в трьох файлах `process_win.cpp`, `process_linux.cpp`, `process_mac.cpp` лежать реалізації. CMake компілює всі три, а директиви `#if defined(...)` залишають активним лише відповідний.

### Структура проєкту

::code-tree

```cpp [process.hpp]
#pragma once
#include <cstddef>
#include <cstdint>
#include <vector>

struct Region { uintptr_t start; size_t size; };

class Process {
public:
    explicit Process(int pid);
    ~Process();
    bool ok() const { return ok_; }
    bool read(uintptr_t addr, void* out, size_t n) const;
    bool write(uintptr_t addr, const void* data, size_t n) const;
    std::vector<Region> writable_regions() const;

    template <class T> bool read_value(uintptr_t a, T& out) const { return read(a, &out, sizeof(T)); }
    template <class T> bool write_value(uintptr_t a, const T& v) const { return write(a, &v, sizeof(T)); }
private:
    int pid_;
    bool ok_ = false;
    /* поля залежать від ОС */
};
```

```cpp [process_linux.cpp]
bool Process::read(uintptr_t addr, void* out, size_t n) const {
    iovec local{out, n};
    iovec remote{reinterpret_cast<void*>(addr), n};
    return process_vm_readv(pid_, &local, 1, &remote, 1, 0) == static_cast<ssize_t>(n);
}

std::vector<Region> Process::writable_regions() const {
    // читаємо /proc/<pid>/maps, залишаємо рядки з правами rw
}
```

```cpp [process_mac.cpp]
bool Process::read(uintptr_t addr, void* out, size_t n) const {
    mach_vm_size_t got = 0;
    kern_return_t kr = mach_vm_read_overwrite(task_, addr, n,
        reinterpret_cast<mach_vm_address_t>(out), &got);
    return kr == KERN_SUCCESS && got == n;
}

// Області: цикл mach_vm_region, залишаємо ті, де protection має READ і WRITE.
```

```cpp [process_win.cpp]
bool Process::read(uintptr_t addr, void* out, size_t n) const {
    SIZE_T got = 0;
    return ReadProcessMemory(handle_, reinterpret_cast<LPCVOID>(addr), out, n, &got) && got == n;
}

// Області: цикл VirtualQueryEx, залишаємо MEM_COMMIT з PAGE_READWRITE.
```

Повний код — у `labs/reverse-engineering/trainer/`. Файл `main.cpp` не містить жодного системного виклику: він працює лише через `Process`.

### Сканер

Для кожної записуваної області тренер зчитує її цілком у буфер і проходить по ньому з кроком 4 байти. Крок у 4 байти використовується, бо `int32_t` зазвичай вирівняний за адресою, кратною 4.

```cpp
for (const Region& r : p.writable_regions()) {
    buf.resize(r.size);
    if (!p.read(r.start, buf.data(), r.size)) continue;
    for (size_t i = 0; i + 4 <= r.size; i += 4) {
        int32_t v;
        std::memcpy(&v, &buf[i], 4);
        if (v == value) printf("0x%llx\n", r.start + i);
    }
}
```

`memcpy` замість приведення вказівника потрібен, щоб уникнути порушення вирівнювання та правил псевдонімів. Читання за один виклик на область швидше, ніж по 4 байти.

### Команди

| Команда | Дія |
| --- | --- |

## Internal-чіт: бібліотека всередині процесу гри

Зовнішній тренер звертається до гри через виклики ОС, кожне читання проходить через ядро. Бібліотека, завантажена в процес, живе в тому самому адресному просторі й бачить пам'ять гри напряму. Вона може читати вказівники, викликати функції гри та міняти код без `ReadProcessMemory`.

| | External | Internal |
| --- | --- | --- |
| Де виконується | окремий процес | всередині гри |
| Швидкість доступу | виклик ядра на кожне читання | прямий доступ до пам'яті |
| Виклик функцій гри | складно | прямо за адресою |
| Складність запуску | проста | потрібна інжекція |
| Легше виявити | аналізом дескрипторів процесу | аналізом списку модулів |

### Як бібліотека потрапляє в процес

::tabs
::tabs-item{label="Linux"}
Змінна `LD_PRELOAD` змушує завантажувач підвантажити бібліотеку першою:
```bash
LD_PRELOAD=$PWD/internal/build/libinternal.so ./target-game/build/target_game
```
::
::tabs-item{label="macOS"}
Аналог — `DYLD_INSERT_LIBRARIES`:
```bash
DYLD_INSERT_LIBRARIES=$PWD/internal/build/libinternal.dylib ./target-game/build/target_game
```
Працює для власних збірок без hardened runtime. Системні програми та підписані застосунки зі SIP/hardened runtime ігнорують змінну.
::
::tabs-item{label="Windows"}
Запущеному процесу бібліотеку підвантажує інжектор: він виділяє пам'ять у грі, записує шлях до DLL і створює віддалений потік, що викликає `LoadLibraryA`.
```cpp
HANDLE h = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
void* remote = VirtualAllocEx(h, nullptr, len, MEM_COMMIT, PAGE_READWRITE);
WriteProcessMemory(h, remote, dllPath, len, nullptr);
CreateRemoteThread(h, nullptr, 0,
    (LPTHREAD_START_ROUTINE)GetProcAddress(GetModuleHandleA("kernel32.dll"), "LoadLibraryA"),
    remote, 0, nullptr);
```
Після завантаження система викликає `DllMain` з `DLL_PROCESS_ATTACH`.
::
::

Код цього модуля на Windows не перевірявся на цій машині: інжектор написаний за документацією WinAPI.

### Код модуля

Модуль викликається під час завантаження (конструктор у Linux/macOS, `DllMain` у Windows) і запускає окремий потік. Потім потік знаходить гравця й підтримує значення.

```cpp
__attribute__((constructor)) static void on_load() { start(); }   // Linux, macOS
// Windows: DllMain -> case DLL_PROCESS_ATTACH -> start();
```

Через `std::thread` робота виконується не в потоці завантажувача: `DllMain` на Windows не повинен чекати. Для зв'язку з пам'яттю гри використано той самий клас `Process`, але для власного PID, тож код однаковий для всіх ОС.

#### Пошук гравця за сигнатурою

Ланцюжок вказівників (розділ «Ланцюжки вказівників») потребує відомої адреси `Game*`. Зсередини процесу простіше знайти структуру за її вмістом: ім'я `Hero`, потім `health == 100` на зміщенні 16 та `armor == 50` на зміщенні 20.

```cpp
for (size_t i = 0; i + 36 <= r.size; i += 16) {
    if (std::memcmp(&buf[i], "Hero\0", 5) != 0) continue;
    int32_t hp, armor;
    std::memcpy(&hp, &buf[i + 16], 4);
    std::memcpy(&armor, &buf[i + 20], 4);
    if (hp == 100 && armor == 50) return r.start + i;
}
```

Крок 16 використано, бо `new` вирівнює об'єкти за 16 байтів. Сигнатура має бути унікальною; одного імені мало, тому додано перевірку значень.

::warning
Internal-модуль виконується з правами гри. Помилка в ньому, наприклад невірний вказівник, завершує гру. У зовнішньому тренері така помилка завершує лише тренер.

Інжектувати можна лише у власні процеси та в ігри, які ви можете запускати локально й офлайн. Інжекція в онлайн-ігри з антічітом розпізнається і блокується.

::::accordion

:::accordion-item{label="❓ Чому не можна просто зробити `static_cast<Player*>` на знайдену адресу?" icon="i-lucide-help-circle"}

Можна, і це типовий internal-підхід: описати `struct Player` з правильними зміщеннями й працювати з нею напряму. У нашому коді використано `Process` для єдиного коду на трьох ОС. Для реальних проєктів `Player* p = reinterpret_cast<Player*>(addr)` — стандартний підхід.

:::

:::accordion-item{label="📋 Завдання: безсмертя без циклу" icon="i-lucide-clipboard-list"}

Змініть internal-модуль так, щоб він не записував 999 кожні 50 мс, а лише відновлював `health`, коли значення стало менше 100.

:::

:::accordion-item{label="✅ Розв'язок" icon="i-lucide-check-circle"}

```cpp
int32_t hp = 0;
self.read_value(player + 16, hp);
if (hp < 100) self.write_value<int32_t>(player + 16, 100);
```
