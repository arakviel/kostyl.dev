# Request і Response: заголовки, статус-коди й типи відповідей

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Читати з `crow::request` метод, URL, заголовки, тіло й адресу клієнта.
- Формувати `crow::response` із потрібним статус-кодом і заголовками.
- Повертати текст, HTML, JSON, XML, файл для завантаження й перенаправлення.
- Обирати статус-код за значенням і знати, які коди Crow не підтримує.
- Будувати єдиний формат помилок і власну відповідь для неіснуючих маршрутів.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **`crow::request`:** об'єкт із усім, що надіслав клієнт.
- **`crow::response`:** об'єкт із кодом, заголовками й тілом відповіді.
- **`Content-Type`:** заголовок, який описує формат тіла.
- **Перенаправлення (*redirect*):** відповідь 3xx із заголовком `Location`.
- **Catch-all маршрут:** обробник для всіх шляхів, які не збіглися з жодним маршрутом.

## Що містить запит

Обробник, який приймає `const crow::request&`, має доступ до всього, що надіслав клієнт.

```cpp
CROW_ROUTE(app, "/inspect").methods(crow::HTTPMethod::GET, crow::HTTPMethod::POST)(
    [](const crow::request& req) {
        std::ostringstream out;
        out << "method: " << crow::method_name(req.method) << "\n"
            << "url: " << req.url << "\n"
            << "raw_url: " << req.raw_url << "\n"
            << "remote_ip: " << req.remote_ip_address << "\n"
            << "User-Agent: " << req.get_header_value("User-Agent") << "\n"
            << "Content-Length: " << req.body.size() << "\n"
            << "body: " << req.body << "\n";
        return crow::response(200, out.str());
    });
```

За замовчуванням `CROW_ROUTE` приймає лише `GET`. Виклик `.methods(...)` перераховує дозволені методи. Запит іншим методом отримує 405 Method Not Allowed від самого Crow.

| Поле або метод | Значення |
| -------------- | -------- |
| `req.method` | метод (`crow::HTTPMethod::GET`, `POST`, …) |
| `req.url` | шлях без query-рядка |
| `req.raw_url` | шлях разом із query-рядком |
| `req.url_params` | розібрані query-параметри |
| `req.get_header_value("Ім'я")` | значення заголовка або порожній рядок |
| `req.body` | тіло запиту як рядок |
| `req.remote_ip_address` | IP-адреса клієнта |

::terminal-preview{title="curl -X POST -d hi localhost:8084/inspect"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s -X POST -d 'hi' localhost:8084/inspect</strong></div>
<div class="line">method: POST</div>
<div class="line">url: /inspect</div>
<div class="line">raw_url: /inspect</div>
<div class="line">remote_ip: 127.0.0.1</div>
<div class="line">User-Agent: curl/8.7.1</div>
<div class="line">Content-Length: 2</div>
<div class="line">body: hi</div>
::

Метод `get_header_value` не розрізняє регістр імені заголовка: `user-agent` і `User-Agent` дають те саме значення, як і вимагає специфікація HTTP.

## Формування відповіді

Конструктор `crow::response(код, тіло)` задає статус і тіло. Інші властивості встановлюються методами.

| Метод | Дія |
| ----- | --- |
| `res.code = 404` | змінити статус-код |
| `res.set_header(ім'я, значення)` | встановити заголовок (замінює попередній) |
| `res.add_header(ім'я, значення)` | додати заголовок ще раз (для повторюваних, як `Set-Cookie`) |
| `res.write(текст)` | дописати до тіла |
| `res.end()` | завершити відповідь |
| `res.redirect(url)` | відповідь 307 із `Location` |
| `res.redirect_perm(url)` | відповідь 308 із `Location` |

Пара `write`/`end` потрібна, коли обробник приймає `crow::response&` другим аргументом і заповнює його замість повернення значення. Обидва стили рівнозначні: повернення значення зручне для простих обробників, а заповнення відповіді зсередини потрібне для catch-all і middleware.

::warning
Після `res.end()` відповідь вважається відправленою. Якщо в обробнику з `crow::response&` забути викликати `end()`, клієнт чекатиме відповідь до тайм-ауту.
::

## Статус-коди

Код відповіді — це контракт між сервером і клієнтом: програма-клієнт вирішує, що робити далі, саме за ним, а не за текстом тіла.

![Сімейства статус-кодів: 1xx, 2xx, 3xx, 4xx, 5xx](/images/cpp/crow-web/request-response/01-status-families.png){.diagram-img}

- **2xx.** Запит виконано. `201 Created` повертають після створення ресурсу, `204 No Content` після видалення чи оновлення без тіла відповіді.
- **3xx.** Клієнту треба звернутися за іншою адресою. `301` — назавжди, `302` — тимчасово, `304` — вміст не змінювався, використовуйте копію з кешу.
- **4xx.** Помилка в запиті клієнта: `400` некоректні дані, `401` треба увійти, `403` прав немає, `404` ресурсу немає, `409` конфлікт зі станом ресурсу, `429` забагато запитів.
- **5xx.** Помилка сервера: `500` необроблена помилка, `503` сервіс тимчасово недоступний.

Правило вибору між 4xx і 5xx: якщо клієнт може виправити запит і повторити, це 4xx; якщо проблема в сервері, 5xx.

### Обмеження: Crow знає не всі коди

Crow перетворює числовий код на текстовий опис за власною таблицею. Для коду, якого в таблиці немає, відповідь має статус `500 Internal Server Error`, хоч код у `crow::response` був інший. Перевірка:

::terminal-preview{title="Демо 04: /status/<код>"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8084/status/201 | head -1</strong></div>
<div class="line">HTTP/1.1 201 Created</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8084/status/204 | head -1</strong></div>
<div class="line">HTTP/1.1 204 No Content</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8084/status/418 | head -1</strong></div>
<div class="line">HTTP/1.1 400 Bad Request</div>
::

Маршрут `/status/<int>` у демо навмисно відхиляє коди поза таблицею. Без цієї перевірки код 418 (чи 422) дав би `500` з тілом, яке ми задали. До підтримуваних належать: 100, 101, 200–206, 300–304, 307, 308, 400, 401, 403, 404, 405, 406, 407, 409, 410, 413, 415, 416, 417, 428, 429, 451, 500–504, 506.

::caution
У довідниках REST для помилок валідації нерідко радять `422 Unprocessable Entity`. У Crow цього коду немає, тому для помилок валідації в цій серії використовується `400 Bad Request` із детальним тілом відповіді.
::

## Типи відповідей

Тип тіла повідомляє заголовок `Content-Type`. Без нього браузер здогадується сам, і HTML може відобразитися як звичайний текст.

```cpp
CROW_ROUTE(app, "/html")([] {
    crow::response res(200, "<html><body><h1>HTML</h1></body></html>");
    res.set_header("Content-Type", "text/html; charset=utf-8");
    return res;
});

CROW_ROUTE(app, "/xml")([] {
    crow::response res(200, "<user><id>1</id><name>Іван</name></user>");
    res.set_header("Content-Type", "application/xml; charset=utf-8");
    return res;
});
```

Параметр `charset=utf-8` важливий для кирилиці: без нього браузер може обрати іншу кодову таблицю, і замість літер з'являться «кракозябри».

JSON-відповідь будується з `crow::json::wvalue`. Достатньо передати його конструктору `crow::response`, і заголовок `Content-Type: application/json` буде встановлено автоматично.

```cpp
CROW_ROUTE(app, "/json")([] {
    crow::json::wvalue body;
    body["id"] = 1;
    body["name"] = "Іван";
    body["tags"] = std::vector<std::string>{"cpp", "web"};
    return crow::response(200, body);
});
```

<div class="line">Content-Type: application/json</div>
<div class="line">Content-Length: 47</div>
<div class="line">Server: Crow/master</div>
<div class="line">Connection: Keep-Alive</div>
<div class="line"></div>

::

### Завантаження файлу

Заголовок `Content-Disposition: attachment` наказує браузеру зберегти вміст як файл, а не показати. У ньому вказується ім'я за замовчуванням.

```cpp
CROW_ROUTE(app, "/download")([] {
    crow::response res(200, "id,name\n1,Іван\n2,Марія\n");
    res.set_header("Content-Type", "text/csv; charset=utf-8");
    res.set_header("Content-Disposition", "attachment; filename=\"users.csv\"");
    return res;
});
```

### Перенаправлення

Відповідь 302 із заголовком `Location` змушує клієнта повторити запит за новою адресою.

```cpp
CROW_ROUTE(app, "/old")([] {
    crow::response res(302);
    res.set_header("Location", "/html");
    return res;
});
```

Те саме скорочено: `res.redirect("/html")`. Але скорочення повертає не 302, а **307 Temporary Redirect**, а `res.redirect_perm(...)` — **308 Permanent Redirect**. Різниця з 302 і 301 суттєва: 307 і 308 зобов'язують клієнта повторити запит тим самим методом і з тим самим тілом, а 302 і 301 браузери часто перетворюють на `GET`. Для перенаправлення після `POST` на сторінку результату потрібен код 303 або 302, тому його задають вручну, як у прикладі вище.

::terminal-preview{title="curl -i localhost:8084/old"}

<div class="line">HTTP/1.1 302 Found</div>
<div class="line">Location: /html</div>
<div class="line">Content-Length: 0</div>
<div class="line">Server: Crow/master</div>
<div class="line">Connection: Keep-Alive</div>
::

`curl` сам за `Location` не переходить; для цього є прапорець `-L`. Браузер переходить автоматично.

## Єдиний формат помилок

Якщо кожен маршрут повертає помилку по-своєму, клієнту доводиться розбирати кілька форматів. Тому обирають один: поле `status`, повідомлення та код.

```cpp
CROW_ROUTE(app, "/api/users/<int>")([](int id) {
    if (id != 1) {
        crow::json::wvalue err;
        err["status"] = "error";
        err["message"] = "Користувача не знайдено";
        err["code"] = 404;
        return crow::response(404, err);
    }
    crow::json::wvalue ok;
    ok["status"] = "success";
    ok["data"]["id"] = 1;
    ok["data"]["name"] = "Іван";
    return crow::response(200, ok);
});
```

::terminal-preview{title="Успіх і помилка в одному форматі"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s localhost:8084/api/users/1</strong></div>
<div class="line">{"data":{"name":"Іван","id":1},"status":"success"}</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s localhost:8084/api/users/7</strong></div>
<div class="line">{"code":404,"message":"Користувача не знайдено","status":"error"}</div>
::

Клієнтський код перевіряє HTTP-статус, а за поясненням звертається до поля `message`. Дублювання коду в тілі зручне для логування, але джерелом істини залишається статус відповіді.

Щоб не повторювати цей код у кожному обробнику, формування помилки виносять у функцію.

```cpp
crow::response make_error(int code, const std::string& message) {
    crow::json::wvalue err;
    err["status"] = "error";
    err["message"] = message;
    err["code"] = code;
    return crow::response(code, err);
}
```

## Власна відповідь для неіснуючих маршрутів

Якщо шлях не збігся з жодним маршрутом, Crow повертає стандартне `404 Not Found`. Обробник `CROW_CATCHALL_ROUTE` замінює його власною сторінкою чи JSON.

```cpp
CROW_CATCHALL_ROUTE(app)([](const crow::request& req, crow::response& res) {
    res.code = 404;
    res.set_header("Content-Type", "text/html; charset=utf-8");
    res.write("<h1>404</h1><p>Немає маршруту " + req.url + "</p>");
    res.end();
});
```

Тут використано стиль із `crow::response&`: обробник заповнює відповідь і викликає `end()`.

::warning
Текст `req.url` потрапляє в HTML без екранування. Якщо клієнт надішле шлях зі спецсимволами, на сторінці з'явиться його розмітка (XSS). У справжніх застосунках значення з запиту перед вставкою в HTML екранують або використовують шаблонізатор, який робить це автоматично (лекція 11).
::

## Запитання

::::accordion

:::accordion-item{label="❓ Чи можна повертати 200 з повідомленням про помилку в тілі?" icon="i-lucide-help-circle"}

Технічно можна, але клієнтські бібліотеки, кеші й засоби моніторингу керуються статус-кодом. Відповідь 200 із текстом «помилка» вони вважають успіхом. Помилку завжди позначають кодом 4xx або 5xx.

:::

:::accordion-item{label="❓ Чому для POST після створення рекомендують 201 і Location?" icon="i-lucide-help-circle"}

Код 201 показує, що ресурс створено, а заголовок `Location: /users/123` повідомляє його адресу. Клієнту не потрібно вгадувати, куди звертатися далі. Докладно це розглядається в лекції про CRUD.

:::

:::accordion-item{label="❓ Що буде, якщо не вказати Content-Type?" icon="i-lucide-help-circle"}

Для рядка, повернутого з обробника, заголовок `Content-Type` у відповіді відсутній (це видно з виводу `curl -i` у попередній лекції), і тип визначає браузер самостійно. Для передбачуваного результату тип завжди задають явно.

:::

::::accordion

:::accordion-item{label="📋 Варіант 1 (легкий): калькулятор API" icon="i-lucide-clipboard-list"}

:::accordion-item{label="📋 Варіант 2 (середній): перелік товарів" icon="i-lucide-clipboard-list"}

:::accordion-item{label="📋 Варіант 3 (середній): скорочувач посилань" icon="i-lucide-clipboard-list"}

:::

## Підсумок

- `crow::request` містить метод, URL, заголовки, тіло й адресу клієнта. `crow::response` задає код, заголовки й тіло.
- Статус-код — основний сигнал результату. Crow підтримує не всі коди: невідомий код стає 500, а 422 у таблиці немає, тому валідація повертає 400.
- Формат тіла завжди позначають `Content-Type`, для кирилиці додають `charset=utf-8`.
- Єдиний формат помилок і власний catch-all роблять API передбачуваним для клієнтів.
