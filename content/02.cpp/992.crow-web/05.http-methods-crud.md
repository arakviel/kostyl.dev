# HTTP-методи і CRUD: TODO API на Crow

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Пояснити семантику методів `GET`, `POST`, `PUT`, `PATCH`, `DELETE` і відрізняти безпечні та ідемпотентні.
- Реалізувати повний CRUD для ресурсу на кількох методах одного шляху.
- Читати тіло запиту й повертати правильні коди: 201 із `Location`, 204, 400, 404.
- Розрізняти `PUT` (повна заміна) і `PATCH` (часткова зміна).
- Захищати спільне сховище м'ютексом, бо Crow обробляє запити в різних потоках.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **CRUD:** Create, Read, Update, Delete — чотири базові операції над даними.
- **Ідемпотентність (*idempotence*):** повторення того самого запиту дає той самий стан сервера.
- **Безпечний метод (*safe*):** не змінює дані на сервері.
- **Колекція та елемент:** `/todos` і `/todos/1`.
- **Умови гонки (*race condition*):** помилка, коли кілька потоків одночасно змінюють спільні дані.

::

::

У лекції 04 кожен маршрут відповідав на `GET`. Справжній API ще й змінює дані, і для цього HTTP має окремі методи. Лекція будує на них застосунок «список справ» (TODO) у пам'яті сервера.

## Методи й їхні властивості

Метод повідомляє, що клієнт хоче зробити з ресурсом. Сервер може покладатися на цю семантику, а проміжні системи (кеші, проксі, браузери) діють відповідно до неї: `GET` кешують і повторюють автоматично, `POST` ні.

| Метод | Дія | Безпечний | Ідемпотентний | Тіло запиту |
| ----- | --- | --------- | ------------- | ----------- |
| `GET` | прочитати | так | так | ні |
| `POST` | створити або виконати дію | ні | ні | так |
| `PUT` | замінити повністю | ні | так | так |
| `PATCH` | змінити частину | ні | залежить від реалізації | так |
| `DELETE` | видалити | ні | так | зазвичай ні |

Ідемпотентність пояснюється на прикладі. `DELETE /todos/1` двічі поспіль залишає сервер в одному стані: задачі 1 немає. Перша відповідь 204, друга 404, але стан однаковий. `POST /todos` двічі створює дві різні задачі, тому метод не ідемпотентний. Для клієнта це практично важливо: якщо відповідь на `PUT` загубилась у мережі, запит можна безпечно повторити, а повтор `POST` може створити дублікат.

## Модель і сховище

Ресурс — задача зі структурою:

```cpp
struct Todo {
    int id = 0;
    std::string title;
    std::string description;
    bool completed = false;
};
```

Сховище інкапсульовано в клас `TodoStore`: він зберігає задачі в `std::map` і видає їм наростаючі ідентифікатори. Усі методи захоплюють `std::mutex`.

```cpp
class TodoStore {
public:
    Todo create(std::string title, std::string description) {
        std::lock_guard<std::mutex> lock(mutex_);
        Todo t{next_id_++, std::move(title), std::move(description), false};
        items_[t.id] = t;
        return t;
    }
    // find, all, replace, remove — за тим самим принципом
private:
    std::mutex mutex_;
    std::map<int, Todo> items_;
    int next_id_ = 1;
};
```

Запит, у якому кілька клієнтів одночасно викликають `create`, без м'ютекса дав би дві задачі з однаковим `id` або пошкодив би `std::map`. Тому `multithreaded()` і спільне змінне сховище завжди йдуть разом із блокуванням.

::note
Сховище в пам'яті втрачає дані після перезапуску сервера. У лекціях 13–15 його замінюють файлом і SQLite, не змінюючи код обробників: це ціль шаблону Repository.
::

## Create: POST

`POST /todos` створює задачу із тіла запиту. Обробник читає JSON, перевіряє обов'язкове поле й повертає **201 Created** із заголовком `Location`, де вказана адреса нового ресурсу.

```cpp
CROW_ROUTE(app, "/todos").methods(crow::HTTPMethod::POST)([&store](const crow::request& req) {
    auto body = crow::json::load(req.body);
    if (!body) return error(400, "Тіло запиту не є коректним JSON");
    if (!body.has("title") || body["title"].t() != crow::json::type::String)
        return error(400, "Поле title (рядок) обов'язкове");

    std::string description = body.has("description") ? std::string(body["description"].s()) : "";
    Todo t = store.create(body["title"].s(), description);

    crow::response res(201, to_json(t));
    res.set_header("Location", "/todos/" + std::to_string(t.id));
    return res;
});
```

Розбір:

- `crow::json::load` повертає порожнє значення для некоректного тексту, а його перевірка `!body` відсікає зламаний JSON.
- Перевірка типу `title` потрібна, бо звернення `.s()` до числа викликало б виняток (докладно в лекції 07).
- Необов'язкове поле `description` має значення за замовчуванням: порожній рядок.
- Клієнт отримує створену задачу разом із `id`, який призначив сервер. Генерувати `id` на клієнті не можна: два клієнти створили б колізію.

## Read: GET

Для колекції й окремого елемента використовують два маршрути з одним методом. Колекція підтримує фільтр за query-параметром.

```cpp
CROW_ROUTE(app, "/todos").methods(crow::HTTPMethod::GET)([&store](const crow::request& req) {
    const char* filter = req.url_params.get("completed");
    crow::json::wvalue::list items;
    for (const auto& t : store.all()) {
        if (filter && (std::string(filter) == "true") != t.completed) continue;
        items.push_back(to_json(t));
    }
    crow::json::wvalue j;
    j["count"] = items.size();
    j["data"] = std::move(items);
    return crow::response(200, j);
});

CROW_ROUTE(app, "/todos/<int>").methods(crow::HTTPMethod::GET)([&store](int id) {
    Todo t;
    if (!store.find(id, t)) return error(404, "Задачу не знайдено");
    return crow::response(200, to_json(t));
});
```

Один шлях можна зареєструвати окремо для кожного методу: Crow підбирає обробник за парою «метод + шлях». Запит методом, для якого обробника немає, отримує 405:

::terminal-preview{title="Метод без обробника"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -i -X PUT localhost:8085/todos</strong></div>
<div class="line">HTTP/1.1 405 Method Not Allowed</div>
<div class="line">Content-Length: 24</div>
<div class="line"></div>
<div class="line">405 Method Not Allowed</div>
::

Порожня колекція — це не помилка: `GET /todos` повертає 200 і `"count": 0`. Код 404 потрібен для відсутнього елемента, а не для порожнього списку.

## Update: PUT і PATCH

Обидва методи змінюють існуючу задачу, але по-різному.

- **PUT** замінює ресурс повністю. Клієнт надсилає усі поля, а поле, яке він не вказав, не залишається зі старим значенням: запит вважається неповним.
- **PATCH** змінює лише передані поля. Решта лишається незмінною.

![PUT вимагає всі поля, PATCH змінює лише передані](/images/cpp/crow-web/http-methods-crud/02-put-vs-patch.png){.diagram-img}

```cpp
// PUT: усі поля обов'язкові
CROW_ROUTE(app, "/todos/<int>").methods(crow::HTTPMethod::PUT)([&store](const crow::request& req, int id) {
    auto body = crow::json::load(req.body);
    if (!body) return error(400, "Тіло запиту не є коректним JSON");
    if (!body.has("title") || !body.has("description") || !body.has("completed"))
        return error(400, "PUT вимагає всі поля: title, description, completed");

    Todo t{id, body["title"].s(), body["description"].s(), body["completed"].b()};
    if (!store.replace(t)) return error(404, "Задачу не знайдено");
    return crow::response(200, to_json(t));
});

// PATCH: змінюються лише ті поля, що передані
CROW_ROUTE(app, "/todos/<int>").methods(crow::HTTPMethod::PATCH)([&store](const crow::request& req, int id) {
    auto body = crow::json::load(req.body);
    if (!body) return error(400, "Тіло запиту не є коректним JSON");

    Todo t;
    if (!store.find(id, t)) return error(404, "Задачу не знайдено");
    if (body.has("title")) t.title = body["title"].s();
    if (body.has("description")) t.description = body["description"].s();
    if (body.has("completed")) t.completed = body["completed"].b();
    store.replace(t);
    return crow::response(200, to_json(t));
});
```

<div class="line">{"error":"PUT вимагає всі поля: title, description, completed"}</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s -X PUT -H 'Content-Type: application/json' -d '{"title":"Нова назва","description":"d","completed":false}' localhost:8085/todos/1</strong></div>
<div class="line">{"completed":false,"description":"d","title":"Нова назва","id":1}</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s -X PATCH -H 'Content-Type: application/json' -d '{"completed":true}' localhost:8085/todos/1</strong></div>
<div class="line">{"completed":true,"description":"d","title":"Нова назва","id":1}</div>
::

Практичне правило вибору: якщо змінюється одне поле (позначити виконаним, змінити статус), потрібен `PATCH`. Якщо клієнт підміняє весь об'єкт, наприклад форма редагування зберігає всі поля, підходить `PUT`.

::warning
У поточній реалізації `PATCH` між `find` і `replace` сховище розблоковується. Якщо два клієнти змінюють одну задачу одночасно, одна зміна може затерти іншу (проблема «втраченого оновлення»). Для навчального демо це прийнятно. У базі даних проблему розв'язують транзакціями або полем версії.
::

## Delete: DELETE

Успішне видалення повертає **204 No Content**: тіла немає, бо повертати нічого. Видалення неіснуючого ресурсу дає 404.

```cpp
CROW_ROUTE(app, "/todos/<int>").methods(crow::HTTPMethod::DELETE)([&store](int id) {
    if (!store.remove(id)) return error(404, "Задачу не знайдено");
    return crow::response(204);
});
```

::terminal-preview{title="Повторне видалення"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -i -X DELETE localhost:8085/todos/1</strong></div>
<div class="line">HTTP/1.1 204 No Content</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -i -X DELETE localhost:8085/todos/1</strong></div>
<div class="line">HTTP/1.1 404 Not Found</div>
<div class="line">{"error":"Задачу не знайдено"}</div>
::

Ідемпотентність `DELETE` стосується стану сервера, а не коду відповіді: після першого й другого запитів задачі немає в обох випадках. Деякі API віддають 204 і на повторне видалення. Обидві поведінки допустимі; головне, щоб вони були описані.

### Фізичне і м'яке видалення

Фізичне видалення стирає запис. **М'яке видалення** (*soft delete*) лише ставить позначку `deleted = true` або час видалення, а запис лишається в сховищі. Це дає змогу відновити дані й зберегти історію, але вимагає фільтрувати позначені записи в кожному читанні.

## Запитання

::::accordion

:::accordion-item{label="❓ Чому не можна видаляти через GET /todos/1/delete?" icon="i-lucide-help-circle"}

`GET` вважається безпечним, тому браузери, пошукові роботи й попередній перегляд посилань викликають його без запиту користувача. Видалення через `GET` стирає дані як побічний ефект навігації.

:::

:::accordion-item{label="❓ Що повертати після PUT і PATCH: оновлений ресурс чи 204?" icon="i-lucide-help-circle"}

Допустимі обидва варіанти. Повернення оновленого ресурсу (200) економить клієнту окремий `GET` і показує значення, обчислені сервером, наприклад час останньої зміни. Код 204 економить трафік.

:::

:::accordion-item{label="❓ Чому використано 201 і Location, а не 200?" icon="i-lucide-help-circle"}

Код 201 повідомляє, що ресурс створено, а `Location` указує його адресу. Клієнт може одразу перейти за нею, не складаючи URL із `id` самостійно.

:::

:::accordion-item{label="❓ Що буде з id після видалення задачі?" icon="i-lucide-help-circle"}

Лічильник `next_id_` лише зростає, тому `id` видаленої задачі не використовується повторно. Повторне використання зробило б старі посилання на видалений ресурс такими, що ведуть до чужих даних.

:::

## Підсумок

- Метод описує намір: `GET` читає, `POST` створює, `PUT` замінює, `PATCH` змінює частину, `DELETE` видаляє. Властивості безпечності й ідемпотентності визначають, що можна повторювати.
- Колекція (`/todos`) і елемент (`/todos/1`) обслуговуються різними маршрутами. Один шлях можна зареєструвати для кількох методів.
- Правильні коди: 201 із `Location` після створення, 204 після видалення, 404 для відсутнього елемента, 405 для невідомого методу.
- Спільне сховище в багатопоточному сервері захищають м'ютексом.
