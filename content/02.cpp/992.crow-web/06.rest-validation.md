## Принципи REST

**REST** (*Representational State Transfer*) — набір угод, за якими HTTP-API стає передбачуваним. Основні з них:

- **Ресурси.** Кожна сутність має адресу: `/users/2`. URL називає річ, а не дію.
- **Стандартні методи.** Дію задає метод: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.
- **Представлення.** Клієнт отримує не сам об'єкт, а його опис у форматі (JSON), і вказує формат у заголовках `Content-Type` та `Accept`.
- **Відсутність стану між запитами.** Кожен запит містить усе потрібне для його обробки.
- **Коди відповідей.** Результат повідомляється статусом, а не лише текстом.

![Дія в URL проти ресурсу та методу](/images/cpp/crow-web/rest-validation/01-rest-urls.png){.diagram-img}

### Правила проєктування URL

| Правило | Приклад |
| ------- | ------- |
| Іменник у множині | `/users`, не `/user` і не `/getUsers` |
| Вкладеність для підпорядкованих ресурсів | `/users/2/orders` |
| Малі літери, дефіси | `/order-items`, не `/orderItems` |
| Фільтри, сортування й пагінація в query | `/users?role=admin&sort=-age&page=2` |
| Версія в префіксі | `/api/v1/users` |
| Глибина вкладеності не більше двох рівнів | `/users/2/orders`, але не `/users/2/orders/5/items/7/tags` |

Не кожна дія лягає на CRUD. Для дій на кшталт «підтвердити замовлення» допустимий підресурс із `POST`: `POST /orders/5/confirm`. Головне, щоб такі виняткові маршрути не стали основним стилем API.

## Рівні валідації

Перевірка запиту складається з кількох послідовних кроків, і кожен має свій код відповіді. Запит зупиняється на першому кроці, який не пройдено.

![Послідовність перевірок і коди відповіді](/images/cpp/crow-web/rest-validation/02-validation-layers.png){.diagram-img}

1. **Формат (415).** Заголовок `Content-Type` не `application/json`. Сервер не вміє читати таке тіло.
2. **Синтаксис (400).** Тіло не є коректним JSON.
3. **Дані (400).** JSON правильний, але в ньому немає обов'язкових полів, типи не ті чи значення поза допустимим діапазоном.
4. **Бізнес-правила (409).** Дані правильні самі по собі, але суперечать стану системи: email уже зареєстровано.

Код 400 стосується неправильного запиту, а 409 — правильного запиту, який не можна виконати в поточному стані. Різниця важлива для клієнта: за 400 він виправляє дані, за 409 змінює задум (обирає інший email чи входить у наявний акаунт).

::note
Стандарти радять код 422 Unprocessable Entity для рівня «Дані». У Crow цього коду немає: відповідь із ним перетворюється на 500 (див. лекцію 04). Тому тут використано 400 з переліком помилок у тілі.
::

## Перелік усіх помилок

Якщо валідатор зупиняється на першій помилці, користувач виправляє форму по одному полю й надсилає її знову й знову. Значно зручніше отримати всі помилки одразу. Функція `validate_user` збирає їх у масив.

```cpp
static std::vector<std::string> validate_user(const crow::json::rvalue& body) {
    std::vector<std::string> errors;

    if (!body.has("name") || body["name"].t() != crow::json::type::String) {
        errors.push_back("name: обов'язкове рядкове поле");
    } else {
        size_t len = utf8_length(body["name"].s());
        if (len < 2 || len > 50) errors.push_back("name: довжина від 2 до 50 символів");
    }

    if (!body.has("email") || body["email"].t() != crow::json::type::String) {
        errors.push_back("email: обов'язкове рядкове поле");
    } else {
        std::string email = body["email"].s();
        auto at = email.find('@');
        bool ok = at != std::string::npos && at > 0 && email.find('.', at) != std::string::npos &&
                  email.find('@', at + 1) == std::string::npos;
        if (!ok) errors.push_back("email: некоректний формат");
    }

    if (!body.has("age") || body["age"].t() != crow::json::type::Number) {
        errors.push_back("age: обов'язкове числове поле");
    } else {
        int age = static_cast<int>(body["age"].i());
        if (age < 0 || age > 150) errors.push_back("age: значення від 0 до 150");
    }
    return errors;
}
```

Кожне поле перевіряється за однією схемою: наявність і тип, потім значення. Саме така послідовність уникає винятку: звернення `.s()` до значення іншого типу кидає помилку (лекція 07).

Для email перевірено лише мінімальну структуру: одна `@`, перед нею хоч один символ, після неї крапка. Повна перевірка за стандартом складніша й не потрібна: справжня перевірка адреси — це лист із посиланням на підтвердження.

::terminal-preview{title="Усі помилки в одній відповіді"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s -X POST -H 'Content-Type: application/json' -d '{"name":"І","email":"bad","age":200}' localhost:8086/users</strong></div>
<div class="line">{"details":["name: довжина від 2 до 50 символів","email: некоректний формат","age: значення від 0 до 150"],"error":"Помилка валідації"}</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s -X POST -H 'Content-Type: application/json' -d '{}' localhost:8086/users</strong></div>

### Довжина рядка: байти й символи

Метод `std::string::size()` повертає кількість байтів. Українська літера в UTF-8 займає два байти, тому ім'я `І` (одна літера) мало б довжину 2 і пройшло б перевірку «мінімум 2». Перша версія демо мала саме цю помилку. Функція `utf8_length` рахує лише початкові байти символів: байти-продовження мають вигляд `10xxxxxx`.

```cpp
static size_t utf8_length(const std::string& s) {
    size_t n = 0;
    for (unsigned char c : s)
        if ((c & 0xC0) != 0x80) ++n;
    return n;
}
```

Функція рахує кодові точки Unicode. Складені символи (літера з окремим знаком наголосу) формально займають кілька точок, але для лімітів довжини в застосунках цього наближення достатньо.

## Повний обробник створення

Рівні перевірок розташовано в тому порядку, у якому запит їх проходить.

```cpp
CROW_ROUTE(app, "/users").methods(crow::HTTPMethod::POST)([](const crow::request& req) {
    const std::string ct = req.get_header_value("Content-Type");
    if (ct.find("application/json") == std::string::npos)
        return error(415, "Content-Type має бути application/json");

    auto body = crow::json::load(req.body);
    if (!body) return error(400, "Тіло запиту не є коректним JSON");

    auto errors = validate_user(body);
    if (!errors.empty()) return validation_error(errors);

    std::lock_guard<std::mutex> lock(g_mutex);
    std::string email = body["email"].s();
    for (const auto& [id, u] : g_users)
        if (u.email == email) return error(409, "Користувач із таким email уже існує");

    User u{g_next_id++, body["name"].s(), email, static_cast<int>(body["age"].i())};
    g_users[u.id] = u;
    crow::response res(201, to_json(u));
    res.set_header("Location", "/users/" + std::to_string(u.id));
    return res;
});
```

Перевірка унікальності й додавання виконуються під одним блокуванням. Якби перевірка та запис були розділені, два запити з однаковим email одночасно пройшли б перевірку й створили дублікат.

::warning
Сервер, на якому перевірку формату зроблено лише у фронтенді, не захищений: запит можна надіслати `curl` в обхід форми. Валідація на сервері обов'язкова, а перевірка в браузері лише покращує зручність.

## Колекції: пагінація, сортування, фільтри

Повернення всіх записів за один запит не масштабується: тисяча користувачів завантажать мережу й пам'ять. Колекція повертається сторінками, а параметри керування лежать у query.

| Параметр | Значення | Приклад |
| -------- | -------- | ------- |
| `page` | номер сторінки, з 1 | `page=2` |
| `limit` | розмір сторінки, з верхнім обмеженням | `limit=10` |
| `sort` | поле; мінус перед іменем означає спадання | `sort=-age` |
| `min_age` та подібні | фільтри за полем | `min_age=30` |

```cpp
int page = 1, limit = 10;
if (const char* p = req.url_params.get("page")) page = std::atoi(p);
if (const char* l = req.url_params.get("limit")) limit = std::atoi(l);
if (page < 1 || limit < 1 || limit > 100)
    return error(400, "page >= 1, 1 <= limit <= 100");
```

Верхня межа `limit` обов'язкова: без неї клієнт запитує `limit=1000000` і змушує сервер скопіювати всю колекцію. Відповідь містить `total`, щоб клієнт знав кількість сторінок.

::terminal-preview{title="Сторінка з фільтром і сортуванням"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s "localhost:8086/users?page=1&limit=2&sort=-age"</strong></div>
<div class="line">{"data":[{"id":4,"name":"User4","email":"u4@x.com","age":40},{"age":30,"email":"u3@x.com","name":"User3","id":3}],"limit":2,"page":1,"total":4}</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -s "localhost:8086/users?min_age=30&page=2&limit=1"</strong></div>
<div class="line">{"data":[{"age":40,"email":"u4@x.com","name":"User4","id":4}],"limit":1,"page":2,"total":2}</div>
::

Фільтрація виконується до розбиття на сторінки: `total` рахується вже після фільтра. Порядок ключів усередині об'єктів різний, бо JSON не гарантує порядку.

## Запитання

::::accordion

:::accordion-item{label="❓ Чи достатньо перевірити дані лише у формі на сайті?" icon="i-lucide-help-circle"}

Ні. Клієнтом може бути `curl`, скрипт чи шкідлива програма. Перевірки на фронтенді лише спрощують роботу користувачам, а захищає систему тільки валідація на сервері.

:::

:::accordion-item{label="❓ Чому 409, а не 400 для зайнятого email?" icon="i-lucide-help-circle"}

Запит коректний за формою, але суперечить станові системи. Клієнт, який отримав 400, виправляє формат. Клієнт, який отримав 409, має змінити сам вибір (інший email) або спиратися на наявний ресурс.

:::

:::accordion-item{label="❓ Що відповісти на запит без Content-Type, але з JSON у тілі?" icon="i-lucide-help-circle"}

Сервер у демо повертає 415: клієнт має явно оголосити формат. Поблажливіші API читають тіло як JSON і без заголовка. Обидва підходи допустимі, головне — послідовність у всьому API.

:::

:::accordion-item{label="❓ Чи розкривати у повідомленні про помилку внутрішні деталі?" icon="i-lucide-help-circle"}

Для помилок клієнта (4xx) пояснення потрібні: вони допомагають виправити запит. Для помилок сервера (5xx) подробиці, як-от текст винятку, шляхи до файлів чи SQL, записують у журнал, а клієнту віддають загальне повідомлення.

:::

## Підсумок

- REST: URL називає ресурс у множині, дію задає метод, результат повідомляє код.
- Валідація запиту проходить рівнями: формат (415), синтаксис (400), дані (400), бізнес-правила (409).
- Усі помилки валідації збираються в одній відповіді. Рядки рахуються в символах, а не в байтах.
- Колекція віддається сторінками з обмеженим `limit` і повертає `total`.
