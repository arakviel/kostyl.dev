# nlohmann/json: DTO, автоматична серіалізація й помилки

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Автоматично перетворювати структури C++ у JSON і назад.
- Описати DTO окремо від моделі та писати власні `from_json`.
- Підставляти значення за замовчуванням і розрізняти обов'язкові та необов'язкові поля.
- Перехоплювати `parse_error`, `out_of_range`, `type_error` і перетворювати їх на відповіді 400.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **nlohmann/json:** найпоширеніша JSON-бібліотека C++ із STL-подібним інтерфейсом.
- **DTO (*Data Transfer Object*):** структура, що описує дані запиту чи відповіді, а не внутрішню модель.
- **`to_json` / `from_json`:** функції перетворення типу у JSON і назад.
- **Конверсія за ADL:** бібліотека знаходить ці функції у просторі імен типу.

::

::

Вбудований JSON Crow (лекція 07) потребує ручного коду для кожного поля. Коли в проєкті десятки структур, цей код множиться. Бібліотека nlohmann/json автоматизує перетворення, а Crow залишається відповідальним за HTTP.

## Підключення

Бібліотека додається до `vcpkg.json` і підключається в CMake. Вона header-only, тому окремого лінкування немає.

::code-group

```json [vcpkg.json]
{
  "dependencies": ["crow", "nlohmann-json"]
}
```

```cmake [CMakeLists.txt]
find_package(Crow CONFIG REQUIRED)
find_package(nlohmann_json CONFIG REQUIRED)

add_executable(json_dto src/main.cpp)
target_link_libraries(json_dto PRIVATE Crow::Crow nlohmann_json::nlohmann_json)
```

::

У коді:

```cpp
#include <nlohmann/json.hpp>
using json = nlohmann::json;
```

## Основи: json як контейнер

Об'єкт `json` поводиться як `std::map` чи `std::vector`: присвоєння ключа створює його, `push_back` додає до масиву, а ітерація працює циклом `for`.

```cpp
json j;
j["name"] = "Іван";
j["age"] = 25;
j["tags"] = {"cpp", "web"};
j["address"] = {{"city", "Київ"}, {"zip", "01001"}};

json parsed = json::parse(R"({"id": 7, "ok": true})");
int id = parsed["id"];          // неявне перетворення
bool ok = parsed.at("ok");      // at() перевіряє наявність ключа
std::string text = j.dump();    // компактний текст
std::string pretty = j.dump(2); // з відступами по 2 пробіли
```

Відмінність від Crow: ключі зберігаються в `std::map`, тому у виводі вони впорядковані за алфавітом, і відповідь однакова при кожному запуску. Це зручно для тестів і порівняння.

Оператор `[]` для відсутнього ключа в `const` об'єкті має невизначену поведінку, а в неконстантному створює `null`. Тому читання завжди робиться через `at()` (кидає виняток) або `value()` (повертає значення за замовчуванням).

## Структури й JSON: to_json і from_json

Бібліотека перетворює тип у JSON і назад через функції `to_json` та `from_json`. Для простих структур їх генерує макрос.

```cpp
struct Address {
    std::string city;
    std::string zip;
};
NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE(Address, city, zip)

struct User {
    int id = 0;
    std::string name;
    std::string email;
    int age = 0;
    std::vector<std::string> roles;
    Address address;
};
NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE(User, id, name, email, age, roles, address)
```

Макрос пишеться **після** оголошення структури, поза її тілом. Версія `NLOHMANN_DEFINE_TYPE_INTRUSIVE` призначена для використання всередині класу (вона генерує `friend`-функції); поставлена зовні, вона дає помилку компіляції `'friend' used outside of class`. Приватні поля потребують саме «внутрішньої» версії.

Тепер структура перетворюється неявно, а вкладені структури й `std::vector` обробляються автоматично:

```cpp
User u;
u.name = "Іван";
json j = u;                    // User → JSON
User back = j.get<User>();     // JSON → User
```

Для `std::optional`, `std::map`, `std::array` та інших типів STL перетворення вже вбудовані. Власні типи, які використовуються як поля, теж повинні мати `to_json`/`from_json`.

## DTO: окремий тип для запиту

Тіло запиту на створення користувача не збігається зі структурою `User`: в ньому немає `id` (його присвоює сервер), а роль необов'язкова. Тому для запиту оголошують окремий тип: **DTO**.

```cpp
struct CreateUserDto {
    std::string name;
    std::string email;
    int age = 0;
    std::string role = "user";
};

void from_json(const json& j, CreateUserDto& d) {
    j.at("name").get_to(d.name);       // at() кидає виняток, якщо ключа немає
    j.at("email").get_to(d.email);
    j.at("age").get_to(d.age);
    d.role = j.value("role", "user");  // value() підставляє значення за замовчуванням
}
```

Відокремлення DTO від моделі захищає від **масового присвоєння** (*mass assignment*): якщо б запит напряму перетворювався на `User`, клієнт міг би надіслати `"id": 1` чи `"roles": ["admin"]` і підмінити службові поля. DTO містить лише ті поля, які клієнту дозволено задавати.

Власна `from_json` дає контроль:

- `at(ключ)` робить поле **обов'язковим**: відсутність викликає виняток;
- `value(ключ, за_замовчуванням)` робить поле **необов'язковим**;
- тип перевіряється під час `get_to`: рядок замість числа викликає `type_error`.

::warning
Функцію `from_json` оголошують у тому ж просторі імен, що й тип (тут глобальний), інакше бібліотека її не знайде. Це правило пошуку за аргументами (ADL).
::

## Помилки й виняткові ситуації

Усі помилки nlohmann — винятки, що наслідують `json::exception`. Для обробників API важливі три.

| Виняток | Причина | Код |
| ------- | ------- | --- |
| `json::parse_error` | текст не є коректним JSON | 101 |
| `json::out_of_range` | `at()` не знайшов ключ | 403 |
| `json::type_error` | значення має інший тип | 302 |

Числа в кінці — внутрішні коди бібліотеки, які видно в повідомленні. Обробник перетворює кожен виняток на відповідь 400:

```cpp
CROW_ROUTE(app, "/users").methods(crow::HTTPMethod::POST)([&](const crow::request& req) {
    try {
        json j = json::parse(req.body);
        CreateUserDto dto = j.get<CreateUserDto>();

        if (dto.age < 0 || dto.age > 150) return error(400, "age: значення від 0 до 150");

        std::lock_guard<std::mutex> lock(mutex);
        User u;
        u.id = next_id++;
        u.name = dto.name;
        u.email = dto.email;
        u.age = dto.age;
        u.roles = {dto.role};
        users[u.id] = u;
        return json_response(201, u);
    } catch (const json::parse_error& e) {
        return error(400, std::string("Некоректний JSON: ") + e.what());
    } catch (const json::out_of_range& e) {
        return error(400, std::string("Відсутнє поле: ") + e.what());
    } catch (const json::type_error& e) {
        return error(400, std::string("Невірний тип поля: ") + e.what());
    }
});
```

![Шлях запиту: розбір, DTO, перевірка, відповідь, і винятки на кожному кроці](/images/cpp/crow-web/json-nlohmann-dto/02-dto-flow.png){.diagram-img}

Допоміжна функція `json_response` пов'язує дві бібліотеки: вона перетворює `json` на рядок і ставить заголовок.

```cpp
static crow::response json_response(int code, const json& j) {
    crow::response res(code, j.dump());
    res.set_header("Content-Type", "application/json");
    return res;
}
```

## Фільтрація й форматований вивід

Об'єкти `json` працюють зі стандартними алгоритмами. Фільтр за роллю використовує `std::find` на векторі ролей:

```cpp
json arr = json::array();
const char* role = req.url_params.get("role");
for (const auto& [id, u] : users) {
    if (role && std::find(u.roles.begin(), u.roles.end(), role) == u.roles.end()) continue;
    arr.push_back(u);
}
return json_response(200, json{{"count", arr.size()}, {"data", arr}});
```

Рядок `json{{"count", arr.size()}, {"data", arr}}` створює об'єкт із двох пар через список ініціалізації. Метод `dump(2)` повертає форматований текст:

## Що вибрати: crow::json чи nlohmann

| Критерій | `crow::json` | nlohmann/json |
| -------- | ------------ | ------------- |
| Залежності | вбудований у Crow | окрема бібліотека |
| Перетворення структур | вручну | автоматично |
| Порядок ключів у виводі | не гарантований | за алфавітом |
| Читання відсутнього ключа | виняток `runtime_error` | `at()` кидає, `value()` дає значення за замовчуванням |
| Типізовані винятки | немає | `parse_error`, `out_of_range`, `type_error` |
| Підходить для | дрібних API | проєктів із багатьма структурами |

У наступних лекціях серії JSON-перетворення виконує nlohmann: це дозволяє тримати шар даних незалежним від Crow.

## Запитання

::::accordion

:::accordion-item{label="❓ Чому не можна просто перетворювати тіло запиту на User?" icon="i-lucide-help-circle"}

Клієнт отримав би контроль над полями, які мають задавати лише сервер або адміністратор: `id`, ролі, баланс. Це вразливість масового присвоєння. DTO обмежує набір полів до дозволеного.

:::

:::accordion-item{label="❓ Що станеться, якщо в JSON є зайві поля?" icon="i-lucide-help-circle"}

Бібліотека їх ігнорує: `from_json` читає лише ті ключі, які в ній названі. Якщо потрібна сувора перевірка (відхиляти невідомі поля), перелічіть ключі об'єкта й порівняйте з дозволеним списком.

:::

:::accordion-item{label="❓ Чи можна використовувати nlohmann для читання, а Crow для відповіді?" icon="i-lucide-help-circle"}

Так, але змішування ускладнює код. Простіше вибрати одну бібліотеку на проєкт і написати допоміжні функції `json_response` та `error` для зв'язку з `crow::response`.

:::

:::accordion-item{label="❓ Чому ключі в відповіді вже відсортовані?" icon="i-lucide-help-circle"}

`nlohmann::json` за замовчуванням зберігає об'єкти в `std::map`, який упорядкований за ключем. Для збереження порядку вставки в бібліотеці є тип `nlohmann::ordered_json`.

:::

## Підсумок

- nlohmann/json перетворює структури у JSON і назад (`NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE` зовні структури, `INTRUSIVE` усередині) та підтримує STL-контейнери.
- DTO описує дані запиту окремо від моделі й захищає службові поля від масового присвоєння.
- `at()` робить поле обов'язковим, `value()` необов'язковим. Помилки приходять типізованими винятками, які обробник перетворює на 400.
- Тексти винятків бібліотеки не віддають клієнтам у виробничому коді.
