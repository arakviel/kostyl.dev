# Middleware: ланцюжок, порядок виконання й ранній вихід

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Пояснити, яку проблему розв'язує middleware, і де він розташований між сервером та обробником.
- Написати middleware зі структурою `context`, `before_handle` та `after_handle`.
- Передбачати порядок виконання кількох middleware в `crow::App<...>`.
- Перервати обробку запиту з middleware і повернути відповідь без виклику обробника.
- Уникати пастки: втрата заголовків, поставлених у `before_handle`.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Middleware (*мідлвар*):** компонент, який виконується до і після обробника маршруту для кожного запиту.
- **Ланцюжок (*chain*):** послідовність middleware в порядку реєстрації.
- **Контекст (*context*):** дані, які middleware зберігає для запиту.
- **Ранній вихід (*early exit*):** завершення відповіді в middleware до обробника.
- **Наскрізна задача (*cross-cutting concern*):** функціональність, потрібна багатьом маршрутам: журнал, автентифікація, CORS.

::

::

У лекціях 05–08 кожен обробник сам перевіряв дані й формував відповіді. Якщо ж потрібно логувати кожен запит, вимірювати час або перевіряти ключ доступу, цей код довелося б скопіювати у всі маршрути. Забути його в одному з них — це дірка в безпеці або прогалина в журналі.

## Ідея middleware

**Middleware** — код, який Crow викликає навколо обробника. Його пишуть один раз, реєструють у застосунку, і він застосовується до всіх запитів. Обробники при цьому залишаються короткими й описують лише бізнес-логіку.

![Запит проходить через before_handle кожного middleware, обробник, потім через after_handle у зворотному порядку](/images/cpp/crow-web/middleware-chain/01-chain-order.png){.diagram-img}

Кожен middleware має дві точки входу:

- `before_handle` викликається **до** обробника: тут перевіряють заголовки, готують контекст, можуть відхилити запит;
- `after_handle` викликається **після** обробника: тут додають заголовки, пишуть журнал, вимірюють час.

Порядок виконання нагадує вкладені виклики: `before_handle` — у порядку реєстрації, `after_handle` — у зворотному. Останній зареєстрований middleware ближчий до обробника.

## Структура middleware

Middleware — звичайна структура з трьома елементами. Перший — вкладена структура `context`, у якій зберігаються дані на час одного запиту. Другий і третій — методи `before_handle` та `after_handle`.

```cpp
struct Timer {
    struct context {
        std::chrono::steady_clock::time_point start = std::chrono::steady_clock::now();
    };
    void before_handle(crow::request&, crow::response& res, context& ctx) {
        ctx.start = std::chrono::steady_clock::now();
    }
    void after_handle(crow::request& req, crow::response& res, context& ctx) {
        auto us = std::chrono::duration_cast<std::chrono::microseconds>(
                      std::chrono::steady_clock::now() - ctx.start).count();
        res.set_header("X-Elapsed-Us", std::to_string(us));
        std::cout << req.url << " оброблено за " << us << " мкс\n";
    }
};
```

`context` створюється окремо для кожного запиту, тому кілька потоків не заважають одне одному. Дані між `before_handle` та `after_handle` одного запиту передаються саме через нього, а не через поля самого middleware: ті спільні для всіх запитів.

Middleware підключаються як параметри шаблону застосунку:

```cpp
crow::App<First, Timer, Gate> app;
```

Тип `crow::SimpleApp`, який використовувався раніше, — це `crow::App<>`, тобто застосунок без middleware.

## Порядок виконання

Демо `09-middleware-chain` має три middleware, і кожен дописує свою мітку в заголовок `X-Trace`. Так порядок видно в `curl`.

```cpp
static void trace(crow::response& res, const std::string& label) {
    std::string current = res.get_header_value("X-Trace");
    res.set_header("X-Trace", current.empty() ? label : current + " > " + label);
}
```

::terminal-preview{title="curl -i localhost:8089/"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8089/ | grep -E "HTTP|X-Trace"</strong></div>
<div class="line">HTTP/1.1 200 OK</div>
<div class="line">X-Trace: First.before > Timer.before > Gate.before > handler > Gate.after > Timer.after > First.after</div>
::

Ланцюжок читається зліва направо: три `before`, обробник, три `after` у зворотному порядку. Звідси практичне правило: що має відпрацювати першим, ставлять першим у списку. Журнал і вимірювання часу стоять на початку, щоб охоплювати все, що відбувається далі, а перевірки доступу — після них, перед обробником.

## Контекст між учасниками

Обробник і інші middleware можуть прочитати контекст конкретного middleware за типом:

```cpp
CROW_ROUTE(app, "/")([&app](const crow::request& req, crow::response& res) {
    auto& timer_ctx = app.get_context<Timer>(req);
    // ... використання timer_ctx
});
```

Так middleware автентифікації залишає ім'я користувача, а обробник читає його, не розбираючи заголовки ще раз. У наступній лекції цей прийом використовується для ключа API.

::note
Усередині middleware контекст свого типу приходить аргументом. Контекст чужого middleware можна прочитати лише з обробника через `app.get_context<M>(req)` або з іншого middleware, який отримує доступ до `all_ctx`. Для навчальних задач достатньо першого способу.
::

## Ранній вихід

Middleware може завершити відповідь сам: тоді обробник маршруту не викликається. Для цього достатньо заповнити відповідь і викликати `res.end()`.

```cpp
struct Gate {
    struct context {};
    void before_handle(crow::request& req, crow::response& res, context&) {
        if (req.url_params.get("deny")) {
            res.code = 403;
            res.write("Доступ заборонено middleware Gate\n");
            res.end();
        }
    }
    void after_handle(crow::request&, crow::response&, context&) {}
};
```

![При ранньому виході обробник не викликається, але after_handle усіх middleware виконуються](/images/cpp/crow-web/middleware-chain/02-early-exit.png){.diagram-img}

::terminal-preview{title="curl -i 'localhost:8089/?deny=1'"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si "localhost:8089/?deny=1" | grep -E "HTTP|X-Trace"</strong></div>
<div class="line">HTTP/1.1 403 Forbidden</div>
<div class="line">X-Trace: First.before > Timer.before > Gate.before > Gate.after > Timer.after > First.after</div>
::

У мітках немає `handler`: його не викликали. Але всі три `after_handle` виконалися, тому журнал і таймер записали навіть відхилений запит. Це важливо для безпеки: заборони теж мають бути в журналі.

::warning
Після `res.end()` в `before_handle` решта коду middleware все одно виконується, якщо не вийти з функції. Пишіть `return` одразу після `res.end()`, щоб випадково не змінити вже завершену відповідь.
::

## Пастка: заголовки, які зникають

Заголовок, поставлений у `before_handle`, потрапляє в об'єкт `crow::response`. Якщо обробник **повертає нову** відповідь (`return crow::response(...)` чи просто рядок), Crow підставляє її замість старої, і заголовки з `before_handle` зникають.

Демо має два маршрути з однаковим результатом, але різними сигнатурами:

```cpp
// Приймає відповідь за посиланням і змінює той самий об'єкт
CROW_ROUTE(app, "/")([&app](const crow::request& req, crow::response& res) {
    trace(res, "handler");
    res.write("Відповідь обробника\n");
    res.end();
});

// Повертає нову відповідь
CROW_ROUTE(app, "/returns")([] {
    crow::response res(200, "Обробник повернув нову відповідь\n");
    trace(res, "handler");
    return res;
});
```

::terminal-preview{title="Порівняння двох сигнатур"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8089/ | grep X-Trace</strong></div>
<div class="line">X-Trace: First.before > Timer.before > Gate.before > handler > Gate.after > Timer.after > First.after</div>
<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si localhost:8089/returns | grep X-Trace</strong></div>
<div class="line">X-Trace: handler > Gate.after > Timer.after > First.after</div>
::

У другому випадку мітки `before` втрачені. Є два способи уникнути цього:

- ставити заголовки в `after_handle`, коли відповідь уже сформована: цей спосіб працює для будь-яких обробників;
- писати обробники з параметром `crow::response&` і не повертати нову відповідь.

Перший спосіб надійніший, бо не залежить від стилю кожного обробника в команді. Саме так працюють лічильник запитів і CORS у наступній лекції.

## Типи middleware

| Тип | Призначення | Де зазвичай стоїть |
| --- | ----------- | ------------------ |
| Журнал і метрики | запис запитів, час виконання | на початку |
| Безпека | CORS, обмеження частоти, перевірка ключа чи сесії | після журналу |
| Підготовка даних | розбір cookies, декодування, стиснення | перед обробником |
| Обробка помилок | перетворення винятків на відповіді | на початку, щоб охоплювати решту |

Типове правило порядку: спочатку те, що має охопити всі випадки (журнал, обмеження частоти), потім те, що відсікає непотрібні запити, далі те, що готує дані.

## Запитання

::::accordion

:::accordion-item{label="❓ Чим middleware відрізняється від звичайної функції, яку викликаєш у кожному обробнику?" icon="i-lucide-help-circle"}

Middleware викликається автоматично для всіх запитів, і забути його підключити неможливо. Звичайна функція у кожному обробнику вимагає дисципліни від кожного, хто пише новий маршрут.

:::

:::accordion-item{label="❓ Чи впливає кількість middleware на швидкість?" icon="i-lucide-help-circle"}

Так, кожен додає виклик до та після обробника. Для легких операцій (перевірка заголовка) витрати мізерні, а для важких (звернення до бази, шифрування) варто підключати middleware лише до потрібних маршрутів (лекція 10).

:::

:::accordion-item{label="❓ Що буде, якщо в before_handle кинути виняток?" icon="i-lucide-help-circle"}

Перевірка показала, що відповіді не буде зовсім. Для винятку в обробнику Crow повертає 500, а для винятку в middleware журнал містить `Worker Crash: An uncaught exception occurred`, і клієнт чекає до тайм-ауту (`curl` завершується без коду відповіді). Сервер при цьому продовжує працювати, а наступні запити обробляються нормально. Тому код middleware обгортають у `try`/`catch` і сам формують відповідь 500.

:::

:::accordion-item{label="❓ Чи можна змінити порядок middleware під час роботи?" icon="i-lucide-help-circle"}

Ні. Список задається типом `crow::App<...>` під час компіляції. Умовна поведінка реалізується всередині самого middleware: наприклад, пропуск запитів за префіксом шляху.

:::

## Практика

::::accordion

:::accordion-item{label="📋 Завдання 1: ідентифікатор запиту" icon="i-lucide-clipboard-list"}

Напишіть `RequestId`, який у `before_handle` генерує числовий ідентифікатор (атомарний лічильник), а в `after_handle` додає заголовок `X-Request-Id`. Перевірте, що він з'являється і в обробниках, які повертають значення.

:::

:::accordion-item{label="✅ Розв'язок завдання 1" icon="i-lucide-check-circle"}

```cpp
struct RequestId {
    struct context {
        unsigned long id = 0;
    };
    void before_handle(crow::request&, crow::response&, context& ctx) {
        static std::atomic<unsigned long> counter{0};
        ctx.id = ++counter;
    }
    void after_handle(crow::request&, crow::response& res, context& ctx) {
        res.set_header("X-Request-Id", std::to_string(ctx.id));
    }
};
```

Потрібно підключити `<atomic>`. Заголовок ставиться в `after_handle`, тому не губиться.

:::

:::accordion-item{label="📋 Завдання 2: режим обслуговування" icon="i-lucide-clipboard-list"}

Створіть middleware `Maintenance`, який при наявності файлу `maintenance.flag` у робочій папці повертає 503 із заголовком `Retry-After: 60`, не викликаючи обробників.

:::

## Підсумок

- Middleware — наскрізний код навколо обробників: `before_handle` у порядку реєстрації, `after_handle` у зворотному.
- Дані одного запиту між фазами передає `context`; чужий контекст обробник читає через `app.get_context<M>(req)`.
- `res.end()` у `before_handle` перериває запит: обробник не викликається, але всі `after_handle` виконуються.
- Заголовки, поставлені в `before_handle`, губляться, якщо обробник повертає нову відповідь; надійне місце для них — `after_handle`.
