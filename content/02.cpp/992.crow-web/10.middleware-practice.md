# Middleware на практиці: журнал, API-ключ, обмеження частоти, CORS

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Реалізувати middleware журналу запитів із часом виконання.
- Створити локальний middleware (`ILocalMiddleware`) і підключити його лише до потрібних маршрутів.
- Обмежити частоту запитів за IP і повернути 429 із `Retry-After`.
- Налаштувати вбудований `CORSHandler` та розуміти, хто саме блокує чужі origin.
- Враховувати особливості preflight-запитів і порядку `after_handle`.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Локальний middleware:** підключається до окремих маршрутів, а не до всіх.
- **Обмеження частоти (*rate limiting*):** ліміт кількості запитів від одного клієнта за період.
- **CORS (*Cross-Origin Resource Sharing*):** механізм, який дозволяє браузеру викликати API з іншого origin.
- **Preflight:** попередній запит `OPTIONS`, який браузер надсилає перед «небезпечним» міждоменним запитом.
- **API-ключ:** секретний рядок, який клієнт передає в заголовку для ідентифікації.

::

::

## Журнал запитів

Журнал фіксує метод, адресу, IP клієнта, код відповіді та час виконання. Час відлічується від `before_handle` до `after_handle`.

```cpp
struct AccessLog {
    struct context {
        std::chrono::steady_clock::time_point start = std::chrono::steady_clock::now();
    };
    void before_handle(crow::request&, crow::response&, context& ctx) {
        ctx.start = std::chrono::steady_clock::now();
    }
    void after_handle(crow::request& req, crow::response& res, context& ctx) {
        auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
                      std::chrono::steady_clock::now() - ctx.start).count();
        std::cout << "[ACCESS] " << crow::method_name(req.method) << " " << req.raw_url << " from "
                  << req.remote_ip_address << " -> " << res.code << " (" << ms << " ms)\n";
    }
};
```

Початкове значення `start` у `context` потрібне не для краси. Під час перевірки без нього журнал показав для preflight-запиту `OPTIONS` час `505725350 ms` і порожню IP-адресу: `after_handle` виконався без попереднього `before_handle` (запит завершив вбудований CORS-обробник). Контекст мусить мати безпечні значення за замовчуванням, а `after_handle` не повинен припускати, що `before_handle` відпрацював.

<div class="line">[ACCESS] GET /public from 127.0.0.1 -> 429 (0 ms)</div>
<div class="line">[ACCESS] GET /admin from 127.0.0.1 -> 403 (0 ms)</div>

У виробничому застосунку журнал пишуть у файл або в систему збору логів, а не в `std::cout`, і додають ідентифікатор запиту для зіставлення рядків.

## Обмеження частоти запитів

Без ліміту один клієнт (чи скрипт) здатен надіслати тисячі запитів на секунду й вичерпати ресурси сервера або підібрати пароль. **Rate limiting** обмежує кількість запитів на клієнта за вікно часу.

![Вікно 10 секунд і ліміт 5 запитів: шостий і сьомий отримують 429, потім лічильник скидається](/images/cpp/crow-web/middleware-practice/01-rate-window.png){.diagram-img}

Демо використовує алгоритм **фіксованого вікна**: для кожної IP-адреси зберігається час початку вікна та лічильник. Коли вікно спливло, лічильник скидається.

```cpp
struct RateLimit {
    struct context {
        int remaining = 0;
    };

    static constexpr int kMaxRequests = 5;
    static constexpr std::chrono::seconds kWindow{10};

    void before_handle(crow::request& req, crow::response& res, context& ctx) {
        const auto now = std::chrono::steady_clock::now();
        std::lock_guard<std::mutex> lock(mutex_);
        Bucket& b = buckets_[req.remote_ip_address];
        if (now - b.window_start >= kWindow) {
            b.window_start = now;
            b.count = 0;
        }
        ++b.count;
        ctx.remaining = std::max(0, kMaxRequests - b.count);

        if (b.count > kMaxRequests) {
            auto retry = std::chrono::duration_cast<std::chrono::seconds>(kWindow - (now - b.window_start)).count();
            res.code = 429;
            res.set_header("Retry-After", std::to_string(retry + 1));
            res.write("Забагато запитів. Повторіть пізніше.\n");
            res.end();
        }
    }

    void after_handle(crow::request&, crow::response& res, context& ctx) {
        res.set_header("X-RateLimit-Limit", std::to_string(kMaxRequests));
        res.set_header("X-RateLimit-Remaining", std::to_string(ctx.remaining));
    }

private:
    struct Bucket {
        std::chrono::steady_clock::time_point window_start{};
        int count = 0;
    };
    std::mutex mutex_;
    std::map<std::string, Bucket> buckets_;
};
```

Розбір:

- `buckets_` спільний для всіх потоків, тому доступ до нього обгорнуто `std::mutex`.
- Код 429 (`Too Many Requests`) разом із `Retry-After` повідомляє клієнтові, через скільки секунд повторити запит.
- Заголовки `X-RateLimit-*` ставляться в `after_handle`, бо в `before_handle` вони зникли б у обробників, що повертають нову відповідь (лекція 09). Перша версія демо мала цю помилку: на успішних відповідях `/admin` лічильника не було.

Через 10 секунд лічильник скидається, і наступний запит знову отримує 200.

::warning
Фіксоване вікно має слабке місце: клієнт може надіслати 5 запитів наприкінці одного вікна та ще 5 на початку наступного, тобто 10 запитів за коротку мить. Точніші алгоритми (ковзне вікно, «відро токенів») складніші. Також за зворотним проксі (Nginx) `remote_ip_address` буде адресою проксі, тому справжній IP беруть із заголовка `X-Forwarded-For`, якому довіряють лише від власного проксі.
::

Мапа `buckets_` зростає разом із кількістю різних IP. У реальному застосунку старі записи періодично видаляють, інакше сервер повільно «з'їдає» пам'ять.

## Локальний middleware: API-ключ

Не всі маршрути потребують однакового захисту: `/public` відкритий, `/admin` вимагає ключ. Для цього middleware оголошується як локальний: структура наслідує `crow::ILocalMiddleware`, а до маршруту підключається макросом `CROW_MIDDLEWARES`.

```cpp
struct ApiKeyAuth : crow::ILocalMiddleware {
    struct context {
        std::string client;
    };
    void before_handle(crow::request& req, crow::response& res, context& ctx) {
        const std::string key = req.get_header_value("X-API-Key");
        if (key.empty()) {
            res.code = 401;
            res.write("Потрібен заголовок X-API-Key\n");
            res.end();
            return;
        }
        if (key != "secret-123") {
            res.code = 403;
            res.write("Невірний API-ключ\n");
            res.end();
            return;
        }
        ctx.client = "demo-client";
    }
    void after_handle(crow::request&, crow::response&, context&) {}
};
```

Реєстрація: тип потрібно перерахувати в `crow::App<...>`, а до маршруту підключити окремо.

```cpp
crow::App<crow::CORSHandler, AccessLog, RateLimit, ApiKeyAuth> app;

CROW_ROUTE(app, "/public")([] { return "Публічний ресурс\n"; });

CROW_ROUTE(app, "/admin").CROW_MIDDLEWARES(app, ApiKeyAuth)([&app](const crow::request& req) {
    auto& ctx = app.get_context<ApiKeyAuth>(req);
    return "Вітаю, " + ctx.client + "\n";
});
```

Відмінність кодів така сама, як у лекції 01: відсутність ключа — 401 (не знаємо, хто це), а хибний ключ — 403 у цьому демо (знаємо, що це не наш клієнт). Дехто повертає 401 в обох випадках; головне — єдине правило.

::caution
Ключ `secret-123` у коді — лише для демонстрації. Реальні ключі беруть із змінної оточення чи сховища секретів, порівнюють за сталий час (щоб відповідь не підказувала довжину збігу), а в базі зберігають як хеш.
::

## CORS

Браузер дозволяє сторінці з одного origin (протокол + хост + порт) звертатися лише до свого origin. Якщо фронтенд на `http://localhost:3000` викликає API на `http://localhost:8080`, це інший origin, і браузер вимагає дозволу від сервера у вигляді заголовків `Access-Control-Allow-*`. Це правило називають **CORS**.

Crow постачає готовий `crow::CORSHandler`:

```cpp
#include "crow/middlewares/cors.h"

crow::App<crow::CORSHandler, AccessLog, RateLimit, ApiKeyAuth> app;

auto& cors = app.get_middleware<crow::CORSHandler>();
cors.global()
    .origin("http://localhost:3000")
    .methods("GET"_method, "POST"_method)
    .headers("Content-Type", "X-API-Key");
```

Для «небезпечних» запитів (методи, окремі від `GET`/`POST` із простими даними, або нестандартні заголовки) браузер спершу надсилає **preflight** — запит `OPTIONS` із питанням «чи дозволено?». `CORSHandler` відповідає на нього сам:

::terminal-preview{title="Preflight-запит"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">curl -si -X OPTIONS -H 'Origin: http://localhost:3000' -H 'Access-Control-Request-Method: POST' localhost:8090/public</strong></div>
<div class="line">HTTP/1.1 204 No Content</div>
<div class="line">Access-Control-Allow-Origin: http://localhost:3000</div>
<div class="line">Access-Control-Allow-Headers: Content-Type, X-API-Key</div>
<div class="line">Allow: OPTIONS, HEAD, GET</div>
<div class="line">Access-Control-Allow-Methods: GET, POST</div>
<div class="line">Content-Length: 0</div>
::

### Хто насправді блокує

Перевірка показала неочевидну річ: запит із чужим origin (`Origin: http://evil.com`) теж отримує заголовки `Access-Control-Allow-*` зі значенням `http://localhost:3000`. Сервер не відмовляє. Блокує **браузер**: бачачи, що дозволений origin інший, він не віддає відповідь сторінці. `curl`, скрипти й інші сервери CORS не зупиняє.

Звідси висновок: CORS захищає користувачів браузерів від чужих сайтів, але не є захистом самого API. Права доступу перевіряють на сервері (ключ, сесія, токен) незалежно від CORS.

::note
Значення `origin("*")` дозволяє будь-який origin. Воно допустиме для відкритих публічних API без автентифікації. Якщо API використовує cookies чи сесії (лекції 16–17), `*` небезпечний, і origin вказують явно.
::

## Порядок у списку

У демо порядок такий: `CORSHandler, AccessLog, RateLimit, ApiKeyAuth`.

- **CORS першим**, щоб preflight завершувався до решти перевірок і заголовки CORS були на кожній відповіді, зокрема на 429.
- **Журнал другим**, щоб охоплювати відхилені запити.
- **Ліміт частоти раніше за автентифікацію**: клієнт, який перебирає ключі, упирається в ліміт.
- **Автентифікація локально**, лише для маршрутів, які її потребують.

## Запитання

::::accordion

:::accordion-item{label="❓ Чому журнал показав 429 з часом 0 мс?" icon="i-lucide-help-circle"}

Запит відхилено в `before_handle` ліміту, а обробник не виконувався, тому вимірюваний інтервал дуже короткий. Це нормально: відхилення дешеве, і в цьому сенс обмеження.

:::

:::accordion-item{label="❓ Чи можна обмежувати частоту не за IP, а за ключем?" icon="i-lucide-help-circle"}

Так, і в API з автентифікацією це правильніше: за одним NAT сотні користувачів мають одну IP-адресу. Тоді ключ для `buckets_` — значення `X-API-Key` чи ідентифікатор користувача.

:::

:::accordion-item{label="❓ Чому 204, а не 200 у відповіді на preflight?" icon="i-lucide-help-circle"}

У preflight-відповіді тіла немає, тож 204 No Content точніший. Браузери приймають обидва коди.

:::

:::accordion-item{label="❓ Чи достатньо CORS, щоб захистити API від чужих сайтів?" icon="i-lucide-help-circle"}

Ні. CORS регулює лише те, що браузер покаже сторінці. Прості запити (наприклад, `POST` із формою) браузер усе одно надішле, і сервер їх виконає. Тому змінювальні операції захищають токенами й перевіркою автентифікації.

:::

## Практика

::::accordion

:::accordion-item{label="📋 Завдання 1: чистка старих записів" icon="i-lucide-clipboard-list"}

Додайте до `RateLimit` видалення записів `buckets_`, які не оновлювались понад два вікна. Виконуйте чистку, наприклад, кожен сотий запит.

:::

:::accordion-item{label="📋 Завдання 2: ключ із ролями" icon="i-lucide-clipboard-list"}

Замість одного ключа тримайте `std::map<std::string, std::string>` «ключ → роль» (`reader`, `admin`). Залишайте роль у контексті; для `DELETE` дозволено лише `admin`, інакше 403.

:::

:::accordion-item{label="📋 Завдання 3: журнал у файл" icon="i-lucide-clipboard-list"}

Запишіть журнал у `access.log` через `std::ofstream` із м'ютексом. Формат: `2026-11-18T13:45:21 GET /admin 403 0ms`.

:::

:::accordion-item{label="✅ Підказка до завдання 3" icon="i-lucide-check-circle"}

```cpp
static std::mutex log_mutex;
static std::ofstream log_file("access.log", std::ios::app);

std::lock_guard<std::mutex> lock(log_mutex);
std::time_t t = std::time(nullptr);
char ts[32];
std::strftime(ts, sizeof(ts), "%Y-%m-%dT%H:%M:%S", std::localtime(&t));
log_file << ts << ' ' << crow::method_name(req.method) << ' ' << req.raw_url
         << ' ' << res.code << ' ' << ms << "ms\n";
```

Без м'ютекса рядки від різних потоків змішаються.

:::

## Домашнє завдання

Оберіть одне. Завдання мають різний рівень складності.

::::accordion

:::accordion-item{label="📋 Логування запитів (легкий)" icon="i-lucide-clipboard-list"}

Middleware має логувати час надходження, метод і URL, IP клієнта та час виконання у форматі `[15:30:45] GET /api/users from 192.168.1.100 - 45ms`. Критерії: middleware реєструється в застосунку, логує всі запити в консоль, вимірює час.

:::

:::accordion-item{label="📋 Rate limiting із ковзним вікном (середній)" icon="i-lucide-clipboard-list"}

Замість фіксованого вікна реалізуйте ковзне: зберігайте час кожного запиту у `std::deque` і викидайте ті, що старші за вікно. Додайте різні ліміти для маршрутів (`/api/*` строгіший за `/public`).

:::

:::accordion-item{label="📋 Розширена авторизація RBAC (складніший)" icon="i-lucide-clipboard-list"}

Ключі мають ролі `guest`, `user`, `admin`. Правила задаються таблицею «шлях + метод → мінімальна роль». Middleware повертає 401 без ключа та 403 при недостатній ролі й пише рішення в журнал.

:::

## Підсумок

- Журнал, обмеження частоти й перевірка ключа — типові наскрізні задачі, які виносяться в middleware.
- Локальний middleware (`ILocalMiddleware` + `CROW_MIDDLEWARES`) підключається лише до потрібних маршрутів.
- Заголовки відповіді ставлять в `after_handle`. Контекст має безпечні початкові значення, бо `after_handle` може виконатися без `before_handle`.
- CORS обмежує браузер, а не сервер. Права доступу перевіряють окремо.
