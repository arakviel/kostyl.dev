# Шар доступу до даних: від прямого читання файлів до патернів

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Пояснити, що таке шар доступу до даних (DAL) і які проблеми він розв'язує.
- Пройти чотири етапи еволюції коду: прямий доступ, функції, DAO, Active Record.
- Бачити на коді, що змінюється в обробниках на кожному етапі.
- Розрізняти патерни Table Data Gateway, Row Data Gateway, Active Record, DAO, Data Mapper, Repository.
- Обирати патерн за розміром і вимогами проєкту.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Шар доступу до даних (*Data Access Layer, DAL*):** частина програми, яка читає й записує дані; решта коду про сховище нічого не знає.
- **DAO (*Data Access Object*):** клас, що інкапсулює операції зі сховищем.
- **Active Record:** об'єкт моделі, який сам вміє зберігати й завантажувати себе.
- **Data Mapper:** окремий клас, який переносить дані між об'єктом і сховищем, а об'єкт про сховище не знає.
- **Зв'язність (*coupling*):** наскільки сильно один компонент залежить від деталей іншого.

::

::

У лекціях 05–08 сховищем був `std::map` у пам'яті, а в домашніх завданнях пропонувалися JSON-файли. Код, що змішує обробку HTTP-запиту з роботою з файлом, швидко стає проблемою: його складно змінювати, тестувати й розвивати. Ця лекція показує, як дійти від такого коду до чистої структури.

## Які проблеми розв'язує шар даних

Якщо обробник маршруту сам відкриває файл, розбирає JSON і записує його назад, виникають чотири проблеми.

- **Дублювання.** Те саме читання файлу копіюється в кожен обробник. Помилку виправляють в одному місці й забувають в іншому.
- **Прив'язка до формату.** Усі обробники знають, що дані лежать у JSON-файлі. Перехід на базу даних означає переписати кожен.
- **Змішування відповідальностей.** В одній функції перемішані HTTP-код, бізнес-правила й ввід-вивід. Змінити одне, не торкнувшись іншого, неможливо.
- **Складність тестування.** Щоб перевірити бізнес-правило, потрібен справжній файл, а іноді й запущений сервер.

Шар доступу до даних збирає все, що стосується сховища, в одному місці й пропонує решті коду простий інтерфейс: «знайти», «додати», «видалити».

## Еволюція підходів

Демо `13-dal-evolution` містить чотири програми з однаковим API (`GET /users`, `POST /users`, `GET /users/<id>`) і однаковими відповідями. Відрізняється лише внутрішня будова. Так зміни видно в чистому вигляді.

![П'ять ступенів розвитку доступу до даних](/images/cpp/crow-web/dal-evolution/01-ladder.png){.diagram-img}

### Етап 1: прямий доступ

Кожен обробник сам відкриває файл, розбирає JSON і записує результат.

```cpp
CROW_ROUTE(app, "/users").methods(crow::HTTPMethod::POST)([&file](const crow::request& req) {
    auto body = nlohmann::json::parse(req.body, nullptr, false);
    if (body.is_discarded() || !body.contains("name") || !body.contains("email"))
        return crow::response(400, "name та email обов'язкові");

    // Читання файлу, скопійоване з GET-обробника
    std::ifstream in(file);
    nlohmann::json all = in ? nlohmann::json::parse(in, nullptr, false) : nlohmann::json::array();
    if (all.is_discarded()) all = nlohmann::json::array();

    int next_id = 1;
    for (const auto& u : all) next_id = std::max<int>(next_id, u["id"].get<int>() + 1);
    nlohmann::json created = {{"id", next_id}, {"name", body["name"]}, {"email", body["email"]}};
    all.push_back(created);

    std::ofstream out(file);
    out << all.dump(2);
    // ...
});
```

Блок читання файлу з трьох рядків повторюється в трьох обробниках з трьох. У програмі на 64 рядки це ще терпимо; у застосунку з двадцятьма маршрутами це двадцять копій. Крім того, обчислення нового `id`, перевірка полів і запис файлу змішані з обробкою запиту.

### Етап 2: функції

Очевидний перший крок: повторюваний код виноситься у функції.

```cpp
std::vector<User> load_users(const std::string& file) {
    std::ifstream in(file);
    if (!in) return {};
    auto j = nlohmann::json::parse(in, nullptr, false);
    if (j.is_discarded()) return {};
    return j.get<std::vector<User>>();
}

void save_users(const std::string& file, const std::vector<User>& users) {
    std::ofstream out(file);
    out << nlohmann::json(users).dump(2);
}
```

Дублювання зникло, а обробники стали коротшими: `auto users = load_users(file);`. Проте залишилися два слабкі місця. По-перше, обробники й досі передають шлях до файлу: вони знають, що дані лежать у файлі. По-друге, ці функції вільні: у них немає спільного стану, тому немає й місця для мютекса, кешу чи відкритого з'єднання з базою.

### Етап 3: DAO

**DAO** збирає операції зі сховищем у клас, який володіє шляхом до файлу, даними в пам'яті й мютексом.

```cpp
class UserDao {
public:
    explicit UserDao(std::string file) : file_(std::move(file)) { load(); }

    std::vector<User> find_all() const;
    std::optional<User> find_by_id(int id) const;
    User insert(User u);

private:
    void load();
    void save() const;

    std::string file_;
    mutable std::mutex mutex_;
    std::vector<User> users_;
};
```

Обробники тепер не знають про файл узагалі:

```cpp
CROW_ROUTE(app, "/users/<int>")([&dao](int id) {
    auto u = dao.find_by_id(id);
    if (!u) return crow::response(404, "Користувача не знайдено");
    return json_response(200, *u);
});
```

![Обробники залежать від файлу напряму проти залежності лише від DAO](/images/cpp/crow-web/dal-evolution/02-coupling.png){.diagram-img}

Якщо завтра сховищем стане база, зміниться тіло `UserDao`, а обробники залишаться незмінними. Мютекс теж захований усередині: обробники не можуть забути заблокувати дані.

### Етап 4: Active Record

У патерні **Active Record** об'єкт моделі сам вміє зберігати себе й шукати подібних: `user.save()`, `User::find(id)`.

```cpp
UserRecord r;
r.name = body["name"];
r.email = body["email"];
r.save();                          // id присвоюється при першому збереженні
auto found = UserRecord::find(2);  // статичний метод
```

Код обробників вийшов компактним, і для невеликих застосунків це зручно: така модель у фреймворках Ruby on Rails чи Laravel. Для C++ вона має слабкості:

- клас моделі знає про файл чи базу, тож його не можна використати без сховища;
- підміна сховища в тестах означає зміну самого класу;
- статичний стан (`file()`, `rows()`) ускладнює тести, бо їх нічого не ізолює.

## Огляд патернів

Крім цих чотирьох підходів, для роботи з даними існують усталені патерни, описані Мартіном Фаулером. Вони відрізняються тим, **хто** відповідає за доступ до сховища.

| Патерн | Ідея | Що знає про сховище |
| ------ | ---- | ------------------- |
| **Active Record** | об'єкт і зберігає себе, і містить логіку | модель |
| **Table Data Gateway** | один об'єкт на таблицю з методами `find`, `insert`, `update`, `delete`; повертає прості записи | шлюз |
| **Row Data Gateway** | один об'єкт на рядок таблиці без бізнес-логіки | об'єкт-рядок |
| **DAO** | клас-посередник між кодом і сховищем для одного типу даних | DAO |
| **Data Mapper** | окремий клас переносить дані між об'єктом домену та сховищем; домен про сховище не знає | маппер |
| **Repository** | колекція об'єктів домену з інтерфейсом «колекції»; реалізація ховає сховище | реалізація репозиторію |

Пояснення різниці через приклад з користувачем:

- **Table Data Gateway:** `UserGateway::find_by_email(email)` повертає запис (структуру-рядок). Логіка («чи може користувач увійти») лежить деінде.
- **Row Data Gateway:** `UserRow row = UserRow::find(2); row.email = "..."; row.update();`. Об'єкт-рядок знає про таблицю, але не про правила.
- **Active Record:** те саме, але в об'єкті є й правила: `user.change_email(...)`, `user.is_adult()`, і він сам зберігається.
- **Data Mapper:** `User` — звичайна структура з правилами, `UserMapper` читає й записує її. Модель чиста, але шарів більше.
- **Repository:** тип, схожий на колекцію: `repo.add(user)`, `repo.find_by_email(...)`. Це DAO, до якого додано два правила: інтерфейс мовою домену (не мовою таблиць) і підміна реалізації без змін у клієнтському коді.

Практичний вибір:

| Проєкт | Патерн |
| ------ | ------ |
| Прототип, скрипт, невелике API | DAO або Active Record |
| Застосунок із бізнес-логікою, який треба тестувати | **Repository** |
| Складна доменна модель, що не збігається зі схемою таблиць | Data Mapper (+ Repository) |
| Застосунок з уже готовою ORM | Active Record або Repository поверх ORM |

::note
Назви патернів у літературі й проєктах нерідко змішують: «DAO» часто означає те, що Фаулер називає Repository, і навпаки. Корисніше орієнтуватися на властивості, а не на назву: чи знає код про сховище, чи можна підмінити реалізацію, чи є інтерфейс.
::

## Запитання

::::accordion

:::accordion-item{label="❓ Коли не варто вводити шар даних?" icon="i-lucide-help-circle"}

Для одноразового скрипта чи демо на кілька десятків рядків окремий клас не окупається. Цінність шару зростає разом із розміром коду, кількістю тестів та ймовірністю змінити сховище.

:::

:::accordion-item{label="❓ Чи не надмірно писати інтерфейс, якщо сховище одне?" icon="i-lucide-help-circle"}

Інтерфейс окупається вже тоді, коли з'являються тести: другою реалізацією стає підроблений репозиторій у пам'яті. Тому навіть із однією «справжньою» реалізацією їх фактично дві (лекція 14).

:::

:::accordion-item{label="❓ Де має лежати мютекс: в обробнику чи в DAO?" icon="i-lucide-help-circle"}

У DAO (або репозиторії): сховище саме відповідає за коректний паралельний доступ. Якщо б блокування залишалось в обробниках, кожен автор нового маршруту мусив би про нього пам'ятати.

:::

:::accordion-item{label="❓ Чим DAO відрізняється від Repository?" icon="i-lucide-help-circle"}

DAO моделює доступ до сховища (операції: `insert`, `select_by_id`), а Repository моделює колекцію об'єктів домену (`add`, `find_by_email`). На практиці різниця в мові інтерфейсу й у тому, що Repository проєктують від потреб бізнес-логіки, а не від структури таблиць.

:::

## Підсумок

- Шар доступу до даних збирає все, що стосується сховища, в одному місці й усуває дублювання та залежність обробників від формату.
- Еволюція: прямий доступ → функції → DAO → (Active Record як альтернатива). Зовнішня поведінка не змінюється, покращується структура.
- Патерни відрізняються тим, хто знає про сховище: модель (Active Record), шлюз, DAO, маппер чи реалізація репозиторію.
- Для застосунків із бізнес-логікою й тестами найкраще підходить Repository: інтерфейс мовою домену й змінні реалізації. Він розглядається в наступній лекції.
