## Реляційна база і SQLite

У **реляційній базі** дані лежать у таблицях: рядки — записи, стовпці — поля з типами. Таблиці можуть мати обмеження цілісності та зв'язки. Працюють із ними мовою **SQL**.

**SQLite** — вбудована база: це бібліотека, яка зберігає все в одному файлі й працює всередині вашого процесу. Окремого сервера немає, тому нічого не треба встановлювати й налаштовувати. Саме тому вона підходить для навчання, мобільних застосунків, невеликих сайтів і локального кешу. Для сайтів із великим навантаженням на запис і кількома серверами застосунку використовують серверні СУБД (PostgreSQL, MySQL).

Підключення до CMake-проєкту (залежність `sqlite3` уже є у `vcpkg.json`):

```cmake
find_package(unofficial-sqlite3 CONFIG REQUIRED)
target_link_libraries(sqlite_repository_api PRIVATE unofficial::sqlite3::sqlite3)
```

## SQL за п'ять хвилин

Схема таблиці користувачів, яку створює демо:

```sql
CREATE TABLE IF NOT EXISTS users (
  id    INTEGER PRIMARY KEY AUTOINCREMENT,
  name  TEXT    NOT NULL,
  email TEXT    NOT NULL UNIQUE,
  age   INTEGER NOT NULL CHECK (age BETWEEN 0 AND 150)
);
```

- `PRIMARY KEY AUTOINCREMENT` — унікальний ідентифікатор, який база присвоює сама й не використовує повторно (як лічильник `next_id_` в інших реалізаціях).
- `NOT NULL` забороняє порожні значення.
- `UNIQUE` гарантує, що двох користувачів з однаковим email не буде.
- `CHECK` перевіряє значення на кожному записі.

Чотири основні операції відповідають CRUD:

```sql
INSERT INTO users (name, email, age) VALUES ('Іван', 'ivan@x.com', 25);   -- Create
SELECT id, name, email, age FROM users WHERE id = 1;                       -- Read
UPDATE users SET email = 'new@x.com' WHERE id = 1;                         -- Update
DELETE FROM users WHERE id = 1;                                            -- Delete
```

Умова `WHERE` відбирає рядки; без неї `UPDATE` і `DELETE` зачеплять усю таблицю. Це найчастіша причина втрати даних, тому перед запуском змінювального запиту його умову перевіряють окремим `SELECT`.

База, створена демо після одного запиту `POST`, виглядає так (утиліта `sqlite3` входить до macOS і більшості Linux):

::terminal-preview{title="sqlite3 users.db"}

<div class="line"><span class="opacity-40">$</span> <strong class="font-bold">sqlite3 users.db ".schema" "SELECT * FROM users;"</strong></div>

## SQLite з C++

SQLite має C API з кількома ключовими функціями. Їх використання вимагає акуратності: кожен відкритий ресурс треба закрити.

| Функція | Призначення |
| ------- | ----------- |
| `sqlite3_open` / `sqlite3_close` | відкрити й закрити з'єднання |
| `sqlite3_exec` | виконати SQL без параметрів і результатів |
| `sqlite3_prepare_v2` / `sqlite3_finalize` | підготувати запит і звільнити його |
| `sqlite3_bind_text`, `sqlite3_bind_int` | підставити значення в позначку `?` |
| `sqlite3_step` | виконати крок: `SQLITE_ROW` (є рядок) або `SQLITE_DONE` |
| `sqlite3_column_int`, `sqlite3_column_text` | прочитати поле поточного рядка |

Виклики `open` та `prepare` повертають ресурси, які треба звільняти. Якщо між ними виникне виняток, ресурс витече. Тому їх огортають у RAII-класи, як `std::unique_ptr`:

```cpp
class Database {
public:
    explicit Database(const std::string& path) {
        sqlite3* raw = nullptr;
        if (sqlite3_open(path.c_str(), &raw) != SQLITE_OK) {
            std::string message = raw ? sqlite3_errmsg(raw) : "не вдалося відкрити базу";
            sqlite3_close(raw);
            throw std::runtime_error("SQLite: " + message);
        }
        db_.reset(raw);
    }
    // ...
private:
    struct Closer {
        void operator()(sqlite3* db) const { sqlite3_close(db); }
    };
    std::unique_ptr<sqlite3, Closer> db_;
};
```

Деструктор `unique_ptr` викликає `sqlite3_close` за будь-якого виходу з області: нормального чи через виняток. Те саме робить клас `Statement` для `sqlite3_finalize`.

## Підготовлені запити

Найпростіше складати SQL рядком: `"SELECT ... WHERE email = '" + email + "'"`. Так робити не можна. Підготовлений запит містить позначки `?`, а значення передаються окремо.

```cpp
std::optional<User> find_by_email(const std::string& email) const override {
    std::lock_guard<std::mutex> lock(mutex_);
    sqlite::Statement st(db_, "SELECT id, name, email, age FROM users WHERE email = ?");
    st.bind(1, email);
    if (!st.step()) return std::nullopt;
    return read_user(st);
}
```

Тут `bind(1, email)` передає значення першій позначці `?` (нумерація з 1). Метод `step()` повертає `true`, коли є рядок результату.

### SQL-ін'єкція

Припустимо, що замість підготовленого запиту написано конкатенацію, і зловмисник передав як email рядок `x' OR '1'='1`. Запит перетворюється на:

```sql
SELECT COUNT(*) FROM users WHERE email = 'x' OR '1'='1'
```

Умова `'1'='1'` завжди істинна, тому підходять **усі** рядки. На логіні це означає вхід без пароля, у видаленні — стирання всієї таблиці. Тест демо відтворює атаку:

```cpp
// Небезпечна функція, яку НЕ можна писати: значення вставлено в текст запиту.
static int count_by_email_unsafe(const sqlite::Database& db, const std::string& email) {
    sqlite::Statement st(db, "SELECT COUNT(*) FROM users WHERE email = '" + email + "'");
    st.step();
    return st.column_int(0);
}

TEST_CASE("SQL-ін'єкція: конкатенація проти підготовленого запиту") {
    SqliteUserRepository repo(":memory:");
    repo.add({"Анна", "anna@example.com", 20});
    repo.add({"Борис", "boris@example.com", 22});

    const std::string attack = "x' OR '1'='1";

    // Конкатенація: умова стала завжди істинною, повернулись ВСІ рядки
    CHECK(count_by_email_unsafe(repo.database(), attack) == 2);

    // Підготовлений запит: той самий рядок шукається як звичайне значення
    CHECK_FALSE(repo.find_by_email(attack).has_value());
}
```

![Конкатенація змінює запит, підготовлений запит передає значення як дані](/images/cpp/crow-web/sqlite-repository/01-injection.png){.diagram-img}

Конкатенація знайшла 2 користувачів із двох, хоча такого email у базі немає. Підготовлений запит знайшов 0. База розбирає текст запиту **до** підстановки значень, тому значення не може змінити структуру запиту, навіть якщо містить лапки й ключові слова SQL.

::warning
Правило без винятків: значення, які приходять ззовні (запит, файл, інша система), у текст SQL ніколи не конкатенують. Лише `bind`. Назви таблиць і стовпців підготовленими запитами підставити не можна; якщо вони приходять від клієнта (наприклад, `sort=age`), їх звіряють зі списком дозволених значень.
::

## Обмеження цілісності

Правило «email унікальний» вже є в сервісі, але між перевіркою `find_by_email` і додаванням можуть вклинитись інші запити, а до бази можуть писати й інші програми. Тому те саме правило дублюється на рівні бази як **остання лінія захисту**. Якщо обмеження порушене, SQLite повертає помилку, а `Statement::step` кидає виняток.

```cpp
TEST_CASE("обмеження бази даних") {
    SqliteUserRepository repo(":memory:");
    repo.add({"Анна", "anna@example.com", 20});

    SUBCASE("UNIQUE на email: другий запис із тим самим email кидає виняток") {
        CHECK_THROWS_AS(repo.add({"Інша Анна", "anna@example.com", 30}), std::runtime_error);
        CHECK(repo.find_all().size() == 1);
    }

    SUBCASE("CHECK на age: значення поза діапазоном відхиляється самою базою") {
        CHECK_THROWS_AS(repo.add({"Дід", "old@example.com", 200}), std::runtime_error);
    }
}
```

Сервіс не видаляється: він формує зрозумілу відповідь (409 із поясненням) у звичайному випадку. База ловить лише ті випадки, які сервіс пропустив.

## Транзакції

Іноді кілька операцій мають виконатись разом. Наприклад, імпорт двох користувачів: якщо другий не вдався, перший не повинен залишитись. **Транзакція** гарантує «все або нічого».

```cpp
std::vector<User> add_many(const std::vector<NewUser>& inputs) {
    std::lock_guard<std::mutex> lock(mutex_);
    db_.exec("BEGIN IMMEDIATE");
    try {
        std::vector<User> created;
        for (const auto& input : inputs) created.push_back(insert(input));
        db_.exec("COMMIT");
        return created;
    } catch (...) {
        db_.exec("ROLLBACK");
        throw;
    }
}
```

`BEGIN IMMEDIATE` починає транзакцію й одразу бере блокування на запис. `COMMIT` фіксує зміни, а `ROLLBACK` скасовує все зроблене після `BEGIN`.

![Транзакція завершується COMMIT або ROLLBACK](/images/cpp/crow-web/sqlite-repository/02-transaction.png){.diagram-img}

Тест перевіряє обидва шляхи, зокрема те, що помилка на другому записі скасовує й перший:

```cpp
SUBCASE("помилка в другому записі скасовує й перший") {
    CHECK_THROWS(repo.add_many({{"Анна", "dup@example.com", 20}, {"Борис", "dup@example.com", 22}}));
    CHECK(repo.find_all().empty());
}
```

Без транзакції першого користувача було б збережено, а в базі залишилася б частина імпорту.

::note
Продуктивність також залежить від транзакцій: за замовчуванням кожен `INSERT` у SQLite виконується в окремій транзакції із записом на диск. Тисяча вставок в одній транзакції на порядки швидша за тисячу окремих.
::

## Міграції схеми

Схема змінюється разом із застосунком: з'являються нові стовпці й таблиці. Метод `migrate()` виконується при кожному запуску та створює таблицю лише якщо її немає (`IF NOT EXISTS`):

```cpp
void migrate() {
    db_.exec(
        "CREATE TABLE IF NOT EXISTS users ("
        "  id INTEGER PRIMARY KEY AUTOINCREMENT,"
        "  name TEXT NOT NULL,"
        "  email TEXT NOT NULL UNIQUE,"
        "  age INTEGER NOT NULL CHECK (age BETWEEN 0 AND 150)"
        ")");
}
```

Тест на перезапуск перевіряє, що повторне відкриття існуючого файла не ламає схему й не губить дані:

```cpp
TEST_CASE("дані в файлі переживають перезапуск") {
    fs::path path = fs::temp_directory_path() / "crow_demo15_persist.db";
    fs::remove(path);
    {
        SqliteUserRepository repo(path.string());
        repo.add({"Анна", "anna@example.com", 20});
    }
    SqliteUserRepository reopened(path.string());  // migrate() повторно не ламає схему
    REQUIRE(reopened.find_all().size() == 1);
    CHECK(reopened.add({"Борис", "boris@example.com", 22}).id == 2);
    fs::remove(path);
}
```

Для змін існуючої таблиці (додати стовпець) `IF NOT EXISTS` недостатньо: потрібні нумеровані міграції та таблиця, що зберігає версію схеми (в SQLite для цього є `PRAGMA user_version`). У великих проєктах це доручають інструментам міграцій.

## Підключення без змін у сервісі

Основне, заради чого створювалась ця будова: нова реалізація підключається в одному місці.

```cpp
std::unique_ptr<IUserRepository> repository;
if (kind == "memory") {
    repository = std::make_unique<InMemoryUserRepository>();
} else if (kind == "json") {
    repository = std::make_unique<JsonFileUserRepository>(path);
} else {
    repository = std::make_unique<SqliteUserRepository>(path);
}

UserService service(*repository);
```

`UserService`, HTTP-шар і всі маршрути — той самий код, що в лекції 14. Контрактні тести перевіряють нову реалізацію тими самими перевірками, додаючи один тип до списку:

```cpp
TEST_CASE_TEMPLATE("контракт IUserRepository", Repo,
                   InMemoryUserRepository, JsonFileUserRepository, SqliteUserRepository) {
    auto repo = Factory<Repo>::make();
    // ... ті самі SUBCASE
}
```

Для SQLite фабрика створює базу в пам'яті (`":memory:"`): вона не залишає файлів і працює швидко.

## Потокобезпечність

Багатопоточний Crow викликає репозиторій із різних потоків. Ця реалізація використовує одне з'єднання й захищає його `std::mutex`: кожен метод блокує мютекс на час запиту. Це просто й надійно, але запити до бази виконуються по черзі. Для більшого навантаження використовують пул з'єднань або кілька з'єднань на читання. Для навчальних і невеликих застосунків достатньо одного.

## Запитання

::::accordion

:::accordion-item{label="❓ Чому не просто зберігати все в JSON-файлі?" icon="i-lucide-help-circle"}

Файл потрібно читати й записувати цілком, пошук потребує перебору, а паралельний запис із двох процесів може зіпсувати його. База індексує дані, змінює окремі рядки, перевіряє обмеження й гарантує цілісність за допомогою транзакцій.

:::

:::accordion-item{label="❓ Чи достатньо екранувати лапки у значенні замість bind?" icon="i-lucide-help-circle"}

Ні. Ручне екранування легко зробити неповним (різні кодування, коментарі `--`, інші діалекти SQL). Підготовлений запит розв'язує проблему структурно: значення й запит не змішуються взагалі.

:::

:::accordion-item{label="❓ Що таке індекс і чи він потрібен тут?" icon="i-lucide-help-circle"}

Індекс — допоміжна структура, яка прискорює пошук за стовпцем. Обмеження `UNIQUE` на `email` вже створює індекс, тому `find_by_email` не перебирає всю таблицю. Для інших частих умов `WHERE` індекс створюють командою `CREATE INDEX`.

:::

:::accordion-item{label="❓ Чому тестова база в пам'яті, а не файл?" icon="i-lucide-help-circle"}

База `:memory:` створюється порожньою для кожного тесту й зникає разом з ним. Тести не залишають файлів, не впливають одне на одного й працюють швидко.

:::

:::accordion-item{label="📋 Завдання 1: метод find_by_age_range" icon="i-lucide-clipboard-list"}

Додайте до інтерфейсу `find_by_age_range(int from, int to)` (із завдання лекції 14) і реалізуйте його в SQLite через `WHERE age BETWEEN ? AND ?`. Додайте до контрактних тестів.

:::accordion-item{label="✅ Підказка до завдання 1" icon="i-lucide-check-circle"}

```cpp
std::vector<User> find_by_age_range(int from, int to) const override {
    std::lock_guard<std::mutex> lock(mutex_);
    sqlite::Statement st(db_,
        "SELECT id, name, email, age FROM users WHERE age BETWEEN ? AND ? ORDER BY age");
    st.bind(1, from).bind(2, to);
    std::vector<User> result;
    while (st.step()) result.push_back(read_user(st));
    return result;
}
```

Вимоги:

- усі запити підготовлені, жодної конкатенації значень у SQL;
- схема з `NOT NULL`, `UNIQUE` і хоча б одним `CHECK`;
- пакетний імпорт у транзакції з тестом на відкат;
- контрактні тести проходять для всіх трьох реалізацій;
- вибір реалізації через аргумент командного рядка в `main`;
- тест, що демонструє, чому конкатенація небезпечна (як у лекції).

## Підсумок

- SQLite — вбудована реляційна база в одному файлі: не потребує сервера. Мова запитів — SQL, а C API обгортають в RAII-класи.
- Значення з зовнішніх джерел передаються лише через `bind` у підготовлених запитах; конкатенація відкриває шлях для SQL-ін'єкції, що тест доводить на двох записах.
- Обмеження бази (`UNIQUE`, `CHECK`, `NOT NULL`) діють як остання лінія захисту поряд із перевірками сервісу. Транзакція гарантує «все або нічого».
- Нова реалізація `IUserRepository` підключається в `main`, а сервіс, HTTP-шар і контрактні тести лишаються тими самими.
