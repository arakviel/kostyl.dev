# Реалізація простої бізнес-логіки

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Пояснювати, чому бізнес-логіка — найважливіша частина програми.
- Реалізовувати патерн **Transaction Script** так, щоб кожна операція була транзакційною.
- Розпізнавати три типові помилки, що псують дані: відсутня транзакція, розподілена транзакція, неявна розподілена транзакція.
- Застосовувати ідемпотентність та оптимістичне керування паралелізмом.
- Використовувати патерн **Active Record** для складних структур даних.
- Розуміти межі обох патернів і чому їх не застосовують для основних піддоменів.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Бізнес-логіка (*business logic*):** правила й процеси, заради яких створюють програму.
- **Transaction Script:** патерн, що організовує логіку у вигляді процедур, по одній на операцію.
- **Транзакційна поведінка:** операція або виконується повністю, або не виконується.
- **Ідемпотентність (*idempotency*):** повторне виконання не змінює результату.
- **Оптимістичне керування паралелізмом:** оновлення виконується лише якщо значення не змінилося.
- **Active Record:** об'єкт, що містить дані рядка таблиці та методи доступу до сховища.
- **CRUD:** створення, читання, оновлення й видалення.
- **ETL:** отримання, перетворення й завантаження даних.

::

## Чому бізнес-логіка важлива

Бізнес-логіка — найважливіша частина програмного забезпечення. Саме заради неї програму взагалі створюють. Інтерфейс користувача може бути привабливим, а база даних — блискавичною й масштабованою. Але якщо програма не корисна для бізнесу, це лише дорога технологічна демонстрація.

![Інтерфейс і база без корисної бізнес-логіки — лише технологічна демонстрація](/images/ddd/simple-business-logic/implementing-simple-business-logic/01-business-logic-matters.png){.diagram-img}

Як ми бачили в темі про аналіз предметної області, піддомени не рівні: вони мають різну стратегічну важливість і складність. У цій темі починається огляд способів моделювання й реалізації бізнес-логіки в коді. Спершу розглянемо два патерни для **досить простої** логіки: Transaction Script і Active Record.

![Тип піддомену підказує патерн реалізації](/images/ddd/simple-business-logic/implementing-simple-business-logic/02-pick-pattern.png){.diagram-img}

## Transaction Script

::note
**Transaction Script** «організовує бізнес-логіку у вигляді процедур, кожна з яких обробляє один запит від рівня подання» (Мартін Фаулер, *Patterns of Enterprise Application Architecture*, 2002).

::

Публічний інтерфейс системи можна розглядати як набір **бізнес-транзакцій**, які можуть виконувати споживачі. Ці транзакції можуть отримувати інформацію, якою керує система, змінювати її або робити і те, і те. Патерн організовує бізнес-логіку за **процедурами**: кожна процедура реалізує операцію, яку споживач виконує через публічний інтерфейс системи. По суті, публічні операції системи стають межами інкапсуляції.

![Transaction script: публічні операції як процедури](/images/ddd/simple-business-logic/implementing-simple-business-logic/03-ts-interface.png){.diagram-img}

### Реалізація

Кожна процедура реалізується як простий, прямолінійний процедурний скрипт. Вона може використовувати тонкий шар абстракції для роботи зі сховищем, але може й звертатися до бази даних безпосередньо.

![Кожна процедура — простий скрипт з транзакційною поведінкою](/images/ddd/simple-business-logic/implementing-simple-business-logic/04-ts-impl.png){.diagram-img}

Єдина вимога до процедур — **транзакційна поведінка**. Кожна операція має або завершитися успішно, або зазнати невдачі, але ніколи не залишити систему в некоректному стані. Навіть якщо виконання скрипта обірветься у найнезручніший момент, система має лишитися узгодженою: або відкотивши всі зміни, зроблені до збою, або виконавши компенсувальні дії. Транзакційність відображено в назві патерна: *transaction script*.

Ось приклад скрипта, що перетворює пакети JSON-файлів у XML-файли:

```csharp
DB.StartTransaction();
var job = DB.LoadNextJob();
var json = LoadFile(job.Source);
var xml = ConvertJsonToXml(json);
WriteFile(job.Destination, xml.ToString());
DB.MarkJobAsCompleted(job);
DB.Commit();
```

![Приклад transaction script: перетворення JSON у XML](/images/ddd/simple-business-logic/implementing-simple-business-logic/05-ts-example.png){.diagram-img}

Рядки коду розбираються так. `StartTransaction()` відкриває транзакцію. Далі скрипт завантажує наступне завдання, читає вхідний файл, перетворює його, записує результат і позначає завдання виконаним. `Commit()` підтверджує всі зміни разом. Якщо щось піде не так до підтвердження, зміни в базі не набудуть чинності.

### Усе не так просто!

Коли автор книги пояснює цей патерн на курсах із DDD, студенти часто питають: «Чи варто на це витрачати час? Хіба ми тут не заради складніших патернів?». Річ у тім, що transaction script — **фундамент** для складніших патернів реалізації бізнес-логіки, які йтимуть далі. До того ж, попри очевидну простоту, цей патерн — **найлегше зробити неправильно**. Значна кількість проблем у продакшні, які автор допомагав налагоджувати, так чи інакше зводилася до неправильної реалізації транзакційної поведінки бізнес-логіки.

![Простота transaction script обманлива](/images/ddd/simple-business-logic/implementing-simple-business-logic/06-not-easy.png){.diagram-img}

Розглянемо три типові приклади пошкодження даних через неправильну реалізацію transaction script.

#### Відсутність транзакційної поведінки

Тривіальний приклад: кілька оновлень без охопної транзакції. Метод оновлює запис у таблиці `Users` і додає запис у таблицю `VisitsLog`:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId, DateTime visitedOn)
    {
        _db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",
                    visitedOn, userId);
        _db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date)
                      VALUES(@p1, @p2)", userId, visitedOn);
    }
}
```

Якщо проблема виникне після оновлення запису в `Users`, але до успішного додавання запису в журнал, система опиниться в **неузгодженому стані**: таблицю користувачів оновлено, а відповідного запису у `VisitsLog` немає. Причиною може бути що завгодно: збій мережі, тайм-аут бази, взаємне блокування або навіть падіння сервера, що виконує процес.

![Збій між двома оновленнями лишає дані неузгодженими](/images/ddd/simple-business-logic/implementing-simple-business-logic/07-no-transaction.png){.diagram-img}

Виправити це можна, ввівши справжню транзакцію, що охоплює обидві зміни:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId, DateTime visitedOn)
    {
        try
        {
            _db.StartTransaction();
            _db.Execute(@"UPDATE Users SET last_visit=@p1
                          WHERE user_id=@p2", visitedOn, userId);
            _db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date)
                          VALUES(@p1, @p2)", userId, visitedOn);
            _db.Commit();
        }
        catch
        {
            _db.Rollback();
            throw;
        }
    }
}
```

![Виправлення: єдина транзакція з відкатом при збої](/images/ddd/simple-business-logic/implementing-simple-business-logic/08-fix-transaction.png){.diagram-img}

Виправлення просте завдяки тому, що реляційні бази даних нативно підтримують транзакції, які охоплюють кілька записів. Складніше стає, коли потрібно виконати кілька оновлень у базі, що не підтримує багатозаписних транзакцій, або коли ви працюєте з кількома сховищами, які неможливо об'єднати в розподілену транзакцію. Розглянемо другий випадок.

#### Розподілені транзакції

У сучасних розподілених системах поширена практика: змінити дані в базі, а потім сповістити інші компоненти системи, опублікувавши повідомлення в шину повідомлень (*message bus*). Припустімо, що в попередньому прикладі замість запису в таблицю ми публікуємо візит у шину:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId, DateTime visitedOn)
    {
        _db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",
                    visitedOn, userId);
        _messageBus.Publish("VISITS_TOPIC",
                            new { UserId = userId, VisitDate = visitedOn });
    }
}
```

Як і раніше, будь-який збій між оновленням бази та успішною публікацією пошкодить стан системи: таблиця `Users` оновлена, а інші компоненти не отримають повідомлення, бо публікація в шину не вдалася.

![База даних оновлена, а повідомлення до шини не дійшло](/images/ddd/simple-business-logic/implementing-simple-business-logic/09-distributed.png){.diagram-img}

На жаль, виправити це не так просто, як у попередньому прикладі. Розподілені транзакції, що охоплюють кілька сховищ, складні, погано масштабуються, схильні до помилок, тому їх зазвичай уникають. У темі про архітектурні патерни ви побачите, як патерн CQRS допомагає наповнювати кілька сховищ. А в темі про патерни взаємодії розглянемо патерн *outbox*, що дозволяє надійно публікувати повідомлення після підтвердження змін в іншій базі.

#### Неявні розподілені транзакції

Розглянемо оманливо простий метод:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId)
    {
        _db.Execute("UPDATE Users SET visits=visits+1 WHERE user_id=@p1",
                    userId);
    }
}
```

Замість дати останнього візиту метод веде **лічильник візитів** для кожного користувача. Кожен виклик збільшує значення на 1. Метод змінює одне значення в одній таблиці в одній базі. Але це все ще розподілена транзакція, яка потенційно може призвести до неузгодженого стану.

Вона розподілена, бо метод передає інформацію і базі даних, і зовнішньому процесу, що його викликав.

![Метод оновлює дані й повідомляє викликача про результат](/images/ddd/simple-business-logic/implementing-simple-business-logic/10-implicit-distributed.png){.diagram-img}

Хоч метод `Execute` має тип `void` і не повертає даних, він усе одно повідомляє, чи операція вдалася: якщо ні, викликач отримає виняток. А що, якщо метод виконався, але передача результату викликачу не вдалася? Наприклад:

- `LogVisit` є частиною REST-сервісу, і сталася мережева аварія;
- `LogVisit` і викликач працюють в одному процесі, але процес завершується, перш ніж викликач встиг зафіксувати успішне виконання.

В обох випадках споживач вирішить, що сталася помилка, і спробує викликати `LogVisit` знову. Повторне виконання логіки неправильно збільшить лічильник: загалом він зросте на **2** замість 1.

![Повторний виклик подвоює приріст лічильника](/images/ddd/simple-business-logic/implementing-simple-business-logic/11-retry-double.png){.diagram-img}

Як і в двох попередніх прикладах, код неправильно реалізує патерн і мимоволі пошкоджує стан системи. Простого виправлення тут немає: усе залежить від бізнес-домену та його потреб. У цьому прикладі один зі способів забезпечити транзакційність — зробити операцію **ідемпотентною**, тобто такою, що веде до того самого результату навіть при кількох повторах.

Наприклад, можна попросити споживача передати значення лічильника. Він має спершу прочитати поточне значення, збільшити його локально й передати оновлене значення параметром. Навіть якщо операція виконається кілька разів, кінцевий результат не зміниться:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId, long visits)
    {
        _db.Execute("UPDATE Users SET visits = @p1 WHERE user_id=@p2",
                    visits, userId);
    }
}
```

![Ідемпотентна операція: значення передає викликач](/images/ddd/simple-business-logic/implementing-simple-business-logic/12-idempotent.png){.diagram-img}

Інший спосіб — **оптимістичне керування паралелізмом**. Перед викликом `LogVisit` викликач читає поточне значення лічильника й передає його як параметр. `LogVisit` оновлює лічильник лише тоді, коли він дорівнює значенню, яке спочатку прочитав викликач:

```csharp
public class LogVisit
{
    // ...
    public void Execute(Guid userId, long expectedVisits)
    {
        _db.Execute(@"UPDATE Users SET visits=visits+1
                      WHERE user_id=@p1 AND visits=@p2",
                    userId, expectedVisits);
    }
}
```

Наступні виклики `LogVisit` з тими самими вхідними параметрами не змінять даних, бо умова `WHERE … visits = @p2` більше не виконується.

![Оптимістичне керування паралелізмом: повтор не змінює даних](/images/ddd/simple-business-logic/implementing-simple-business-logic/13-optimistic.png){.diagram-img}

::tip
Запитайте себе про кожну операцію: що станеться, якщо вона обірветься в будь-якому місці? А що, якщо викликач повторить її? Якщо відповідь «дані зіпсуються», потрібні транзакція, ідемпотентність або оптимістичне керування паралелізмом.

::

### Коли застосовувати Transaction Script

Патерн добре підходить для найпростіших проблемних областей, де бізнес-логіка нагадує прості процедурні операції. Наприклад, в операціях **ETL** (*extract-transform-load*): кожна операція отримує дані з джерела, застосовує логіку перетворення для іншої форми й завантажує результат у сховище призначення.

![ETL: отримання, перетворення, завантаження](/images/ddd/simple-business-logic/implementing-simple-business-logic/14-ts-etl.png){.diagram-img}

Transaction script природно підходить для **допоміжних піддоменів**, де за означенням бізнес-логіка проста. Його також можна використовувати як адаптер для інтеграції із зовнішніми системами, наприклад, універсальними піддоменами, чи як частину запобіжного шару (докладніше в темі про патерни взаємодії).

![Де підходить Transaction Script](/images/ddd/simple-business-logic/implementing-simple-business-logic/15-ts-where.png){.diagram-img}

Головна перевага патерна — **простота**. Він вводить мінімум абстракцій і мінімізує накладні витрати як на швидкодію, так і на розуміння бізнес-логіки. Водночас ця простота — і недолік. Чим складніша логіка, тим більше схильність до **дублювання** бізнес-логіки в різних транзакціях і, як наслідок, до неузгодженої поведінки, коли дубльований код розходиться. Через це Transaction Script **ніколи не слід використовувати для основних піддоменів**: патерн не впорається з високою складністю їхньої бізнес-логіки.

![Переваги й недоліки Transaction Script](/images/ddd/simple-business-logic/implementing-simple-business-logic/16-ts-pros-cons.png){.diagram-img}

Така простота створила патерну сумнівну репутацію. Іноді його навіть вважають антипатерном. Зрештою, якщо складну бізнес-логіку реалізувати як transaction script, то рано чи пізно вона перетвориться на **великий клубок бруду** (*big ball of mud*), який неможливо підтримувати. Але, попри простоту, цей патерн повсюдний у розробці. Усі патерни реалізації бізнес-логіки, які ми розглянемо в цій і наступних темах, так чи інакше ґрунтуються на Transaction Script.

![Складна логіка в скриптах перетворюється на клубок бруду](/images/ddd/simple-business-logic/implementing-simple-business-logic/17-ball-of-mud.png){.diagram-img}

## Active Record

::note
**Active Record** — «об'єкт, що огортає рядок у таблиці чи поданні бази даних, інкапсулює доступ до бази й додає до цих даних доменну логіку» (Мартін Фаулер).

::

Як і Transaction Script, Active Record підтримує випадки простої бізнес-логіки. Але тут логіка може працювати зі **складнішими структурами даних**. Наприклад, замість плоских записів можуть бути складніші дерева об'єктів та ієрархії з відношеннями «один до багатьох» і «багато до багатьох».

![Складніша модель даних із відношеннями один-до-багатьох і багато-до-багатьох](/images/ddd/simple-business-logic/implementing-simple-business-logic/18-active-record-data.png){.diagram-img}

Робота з такими структурами через простий transaction script призвела б до величезної кількості повторюваного коду. Відображення даних на подання в пам'яті дублювалося б усюди.

### Реалізація

Тому цей патерн використовує спеціальні об'єкти, відомі як **active record**, для подання складних структур даних. Окрім самої структури, такі об'єкти реалізують методи доступу до даних для створення, читання, оновлення й видалення записів, тобто **CRUD-операції**. Через це active record-об'єкти прив'язані до об'єктно-реляційного відображення (ORM) або іншого фреймворку доступу до даних. Назва патерна походить від того, що кожна структура даних «активна»: вона реалізує логіку доступу до даних.

Як і в попередньому патерні, бізнес-логіка системи організована як transaction script. Різниця в тому, що замість прямого доступу до бази скрипт маніпулює об'єктами active record. Після завершення операція має виконатися або повністю, або не виконатися як атомарна транзакція:

```csharp
public class CreateUser
{
    // ...
    public void Execute(UserDetails userDetails)
    {
        try
        {
            _db.StartTransaction();
            var user = new User();
            user.Name = userDetails.Name;
            user.Email = userDetails.Email;
            user.Save();
            _db.Commit();
        }
        catch
        {
            _db.Rollback();
            throw;
        }
    }
}
```

![Active record: об'єкт сам зберігається у базу](/images/ddd/simple-business-logic/implementing-simple-business-logic/19-active-record-impl.png){.diagram-img}

Мета патерна — інкапсулювати складність відображення об'єкта в пам'яті на схему бази даних. Крім відповідальності за збереження, active record-об'єкти можуть містити бізнес-логіку: наприклад, валідацію нових значень полів або навіть бізнес-процедури, що змінюють дані об'єкта. Але характерна ознака active record — **розділення структур даних і поведінки** (бізнес-логіки). Зазвичай поля такого об'єкта мають публічні get/set-методи, що дозволяють зовнішнім процедурам змінювати його стан.

![Active record — це transaction script, який працює з об'єктами](/images/ddd/simple-business-logic/implementing-simple-business-logic/20-ar-vs-ts.png){.diagram-img}

![Дані й поведінка в active record розділені](/images/ddd/simple-business-logic/implementing-simple-business-logic/21-ar-data-vs-behavior.png){.diagram-img}

### Коли застосовувати Active Record

Оскільки active record по суті — transaction script, що оптимізує доступ до баз даних, цей патерн підтримує лише відносно просту бізнес-логіку: CRUD-операції, які в крайньому випадку перевіряють введені користувачем дані.

Тому, як і Transaction Script, Active Record підходить для допоміжних піддоменів, інтеграції зовнішніх рішень для універсальних піддоменів або завдань перетворення моделей. Різниця патернів у тому, що Active Record розв'язує складність відображення **складних структур даних** на схему бази.

![Де підходить Active Record](/images/ddd/simple-business-logic/implementing-simple-business-logic/22-ar-where.png){.diagram-img}

Active Record також відомий як антипатерн **анемічної доменної моделі** (*anemic domain model*): тобто неправильно спроєктованої доменної моделі. Автор книги не любить негативного забарвлення слів «анемічний» і «антипатерн». Цей патерн — інструмент. Як і будь-який інструмент, він може розв'язувати проблеми, але може принести більше шкоди, ніж користі, якщо застосувати його в неправильному контексті. У використанні active record при простій бізнес-логіці немає нічого поганого. Більше того, **складніший патерн для простої бізнес-логіки також шкодить**, бо додає випадкову складність. У наступній темі ви дізнаєтеся, що таке доменна модель і чим вона відрізняється від active record.

::warning
У цьому контексті *active record* — це проєктний **патерн**, а не фреймворк Active Record. Патерн запровадив Мартін Фаулер у книзі *Patterns of Enterprise Application Architecture*. Фреймворк з'явився пізніше як один зі способів реалізації патерна. Тут ми говоримо про патерн і його ідеї, а не про конкретну реалізацію.

::

![Патерн Active Record і однойменний фреймворк — різні речі](/images/ddd/simple-business-logic/implementing-simple-business-logic/23-pattern-vs-framework.png){.diagram-img}

## Приклад: книгарня від скрипта до Active Record

Розгляньмо невелику інтернет-книгарню. Клієнт оформлює замовлення, оплачує його, а ми нараховуємо бонуси: 1 бал за кожні 10 грн. Знижка — 10% від 1000 грн. Покажемо типовий «поганий» скрипт, виправимо його, а потім перенесемо логіку в active record.

### До: скрипт, який «працює»

```csharp
public static class OrderScripts
{
    public static void Pay(Db db, int orderId)
    {
        var order = db.Orders.First(o => o.Id == orderId);
        order.Status = "Payed";                      // (1)
        var customer = db.Customers.First(c => c.Id == order.CustomerId);
        customer.BonusPoints += (int)(order.Total / 10);
        db.SaveChanges();
    }

    public static void Ship(Db db, int orderId)
    {
        var order = db.Orders.First(o => o.Id == orderId);
        if (order.Status == "Paid")                  // (2)
            order.Status = "Shipped";
        db.SaveChanges();
    }
}
```

Тут одразу кілька проблем:

- **Статус — рядок.** У `Pay` помилково записано `"Payed"`, а `Ship` перевіряє `"Paid"`. Компілятор мовчить, а жодне замовлення ніколи не буде відправлене.
- **Немає перевірки стану в `Pay`.** Повторний виклик (наприклад, клієнт двічі натиснув кнопку) нарахує бонуси вдруге: операція не ідемпотентна.
- **Немає транзакції.** Якщо збій станеться між зміною замовлення й нарахуванням балів, дані розійдуться.
- **Правила розмазані.** Розрахунок знижки з'явиться ще в одному скрипті, потім у третьому, і незабаром вони розбіжаться.

### Після: той самий скрипт, але правильний

```csharp
public enum OrderStatus { New, Paid, Shipped, Cancelled }

public static void Pay(Db db, int orderId)
{
    using var tx = db.BeginTransaction();            // уся операція або вся, або жодної
    var order = db.Orders.First(o => o.Id == orderId);

    if (order.Status != OrderStatus.New)             // повторний виклик не нараховує бонуси вдруге
        throw new InvalidOperationException("Оплатити можна лише нове замовлення");

    order.Status = OrderStatus.Paid;
    var customer = db.Customers.First(c => c.Id == order.CustomerId);
    customer.BonusPoints += (int)(order.Total / 10);

    db.SaveChanges();
    tx.Commit();
}
```

Що саме виправлено:

| Було | Стало | Навіщо |
|---|---|---|
| `"Payed"` / `"Paid"` | `enum OrderStatus` | Помилку у назві ловить компілятор |
| Немає перевірки статусу | Guard на початку | Операція безпечна до повтору |
| Дві зміни без транзакції | `BeginTransaction` / `Commit` | Дані не розходяться після збою |

### Active Record: те саме, але з об'єктами

Коли таблиць і зв'язків побільшало, ті самі скрипти починають повторювати код читання й збереження. Тоді дані загортають в active record, а скрипт працює з об'єктами:

```csharp
public class Order
{
    public int Id { get; private set; }
    public int CustomerId { get; private set; }
    public OrderStatus Status { get; private set; } = OrderStatus.New;
    public decimal Total { get; private set; }

    public static Order Find(int id) { /* читання з бази */ }
    public void Save() { /* запис у базу */ }

    public void Pay()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException("Оплатити можна лише нове замовлення");
        Status = OrderStatus.Paid;
        Save();

        var customer = Customer.Find(CustomerId);
        customer.AddBonus((int)(Total / 10));
        customer.Save();
    }
}
```

Виклик став читабельним: `Order.Find(id).Pay()`. Але зверніть увагу на ціну. Об'єкт залежить від сховища, бо знає, як себе зберігати. Правила знижки й бонусів лишаються в методах `Order` і `Customer`, а `decimal` досі означає і гроші, і кількість. Для допоміжного піддомену цього достатньо. Для основного піддомену така модель швидко стане тісною, і в наступній темі ми побачимо, як її розвинути в доменну модель.

## Будьте прагматичні

Хоч бізнес-дані важливі, а код, який ми проєктуємо й будуємо, має захищати їхню цілісність, бувають випадки, де доречніший прагматичний підхід. Особливо на високих масштабах гарантії узгодженості даних можна послабити. Перевірте, чи справді пошкодження стану одного запису з мільйона є критичним для бізнесу й чи може воно негативно вплинути на продуктивність і прибутковість.

Припустімо, ви будуєте систему, що приймає мільярди подій на добу від IoT-пристроїв. Чи так страшно, якщо 0,001% подій буде продубльовано або втрачено?

![Прагматизм: чи критичні 0,001% втрат для бізнесу](/images/ddd/simple-business-logic/implementing-simple-business-logic/24-pragmatic.png){.diagram-img}

Як завжди, універсальних законів немає. Усе залежить від бізнес-домену, у якому ви працюєте. Дозволено «зрізати кути», де це можливо; потрібно лише оцінити ризики й наслідки для бізнесу.

## Підсумки

У цій темі розглянуто два патерни реалізації бізнес-логіки:

| Патерн | Суть |
| --- | --- |
| **Transaction Script** | Операції системи організовані як прості процедурні скрипти. Кожна операція транзакційна: або виконується, або ні. Підходить для допоміжних піддоменів із простою, схожою на ETL логікою |
| **Active Record** | Коли логіка проста, але працює зі складними структурами даних, їх реалізують як active record: структура даних із простими методами CRUD-доступу |

![Підсумок: два патерни для простої бізнес-логіки](/images/ddd/simple-business-logic/implementing-simple-business-logic/25-summary.png){.diagram-img}

Обидва патерни орієнтовані на випадки досить простої бізнес-логіки. У наступній темі ми перейдемо до складнішої логіки й розглянемо патерн доменної моделі (*domain model*).

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Який патерн слід використовувати для основного піддомену?" icon="i-lucide-help-circle"}

Варіанти: А) Transaction Script; Б) Active Record; В) жоден із цих патернів; Г) обидва.

**Відповідь: В.** Обидва патерни призначені для простої бізнес-логіки, а основні піддомени мають складнішу.

:::

:::accordion-item{label="📋 Питання 2. Які проблеми узгодженості даних є в цьому коді?" icon="i-lucide-clipboard-list"}

Припустімо, що транзакційного механізму високого рівня немає:

```csharp
public void CreateTicket(TicketData data)
{
    var agent = FindLeastBusyAgent();
    agent.ActiveTickets = agent.ActiveTickets + 1;
    agent.Save();
    var ticket = new Ticket();
    ticket.Id = Guid.New();
    ticket.Data = data;
    ticket.AssignedAgent = agent;
    ticket.Save();
    _alerts.Send(agent, "You have a new ticket!");
}
```

Варіанти: А) лічильник активних заявок агента може зрости більше ніж на 1; Б) лічильник зросте на 1, але нових заявок агенту не призначать; В) агент отримає заявку, але не отримає сповіщення; Г) усе вищеперелічене.

:::

:::accordion-item{label="✅ Відповіді до питань 2 і 3" icon="i-lucide-check-circle"}

**Питання 2: Г.** Можливі всі проблеми:

- Якщо виконання обірветься після оновлення лічильника агента, викликач повторить операцію, і той самий агент буде обраний `FindLeastBusyAgent`, лічильник `ActiveTickets` збільшиться більше ніж на 1.
- Якщо виконання обірветься після оновлення лічильника, а викликач не повторить операцію, лічильник зросте, а заявку не буде створено.
- Якщо виконання обірветься після збереження заявки, заявка створена й призначена, але сповіщення не буде надіслано.

**Питання 3.** Є ще один крайній випадок: якщо виконання обірветься після збереження заявки, викликач повторить операцію, і вона вдасться, то та сама заявка буде збережена й призначена двічі.
