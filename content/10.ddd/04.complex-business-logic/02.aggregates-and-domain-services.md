# Агрегати, доменні події та доменні сервіси

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Проєктувати агрегат як межу узгодженості та транзакції.
- Виражати зміни стану через команди й обробляти паралельні оновлення (версія агрегата).
- Визначати межі агрегата за критерієм сильної узгодженості та посилатися на інші агрегати за ідентифікатором.
- Використовувати доменні події для зв'язку з зовнішнім світом.
- Застосовувати доменні сервіси для логіки, що не належить жодному агрегату.
- Пояснювати, як доменна модель зменшує складність через інкапсуляцію інваріантів.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Агрегат (*aggregate*):** ієрархія сутностей зі спільною межею транзакції.
- **Корінь агрегата (*aggregate root*):** єдина сутність, через яку змінюють агрегат.
- **Команда (*command*):** публічний метод агрегата, що змінює стан.
- **Доменна подія (*domain event*):** повідомлення про значущу подію в домені.
- **Доменний сервіс (*domain service*):** безстановий об'єкт із бізнес-логікою.
- **Ступені свободи (*degrees of freedom*):** кількість даних, потрібних для опису стану системи.

::

## Агрегати

Попередня стаття описала об'єкти-значення й сутності. Тепер розглянемо головний будівельний блок доменної моделі — **агрегат**.

**Агрегат** — це сутність: потрібне явне поле ідентифікації, а стан має змінюватися протягом життєвого циклу екземпляра. Але він — набагато більше, ніж проста сутність. Мета патерна — захищати **узгодженість** своїх даних. Оскільки дані агрегата змінні, патерн має розв'язувати наслідки й виклики, щоб стан залишався узгодженим завжди.

![Агрегат: корінь, сутності й об'єкти-значення в одній межі](/images/ddd/complex-business-logic/aggregates-and-domain-services/01-aggregate-overview.png){.diagram-img}

### Забезпечення узгодженості

Оскільки стан агрегата можна змінювати, виникає багато способів пошкодити його дані. Щоб забезпечити узгодженість, патерн проводить чітку межу між агрегатом і зовнішнім світом: агрегат — **межа застосування узгодженості**. Логіка агрегата має перевіряти всі вхідні зміни й гарантувати, що вони не суперечать його бізнес-правилам.

З погляду реалізації узгодженість забезпечується тим, що змінювати стан може **лише власна бізнес-логіка** агрегата. Усі процеси й об'єкти поза агрегатом можуть тільки читати його стан. Змінити його можна лише виконанням відповідних методів публічного інтерфейсу.

![Агрегат — межа узгодженості: ззовні лише команди](/images/ddd/complex-business-logic/aggregates-and-domain-services/02-consistency-boundary.png){.diagram-img}

Методи публічного інтерфейсу, що змінюють стан, часто називають **командами** (*commands*): «команда щось зробити». Команду можна реалізувати двома способами. По-перше, як звичайний публічний метод агрегата:

```csharp
public class Ticket
{
    // ...
    public void AddMessage(UserId from, string body)
    {
        var message = new Message(from, body);
        _messages.Append(message);
    }
    // ...
}
```

Або ж команду можна подати як **об'єкт-параметр**, що інкапсулює всі вхідні дані для виконання команди:

```csharp
public class Ticket
{
    // ...
    public void Execute(AddMessage cmd)
    {
        var message = new Message(cmd.from, cmd.body);
        _messages.Append(message);
    }
    // ...
}
```

Як виражати команди в коді — питання смаку. Автор віддає перевагу явнішому способу: визначати структури команд і передавати їх поліморфно відповідному методу `Execute`.

![Два способи виразити команду](/images/ddd/complex-business-logic/aggregates-and-domain-services/04-command-forms.png){.diagram-img}

![Стан змінюють лише команди: дозволені й заборонені дії](/images/ddd/complex-business-logic/aggregates-and-domain-services/03-commands.png){.diagram-img}

Публічний інтерфейс агрегата відповідає за перевірку вхідних даних і дотримання всіх відповідних бізнес-правил та інваріантів. Ця сувора межа гарантує, що вся пов'язана з агрегатом бізнес-логіка реалізована в одному місці: самому агрегаті.

Через це **прикладний шар** (*application layer*), що оркеструє операції над агрегатами, стає досить простим: усе, що він робить, — завантажує поточний стан агрегата, виконує потрібну дію, зберігає змінений стан і повертає результат операції викликачу:

```csharp
public ExecutionResult Escalate(TicketId id, EscalationReason reason)
{
    try
    {
        var ticket = _ticketRepository.Load(id);
        var cmd = new Escalate(reason);
        ticket.Execute(cmd);
        _ticketRepository.Save(ticket);
        return ExecutionResult.Success();
    }
    catch (ConcurrencyException ex)
    {
        return ExecutionResult.Error(ex);
    }
}
```

![Прикладний шар: завантажити, виконати, зберегти, повернути](/images/ddd/complex-business-logic/aggregates-and-domain-services/05-application-layer.png){.diagram-img}

Зверніть увагу на перевірку паралелізму (`ConcurrencyException`). Вона життєво важлива для захисту узгодженості стану агрегата. Якщо кілька процесів одночасно оновлюють той самий агрегат, потрібно не дати пізнішій транзакції сліпо перезаписати зміни першої. У такому разі другий процес треба повідомити, що стан, на якому він ґрунтував свої рішення, застарів, і він має повторити операцію.

Тому база, що зберігає агрегати, мусить підтримувати керування паралелізмом. У найпростішій формі агрегат має мати поле **версії**, що збільшується після кожного оновлення:

```csharp
class Ticket
{
    TicketId _id;
    int _version;
    // ...
}
```

При збереженні змін у базу треба переконатися, що версія, яку перезаписуємо, збігається з тією, що була прочитана спочатку. Наприклад, у SQL:

```sql
UPDATE tickets
SET ticket_status = @new_status,
    agg_version = agg_version + 1
WHERE ticket_id = @id AND agg_version = @expected_version;
```

Цей оператор застосовує зміни стану агрегата, збільшує лічильник версії, але лише якщо поточна версія дорівнює тій, що була прочитана до змін.

![Керування паралелізмом через версію агрегата](/images/ddd/complex-business-logic/aggregates-and-domain-services/06-version-field.png){.diagram-img}

![Два процеси оновлюють агрегат: другий отримує ConcurrencyException](/images/ddd/complex-business-logic/aggregates-and-domain-services/07-concurrency-flow.png){.diagram-img}

Керування паралелізмом можна реалізувати й не в реляційній базі. Документні бази взагалі природніше працюють з агрегатами. Головне — переконатися, що база, де зберігаються дані агрегата, підтримує керування паралелізмом.

### Межа транзакції

Оскільки стан агрегата змінює лише його власна бізнес-логіка, агрегат також є **межею транзакції**. Усі зміни стану агрегата підтверджуються транзакційно як одна атомарна операція: або всі зміни зберігаються, або жодна. Більше того, жодна операція системи не може припускати транзакції на кілька агрегатів. Зміни стану агрегата підтверджуються окремо: **один агрегат на одну транзакцію бази**.

Вимога «один екземпляр агрегата на транзакцію» змушує обережно проєктувати межі агрегата, щоб дизайн відповідав інваріантам і правилам домену. Потреба підтверджувати зміни в кількох агрегатах — сигнал неправильної межі транзакції, а отже, неправильних меж агрегатів.

![Один агрегат на одну транзакцію](/images/ddd/complex-business-logic/aggregates-and-domain-services/08-transaction-boundary.png){.diagram-img}

![Потреба змінити два агрегати разом — сигнал хибних меж](/images/ddd/complex-business-logic/aggregates-and-domain-services/09-wrong-boundary.png){.diagram-img}

Це здається обмеженням моделювання. А що, якщо потрібно змінити кілька об'єктів в одній транзакції? Подивімося, як патерн вирішує таку ситуацію.

### Ієрархія сутностей

Ми не використовуємо сутності як самостійний патерн, а лише як частину агрегата. Розгляньмо принципову різницю між сутностями й агрегатами та чому сутності — будівельний блок агрегата, а не всієї доменної моделі.

Існують бізнес-сценарії, у яких кілька об'єктів мають ділити межу транзакції: наприклад, коли їх можна змінювати одночасно або коли бізнес-правила одного об'єкта залежать від стану іншого. DDD вимагає, щоб дизайн системи визначався її бізнес-доменом, і агрегати не виняток. Щоб підтримати зміни кількох об'єктів в одній атомарній транзакції, патерн агрегат нагадує **ієрархію сутностей**, що ділять транзакційну узгодженість.

![Агрегат як ієрархія сутностей із об'єктів-значень](/images/ddd/complex-business-logic/aggregates-and-domain-services/10-hierarchy.png){.diagram-img}

Ієрархія містить і сутності, і об'єкти-значення. Усі вони належать одному агрегату, якщо пов'язані бізнес-логікою домену. Тому патерн так і називається «агрегат»: він **агрегує** бізнес-сутності й об'єкти-значення, що належать одній межі транзакції.

Приклад коду демонструє бізнес-правило, що охоплює кілька сутностей у межах агрегата: «Якщо агент не відкрив ескальовану заявку протягом 50% ліміту часу відповіді, вона автоматично перепризначається іншому агентові»:

```csharp
public class Ticket
{
    // ...
    List<Message> _messages;
    // ...

    public void Execute(EvaluateAutomaticActions cmd)
    {
        if (this.IsEscalated && this.RemainingTimePercentage < 0.5 &&
            GetUnreadMessagesCount(for: AssignedAgent) > 0)
        {
            _agent = AssignNewAgent();
        }
    }

    public int GetUnreadMessagesCount(UserId id)
    {
        return _messages.Where(x => x.To == id && !x.WasRead).Count();
    }
    // ...
}
```

Метод перевіряє значення заявки: чи вона ескальована й чи залишок часу менший за поріг 50%. Також перевіряє, чи є повідомлення, які поточний агент не прочитав. Якщо всі умови виконано, заявку призначають іншому агенту. Агрегат гарантує, що всі умови перевіряються за **суворо узгодженими** даними, і вони не зміняться після перевірки, бо всі зміни даних агрегата виконуються як одна атомарна транзакція.

![Правило, що охоплює кілька сутностей одного агрегата](/images/ddd/complex-business-logic/aggregates-and-domain-services/11-rule-across-entities.png){.diagram-img}

### Посилання на інші агрегати

Оскільки всі об'єкти агрегата ділять одну межу транзакції, при надто великому агрегаті виникають проблеми з продуктивністю та масштабованістю. Зручним орієнтиром для проєктування меж є **узгодженість даних**. До агрегата має входити лише та інформація, що за бізнес-логікою потребує **строгої** узгодженості. Усе, що може бути **остаточно** узгодженим, має бути поза межею агрегата: наприклад, у складі іншого агрегата.

Практичне правило: тримайте агрегати **якомога меншими** й включайте лише об'єкти, яким бізнес-логіка агрегата потребує строго узгодженого стану:

```csharp
public class Ticket
{
    private UserId _customer;
    private List<ProductId> _products;
    private UserId _assignedAgent;
    private List<Message> _messages;
    // ...
}
```

У цьому прикладі агрегат `Ticket` посилається на колекцію повідомлень, що належать його межі. Натомість клієнт, колекція продуктів заявки й призначений агент до агрегата не належать, тому на них посилаються **за ідентифікатором**.

![Усередині агрегата — повідомлення; зовнішні агрегати — за ідентифікатором](/images/ddd/complex-business-logic/aggregates-and-domain-services/12-small-aggregates.png){.diagram-img}

Причина посилання на зовнішні агрегати за ID — підкреслити, що ці об'єкти не належать межі агрегата, і гарантувати, що кожен агрегат має власну межу транзакції.

Щоб вирішити, чи належить сутність до агрегата, перевірте, чи є в агрегаті бізнес-логіка, що може призвести до неправильного стану системи, працюючи з остаточно узгодженими даними. Повернімося до прикладу перепризначення заявки, якщо агент не прочитав нові повідомлення протягом 50% ліміту. А якщо інформація про прочитані/непрочитані повідомлення була б остаточно узгодженою, тобто підтвердження прочитання приходило б із затримкою? Тоді значна кількість заявок була б перепризначена без потреби. Це, звісно, зіпсувало б стан системи. Тому дані повідомлень належать межі агрегата.

![Критерій меж агрегата: потрібна сильна узгодженість чи достатня остаточна](/images/ddd/complex-business-logic/aggregates-and-domain-services/13-consistency-guide.png){.diagram-img}

### Корінь агрегата

Ми бачили, що стан агрегата можна змінити, лише виконавши одну з його команд. Оскільки агрегат — ієрархія сутностей, лише **одна з них** має бути призначена публічним інтерфейсом: це **корінь агрегата** (*aggregate root*).

Розглянемо уривок агрегата `Ticket`:

```csharp
public class Ticket
{
    // ...
    List<Message> _messages;
    // ...

    public void Execute(AcknowledgeMessage cmd)
    {
        var message = _messages.Where(x => x.Id == cmd.id).First();
        message.WasRead = true;
    }
    // ...
}
```

У цьому прикладі агрегат відкриває команду, що дозволяє позначити певне повідомлення прочитаним. Хоч операція змінює екземпляр сутності `Message`, він доступний лише через свій корінь: `Ticket`.

![Корінь агрегата — єдиний шлях до внутрішніх сутностей](/images/ddd/complex-business-logic/aggregates-and-domain-services/14-aggregate-root.png){.diagram-img}

Окрім публічного інтерфейсу кореня, є ще один механізм взаємодії зовнішнього світу з агрегатами: **доменні події**.

### Доменні події

**Доменна подія** (*domain event*) — це повідомлення, що описує значущу подію, яка сталася в бізнес-домені. Наприклад:

- заявку призначено (*Ticket assigned*);
- заявку ескальовано (*Ticket escalated*);
- повідомлення отримано (*Message received*).

Оскільки доменні події описують те, що **вже сталося**, їхні назви слід формулювати **в минулому часі**.

![Доменні події: назви в минулому часі](/images/ddd/complex-business-logic/aggregates-and-domain-services/15-domain-events.png){.diagram-img}

Мета події — описати, що сталося в бізнес-домені, і надати всі необхідні пов'язані дані. Наприклад, ця доменна подія повідомляє, що конкретну заявку ескальовано, коли й чому:

```json
{
  "ticket-id": "c9d286ff-3bca-4f57-94d4-4d4e490867d1",
  "event-id": 146,
  "event-type": "ticket-escalated",
  "escalation-reason": "missed-sla",
  "escalation-time": 1628970815
}
```

Як майже у всьому в програмній інженерії, **іменування** важливе: переконайтеся, що назви доменних подій стисло відображають те, що саме сталося.

![Приклад доменної події у форматі JSON](/images/ddd/complex-business-logic/aggregates-and-domain-services/16-event-json.png){.diagram-img}

Доменні події — частина публічного інтерфейсу агрегата. Агрегат публікує свої доменні події. Інші процеси, агрегати чи навіть зовнішні системи можуть підписатися на них і виконувати власну логіку у відповідь.

![Потік публікації доменних подій](/images/ddd/complex-business-logic/aggregates-and-domain-services/17-event-flow.png){.diagram-img}

У наступному уривку з агрегата `Ticket` створюється нова доменна подія й додається до колекції доменних подій заявки:

```csharp
public class Ticket
{
    // ...
    private List<DomainEvent> _domainEvents;
    // ...

    public void Execute(RequestEscalation cmd)
    {
        if (!this.IsEscalated && this.RemainingTimePercentage <= 0)
        {
            this.IsEscalated = true;
            var escalatedEvent = new TicketEscalated(_id, cmd.Reason);
            _domainEvents.Append(escalatedEvent);
        }
    }
    // ...
}
```

У темі про патерни взаємодії розглянемо, як надійно публікувати доменні події зацікавленим підписникам.

### Єдина мова

Нарешті, агрегати мають відображати **єдину мову**. Термінологія, що використовується для назви агрегата, його полів, дій і доменних подій, має бути сформульована єдиною мовою обмеженого контексту. Як казав Ерік Еванс, код має базуватися на тій самій мові, якою розробники спілкуються між собою й з експертами предметної області. Це особливо важливо для реалізації складної бізнес-логіки.

## Доменні сервіси

Рано чи пізно ви можете натрапити на бізнес-логіку, яка не належить жодному агрегату чи об'єкту-значенню або здається важливою для кількох агрегатів. DDD пропонує реалізувати таку логіку як **доменний сервіс** (*domain service*).

Доменний сервіс — це **безстановий об'єкт**, що реалізує бізнес-логіку. У переважній більшості випадків така логіка оркеструє виклики різних компонентів системи для виконання певного обчислення чи аналізу.

Повернімося до прикладу агрегата заявки. Призначений агент має обмежений час, щоб запропонувати рішення клієнту. Цей час залежить не лише від даних заявки (пріоритету й статусу ескалації), а й від політики відділу агента щодо SLA для кожного пріоритету та від робочого графіка агента (змін): не можна очікувати відповіді в неробочі години.

Логіці розрахунку часу відповіді потрібна інформація з кількох джерел: заявка, відділ призначеного агента та розклад роботи. Це ідеальний кандидат на доменний сервіс:

```csharp
public class ResponseTimeFrameCalculationService
{
    // ...
    public ResponseTimeframe CalculateAgentResponseDeadline(
        UserId agentId, Priority priority, bool escalated, DateTime startTime)
    {
        var policy = _departmentRepository.GetDepartmentPolicy(agentId);
        var maxProcTime = policy.GetMaxResponseTimeFor(priority);
        if (escalated)
        {
            maxProcTime = maxProcTime * policy.EscalationFactor;
        }
        var shifts = _departmentRepository.GetUpcomingShifts(
            agentId, startTime, startTime.Add(policy.MaxAgentResponseTime));
        return CalculateTargetTime(maxProcTime, shifts);
    }
    // ...
}
```

![Доменний сервіс збирає дані кількох джерел для розрахунку](/images/ddd/complex-business-logic/aggregates-and-domain-services/19-domain-service.png){.diagram-img}

Доменні сервіси спрощують координацію роботи кількох агрегатів. Але завжди пам'ятайте про обмеження патерна агрегат: **змінювати лише один екземпляр агрегата в одній транзакції бази**. Доменні сервіси — не лазівка в цьому обмеженні. Правило «один екземпляр на транзакцію» діє й тут. Натомість доменні сервіси добре підходять для обчислювальної логіки, що потребує читання даних кількох агрегатів.

Важливо також наголосити: доменні сервіси не мають жодного стосунку до мікросервісів, сервісно-орієнтованої архітектури та майже будь-якого іншого вжитку слова «сервіс» у програмній інженерії. Це лише об'єкт без стану, що містить бізнес-логіку.

![Доменний сервіс: читає, обчислює, але не змінює кілька агрегатів разом](/images/ddd/complex-business-logic/aggregates-and-domain-services/20-service-rules.png){.diagram-img}

## Керування складністю

Як зазначено у вступі, патерни агрегат і об'єкт-значення запровадили як засіб боротьби зі складністю реалізації бізнес-логіки. Розгляньмо логіку цього.

Бізнес-гуру Еліягу Голдрат у книзі *The Choice* дав стислу, але потужну дефініцію складності системи. За Голдратом, оцінюючи складність системи, ми оцінюємо **складність контролю й прогнозування** її поведінки. Ці два аспекти відображаються **ступенями свободи** системи.

Ступені свободи системи — це точки даних, потрібні, щоб описати її стан. Розгляньмо два класи:

```csharp
public class ClassA
{
    public int A { get; set; }
    public int B { get; set; }
    public int C { get; set; }
    public int D { get; set; }
    public int E { get; set; }
}

public class ClassB
{
    private int _a, _d;

    public int A
    {
        get => _a;
        set
        {
            _a = value;
            B = value / 2;
            C = value / 3;
        }
    }
    public int B { get; private set; }
    public int C { get; private set; }

    public int D
    {
        get => _d;
        set
        {
            _d = value;
            E = value * 2;
        }
    }
    public int E { get; private set; }
}
```

На перший погляд здається, що `ClassB` набагато складніший за `ClassA`: змінних стільки ж, але ще й реалізовані додаткові обчислення. Чи він складніший?

Проаналізуємо обидва класи з погляду ступенів свободи. Скільки елементів даних потрібно, щоб описати стан `ClassA`? П'ять: його п'ять змінних. Отже, у `ClassA` **п'ять** ступенів свободи.

Скільки елементів потрібно для опису стану `ClassB`? Дивлячись на логіку присвоєння властивостей `A` і `D`, помітите, що значення `B`, `C`, `E` — функції від `A` і `D`. Якщо відомо `A` і `D`, решту змінних можна вивести. Отже, `ClassB` має лише **два** ступені свободи.

Повертаючись до питання, який клас складніше контролювати й прогнозувати його поведінку? Той, що має більше ступенів свободи, тобто `ClassA`. **Інваріанти**, запроваджені в `ClassB`, зменшують його складність. Саме це роблять патерни агрегат і об'єкт-значення: **інкапсулюють інваріанти** й тим зменшують складність.

![Ступені свободи: ClassA має 5, ClassB лише 2](/images/ddd/complex-business-logic/aggregates-and-domain-services/21-degrees-of-freedom.png){.diagram-img}

Вся бізнес-логіка, пов'язана зі станом об'єкта-значення, розташована в його межах. Те саме стосується агрегатів: агрегат можна змінювати лише його власними методами. Його бізнес-логіка інкапсулює й захищає бізнес-інваріанти, тим самим зменшуючи ступені свободи.

Оскільки патерн доменної моделі застосовують лише для піддоменів зі складною бізнес-логікою, можна припустити, що це **основні піддомени**: серце програмного забезпечення.

![Інкапсуляція інваріантів зменшує складність: для основних піддоменів](/images/ddd/complex-business-logic/aggregates-and-domain-services/22-encapsulate-invariants.png){.diagram-img}

## Приклад: книгарня від відкритого стану до агрегату

На попередньому кроці ми зробили типи значень. Але сама сутність `Order` може лишитися вразливою.

### До: публічний стан, який можна обійти

```csharp
public class Order
{
    public int Id { get; set; }
    public List<OrderLine> Lines { get; } = new();
    public OrderStatus Status { get; set; } = OrderStatus.New;
    public Money Total { get; set; }

    public void Pay()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException("Оплатити можна лише нове замовлення");
        Status = OrderStatus.Paid;
    }

    public void Ship()
    {
        if (Status != OrderStatus.Paid)
            throw new InvalidOperationException("Відправити можна лише оплачене замовлення");
        Status = OrderStatus.Shipped;
    }
}

// Десь в іншому місці програми:
order.Status = OrderStatus.Shipped;   // оплати не було
order.Lines.Clear();                  // лишили замовлення без рядків
order.Total = Money.Uah(1);           // сума більше не відповідає рядкам
```

Правила в `Pay` і `Ship` є, але ніщо не змушує ними користуватися. Будь-хто змінює стан напряму, і інваріанти (відправити можна лише оплачене; сума відповідає рядкам; є хоча б один рядок) перестають діяти. Це і є слабке місце моделі без меж.

### Після: агрегат із єдиною точкою входу

```csharp
public class Order
{
    private readonly List<OrderLine> _lines = new();
    private readonly List<IDomainEvent> _events = new();

    public int Id { get; }
    public int CustomerId { get; }
    public OrderStatus Status { get; private set; } = OrderStatus.New;
    public Money Total { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;

    private Order(int id, int customerId, IEnumerable<OrderLine> lines, Money total) { /* ... */ }

    public static Order Place(int id, int customerId, IEnumerable<OrderLine> lines, Money totalAfterDiscount)
    {
        var list = lines.ToList();
        if (list.Count == 0)
            throw new InvalidOperationException("Кошик порожній");
        if (list.Select(l => l.Isbn).Distinct().Count() != list.Count)
            throw new InvalidOperationException("Одна книга не може бути у двох рядках");

        var order = new Order(id, customerId, list, totalAfterDiscount);
        order._events.Add(new OrderPlaced(id, customerId, totalAfterDiscount));
        return order;
    }

    public void Pay()
    {
        if (Status != OrderStatus.New)
            throw new InvalidOperationException("Оплатити можна лише нове замовлення");
        Status = OrderStatus.Paid;
        _events.Add(new OrderPaid(Id, CustomerId, Total));
    }
}
```

Тепер `order.Status = ...` не скомпілюється, `Lines` доступні лише для читання, а створити замовлення без рядків неможливо. Агрегат гарантує власну узгодженість, а все інше відбувається через його методи.

### Що виходить за межі агрегату

Замовлення не повинно саме змінювати залишки книг і бонуси клієнта: це інші агрегати. Замість спільної транзакції `Order` лише **повідомляє** про факт подією, а реакцію виконує окремий обробник:

```csharp
private void OnEvent(IDomainEvent e)
{
    switch (e)
    {
        case OrderPaid paid:
            var buyer = _customers.Get(paid.CustomerId);
            buyer.Earn(BonusPoints.From(paid.Total));
            _customers.Save(buyer);
            break;
    }
}
```

Правило знижки залежить і від суми замовлення, і від рівня клієнта, тому воно не належить жодному з двох агрегатів. Його виносять у **доменний сервіс**:

```csharp
public class DiscountService
{
    public Money Apply(Money subtotal, Customer customer)
    {
        decimal percent = 0;
        if (subtotal.Amount >= 1000) percent += 10;
        if (customer.Loyalty == Loyalty.Gold) percent += 5;
        return subtotal - subtotal.Percent(percent);
    }
}
```

::tip
У цьому прикладі помилки кидають винятки, щоб не відволікати від ідеї патерна. У реальних C#-проєктах очікувані помилки прийнято повертати через **Result** і створювати об'єкти методом `Create`. Це докладно розібрано в статті «Тактичні патерни DDD у C#».

::

### Підсумок порівняння

| Було | Стало |
|---|---|
| Публічні `Status`, `Total`, `Lines` | Закритий стан, доступ через методи |
| Інваріанти залежать від дисципліни | Інваріанти неможливо обійти |
| Один об'єкт змінює все підряд | Агрегати зв'язані подіями |
| Правило знижки в замовленні | Окремий доменний сервіс |

::warning
У цьому прикладі події обробляються в тому самому процесі й одразу. У реальній розподіленій системі між агрегатами діє кінцева узгодженість, і для надійної доставки подій додають, наприклад, патерн outbox (див. тему про взаємодію контекстів).

::

## Підсумки

Патерн доменної моделі призначений для складної бізнес-логіки. Він складається з трьох основних будівельних блоків:

| Блок | Суть |
| --- | --- |
| **Об'єкти-значення** | Поняття домену, які ідентифікуються лише значеннями й не потребують явного ID. Зміна поля семантично створює нове значення, тому вони незмінні; моделюють і дані, і поведінку |
| **Агрегати** | Ієрархія сутностей, що ділять межу транзакції. Усі дані в межі мусять бути строго узгодженими. Стан змінюють лише його публічним інтерфейсом (командами); зміни підтверджуються однією атомарною транзакцією; взаємодія із зовнішнім світом — через доменні події |
| **Доменні сервіси** | Безстановий об'єкт із бізнес-логікою, що природно не належить жодному агрегату чи об'єкту-значенню |

![Підсумок: об'єкти-значення, агрегати, доменні сервіси](/images/ddd/complex-business-logic/aggregates-and-domain-services/23-summary.png){.diagram-img}

Будівельні блоки доменної моделі приборкують складність бізнес-логіки, інкапсулюючи її в межах об'єктів-значень і агрегатів. Неможливість змінювати стан об'єктів ззовні гарантує, що вся відповідна бізнес-логіка реалізована в межах агрегатів та об'єктів-значень і не дублюватиметься у прикладному шарі. У наступній темі розглянемо просунутий спосіб реалізації доменної моделі, де **вимір часу** є невід'ємною частиною моделі.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Яке загальне правило проєктування меж агрегата?" icon="i-lucide-help-circle"}

Варіанти: А) агрегат може містити лише одну сутність; Б) агрегати мають бути якомога меншими, якщо збережено вимоги до узгодженості даних домену; В) агрегати мають бути якомога ширшими; Г) залежить від домену.

**Відповідь: Б.** Агрегати проєктують якомога меншими, поки збережені вимоги до узгодженості даних домену.

:::

:::accordion-item{label="❓ Питання 2. Чому в одній транзакції можна підтвердити лише один екземпляр агрегата?" icon="i-lucide-help-circle"}

Варіанти: А) щоб модель витримувала високе навантаження; Б) щоб гарантувати правильні межі транзакцій; В) такої вимоги немає; Г) щоб працювати з базами без багатозаписних транзакцій.

**Відповідь: Б.** Щоб забезпечити правильні межі транзакцій.

:::

:::accordion-item{label="❓ Питання 3. Що найкраще описує відносини між блоками доменної моделі?" icon="i-lucide-help-circle"}

Варіанти: А) об'єкти-значення описують властивості сутностей; Б) об'єкти-значення можуть створювати доменні події; В) агрегат містить одну чи кілька сутностей; Г) А і В.

**Відповідь: Г.**

:::

:::accordion-item{label="❓ Питання 4. Яка різниця між active record і агрегатом?" icon="i-lucide-help-circle"}

Варіанти: А) active record містить лише дані, агрегат ще й поведінку; Б) агрегат інкапсулює всю свою логіку, а логіка над active record може бути поза його межами; В) агрегат містить лише дані; Г) агрегат містить набір active record.

**Відповідь: Б.**

:::
