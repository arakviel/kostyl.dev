# Тактичні патерни DDD у C#: Result, Create, базові класи

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Реалізовувати об'єкти-значення з приватним конструктором і фабричним методом `Create`.
- Повертати помилки через **Result pattern** і розрізняти його із ситуаціями, де потрібен виняток.
- Будувати базові класи `ValueObject`, `Entity<TId>` та `AggregateRoot<TId>`.
- Застосовувати типізовані ідентифікатори замість `Guid` та `int`.
- Накопичувати й розсилати доменні події з агрегату.
- Передавати доменний сервіс у метод агрегату й тестувати все без інфраструктури.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Result pattern:** операція повертає значення, що описує успіх чи помилку, замість викидання винятку.
- **Фабричний метод `Create`:** єдина публічна точка створення об'єкта, яка перевіряє інваріанти.
- **Типізований ідентифікатор (*strongly typed id*):** окремий тип для ідентифікатора кожної сутності.
- **Базовий клас `Entity<TId>`:** рівність за ідентичністю.
- **`AggregateRoot<TId>`:** сутність, що накопичує доменні події.
- **Диспетчер подій:** компонент, який передає події обробникам.

::

## Навіщо ця тема

У попередніх статтях ми розбирали, **що таке** об'єкт-значення, сутність, агрегат і доменна подія. Приклади були короткі: конструктор, що кидає `ArgumentException`, і публічні методи. Для навчання цього достатньо, але в реальних C#-проєктах прийнято інакше:

- помилки введення користувача **не** викидають винятків: вони повертаються як значення;
- об'єкт створюють через `Create`, а конструктор приховують;
- спільну поведінку виносять у базові класи;
- ідентифікатори мають власні типи.

Усі приклади нижче походять із навчального проєкту «Книгарня», і кожен прийом підтверджено тестами. Домен той самий: замовлення книг, знижка, бонуси.

## Result pattern

### Проблема винятків

Розгляньмо створення ISBN:

```csharp
public Isbn(string value)
{
    if (string.IsNullOrWhiteSpace(value))
        throw new ArgumentException("ISBN не може бути порожнім");
    // ...
}
```

Користувач ввів порожнє поле. Це не виняткова ситуація, а **звичайна** подія. Але виняток:

- не видно в сигнатурі методу, тож викликач не знає про можливий збій;
- розмотує стек, а це повільно, коли ситуація трапляється часто;
- змушує обгортати код у `try/catch` або покладатися на глобальний обробник.

### Result: помилка як значення

Опишемо помилку та результат двома невеликими типами.

```csharp
public sealed record Error(string Code, string Message)
{
    public static readonly Error None = new(string.Empty, string.Empty);
}

public class Result
{
    protected Result(bool isSuccess, Error error) { /* перевірка узгодженості */ }

    public bool IsSuccess { get; }
    public bool IsFailure => !IsSuccess;
    public Error Error { get; }

    public static Result Success() => new(true, Error.None);
    public static Result Failure(Error error) => new(false, error);

    public static Result Combine(params Result[] results) =>
        results.FirstOrDefault(r => r.IsFailure) ?? Success();

    public static implicit operator Result(Error error) => Failure(error);
}

public sealed class Result<T> : Result
{
    private readonly T? _value;
    internal Result(T? value, bool isSuccess, Error error) : base(isSuccess, error) => _value = value;

    public T Value => IsSuccess
        ? _value!
        : throw new InvalidOperationException($"Немає значення: {Error.Code}");

    public static implicit operator Result<T>(T value) => Success(value);
    public static implicit operator Result<T>(Error error) => Failure<T>(error);
}
```

Два **неявні перетворення** роблять код лаконічним: з методу можна повертати і значення, і помилку без жодної обгортки.

Зверніть увагу на деталь: звернення до `Value` невдалого результату **кидає виняток**. Це свідома поведінка. Забути перевірити `IsFailure` — помилка програміста, і вона має гучно проявитися.

### Помилки як константи

Помилки зручно групувати поряд із типом, якого вони стосуються. Код помилки стабільний і придатний для тестів, логів і перекладу на клієнті.

```csharp
public static class IsbnErrors
{
    public static readonly Error Empty = new("Isbn.Empty", "ISBN не може бути порожнім");
    public static readonly Error Format = new("Isbn.Format", "ISBN-13 має містити 13 цифр");
    public static readonly Error Checksum = new("Isbn.Checksum", "Контрольна цифра ISBN не збігається");
}
```

Помилку з параметрами описують статичним методом:

```csharp
public static Error InvalidState(string action, OrderStatus status) =>
    new("Order.InvalidState", $"Не можна виконати «{action}» для замовлення у статусі {status}");
```

### Корисні операції: Map, Bind, Ensure, Match

```csharp
public Result<TOut> Map<TOut>(Func<T, TOut> map) =>
    IsSuccess ? Success(map(Value)) : Failure<TOut>(Error);

public Result<TOut> Bind<TOut>(Func<T, Result<TOut>> next) =>
    IsSuccess ? next(Value) : Failure<TOut>(Error);

public Result<T> Ensure(Func<T, bool> predicate, Error error) =>
    IsFailure ? this : predicate(Value) ? this : Failure<T>(error);

public TOut Match<TOut>(Func<T, TOut> onSuccess, Func<Error, TOut> onFailure) =>
    IsSuccess ? onSuccess(Value) : onFailure(Error);
```

| Операція | Що робить |
|---|---|
| `Map` | Перетворює значення, якщо все гаразд |
| `Bind` | Продовжує ланцюжок операцій, кожна з яких може завершитися помилкою |
| `Ensure` | Додає перевірку до вже отриманого значення |
| `Match` | Перетворює успіх і помилку на один тип, наприклад на HTTP-відповідь |
| `Combine` | Повертає першу помилку зі списку перевірок |

Тести фіксують контракт:

```csharp
[Fact]
public void Bind_chains_and_stops_at_first_failure()
{
    var calls = 0;
    Result<int> start = 1;
    var result = start
        .Bind<int>(_ => Boom)
        .Bind(x => { calls++; return Result.Success(x); });

    Assert.Equal(Boom, result.Error);
    Assert.Equal(0, calls);          // після помилки ланцюжок не продовжується
}
```

### Коли Result, а коли виняток

| Ситуація | Інструмент | Приклад |
|---|---|---|
| Очікуване порушення правил, що залежить від даних | **Result** | Порожній ISBN, індекс із 4 цифр, оплата відправленого замовлення |
| Порушення припущення, яке код мав гарантувати | **Виняток** | Віднімання дало б від'ємну суму, звернення до `Value` невдалого результату |
| Збій інфраструктури | **Виняток** | База не відповідає, мережа недоступна |

Правило просте: якщо викликач може розумно відреагувати на помилку (показати повідомлення, запропонувати виправити), це `Result`. Якщо єдина розумна реакція — зупинити операцію та залогувати, це виняток.

::tip
У промислових проєктах замість власної реалізації часто беруть готові бібліотеки: CSharpFunctionalExtensions, ErrorOr або FluentResults. Ідея в усіх однакова. Власна мінімальна версія корисна для розуміння принципу.

::

## Об'єкти-значення з методом Create

### Приватний конструктор і фабрика

Якщо конструктор публічний, будь-хто створить некоректний об'єкт або зловить виняток у несподіваному місці. Тому конструктор ховають, а перевірки переносять у фабричний метод:

```csharp
public sealed record Quantity
{
    public const int Max = 10;

    public int Value { get; }

    private Quantity(int value) => Value = value;

    public static Result<Quantity> Create(int value) =>
        value is < 1 or > Max ? QuantityErrors.OutOfRange : new Quantity(value);

    public Result<Quantity> Add(Quantity other) => Create(Value + other.Value);
}
```

Ключові рішення:

- `sealed record` дає рівність за значенням без жодного додаткового коду;
- приватний конструктор гарантує, що кожен `Quantity` у системі коректний;
- метод `Add` повертає `Result`, бо сума двох коректних кількостей може вийти за максимум.

### Інваріант із реальним правилом: ISBN-13

Приклад, де перевірка нетривіальна, — контрольна цифра ISBN:

```csharp
public static Result<Isbn> Create(string? input)
{
    if (string.IsNullOrWhiteSpace(input)) return IsbnErrors.Empty;

    var digits = new string(input.Where(char.IsDigit).ToArray());
    if (digits.Length != 13) return IsbnErrors.Format;

    // Контрольна цифра ISBN-13: ваги 1 і 3 по черзі.
    var sum = digits.Take(12).Select((c, i) => (c - '0') * (i % 2 == 0 ? 1 : 3)).Sum();
    var check = (10 - sum % 10) % 10;
    return check == digits[12] - '0' ? new Isbn(digits) : IsbnErrors.Checksum;
}
```

Тут ще й **нормалізація**: `978-0-13-235088-4` і `9780132350884` дають однакові значення, а отже, рівні об'єкти:

```csharp
[Fact]
public void Isbn_normalization_makes_equal_values() =>
    Assert.Equal(Isbn.Create("978-0-13-235088-4").Value, Isbn.Create("9780132350884").Value);

[Theory]
[InlineData("", "Isbn.Empty")]
[InlineData("123", "Isbn.Format")]
[InlineData("978-0-13-235088-9", "Isbn.Checksum")]
public void Invalid_isbn_reports_reason(string input, string code) =>
    Assert.Equal(code, Isbn.Create(input).Error.Code);
```

### Гроші: коректність арифметики

```csharp
public sealed record Money
{
    public static readonly Money Zero = new(0m);

    public decimal Amount { get; }
    private Money(decimal amount) => Amount = amount;

    public static Result<Money> Create(decimal amount) =>
        amount < 0
            ? MoneyErrors.Negative
            : new Money(decimal.Round(amount, 2, MidpointRounding.AwayFromZero));

    public static Money operator +(Money a, Money b) => new(a.Amount + b.Amount);
    public static Money operator *(Money a, int times) => new(a.Amount * times);

    public Money Percent(decimal percent) =>
        new(decimal.Round(Amount * percent / 100m, 2, MidpointRounding.AwayFromZero));

    // Порушення тут — помилка програміста, а не користувача, тому виняток.
    public static Money operator -(Money a, Money b) =>
        a.Amount >= b.Amount
            ? new(a.Amount - b.Amount)
            : throw new InvalidOperationException("Віднімання дало б від'ємну суму");
}
```

Є три тонкощі:

1. Округлення **завжди** `AwayFromZero`. За замовчуванням .NET використовує банківське округлення, і `10.125` дало б `10.12`. Для грошей це несподівано.
2. Додавання та множення на коректних значеннях завжди дають коректний результат, тому повертають просто `Money`.
3. Віднімання може порушити інваріант. Тут ми свідомо обрали виняток, бо код, який віднімає більше, ніж є, містить помилку, і користувач нічого не вирішує.

### Складений об'єкт-значення на базовому класі

Коли значення складається з кількох полів, зручно мати базовий клас, що реалізує рівність за складовими:

```csharp
public abstract class ValueObject : IEquatable<ValueObject>
{
    protected abstract IEnumerable<object?> GetEqualityComponents();

    public bool Equals(ValueObject? other) =>
        other is not null && GetType() == other.GetType() &&
        GetEqualityComponents().SequenceEqual(other.GetEqualityComponents());

    public override bool Equals(object? obj) => obj is ValueObject vo && Equals(vo);

    public override int GetHashCode() =>
        GetEqualityComponents().Aggregate(0, (hash, c) => HashCode.Combine(hash, c));

    public static bool operator ==(ValueObject? a, ValueObject? b) => a?.Equals(b) ?? b is null;
    public static bool operator !=(ValueObject? a, ValueObject? b) => !(a == b);
}
```

Адреса доставки:

```csharp
public sealed class ShippingAddress : ValueObject
{
    public string Street { get; }
    public string City { get; }
    public string PostalCode { get; }

    private ShippingAddress(string street, string city, string postalCode) { /* ... */ }

    public static Result<ShippingAddress> Create(string? street, string? city, string? postalCode)
    {
        if (string.IsNullOrWhiteSpace(street)) return AddressErrors.Street;
        if (string.IsNullOrWhiteSpace(city)) return AddressErrors.City;
        var code = postalCode?.Trim() ?? "";
        if (code.Length != 5 || !code.All(char.IsDigit)) return AddressErrors.PostalCode;
        return new ShippingAddress(street.Trim(), city.Trim(), code);
    }

    protected override IEnumerable<object?> GetEqualityComponents()
    {
        yield return Street;
        yield return City;
        yield return PostalCode;
    }
}
```

```csharp
[Fact]
public void Address_equality_is_by_components()
{
    var a = ShippingAddress.Create("Хрещатик 1", "Київ", "01001").Value;
    var b = ShippingAddress.Create(" Хрещатик 1 ", "Київ", "01001").Value;
    Assert.Equal(a, b);   // пробіли обрізано під час створення
}
```

::note
Коли обирати `record`, а коли базовий клас? Для значень з одним-двома полями `sealed record` простіший. Для складених значень із колекціями або власною логікою рівності зручніший `ValueObject`. Обидва варіанти правильні, головне, щоб у проєкті був один стиль.

::

## Типізовані ідентифікатори

Коли всі ідентифікатори — `Guid`, компілятор не помітить, що замовлення передали туди, де чекають клієнта:

```csharp
// До: параметри однакового типу легко переплутати
void Pay(Guid orderId, Guid customerId);
Pay(customerId, orderId);   // компілюється, але це помилка
```

Рішення — власний тип на кожен ідентифікатор. `readonly record struct` не додає накладних витрат на пам'ять:

```csharp
public readonly record struct OrderId(Guid Value)
{
    public static OrderId New() => new(Guid.NewGuid());
}

public readonly record struct CustomerId(Guid Value)
{
    public static CustomerId New() => new(Guid.NewGuid());
}
```

Тепер `Pay(CustomerId, OrderId)` у помилковому порядку не скомпілюється. Це той самий принцип, що й в об'єктів-значень: уся логіка плутанини виявляється під час компіляції.

## Базові класи для сутностей і агрегатів

### Entity: рівність за ідентичністю

Об'єкти-значення рівні, якщо рівні їхні значення. Сутності рівні, якщо **збігаються ідентифікатори**, навіть коли інші поля відрізняються:

```csharp
public abstract class Entity<TId> : IEquatable<Entity<TId>> where TId : notnull
{
    protected Entity(TId id) => Id = id;

    public TId Id { get; }

    public bool Equals(Entity<TId>? other) =>
        other is not null && GetType() == other.GetType() &&
        EqualityComparer<TId>.Default.Equals(Id, other.Id);

    public override bool Equals(object? obj) => obj is Entity<TId> e && Equals(e);
    public override int GetHashCode() => HashCode.Combine(GetType(), Id);
}
```

### AggregateRoot: накопичення подій

Корінь агрегату додає до сутності список доменних подій:

```csharp
public interface IDomainEvent { }

public abstract class AggregateRoot<TId> : Entity<TId> where TId : notnull
{
    private readonly List<IDomainEvent> _domainEvents = new();

    protected AggregateRoot(TId id) : base(id) { }

    public IReadOnlyCollection<IDomainEvent> DomainEvents => _domainEvents;

    protected void Raise(IDomainEvent domainEvent) => _domainEvents.Add(domainEvent);
    public void ClearDomainEvents() => _domainEvents.Clear();
}
```

- `Raise` захищений, тож подію може створити лише сам агрегат.
- Список подій доступний ззовні лише для читання.
- `ClearDomainEvents` викликає інфраструктура після розсилання.

## Агрегат Order

Зберемо все разом. Агрегат `Order` складається з кореня і рядків замовлення. Рядок — це сутність із **локальною** ідентичністю: у межах замовлення книгу ідентифікує її ISBN.

```csharp
public sealed class OrderLine : Entity<Isbn>
{
    public Quantity Quantity { get; private set; }
    public Money UnitPrice { get; }

    internal OrderLine(Isbn isbn, Quantity quantity, Money unitPrice) : base(isbn)
    {
        Quantity = quantity;
        UnitPrice = unitPrice;
    }

    public Money Subtotal => UnitPrice * Quantity.Value;

    internal Result IncreaseBy(Quantity extra) =>
        Quantity.Add(extra).Bind<bool>(q => { Quantity = q; return true; });
}
```

Конструктор `internal`: створити рядок можна лише всередині збірки домену, а на практиці лише з агрегату.

### Створення і стан

```csharp
public enum OrderStatus { Draft, Placed, Paid, Shipped, Cancelled }

public sealed class Order : AggregateRoot<OrderId>
{
    private readonly List<OrderLine> _lines = new();

    public CustomerId CustomerId { get; }
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public Money Total { get; private set; } = Money.Zero;
    public ShippingAddress? Address { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;

    private Order(OrderId id, CustomerId customerId) : base(id) => CustomerId = customerId;

    public static Order Create(CustomerId customerId) => new(OrderId.New(), customerId);
}
```

`Create` тут повертає просто `Order`, а не `Result<Order>`: з одного лише `CustomerId` створити некоректне замовлення неможливо, отже й помилці нізвідки взятися. Не обгортайте в `Result` те, що не може не вдатися.

### Операції повертають Result

```csharp
public Result AddLine(Isbn isbn, Quantity quantity, Money unitPrice)
{
    if (Status != OrderStatus.Draft)
        return OrderErrors.InvalidState("додати книгу", Status);

    var existing = _lines.FirstOrDefault(l => l.Id == isbn);
    if (existing is null)
    {
        _lines.Add(new OrderLine(isbn, quantity, unitPrice));
        return Result.Success();
    }
    return existing.IncreaseBy(quantity);   // та сама книга двічі: об'єднуємо
}
```

Бізнес-правило «одна книга — один рядок, не більше 10 штук» тепер виконується в одному місці й не залежить від викликача. Тест перевіряє і межу, і те, що невдала операція **не змінює стан**:

```csharp
[Fact]
public void Merging_beyond_maximum_fails_without_changing_the_line()
{
    var order = DraftWith((A, 8, 100));
    var result = order.AddLine(A, Q(5), M(100));

    Assert.Equal(QuantityErrors.OutOfRange, result.Error);
    Assert.Equal(8, order.Lines.Single().Quantity.Value);
}
```

### Доменний сервіс як параметр

Знижка залежить і від замовлення, і від клієнта, тому це доменний сервіс. Передамо його в метод агрегату. Так агрегат не створює залежностей і лишається тестованим:

```csharp
public interface IDiscountPolicy
{
    Money Apply(Money subtotal, Loyalty loyalty);
}

public sealed class DiscountPolicy : IDiscountPolicy
{
    public Money Apply(Money subtotal, Loyalty loyalty)
    {
        decimal percent = 0;
        if (subtotal.Amount >= 1000) percent += 10;
        if (loyalty == Loyalty.Gold) percent += 5;
        return subtotal - subtotal.Percent(percent);
    }
}
```

```csharp
public Result Place(IDiscountPolicy discounts, Loyalty loyalty, ShippingAddress address)
{
    if (Status != OrderStatus.Draft)
        return OrderErrors.InvalidState("оформити", Status);
    if (_lines.Count == 0)
        return OrderErrors.Empty;

    Total = discounts.Apply(Subtotal, loyalty);
    Address = address;
    Status = OrderStatus.Placed;
    Raise(new OrderPlaced(Id, CustomerId, Total));
    return Result.Success();
}
```

Зверніть увагу на порядок: усі перевірки йдуть **до** зміни стану. Якщо хоч одна не пройшла, агрегат залишається незайманим і подій не породжує.

### Решта переходів

```csharp
public Result Pay()
{
    if (Status != OrderStatus.Placed)
        return OrderErrors.InvalidState("оплатити", Status);
    Status = OrderStatus.Paid;
    Raise(new OrderPaid(Id, CustomerId, Total));
    return Result.Success();
}

public Result Cancel()
{
    if (Status is OrderStatus.Shipped or OrderStatus.Cancelled)
        return OrderErrors.InvalidState("скасувати", Status);
    var wasPaid = Status == OrderStatus.Paid;
    Status = OrderStatus.Cancelled;
    Raise(new OrderCancelled(Id, CustomerId, Total, wasPaid));
    return Result.Success();
}
```

Схема станів: `Draft → Placed → Paid → Shipped`, а скасувати можна з будь-якого стану, окрім `Shipped` і `Cancelled`.

## Доменні події

### Події як незмінні записи

Подія — це факт, що вже відбувся, тому називаємо її в минулому часі й робимо незмінною:

```csharp
public sealed record OrderPlaced(OrderId OrderId, CustomerId CustomerId, Money Total) : IDomainEvent;
public sealed record OrderPaid(OrderId OrderId, CustomerId CustomerId, Money Total) : IDomainEvent;
public sealed record OrderShipped(OrderId OrderId) : IDomainEvent;
public sealed record OrderCancelled(OrderId OrderId, CustomerId CustomerId, Money Total, bool WasPaid) : IDomainEvent;
```

Подія несе все, що потрібно обробникам. Вони не завантажують агрегат повторно. Зверніть увагу на `WasPaid` у `OrderCancelled`: без нього обробник не знав би, чи треба забирати бонуси.

### Обробники та диспетчер

```csharp
public interface IDomainEventHandler<in TEvent> where TEvent : IDomainEvent
{
    void Handle(TEvent domainEvent);
}

public sealed class DomainEventDispatcher
{
    private readonly Dictionary<Type, List<Action<IDomainEvent>>> _handlers = new();

    public void Register<TEvent>(IDomainEventHandler<TEvent> handler) where TEvent : IDomainEvent
    {
        if (!_handlers.TryGetValue(typeof(TEvent), out var list))
            _handlers[typeof(TEvent)] = list = new();
        list.Add(e => handler.Handle((TEvent)e));
    }

    public void Dispatch(AggregateRoot<OrderId> aggregate)
    {
        var events = aggregate.DomainEvents.ToList();
        aggregate.ClearDomainEvents();
        foreach (var e in events)
            if (_handlers.TryGetValue(e.GetType(), out var list))
                foreach (var h in list) h(e);
    }
}
```

Кожна реакція живе у власному класі з одним завданням:

```csharp
public sealed class AwardBonusOnPaid : IDomainEventHandler<OrderPaid>
{
    private readonly ICustomerRepository _customers;
    public AwardBonusOnPaid(ICustomerRepository customers) => _customers = customers;

    public void Handle(OrderPaid e)
    {
        var customer = _customers.Find(e.CustomerId)!;
        customer.EarnBonus((int)(e.Total.Amount / 10));
        _customers.Save(customer);
    }
}
```

Так агрегат `Order` нічого не знає про бонуси. Щоб додати нову реакцію (наприклад, надіслати лист), достатньо зареєструвати ще один обробник, а `Order` лишається без змін.

::warning
У навчальному прикладі події обробляються одразу й у тому самому процесі. У розподіленій системі подію спершу зберігають у тій самій транзакції (outbox), а доставляють пізніше. Тоді обробники мають бути ідемпотентними.

::

## Обробник команди: Result від краю до краю

Прикладний рівень перетворює сирі дані на об'єкти-значення й веде агрегат. Будь-яка помилка зупиняє сценарій і повертається викликачу значенням:

```csharp
public Result<OrderId> Handle(PlaceOrderCommand command)
{
    var customer = _customers.Find(new CustomerId(command.CustomerId));
    if (customer is null) return CustomerErrors.NotFound;

    var address = ShippingAddress.Create(command.Street, command.City, command.PostalCode);
    if (address.IsFailure) return address.Error;

    var order = Order.Create(customer.Id);
    foreach (var book in command.Books)
    {
        var added = AddBook(order, book);
        if (added.IsFailure) return added.Error;
    }

    var placed = order.Place(_discounts, customer.Loyalty, address.Value);
    if (placed.IsFailure) return placed.Error;

    _orders.Save(order);
    _events.Dispatch(order);
    return order.Id;
}

private Result AddBook(Order order, BookRequest request)
{
    var isbn = Isbn.Create(request.Isbn);
    var quantity = Quantity.Create(request.Quantity);
    var checks = Result.Combine(isbn, quantity);
    if (checks.IsFailure) return checks.Error;

    var price = _catalog.PriceOf(isbn.Value);
    return price is null
        ? CatalogErrors.UnknownBook
        : order.AddLine(isbn.Value, quantity.Value, price);
}
```

Три моменти:

- `return address.Error;` працює завдяки неявному перетворенню `Error → Result<OrderId>`.
- `Result.Combine(isbn, quantity)` перевіряє кілька значень разом, а далі код безпечно звертається до `.Value`.
- `return order.Id;` повертає `Result<OrderId>` через неявне перетворення значення.

### Верхній шар: Result → відповідь

На межі системи (контролер, консоль) результат перетворюють на відповідь через `Match`:

```csharp
var result = placeOrder.Handle(command);

Console.WriteLine(result.Match(
    id => $"Замовлення {id} оформлено",
    error => $"Помилка: {error.Message}"));
```

У веб-застосунку на цьому місці `Match` повертав би `201 Created` або `400 Bad Request` із кодом помилки в тілі.

### Тести обробника

```csharp
[Theory]
[InlineData("", 1, "01001", "Isbn.Empty")]
[InlineData("978-0-13-235088-9", 1, "01001", "Isbn.Checksum")]
[InlineData(BookA, 0, "01001", "Quantity.OutOfRange")]
[InlineData(BookA, 1, "1", "Address.PostalCode")]
[InlineData("978-3-16-148410-0", 1, "01001", "Catalog.UnknownBook")]
public void Invalid_input_returns_error_without_saving(string isbn, int qty, string postal, string code)
{
    var result = _place.Handle(Command(isbn, qty, postal));
    Assert.Equal(code, result.Error.Code);
}

[Fact]
public void Paying_awards_bonus_through_domain_event()
{
    var id = _place.Handle(Command()).Value;
    Assert.True(_lifecycle.Pay(id).IsSuccess);
    Assert.Equal(108, _customers.Find(_customer.Id)!.BonusPoints);
}
```

Усі п'ять видів помилок введення перевіряються одним параметризованим тестом, а жоден тест не потребує бази даних.

## Типові помилки

### Публічний конструктор поруч із Create

```csharp
// Погано: Create є, але обійти його можна
public record Quantity(int Value)
{
    public static Result<Quantity> Create(int value) => /* ... */;
}
var q = new Quantity(-5);   // компілюється
```

Якщо конструктор записаного `record` публічний, фабричний метод нічого не гарантує. Робіть конструктор приватним.

### Result скрізь

Не повертайте `Result` із методів, які не можуть не вдатися (`Order.Create(customerId)`), і з методів, що порушення яких означають помилку програмера (`Money.operator -`). Інакше викликачі змушені писати нескінченні перевірки, які ніколи не спрацюють.

### Ігнорований Result

```csharp
order.Pay();                 // результат викинуто: помилка загубилася
_orders.Save(order);
```

Це найпоширеніша помилка патерна. Захищайтеся тестами, аналізаторами та правилом: результат операції агрегату або перевіряється, або повертається далі.

### Зміна стану до перевірок

```csharp
// Погано: статус уже змінено, а потім виявляється помилка
Status = OrderStatus.Placed;
if (_lines.Count == 0) return OrderErrors.Empty;
```

Спершу всі перевірки, потім зміна стану, потім подія.

### Події із агрегатами всередині

Подія, що містить посилання на цілий агрегат `Customer`, дозволяє обробникам змінювати його. Передавайте в подіях лише ідентифікатори й значення.

## Підсумкове порівняння

| Аспект | Спрощений стиль | Ідіоматичний C# |
|---|---|---|
| Помилки введення | `throw new ArgumentException` | `Result<T>` з кодом помилки |
| Створення об'єктів-значень | Публічний конструктор | Приватний конструктор + `Create` |
| Ідентифікатори | `Guid`, `int` | `OrderId`, `CustomerId` |
| Рівність сутностей | Вручну або взагалі ніяк | Базовий `Entity<TId>` |
| Доменні події | Окремий список у кожному агрегаті | `AggregateRoot<TId>` з `Raise` |
| Доменний сервіс | Створюється всередині | Передається параметром |
| Перевірка в тестах | `Assert.Throws` | `Assert.Equal(код, result.Error.Code)` |

---

## Підсумки

- Очікувані помилки повертають через **Result**, помилки програміста лишаються винятками.
- Об'єкти-значення мають приватний конструктор і метод `Create`, який перевіряє й нормалізує дані.
- Типізовані ідентифікатори переносять перевірки плутанини в компілятор.
- Базові класи `ValueObject`, `Entity<TId>` та `AggregateRoot<TId>` усувають повторюваний код і фіксують стиль проєкту.
- Агрегат спершу перевіряє, потім змінює стан, потім породжує подію.
- Доменні події розв'язують агрегати між собою, а обробники живуть у власних класах.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Користувач ввів порожній ISBN. Що правильніше?" icon="i-lucide-help-circle"}

Варіанти: А) кинути `ArgumentException`; Б) повернути `Result` з помилкою `Isbn.Empty`; В) повернути `null`; Г) проігнорувати.

**Відповідь: Б.** Це очікувана ситуація, яку викликач може обробити: показати повідомлення й попросити виправити.

:::

:::accordion-item{label="❓ Питання 2. Навіщо робити конструктор об'єкта-значення приватним?" icon="i-lucide-help-circle"}

Варіанти: А) щоб прискорити код; Б) щоб неможливо було створити об'єкт, оминувши перевірки в `Create`; В) бо так вимагає C#; Г) щоб заборонити рівність.

**Відповідь: Б.** Тоді кожен екземпляр у системі гарантовано коректний.

:::

:::accordion-item{label="❓ Питання 3. Чому `Money.operator -` кидає виняток, а не повертає Result?" icon="i-lucide-help-circle"}

Варіанти: А) бо Result не підтримує decimal; Б) бо від'ємний результат означає помилку програміста, а не помилку введення; В) бо оператори не можуть повертати Result; Г) це випадковість.

**Відповідь: Б.** Код, який віднімає більше, ніж є, містить помилку, і викликач нічого не може з нею розумно зробити.

:::

:::accordion-item{label="❓ Питання 4. Чим типізований ідентифікатор кращий за Guid?" icon="i-lucide-help-circle"}

Варіанти: А) він швидший; Б) компілятор не дозволить передати `CustomerId` замість `OrderId`; В) його не можна порівнювати; Г) він займає менше пам'яті.

**Відповідь: Б.** Плутанину ідентифікаторів виявляє компіляція.

:::

:::accordion-item{label="❓ Питання 5. У якому порядку `Order.Place` має працювати?" icon="i-lucide-help-circle"}

Варіанти: А) змінити стан, потім перевірити; Б) перевірити, змінити стан, породити подію; В) породити подію, потім перевірити; Г) порядок неважливий.

**Відповідь: Б.** Інакше невдала операція залишить агрегат у напівзміненому стані або розішле подію про те, чого не сталося.

:::

:::accordion-item{label="❓ Питання 6. Чому обробник `AwardBonusOnPaid` — окремий клас, а не код усередині `Order.Pay`?" icon="i-lucide-help-circle"}

Варіанти: А) щоб агрегат `Order` не знав про бонуси, а нові реакції додавалися без змін у ньому; Б) бо `Pay` не може викликати інший код; В) це вимога C#; Г) для економії пам'яті.

**Відповідь: А.** Події роз'єднують агрегати: бонуси належать іншому агрегату (`Customer`).

:::
