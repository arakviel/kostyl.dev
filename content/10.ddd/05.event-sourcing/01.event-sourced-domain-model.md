# Фактор часу: подієве джерело (Event Sourcing)

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Пояснювати, чим **подієве джерело** (*event sourcing*) відрізняється від збереження поточного стану.
- Будувати **проєкції** (*projections*) стану з потоку доменних подій.
- Описувати **сховище подій** (*event store*) та оптимістичне керування паралелізмом.
- Реалізовувати агрегат за патерном **Event-Sourced Domain Model**.
- Оцінювати переваги й недоліки патерна та відповідати на типові запитання щодо продуктивності, масштабування й видалення даних.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Подієве джерело (*event sourcing*):** зберігання змін як послідовності подій.
- **Проєкція (*projection*):** подання стану, обчислене з подій.
- **Сховище подій (*event store*):** сховище лише для додавання подій.
- **Знімок (*snapshot*):** кешована проєкція до певної версії.
- **Джерело істини (*source of truth*):** єдине сильно узгоджене сховище даних.

::

::

## Вступ

Подієво-орієнтована доменна модель (*event-sourced domain model*) спирається на ту саму ідею, що й звичайна доменна модель: бізнес-логіка складна й належить до **основного піддомену**. Вона використовує ті самі тактичні патерни: об'єкти-значення, агрегати й доменні події.

Різниця лише в тому, **як зберігається стан агрегатів**. Замість запису поточного стану модель породжує доменні події, що описують кожну зміну, і саме вони стають **джерелом істини** для даних агрегата.

![Дві моделі даних: стан і історія](/images/ddd/event-sourcing/event-sourced-domain-model/01-two-models.png){.diagram-img}

## Подієве джерело

> Покажіть мені блок-схему й сховайте таблиці, і я лишуся в непорозумінні. Покажіть таблиці, і блок-схема зазвичай не потрібна: вона очевидна.
> — Фред Брукс

Скористаймося думкою Брукса, щоб зрозуміти патерн. Подивіться на таблицю й спробуйте зрозуміти, що вона розповідає про систему.

![Таблиця лідів](/images/ddd/event-sourcing/event-sourced-domain-model/02-state-table.png){.diagram-img}

Очевидно, що таблиця керує **потенційними клієнтами** (лідами) у системі телемаркетингу. Для кожного ліда є ідентифікатор, ім'я, прізвище, телефон, час створення й оновлення та поточний статус. За статусами можна припустити цикл обробки:

- Продаж починається зі статусу `NEW_LEAD`.
- Дзвінок може завершитися відмовою (`CLOSED`), запланованим повторним дзвінком (`FOLLOWUP_SET`) або згодою на пропозицію (`PENDING_PAYMENT`).
- Якщо оплата успішна, лід стає клієнтом (`CONVERTED`); якщо ні, статус `PAYMENT_FAILED`.

![Життєвий цикл ліда](/images/ddd/event-sourcing/event-sourced-domain-model/03-lead-lifecycle.png){.diagram-img}

Із схеми таблиці можна припустити навіть єдину мову, використану під час моделювання. Але чого в ній **не вистачає**?

Таблиця документує **поточні стани** лідів, але не розповідає, **як** кожен лід до нього дійшов. Ми не знаємо, скільки дзвінків було до конвертації, чи була покупка одразу, чи був довгий шлях. Не знаємо, чи варто телефонувати після кількох відкладень, чи ефективніше закрити ліда й перейти до перспективнішого. Це важливі бізнес-запитання для оптимізації процесу продажу.

![Чого не вистачає таблиці](/images/ddd/event-sourcing/event-sourced-domain-model/04-missing-story.png){.diagram-img}

::tip
Один зі способів заповнити відсутню інформацію: **подієве джерело**. Патерн додає до моделі даних **вимір часу**.

::

Замість схеми, що відображає поточний стан агрегата, система зберігає **події**, які документують кожну зміну його життєвого циклу. Ось як дані ліда №12 (`CONVERTED`) виглядають у системі на подіях:

```json
{ "lead-id": 12, "event-id": 0, "event-type": "lead-initialized",
  "first-name": "Casey", "last-name": "David", "phone-number": "555-2951",
  "timestamp": "2020-05-20T09:52:55.95Z" },
{ "lead-id": 12, "event-id": 1, "event-type": "contacted",
  "timestamp": "2020-05-20T12:32:08.24Z" },
{ "lead-id": 12, "event-id": 2, "event-type": "followup-set",
  "followup-on": "2020-05-27T12:00:00.00Z", "timestamp": "2020-05-20T12:32:08.24Z" },
{ "lead-id": 12, "event-id": 3, "event-type": "contact-details-updated",
  "first-name": "Casey", "last-name": "Davis", "phone-number": "555-8101",
  "timestamp": "2020-05-20T12:32:08.24Z" },
{ "lead-id": 12, "event-id": 4, "event-type": "contacted",
  "timestamp": "2020-05-27T12:02:12.51Z" },
{ "lead-id": 12, "event-id": 5, "event-type": "order-submitted",
  "payment-deadline": "2020-05-30T12:02:12.51Z", "timestamp": "2020-05-27T12:02:12.51Z" },
{ "lead-id": 12, "event-id": 6, "event-type": "payment-confirmed",
  "status": "converted", "timestamp": "2020-05-27T12:38:44.12Z" }
```

![Потік подій ліда №12](/images/ddd/event-sourcing/event-sourced-domain-model/05-event-stream.png){.diagram-img}

Події розповідають історію клієнта. Ліда створили в системі (подія 0), приблизно за дві години з ним зв'язався агент (подія 1). Під час розмови домовилися про повторний дзвінок за тиждень (подія 2), але на інший номер (подія 3); агент також виправив помилку в прізвищі (подія 3). Лід відповів у домовлений час (подія 4) і оформив замовлення (подія 5) з оплатою протягом трьох днів, а оплата надійшла приблизно за пів години (подія 6), після чого лід став клієнтом.

## Проєкція стану з подій

Стан клієнта легко **спроєктувати** з подій: достатньо послідовно застосувати просту логіку перетворення до кожної з них.

```csharp
public class LeadSearchModelProjection
{
    public long LeadId { get; private set; }
    public HashSet<string> FirstNames { get; private set; }
    public HashSet<string> LastNames { get; private set; }
    public HashSet<PhoneNumber> PhoneNumbers { get; private set; }
    public int Version { get; private set; }

    public void Apply(LeadInitialized @event)
    {
        LeadId = @event.LeadId;
        FirstNames = new HashSet<string>();
        LastNames = new HashSet<string>();
        PhoneNumbers = new HashSet<PhoneNumber>();

        FirstNames.Add(@event.FirstName);
        LastNames.Add(@event.LastName);
        PhoneNumbers.Add(@event.PhoneNumber);
        Version = 0;
    }

    public void Apply(ContactDetailsChanged @event)
    {
        FirstNames.Add(@event.FirstName);
        LastNames.Add(@event.LastName);
        PhoneNumbers.Add(@event.PhoneNumber);
        Version += 1;
    }

    public void Apply(Contacted @event)       { Version += 1; }
    public void Apply(FollowupSet @event)     { Version += 1; }
    public void Apply(OrderSubmitted @event)  { Version += 1; }
    public void Apply(PaymentConfirmed @event){ Version += 1; }
}
```

![Проєкція: подія за подією до стану](/images/ddd/event-sourcing/event-sourced-domain-model/06-projection.png){.diagram-img}

Перебір подій агрегата й послідовна передача їх у відповідні перевизначення методу `Apply` дає саме те подання стану, яке моделює таблиця.

::note
Зверніть увагу на поле `Version`: воно збільшується після кожної події, тому показує загальну кількість змін бізнес-сутності. Якщо застосувати лише підмножину подій, можна **«подорожувати в часі»**: стан у версії 5 дають перші п'ять подій.

::

![Подорож у часі](/images/ddd/event-sourcing/event-sourced-domain-model/07-time-travel.png){.diagram-img}

Більше того, ми не обмежені лише одним поданням стану. Розгляньмо два сценарії.

### Пошук

Потрібно реалізувати пошук. Контактні дані ліда можуть змінюватися (ім'я, прізвище, телефон), а агенти можуть не знати про зміни інших, тому хочуть шукати й за **історичними** значеннями. Проєкція легко це робить: події `LeadInitialized` і `ContactDetailsChanged` наповнюють множини контактних даних, а решта подій лише збільшує версію.

Для подій Casey Davis результат буде таким:

```text
LeadId: 12
FirstNames: ['Casey']
LastNames: ['David', 'Davis']
PhoneNumbers: ['555-2951', '555-8101']
Version: 6
```

![Проєкція для пошуку](/images/ddd/event-sourcing/event-sourced-domain-model/08-search-projection.png){.diagram-img}

### Аналіз

Відділ бізнес-аналітики просить зручніше подання даних про лідів: для дослідження потрібна кількість запланованих повторних дзвінків для різних лідів. Пізніше вони відфільтрують конвертованих і закритих лідів та оптимізують процес продажу.

```csharp
public class AnalysisModelProjection
{
    public long LeadId { get; private set; }
    public int Followups { get; private set; }
    public LeadStatus Status { get; private set; }
    public int Version { get; private set; }

    public void Apply(LeadInitialized @event)
    {
        LeadId = @event.LeadId;
        Followups = 0;
        Status = LeadStatus.NEW_LEAD;
        Version = 0;
    }

    public void Apply(Contacted @event) { Version += 1; }

    public void Apply(FollowupSet @event)
    {
        Status = LeadStatus.FOLLOWUP_SET;
        Followups += 1;
        Version += 1;
    }

    public void Apply(ContactDetailsChanged @event) { Version += 1; }

    public void Apply(OrderSubmitted @event)
    {
        Status = LeadStatus.PENDING_PAYMENT;
        Version += 1;
    }

    public void Apply(PaymentConfirmed @event)
    {
        Status = LeadStatus.CONVERTED;
        Version += 1;
    }
}
```

Логіка веде лічильник появ подій повторного дзвінка. Для тих самих подій результат такий:

```text
LeadId: 12
Followups: 1
Status: Converted
Version: 6
```

![Проєкція для аналізу](/images/ddd/event-sourcing/event-sourced-domain-model/09-analysis-projection.png){.diagram-img}

![Одні події, багато проєкцій](/images/ddd/event-sourcing/event-sourced-domain-model/10-many-projections.png){.diagram-img}

::warning
Наведені проєкції існують лише **в пам'яті**. Щоб реалізувати функціональність, проєкції треба зберігати в базі даних. Патерн, який це дозволяє, називається **CQRS** (*command-query responsibility segregation*), і про нього йтиметься в наступній темі.

::

## Джерело істини

Щоб патерн працював, **усі** зміни стану об'єкта мають бути подані й збережені як події. Ці події стають **джерелом істини** системи, звідси й назва патерна.

![Агрегат, події й сховище](/images/ddd/event-sourcing/event-sourced-domain-model/11-source-of-truth.png){.diagram-img}

База даних, що зберігає події системи, є єдиним сильно узгодженим сховищем. Її називають **сховищем подій** (*event store*).

### Сховище подій

Сховище подій не повинно дозволяти змінювати чи видаляти події, адже воно працює лише на додавання (*append-only*). Для підтримки патерна воно має вміти щонайменше два: отримати всі події певної бізнес-сутності та додати нові.

```csharp
interface IEventStore
{
    IEnumerable<Event> Fetch(Guid instanceId);
    void Append(Guid instanceId, Event[] newEvents, int expectedVersion);
}
```

![Інтерфейс сховища подій](/images/ddd/event-sourcing/event-sourced-domain-model/12-event-store-api.png){.diagram-img}

Аргумент `expectedVersion` у методі `Append` потрібен для **оптимістичного керування паралелізмом**. Додаючи події, ми вказуємо версію сутності, на якій базуємо рішення. Якщо версія застаріла (після неї додано нові події), сховище має згенерувати виняток паралелізму.

![Оптимістичний паралелізм](/images/ddd/event-sourcing/event-sourced-domain-model/13-concurrency.png){.diagram-img}

::note
Подієве джерело не нове. Фінансова галузь використовує події для змін у бухгалтерській книзі. **Книга** (*ledger*) — журнал лише для додавання, що документує транзакції. Поточний стан (наприклад, баланс рахунку) завжди можна вивести, «спроєктувавши» записи книги.

::

![Бухгалтерська книга](/images/ddd/event-sourcing/event-sourced-domain-model/14-ledger.png){.diagram-img}

## Подієво-орієнтована доменна модель

Звичайна доменна модель підтримує подання стану агрегатів і випромінює окремі доменні події. **Подієво-орієнтована** використовує доменні події **виключно** для моделювання життєвого циклу агрегатів: усі зміни стану мають бути виражені як події.

Кожна операція над таким агрегатом виконує сценарій:

1. Завантажити доменні події агрегата.
2. Відновити подання стану: спроєктувати події в стан, придатний для бізнес-рішень.
3. Виконати команду агрегата, тобто бізнес-логіку, що породжує нові події.
4. Зафіксувати нові доменні події у сховищі подій.

![Сценарій операції](/images/ddd/event-sourcing/event-sourced-domain-model/15-script.png){.diagram-img}

Повернімося до агрегата `Ticket` з попередньої теми й подивімося, як він реалізується на подіях. Прикладний сервіс виконує описаний сценарій: завантажує події заявки, відновлює екземпляр агрегата, викликає команду й зберігає зміни.

```csharp
public class TicketAPI
{
    private ITicketsRepository _ticketsRepository;
    ...

    public void RequestEscalation(TicketId id, EscalationReason reason)
    {
        var events = _ticketsRepository.LoadEvents(id);
        var ticket = new Ticket(events);
        var originalVersion = ticket.Version;
        var cmd = new RequestEscalation(reason);
        ticket.Execute(cmd);
        _ticketsRepository.CommitChanges(ticket, originalVersion);
    }
}
```

Конструктор агрегата створює екземпляр проєктора стану `TicketState` і послідовно викликає `AppendEvent` для кожної події заявки:

```csharp
public class Ticket
{
    private List<DomainEvent> _domainEvents = new List<DomainEvent>();
    private TicketState _state;

    public Ticket(IEnumerable<IDomainEvents> events)
    {
        _state = new TicketState();
        foreach (var e in events)
        {
            AppendEvent(e);
        }
    }

    private void AppendEvent(IDomainEvent @event)
    {
        _domainEvents.Append(@event);
        // Динамічно викликаємо потрібне перевантаження Apply
        ((dynamic)_state).Apply((dynamic)@event);
    }

    public void Execute(RequestEscalation cmd)
    {
        if (!_state.IsEscalated && _state.RemainingTimePercentage <= 0)
        {
            var escalatedEvent = new TicketEscalated(_id, cmd.Reason);
            AppendEvent(escalatedEvent);
        }
    }
}
```

На відміну від попередньої реалізації, метод `RequestEscalation` **не встановлює** прапорець `IsEscalated` у `true` явно. Він створює відповідну подію й передає її в `AppendEvent`. Усі додані події потрапляють у логіку проєкції класу `TicketState`, де змінюються відповідні поля:

```csharp
public class TicketState
{
    public TicketId Id { get; private set; }
    public int Version { get; private set; }
    public bool IsEscalated { get; private set; }
    ...

    public void Apply(TicketInitialized @event)
    {
        Id = @event.Id;
        Version = 0;
        IsEscalated = false;
        ...
    }

    public void Apply(TicketEscalated @event)
    {
        IsEscalated = true;
        Version += 1;
    }
}
```

![Агрегат Ticket на подіях](/images/ddd/event-sourcing/event-sourced-domain-model/16-ticket-code.png){.diagram-img}

::tip
Чому «event-sourced domain model», а не просто «event sourcing»? Зберігати переходи станів подіями можна **з будівельними блоками доменної моделі й без них**. Довший термін явно вказує, що подієве джерело застосовано для змін у життєвих циклах **агрегатів доменної моделі**.

::

## Переваги

Порівняно з традиційною моделлю, де зберігається поточний стан агрегатів, подієво-орієнтована модель потребує більше зусиль для моделювання агрегатів. Але вона дає суттєві переваги.

::card-group

::card{title="Подорож у часі" icon="i-lucide-history"}
Події, що відновлюють поточний стан, можуть відновити й усі **минулі стани**. Це використовують для аналізу поведінки системи, перевірки її рішень і **ретроспективного налагодження**: агрегат повертають у точний стан, у якому спостерігали помилку.

::

::card{title="Глибока аналітика" icon="i-lucide-search"}
Оптимізація основних піддоменів стратегічно важлива. Подієве джерело дає глибоке розуміння стану й поведінки системи, а нові **проєкції** можна завжди додати над наявними подіями.

::

::card{title="Журнал аудиту" icon="i-lucide-scroll-text"}
Збережені події становлять **сильно узгоджений** журнал усього, що відбувалося зі станами агрегатів. Деякі галузі за законом зобов'язані вести такий журнал. Зручно для систем із грошима.

::

::card{title="Розширений паралелізм" icon="i-lucide-scale"}
Класична оптимістична модель просто викидає виняток. З подіями можна запитати, **які саме події** додали паралельно, і ухвалити рішення за змістом: чи конфліктують вони зі спробою операції, чи їх можна ігнорувати.

::

::

## Поширені запитання

### Продуктивність

*Відновлення стану з подій погіршує продуктивність, і вона падає зі зростанням кількості подій. Як це може працювати?*

Проєкція справді потребує обчислень, що зростають разом із подіями. Тому важливо **виміряти** вплив на продуктивність: сотень чи тисяч подій. Результат порівнюють із очікуваним життєвим циклом агрегата. У більшості систем помітне погіршення починається лише після **10 000+ подій** на агрегат, а середній життєвий цикл рідко перевищує **100 подій**.

У рідкісних випадках, коли проєкція все ж стає проблемою, застосовують патерн **знімок** (*snapshot*):

1. Процес безперервно перебирає нові події у сховищі, генерує проєкції й зберігає їх у кеші.
2. Коли потрібна проєкція в пам'яті для дії над агрегатом, процес бере поточну проєкцію з кешу, отримує події, що надійшли після версії знімка, і застосовує їх у пам'яті.

![Знімок](/images/ddd/event-sourcing/event-sourced-domain-model/19-snapshot.png){.diagram-img}

::warning
Знімок — оптимізація, яку треба обґрунтувати. Якщо агрегати не накопичують 10 000+ подій, реалізація знімка лише **випадкова складність**. Спершу перевірте межі агрегата.

::

### Масштабування

*Модель генерує величезні обсяги даних. Чи масштабується вона?*

Так, легко. Усі операції відбуваються в контексті одного агрегата, тому сховище подій можна **шардувати за ідентифікатором агрегата**: усі події одного екземпляра лежать в одному шарді.

![Шардування сховища подій](/images/ddd/event-sourcing/event-sourced-domain-model/20-sharding.png){.diagram-img}

### Видалення даних

*Сховище працює лише на додавання, а якщо дані треба фізично видалити, наприклад згідно з GDPR?*

Це розв'язує патерн **«забувана корисна дія»** (*forgettable payload*): усю чутливу інформацію в подіях зберігають **зашифрованою**, а ключ шифрування лежить у зовнішньому сховищі «ключ-значення», де ключ — ідентифікатор агрегата. Коли дані треба видалити, видаляють ключ, і чутлива інформація в подіях стає недоступною.

![Забувана корисна дія](/images/ddd/event-sourcing/event-sourced-domain-model/21-forgettable.png){.diagram-img}

### А чому б просто…

::::accordion

:::accordion-item{label="…писати логи у текстовий файл як журнал аудиту?" icon="i-lucide-file-text"}
Запис і в операційну базу, і у файл логів схильний до помилок: це транзакція над двома сховищами. Якщо транзакція бази зазнає невдачі, ніхто не видаляє попередні повідомлення з логу, тож такі логи не узгоджені, а лише **зрештою неузгоджені**.

:::

:::accordion-item{label="…лишити модель стану, а в тій самій транзакції додавати записи до таблиці логів?" icon="i-lucide-table"}
Інфраструктурно це дає узгодженість, але лишається схильним до помилок: майбутній інженер може **забути** додати запис. До того ж схема таблиці логів швидко вироджується в хаос, бо немає способу змусити писати всю потрібну інформацію в правильному форматі.

:::

:::accordion-item{label="…додати тригер, що копіює запис в історичну таблицю?" icon="i-lucide-copy"}
Тригер долає попередній недолік, але історія міститиме лише «сухі факти»: **які** поля змінилися. Бракує бізнес-контексту, **чому** змінилися. Без «чому» проєктувати додаткові моделі майже неможливо.

:::

## Підсумки

- У **подієво-орієнтованій доменній моделі** всі зміни стану агрегата виражені як послідовність доменних подій, на відміну від традиційного підходу, де зміна оновлює запис у базі.
- Події дають змогу **проєктувати** поточний стан і кілька подань, кожне з яких оптимізоване під свою задачу.
- Патерн підходить, коли потрібне глибоке розуміння даних системи: для аналізу й оптимізації або через юридичну вимогу журналу аудиту.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Що правда про зв'язок доменних подій та об'єктів-значень?" icon="i-lucide-help-circle"}

Варіанти: А) події використовують об'єкти-значення для опису того, що сталося; Б) при реалізації подієвої моделі об'єкти-значення треба перетворити на агрегати; В) об'єкти-значення стосуються лише доменної моделі й у подієвій замінюються подіями; Г) усі твердження хибні.

**Відповідь: А.** Доменні події використовують об'єкти-значення для опису того, що сталося в бізнес-домені.

:::

:::accordion-item{label="❓ Питання 2. Що правда про проєктування стану з серії подій?" icon="i-lucide-help-circle"}

Варіанти: А) з подій можна спроєктувати лише одне подання; Б) багато подань, але події треба змоделювати так, щоб це підтримувати; В) багато подань, і нові проєкції можна додавати завжди; Г) усі твердження хибні.

**Відповідь: В.** Можна проєктувати кілька подань стану, і додаткові проєкції можна додати в майбутньому.

:::

:::accordion-item{label="❓ Питання 3. Чим відрізняються агрегати на стані й на подіях?" icon="i-lucide-help-circle"}

Варіанти: А) лише подієвий агрегат може породжувати події; Б) обидва варіанти породжують події, але лише подієві використовують їх як джерело істини; В) подієві гарантують генерацію події для кожного переходу стану; Г) правильні Б і В.

**Відповідь: Г.** Обидва варіанти породжують події, лише подієві використовують їх як джерело істини й гарантують подію для кожного переходу стану.

:::

:::accordion-item{label="📋 Питання 4. Яку функціональність WolfDesk варто реалізувати подієво?" icon="i-lucide-clipboard-list"}

Алгоритм життєвого циклу заявки: генерація подій для всіх переходів стану спрощує проєктування додаткових подань, оптимізованих для алгоритму виявлення шахрайства й функціональності «автопілота» підтримки.

:::
