# Багатошарова архітектура на практиці

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Розкласти невеликий застосунок на чотири шари та пояснити, що в кожному живе.
- Перевіряти напрямок залежностей між проєктами за посиланнями в `.csproj`.
- Розпізнавати типові порушення шарів: бізнес-логіку в поданні й обхід сервісного рівня.
- Оцінювати слабкі місця патерна, зокрема жорстку залежність від шару даних.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Шар (*layer*):** група коду з однією технічною відповідальністю.
- **Сервісний рівень (*service layer*):** шар, що реалізує сценарії використання поверх домену.
- **Залежність вниз:** кожен шар посилається лише на шар під собою.
- **Корінь композиції (*composition root*):** місце, де вручну створюють об'єкти та з'єднують їх.

::

::

## Задача

Ми продовжуємо працювати з **інтернет-книгарнею**: клієнт оформлює замовлення з кількох книг, оплачує його, а ми нараховуємо бонуси. Правила прості:

- знижка 10% від 1000 грн і ще 5% для Gold-клієнтів;
- статуси `New → Paid → Shipped`, відправити неоплачене не можна;
- оплата дає 1 бал за кожні 10 грн.

У попередній теорії ми описали багатошарову архітектуру загалом. Тут покажемо, як вона виглядає в коді, і де вона підводить.

---

## Крок 1. Як виглядає погана реалізація

Почнімо з вихідного варіанта, який часто трапляється на практиці: уся логіка живе у формі, консольній команді чи контролері.

```csharp
// «Подання», яке робить усе
Console.Write("ISBN: ");
var isbn = Console.ReadLine();
Console.Write("Кількість: ");
var qty = int.Parse(Console.ReadLine()!);

var book = db.Books.First(b => b.Isbn == isbn);
if (book.Stock < qty) { Console.WriteLine("Немає на складі"); return; }

var subtotal = book.Price * qty;
var total = subtotal >= 1000 ? subtotal * 0.9m : subtotal;   // знижка тут
book.Stock -= qty;
db.Orders.Add(new OrderRow { Total = total, Status = "New" });
db.SaveChanges();
```

Проблеми видно одразу:

| Проблема | Наслідок |
|---|---|
| Правило знижки лежить поруч із `Console.ReadLine` | Те саме правило довелося б копіювати в HTTP-контролер і у фонову задачу |
| Вхідні дані, правила й база змішані | Єдиний спосіб протестувати правило знижки — запустити консоль |
| Немає місця для нових вимог | Кожна нова вимога додає ще кілька рядків у ту саму «кашу» |

## Крок 2. Розкладаємо на шари

Рішення розкласти код на чотири проєкти. Кожен шар має одну відповідальність.

| Шар | Проєкт | Що містить |
|---|---|---|
| Подання | `BookShop.Console` | Читання введення, друк результату, збирання залежностей |
| Бізнес-логіка | `BookShop.Services` | Сценарії: оформити, оплатити, відправити, скасувати |
| Доступ до даних | `BookShop.Data` | Репозиторії для книг, клієнтів, замовлень |
| Предметна область | `BookShop.Domain` | `Money`, `Quantity`, `Order`, `DiscountPolicy` |

Напрямок залежностей фіксується в проєктних файлах. Подання посилається на сервіси, сервіси на дані, а всі разом на домен:

```xml
<!-- BookShop.Services.csproj -->
<ItemGroup>
  <ProjectReference Include="../BookShop.Domain/BookShop.Domain.csproj" />
  <ProjectReference Include="../BookShop.Data/BookShop.Data.csproj" />
</ItemGroup>
```

Це корисна перевірка: якщо в `BookShop.Domain.csproj` з'явилося посилання на `BookShop.Data`, архітектуру порушено, і компілятор не дасть її зібрати.

::note
Для невеликих систем шари можуть бути папками в одному проєкті. Окремі проєкти корисні тим, що компілятор сам забороняє заборонені залежності.

::

## Крок 3. Шар домену

Домен не знає ні про базу, ні про консоль. Він містить типи значень і правила.

```csharp
namespace BookShop.Domain;

public class DiscountPolicy
{
    public Money Apply(Money subtotal, Customer customer)
    {
        decimal percent = 0;
        if (subtotal.Amount >= 1000) percent += 10;
        if (customer.Loyalty == Loyalty.Gold) percent += 5;
        return subtotal - subtotal.Percent(percent);
    }
}
```

Це чистий код без залежностей, його тестують за одну секунду:

```csharp
[Theory]
[InlineData(200, false, 200)]
[InlineData(1200, false, 1080)]
[InlineData(1200, true, 1020)]
public void Discount_rules(decimal subtotal, bool gold, decimal expected)
{
    var customer = new Customer(1, "x", gold ? Loyalty.Gold : Loyalty.Regular);
    Assert.Equal(Money.Uah(expected), new DiscountPolicy().Apply(Money.Uah(subtotal), customer));
}
```

## Крок 4. Шар даних

Репозиторії приховують, як і де зберігаються об'єкти. У навчальному прикладі це словники в пам'яті, у реальному проєкті на їх місці були б SQL або ORM.

```csharp
namespace BookShop.Data;

public class OrderRepository
{
    private readonly Dictionary<int, Order> _items = new();
    private int _next = 1;

    public int NextId() => _next++;
    public Order Get(int id) => _items.TryGetValue(id, out var o)
        ? o : throw new KeyNotFoundException("Замовлення не знайдено");
    public void Save(Order order) => _items[order.Id] = order;
}
```

## Крок 5. Сервісний рівень

Сервіс описує сценарії. Він бере об'єкти з репозиторіїв, викликає правила домену й зберігає результат.

```csharp
namespace BookShop.Services;

public class OrderService
{
    private readonly BookRepository _books;
    private readonly CustomerRepository _customers;
    private readonly OrderRepository _orders;
    private readonly DiscountPolicy _discounts = new();

    // ... конструктор

    public int Checkout(int customerId, IEnumerable<(Isbn Isbn, Quantity Quantity)> items)
    {
        var customer = _customers.Get(customerId);
        var lines = new List<OrderLine>();
        foreach (var (isbn, quantity) in items)
        {
            var book = _books.Get(isbn);
            book.Take(quantity);
            _books.Save(book);
            lines.Add(new OrderLine(isbn, quantity, book.Price));
        }

        var subtotal = lines.Aggregate(Money.Zero, (sum, l) => sum + l.Subtotal);
        var order = new Order(_orders.NextId(), customerId, lines, _discounts.Apply(subtotal, customer));
        _orders.Save(order);
        return order.Id;
    }

    public void Pay(int orderId)
    {
        var order = _orders.Get(orderId);
        order.Pay();
        _orders.Save(order);

        var customer = _customers.Get(order.CustomerId);
        customer.Earn(BonusPoints.From(order.Total));
        _customers.Save(customer);
    }
}
```

Зверніть увагу, що саме *не* лежить у сервісі: правило знижки (воно в домені) і введення з консолі (воно в поданні). Сервіс лише **оркеструє**.

## Крок 6. Шар подання

Подання збирає об'єкти і викликає сервіс. Місце, де всі залежності створюють вручну, називають коренем композиції.

```csharp
var books = new BookRepository();
var customers = new CustomerRepository();
var orders = new OrderRepository();

var service = new OrderService(books, customers, orders);
var id = service.Checkout(1, new[]
{
    (new Isbn("978-0-13-235088-4"), new Quantity(1)),
    (new Isbn("978-0-321-12521-7"), new Quantity(1)),
});
service.Pay(id);
```

## Типові помилки та їх виправлення

### Бізнес-логіка в поданні

```csharp
// До: правило знижки в обробнику кнопки
var total = subtotal >= 1000 ? subtotal * 0.9m : subtotal;

// Після: подання лише викликає сервіс
var id = service.Checkout(customerId, cart);
```

### Обхід сервісного рівня

Подання напряму бере репозиторій і змінює замовлення:

```csharp
// До: подання минає сервіс і не нараховує бонуси
var order = orders.Get(id);
order.Pay();
orders.Save(order);
```

Бонуси не нараховано, бо цю логіку знає тільки `OrderService.Pay`. Виправлення просте: **подання не посилається на шар даних**. Якщо в `.csproj` подання немає посилання на `BookShop.Data`, такий код не скомпілюється. У навчальному прикладі корінь композиції створює репозиторії, тому посилання там залишається, але в реальному застосунку це місце виносять в окремий проєкт.

### Анемічні сервіси

Якщо в `OrderService` з'являються правила («якщо сума більша за 1000, то…»), а домен складається лише з геттерів і сеттерів, шари сформально є, але логіка лежить не там. Правила, що стосуються понять домену, мають жити в домені.

---

## Слабке місце патерна

Подивімося на конструктор сервісу:

```csharp
public OrderService(BookRepository books, CustomerRepository customers, OrderRepository orders)
```

Сервіс залежить від **конкретних класів** шару даних. Тому тест сервісу змушений створювати справжні репозиторії:

```csharp
public OrderServiceTests()
{
    _books.Save(new Book(new Isbn("A"), "Книга A", Money.Uah(600), 5));
    _customers.Save(new Customer(1, "Тест"));
    // Щоб протестувати сервіс, потрібен справжній шар даних: залежність жорстка.
    _service = new OrderService(_books, _customers, new OrderRepository());
}
```

Поки сховище в пам'яті, це не болить. Але коли замість нього буде SQL-база або платіжний шлюз, тести стануть повільними й нестабільними, а заміна сховища потягне за собою зміни в бізнес-логіці. Ця проблема має назву: **бізнес-логіка залежить від інфраструктури**. Її вирішує наступний патерн, порти й адаптери.

---

## Коли обирати багатошарову архітектуру

| Підходить | Не підходить |
|---|---|
| Бізнес-логіка реалізована як transaction script або active record | Основний піддомен зі складним доменом |
| Допоміжні та універсальні піддомени | Системи, де інфраструктура часто змінюється і потрібні швидкі тести |
| Невеликі команди, прості сценарії | Багато зовнішніх інтеграцій з власною логікою |

---

## Підсумки

- Шари розділяють відповідальності: подання, сервіси, дані, домен.
- Залежності йдуть тільки вниз; їх зручно фіксувати посиланнями в `.csproj`.
- Сервісний рівень оркеструє сценарії, правила лишаються в домені.
- Головне слабке місце: сервіси залежать від конкретного шару даних.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Де має лежати правило «знижка 10% від 1000 грн»?" icon="i-lucide-help-circle"}

Варіанти: А) в обробнику кнопки; Б) у репозиторії; В) у домені (`DiscountPolicy`); Г) у конфігурації бази.

**Відповідь: В.** Правило належить предметній області й не залежить ні від подання, ні від даних.

:::

:::accordion-item{label="❓ Питання 2. Що має робити сервіс `OrderService.Pay`?" icon="i-lucide-help-circle"}

Варіанти: А) містити формулу знижки; Б) знайти замовлення, викликати `order.Pay()`, зберегти, нарахувати бонуси; В) малювати кнопку; Г) створювати таблиці.

**Відповідь: Б.** Сервіс оркеструє сценарій, а правила викликає в домені.

:::

:::accordion-item{label="❓ Питання 3. Що вказує на порушення шарів?" icon="i-lucide-help-circle"}

Варіанти: А) `BookShop.Domain.csproj` посилається на `BookShop.Data`; Б) сервіс посилається на домен; В) подання посилається на сервіс; Г) дані посилаються на домен.

**Відповідь: А.** Домен — нижній шар, він не має залежати від жодного шару вище.

:::

:::accordion-item{label="❓ Питання 4. Чому тестувати `OrderService` незручно?" icon="i-lucide-help-circle"}

Варіанти: А) бо він надто короткий; Б) бо він залежить від конкретних класів шару даних; В) бо в ньому немає методів; Г) бо C# не підтримує тести.

**Відповідь: Б.** Підмінити шар даних не можна, адже сервіс посилається на конкретні класи, а не на інтерфейси.

:::
