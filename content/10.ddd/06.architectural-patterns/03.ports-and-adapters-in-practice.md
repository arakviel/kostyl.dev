# Порти й адаптери на практиці

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Виділяти порти (інтерфейси) в ядрі застосунку та описувати їх мовою предметної області.
- Писати адаптери, що реалізують порти, і розуміти, чому вони не потрапляють у ядро.
- Збирати застосунок у корені композиції.
- Тестувати сценарії з двійниками портів без бази даних та мережі.
- Помічати типові помилки: «течуть» типи інфраструктури, інтерфейси копіюють форму бази.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Порт (*port*):** інтерфейс, який оголошує ядро для зв'язку із зовнішнім світом.
- **Адаптер (*adapter*):** реалізація порту для конкретної технології.
- **Інверсія залежностей:** ядро оголошує інтерфейс, а інфраструктура від нього залежить.
- **Тестовий двійник (*test double*):** проста заміна справжнього адаптера в тестах.

::

::

## Проблема, яку ми вирішуємо

У багатошаровому варіанті книгарні сервіс залежав від конкретних класів шару даних. Тестувати такий сервіс без реальної бази неможливо, а додати нову залежність (платіжний шлюз, сповіщення) означає ще один конкретний клас у конструкторі.

Порти й адаптери змінюють напрямок залежностей. Тепер **ядро** (домен та сценарії) не знає про інфраструктуру, а інфраструктура підлаштовується під ядро.

---

## Структура рішення

| Проєкт | Роль | Залежить від |
|---|---|---|
| `BookShop.Domain` | Сутності, правила | нічого |
| `BookShop.Application` | Сценарії та **порти** | `Domain` |
| `BookShop.Adapters` | **Адаптери** (сховище, шлюз, сповіщення) | `Domain`, `Application` |
| `BookShop.Console` | Корінь композиції | усі |

Порівняйте з багатошаровим варіантом: тоді `Services` посилався на `Data`. Тепер `Application` не посилається ні на що зовнішнє. Адаптери посилаються на нього, і стрілка залежності обернулася.

---

## Крок 1. Порти

Порти оголошує **застосунок**. Інтерфейси описують те, що потрібно сценаріям, а не те, як працює база.

```csharp
namespace BookShop.Application;

public interface IOrderRepository
{
    int NextId();
    Order Get(int id);
    void Save(Order order);
}

// Вихідний порт до зовнішньої системи
public interface IPaymentGateway
{
    bool Charge(int customerId, Money amount);
}

public interface INotifier
{
    void Send(int customerId, string message);
}
```

Зверніть увагу на мову: `Charge(customerId, amount)` говорить про намір («списати гроші»), а не про HTTP-запит чи JSON.

## Крок 2. Сценарії залежать лише від портів

```csharp
public class OrderUseCases
{
    private readonly IBookRepository _books;
    private readonly ICustomerRepository _customers;
    private readonly IOrderRepository _orders;
    private readonly IPaymentGateway _payments;
    private readonly INotifier _notifier;
    private readonly DiscountPolicy _discounts = new();

    // ... конструктор отримує інтерфейси

    public void Pay(int orderId)
    {
        var order = _orders.Get(orderId);
        if (!_payments.Charge(order.CustomerId, order.Total))
            throw new InvalidOperationException("Платіж відхилено");

        order.Pay();
        _orders.Save(order);

        var customer = _customers.Get(order.CustomerId);
        customer.Earn(BonusPoints.From(order.Total));
        _customers.Save(customer);
        _notifier.Send(order.CustomerId, $"Замовлення #{orderId} оплачено");
    }
}
```

У цьому класі немає жодного `using` на базу чи HTTP-клієнт. Його можна запустити без мережі.

## Крок 3. Адаптери

Адаптери лежать в окремому проєкті й реалізують порти.

```csharp
namespace BookShop.Adapters;

public class InMemoryOrders : IOrderRepository
{
    private readonly Dictionary<int, Order> _items = new();
    private int _next = 1;

    public int NextId() => _next++;
    public Order Get(int id) => _items.TryGetValue(id, out var o)
        ? o : throw new KeyNotFoundException("Замовлення не знайдено");
    public void Save(Order order) => _items[order.Id] = order;
}

public class FakePaymentGateway : IPaymentGateway
{
    public bool Charge(int customerId, Money amount) => true;
}

public class ConsoleNotifier : INotifier
{
    public void Send(int customerId, string message) =>
        Console.WriteLine($"[сповіщення клієнту {customerId}] {message}");
}
```

Коли з'явиться справжній платіжний провайдер, ви додасте `StripePaymentGateway : IPaymentGateway` в `Adapters`, а `OrderUseCases` не зміниться.

## Крок 4. Корінь композиції

Єдине місце, де порти з'єднують з адаптерами:

```csharp
var useCases = new OrderUseCases(
    new InMemoryBooks(), new InMemoryCustomers(), new InMemoryOrders(),
    new FakePaymentGateway(), new ConsoleNotifier());

var id = useCases.Checkout(1, cart);
useCases.Pay(id);
```

У реальному застосунку цю роль виконує контейнер залежностей, але ідея та сама.

## Крок 5. Тести без інфраструктури

Головна практична вигода: сценарії тестуються за допомогою простих двійників.

```csharp
class DecliningGateway : IPaymentGateway
{
    public bool Charge(int customerId, Money amount) => false;
}

class SpyNotifier : INotifier
{
    public List<string> Messages { get; } = new();
    public void Send(int customerId, string message) => Messages.Add(message);
}

[Fact]
public void Declined_payment_keeps_order_new_and_gives_no_bonus()
{
    var useCases = Create(new DecliningGateway());
    var id = useCases.Checkout(1, Cart(2));

    Assert.Throws<InvalidOperationException>(() => useCases.Pay(id));
    Assert.Equal(OrderStatus.New, useCases.Get(id).Status);
    Assert.Equal(0, _customers.Get(1).BonusPoints);
}
```

Перевірити відмову платіжної системи зі справжнім шлюзом було б складно. Тут це три рядки.

## Типові помилки

### Інтерфейс копіює форму бази

```csharp
// До: порт повторює таблицю й SQL
public interface IOrderRepository
{
    DataTable ExecuteQuery(string sql);
    void InsertRow(string table, Dictionary<string, object> values);
}

// Після: порт говорить мовою домену
public interface IOrderRepository
{
    Order Get(int id);
    void Save(Order order);
}
```

Перший інтерфейс формально абстракція, але ядро досі знає про таблиці й SQL, тож заміна сховища все одно зачепить сценарії.

### Типи інфраструктури потрапили в ядро

Якщо `OrderUseCases` приймає `HttpRequest` або повертає `DbDataReader`, порт існує, а залежність ні. Ядро має працювати лише з типами домену й простими DTO.

### Адаптер містить бізнес-правила

```csharp
// Погано: правило знижки сховалося в адаптері
public class SqlOrders : IOrderRepository
{
    public void Save(Order order)
    {
        if (order.Total.Amount > 1000) order.ApplyExtraDiscount(); // це справа домену
        // ...
    }
}
```

Адаптер лише перекладає між ядром і технологією. Правила тримайте в домені.

### Порт на кожен клас

Не створюйте інтерфейс для кожного класу «про всяк випадок». Порт потрібен там, де є реальна межа: база, мережа, годинник, файлова система, інша команда.

## Порівняння з багатошаровою архітектурою

| Критерій | Шари | Порти й адаптери |
|---|---|---|
| Напрямок залежності на дані | Сервіс → Дані | Адаптер → Ядро |
| Тестування сценаріїв | Потрібен шар даних | Двійники портів |
| Заміна інфраструктури | Зачіпає сервіси | Нова реалізація адаптера |
| Складність | Менша | Трохи більша (інтерфейси, композиція) |
| Підходить для | Простої логіки | Моделі домену, агрегатів, event sourcing |

---

## Підсумки

- Порти оголошує ядро; адаптери їх реалізують.
- Залежності спрямовані до ядра, тому його можна тестувати й розвивати незалежно.
- Корінь композиції — єдине місце, де знають конкретні адаптери.
- Не створюйте порт без реальної межі й не кладіть правила в адаптери.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Хто оголошує порт?" icon="i-lucide-help-circle"}

Варіанти: А) інфраструктура; Б) ядро (застосунок); В) база даних; Г) UI.

**Відповідь: Б.** Інтерфейс належить тому, кому він потрібен, тобто ядру.

:::

:::accordion-item{label="❓ Питання 2. Що змінилося в графі залежностей порівняно з шарами?" icon="i-lucide-help-circle"}

Варіанти: А) нічого; Б) сервіс тепер залежить від даних; В) адаптери залежать від ядра, а не навпаки; Г) UI залежить від бази.

**Відповідь: В.** Це і є інверсія залежностей.

:::

:::accordion-item{label="❓ Питання 3. Як перевірити поведінку при відмові платіжного шлюзу?" icon="i-lucide-help-circle"}

Варіанти: А) відключити інтернет; Б) передати в сценарій двійник `IPaymentGateway`, який повертає `false`; В) змінити код сценарію; Г) вручну в продакшні.

**Відповідь: Б.** Двійник повертає потрібну відповідь без мережі.

:::

:::accordion-item{label="❓ Питання 4. Чому інтерфейс `ExecuteQuery(string sql)` — поганий порт?" icon="i-lucide-help-circle"}

Варіанти: А) бо він надто швидкий; Б) бо ядро знає про SQL і таблиці; В) бо в ньому немає параметрів; Г) бо його неможливо реалізувати.

**Відповідь: Б.** Порт має описувати наміри домену, а не форму сховища.

:::
