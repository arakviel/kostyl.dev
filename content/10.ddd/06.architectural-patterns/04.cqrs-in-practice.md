# CQRS на практиці

::card-group

::card{title="🎯 Навчальні цілі" icon="i-lucide-graduation-cap"}

- Відрізняти команди від запитів і розуміти, чому їхні моделі розділяють.
- Будувати модель читання з доменних подій за допомогою проєктора.
- Писати запити, які не залежать від агрегатів.
- Оцінювати ціну патерна: дві моделі, затримка читання, перебудова проєкції.
- Розпізнавати випадки, коли CQRS зайвий.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Команда (*command*):** намір змінити стан системи.
- **Запит (*query*):** читання даних без побічних ефектів.
- **Модель читання (*read model*):** пласка структура, оптимізована під конкретні запити.
- **Проєктор (*projector*):** компонент, що оновлює модель читання за подіями.
- **Кінцева узгодженість:** модель читання відстає від запису на короткий час.

::

::

## Навіщо розділяти

В агрегата з теми про доменну модель добре виходить **захищати правила**: оплатити, відправити, скасувати. Але інколи від системи потрібні й такі запити:

- «Покажи всі замовлення клієнта з номером, статусом і сумою»;
- «Які 5 книг найбільше купують?».

Щоб відповісти на це з агрегатів, довелося б завантажити тисячі `Order` з усіма рядками, а потім групувати їх у пам'яті. Агрегат зручний для змін, а не для звітів. CQRS пропонує дві окремі моделі: одну для **запису** (агрегати), другу для **читання** (пласкі структури під екрани).

---

## Структура рішення

| Частина | Відповідальність |
|---|---|
| `Order`, `Book`, `Customer` | Модель запису: правила та інваріанти |
| `PlaceOrder`, `PayOrder`, `CancelOrder` | Команди |
| `OrderCommandHandlers` | Виконання команд над агрегатами |
| `OrderPlaced`, `OrderPaid` та інші | Події, що зв'язують два боки |
| `OrderProjector` | Оновлення моделі читання за подіями |
| `ReadStore`, `OrderSummary`, `BestSeller` | Модель читання |
| `OrderQueries` | Запити |

## Крок 1. Команди

Команда — проста структура, яка описує намір.

```csharp
public record PlaceOrder(int CustomerId, IReadOnlyList<(Isbn Isbn, Quantity Quantity)> Items);
public record PayOrder(int OrderId);
public record CancelOrder(int OrderId);
```

Обробник завантажує агрегат, викликає його метод і публікує події. Правила залишаються в `Order`:

```csharp
public void Handle(PayOrder command)
{
    var order = _orders.Get(command.OrderId);
    order.Pay();

    var buyer = _customers.Get(order.CustomerId);
    buyer.Earn(BonusPoints.From(order.Total));
    _customers.Save(buyer);

    Commit(order);
}

private void Commit(Order order)
{
    _orders.Save(order);
    _events.Dispatch(order.PullEvents());
}
```

Обробник нічого не повертає, крім, за потреби, ідентифікатора (як `PlaceOrder` повертає номер).

## Крок 2. Події несуть дані для читання

Щоб проєктор міг побудувати модель без звернення до агрегату, подія містить усе потрібне:

```csharp
public record OrderPlaced(
    int OrderId, int CustomerId, IReadOnlyList<OrderLine> Lines, Money Total) : IDomainEvent;
public record OrderPaid(int OrderId, int CustomerId, Money Total) : IDomainEvent;
public record OrderCancelled(int OrderId, int CustomerId, bool WasPaid, Money Total) : IDomainEvent;
```

## Крок 3. Модель читання

Структура під екран: жодних інваріантів, лише дані.

```csharp
public record OrderSummary(int OrderId, int CustomerId, string Status, decimal Total, int ItemCount);
public record BestSeller(string Isbn, int Copies);
```

Проєктор слухає події й оновлює окреме сховище:

```csharp
public void On(IDomainEvent e)
{
    switch (e)
    {
        case OrderPlaced p:
            _store.Orders[p.OrderId] = new OrderSummary(
                p.OrderId, p.CustomerId, "New", p.Total.Amount, p.Lines.Sum(l => l.Quantity.Value));
            _store.LinesByOrder[p.OrderId] = p.Lines.Select(l => (l.Isbn.Value, l.Quantity.Value)).ToList();
            break;

        case OrderPaid paid:
            SetStatus(paid.OrderId, "Paid");
            foreach (var (isbn, qty) in _store.LinesByOrder[paid.OrderId])
                _store.Sold[isbn] = _store.Sold.GetValueOrDefault(isbn) + qty;
            break;

        case OrderCancelled c:
            SetStatus(c.OrderId, "Cancelled");
            if (c.WasPaid)
                foreach (var (isbn, qty) in _store.LinesByOrder[c.OrderId])
                    _store.Sold[isbn] -= qty;
            break;
    }
}
```

Ось де видно силу підходу. «Хіти продажів» враховують **лише оплачені** замовлення й автоматично зменшуються при скасуванні. Це правило читання, і воно живе лише в проєкторі, а агрегат про нього не знає.

## Крок 4. Запити

```csharp
public class OrderQueries
{
    private readonly ReadStore _store;
    public OrderQueries(ReadStore store) => _store = store;

    public OrderSummary? GetOrder(int orderId) => _store.Orders.GetValueOrDefault(orderId);

    public IReadOnlyList<OrderSummary> OrdersOfCustomer(int customerId) =>
        _store.Orders.Values.Where(o => o.CustomerId == customerId).OrderBy(o => o.OrderId).ToList();

    public IReadOnlyList<BestSeller> BestSellers(int top) =>
        _store.Sold.Where(kv => kv.Value > 0)
            .OrderByDescending(kv => kv.Value)
            .Take(top)
            .Select(kv => new BestSeller(kv.Key, kv.Value))
            .ToList();
}
```

У запитах немає жодного посилання на `Order` чи `Customer`. Вони не можуть випадково щось змінити.

## Крок 5. Тести

```csharp
[Fact]
public void Best_sellers_count_only_paid_orders()
{
    var paid = Place("A", 3);
    Place("B", 5);                    // не оплачено
    _commands.Handle(new PayOrder(paid));

    var top = _queries.BestSellers(5);
    Assert.Single(top);
    Assert.Equal(new BestSeller("A", 3), top[0]);
}

[Fact]
public void Cancelling_paid_order_removes_it_from_best_sellers()
{
    var id = Place("A", 3);
    _commands.Handle(new PayOrder(id));
    _commands.Handle(new CancelOrder(id));

    Assert.Empty(_queries.BestSellers(5));
    Assert.Equal("Cancelled", _queries.GetOrder(id)!.Status);
}
```

## Синхронна й асинхронна проєкція

У навчальному прикладі проєктор викликається одразу після збереження, тому читання завжди актуальне. У реальній системі є два варіанти:

| Варіант | Як працює | Плюси | Мінуси |
|---|---|---|---|
| Синхронна проєкція | Оновлюється в тій самій операції | Читання одразу бачить зміни | Запис повільніший, зв'язок між моделями тісніший |
| Асинхронна проєкція | Окремий процес читає події з черги чи журналу | Масштабується, не гальмує запис | Читання відстає; потрібна контрольна точка |

Для асинхронного варіанта клієнт, який щойно оплатив замовлення, на мить побачить старий статус. Це ціна кінцевої узгодженості. Практичний вихід: після команди повертати нове значення з моделі запису або показувати користувачу «оновлюється».

## Типові помилки

### Запит змінює стан

```csharp
// Погано: «читання» збільшує лічильник у моделі запису
public OrderSummary GetOrder(int id)
{
    var order = _orders.Get(id);
    order.MarkViewed();   // запит став командою
    _orders.Save(order);
    // ...
}
```

Запит не має побічних ефектів. Якщо потрібен лічильник переглядів, це окрема команда.

### Проєктор містить бізнес-правила

Проєктор лише переносить факти з подій у зручний вигляд. Якщо в ньому з'являються перевірки «чи можна оплатити», правила дублюються й розходяться з агрегатом.

### CQRS для кожного екрана

```csharp
// Зайве: простий довідник «Жанри» не потребує двох моделей
public record GetGenreQuery(int Id);
public record GenreReadModel(int Id, string Name);
```

Для довідників та CRUD-екранів двох моделей і проєкторів не потрібно. Вони лише збільшать обсяг коду.

### Забули про перебудову

Помилка в проєкторі пошкодила модель читання. Якщо джерелом правди є події чи таблиці запису, модель читання можна очистити й побудувати заново. Закладайте цю можливість із самого початку.

## Коли виправдано CQRS

| Підходить | Не підходить |
|---|---|
| Різні вимоги до читання й запису (навантаження, форма даних) | Простий CRUD |
| Складні запити, що погано лягають на агрегати | Команда, яка не може підтримувати дві моделі |
| Є event sourcing: проєкції потрібні майже завжди | Усі екрани читають ті самі агрегати без звітів |
| Кілька різних подань тих самих даних | Жорстка вимога негайної узгодженості скрізь |

---

## Підсумки

- Команди змінюють стан через агрегати, запити читають окрему модель.
- Модель читання будується проєктором за подіями й може бути перебудована.
- Асинхронні проєкції масштабуються, але дають затримку читання.
- CQRS додає складність: використовуйте його там, де читання й запис справді різні.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Питання 1. Що повертає обробник команди?" icon="i-lucide-help-circle"}

Варіанти: А) довільний звіт; Б) нічого або мінімум, як ідентифікатор створеного об'єкта; В) повну модель читання; Г) HTML-сторінку.

**Відповідь: Б.** Команда змінює стан; дані для показу читають запитом.

:::

:::accordion-item{label="❓ Питання 2. Чому «хіти продажів» легше будувати в моделі читання?" icon="i-lucide-help-circle"}

Варіанти: А) бо вона швидша за процесор; Б) бо проєктор уже підсумовує проданий обсяг за подіями, не завантажуючи агрегати; В) бо агрегат не має ISBN; Г) бо запити можуть змінювати агрегати.

**Відповідь: Б.** Модель читання зберігає готові значення під запит.

:::

:::accordion-item{label="❓ Питання 3. Що станеться з асинхронною проєкцією після команди?" icon="i-lucide-help-circle"}

Варіанти: А) модель читання оновиться миттєво; Б) модель читання може на короткий час відставати; В) агрегат зникне; Г) команда відкотиться.

**Відповідь: Б.** Це кінцева узгодженість.

:::

:::accordion-item{label="❓ Питання 4. Для якого екрана CQRS зайвий?" icon="i-lucide-help-circle"}

Варіанти: А) звіт про хіти продажів; Б) простий довідник жанрів; В) історія замовлень із фільтрами; Г) панель керівника з агрегованими показниками.

**Відповідь: Б.** Простий довідник не потребує окремої моделі читання.

:::
