# RTK Query на mobile

## Відкриття: серверний state — це окрема відповідальність

У попередній статті ми навчилися керувати **клієнтським state** через Redux Toolkit: тема інтерфейсу, вибрані фільтри, стан форми — усе, що живе лише в пам'яті застосунку й не залежить від сервера. Ми створили slice, написали reducer, підключили typed hooks. Усе працювало добре, поки ми не зіткнулися з реальною задачею: **отримати дані з API**.

Уявіть типову ситуацію. Користувач відкриває екран списку поїздок у застосунку Nomad. Застосунок надсилає HTTP-запит на сервер: `GET /api/trips`. Сервер повертає масив об'єктів. Ми зберігаємо цей масив у Redux store, щоб компонент міг його відмалювати. Поки що все логічно.

Але через хвилину користувач повертається на цей самий екран. Що робити? Запитати сервер ще раз — навіть якщо дані не змінилися? Чи показати те, що вже є в пам'яті? А якщо дані застаріли — як зрозуміти, коли їх треба оновити? А якщо користувач створив нову поїздку на іншому екрані — як автоматично «визнати застарілим» список, щоб при поверненні він оновився?

Ці питання **не стосуються бізнес-логіки** вашого продукту. Вони стосуються **інфраструктури роботи з сервером**: коли запитувати, як кешувати, як оновлювати, як показувати spinner під час запиту, як обробляти помилки. Якщо писати цю логіку вручну в кожному slice — ви отримаєте купу однотипного коду: `loading`, `error`, `data`, thunk для fetch, обробка success/failure, invalidation вручну.

**RTK Query** (скорочено RTKQ) — це офіційний інструмент Redux Toolkit, який бере на себе всю цю рутину. Ви описуєте **endpoints** (які запити існують у вашому API), а RTKQ автоматично генерує Redux-slice з усією логікою кешування, hooks для компонентів, механізм invalidation і навіть optimistic updates. Ви пишете менше коду, а отримуєте більше можливостей.

У цій статті ми розглянемо, як працює RTK Query у контексті мобільного застосунку — де є особливості lifecycle (застосунок ховається у фон, повертається на передній план), де мережа може зникнути й з'явитися знову, де користувач очікує миттєвого відгуку навіть під час завантаження. Ми розберемо `createApi`, систему тегів для invalidation, автоматичне refetch при поверненні на екран, optimistic updates і pagination. Міні-проєкт покаже, як зробити простий TODO-список з віддаленим API, а в Nomad ми перепишемо роботу зі списком поїздок через RTK Query замість ручного `fetch` і slice.

::note
**Головна думка розділу**  
RTK Query — це **не окремий state manager**, а спеціалізований шар поверх Redux Toolkit для роботи з серверним state. Він автоматично керує кешем, запитами, invalidation і UI-станами (loading/error), щоб ви могли зосередитися на бізнес-логіці, а не на рутині fetch/cache.
::

## Що таке RTK Query і навіщо він потрібен

### Серверний state vs клієнтський state

У React-застосунку (і веб, і мобільному) є два типи даних, які живуть у state:

1. **Клієнтський state** (client state) — те, що існує лише на пристрої користувача й не залежить від сервера. Наприклад: вибрана тема інтерфейсу (light/dark), відкрита вкладка навігації, стан форми (користувач набрав текст, але ще не відправив), UI-флаги («показати модальне вікно», «згорнути секцію»). Цей state **не синхронізується** з сервером — він існує лише в пам'яті застосунку, і якщо перезапустити застосунок без персистенції, він зникне або повернеться до дефолтних значень.

2. **Серверний state** (server state) — дані, **джерело правди** яких лежить на сервері. Наприклад: список поїздок користувача, профіль користувача, повідомлення в чаті. Застосунок **запитує** ці дані через API, зберігає локальну копію (кеш), малює UI на основі цієї копії. Але «справжні» дані — на сервері; локальна копія може застаріти, і тоді треба запитати знову.

Історично в Redux-застосунках обидва типи state часто мішали в одному store. Наприклад, ви створювали slice `trips` з полями:

```typescript
interface TripsState {
  items: Trip[];
  loading: boolean;
  error: string | null;
}
```

І писали async thunk:

```typescript
export const fetchTrips = createAsyncThunk('trips/fetch', async () => {
  const response = await fetch('/api/trips');
  return response.json();
});
```

І в reducer обробляли `pending`, `fulfilled`, `rejected`. І робили те саме для `createTrip`, `updateTrip`, `deleteTrip`. І в кожному slice повторювали цю тріаду `loading`/`error`/`data`. І вручну писали логіку invalidation: «якщо створили поїздку, треба скинути флаг "дані актуальні" для списку, щоб він запитався знову».

**RTK Query каже:** весь цей шаблонний код можна генерувати автоматично. Ви просто **описуєте endpoints** (які HTTP-методи і URL існують у вашому API), а RTKQ створює:

- Redux slice з усіма reducer для кешу;
- React hooks на кшталт `useGetTripsQuery()`, `useCreateTripMutation()`;
- логіку автоматичного refetch при зміні аргументів запиту або при invalidation;
- UI-стани `isLoading`, `isFetching`, `isError`, `data`, `error` — прямо в hook;
- механізм тегів (tags) для декларативної invalidation: «якщо створили поїздку, визнай застарілим список поїздок».

### Lifecycle серверного state

Коли ви працюєте з серверним state, ви проходите через кілька етапів:

1. **Запит** (request) — застосунок надсилає HTTP-запит на сервер (GET, POST, PATCH, DELETE тощо).
2. **Очікування** (loading) — UI показує spinner або skeleton, щоб користувач розумів: «дані в дорозі».
3. **Отримання відповіді** (response) — сервер повертає дані або помилку.
4. **Кешування** (caching) — якщо запит успішний, дані зберігаються в пам'яті (кеш), щоб наступного разу не запитувати сервер знову (якщо дані ще актуальні).
5. **Invalidation** — коли щось змінилося на сервері (користувач створив/видалив/оновив сутність), локальний кеш стає застарілим. Треба або викинути його, або запитати сервер знову.
6. **Refetch** — застосунок запитує сервер повторно, щоб отримати свіжі дані (наприклад, користувач потягнув список вниз — pull-to-refresh, або застосунок повернувся з фону на передній план).

Якщо писати це вручну, ви витратите багато часу на «сантехніку» замість бізнес-логіки. RTK Query автоматизує весь цей lifecycle.

### Порівняння з іншими інструментами

У веб-екосистемі React є кілька популярних бібліотек для роботи з серверним state:

| Інструмент | Філософія | Коли підходить |
|------------|-----------|----------------|
| **RTK Query** | Вбудований у Redux Toolkit; декларативні endpoints + tags invalidation | Якщо ви вже використовуєте Redux для клієнтського state і хочете єдину екосистему |
| **TanStack Query** (колишня React Query) | Agnostic до state manager; hooks-first; автоматичне refetch, stale-while-revalidate | Якщо ви не хочете Redux або вже маєте Zustand/Context для клієнтського state |
| **SWR** | Stale-while-revalidate pattern; мінімалістичний | Легкі застосунки без складної invalidation |
| **Apollo Client** | Спеціалізований для GraphQL | Якщо ваш backend — GraphQL, а не REST |

У попередній статті курсу (17) ми розглянемо альтернативу: Zustand + TanStack Query. Зараз зосередимося на **RTK Query**, бо він найкраще інтегрується з Redux Toolkit, який ми вже налаштували в Nomad.

::tip
**Запам'ятайте аналогію**  
RTK Query — це як «автоматична коробка передач» для серверних запитів. Ви говорите **куди** їхати (який endpoint), а вона сама перемикає «передачі» (loading → success → cache → invalidation). Ручний fetch + reducer — це «механіка»: ви контролюєте кожен рух, але це довше й складніше.
::

## Анатомія `createApi`

RTK Query працює через функцію **`createApi`**. Ви викликаєте її один раз (зазвичай у файлі `api.ts` або `baseApi.ts`), описуєте endpoints вашого API, і вона повертає об'єкт з автоматично згенерованими hooks і reducer.

### Мінімальний приклад

```typescript
// src/services/api.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

interface Trip {
  id: string;
  title: string;
  startDate: string;
}

export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
    }),
  }),
});

export const { useGetTripsQuery } = api;
```

Що тут відбувається:

1. **`reducerPath`** — ім'я slice у Redux store. Зазвичай `'api'`, але якщо у вас кілька API (наприклад, один для основного backend, другий для аналітики), можна назвати інакше (`'mainApi'`, `'analyticsApi'`).

2. **`baseQuery`** — функція, яка виконує HTTP-запити. `fetchBaseQuery` — це обгортка над браузерним `fetch`, яка автоматично додає `baseUrl` до кожного endpoint і серіалізує JSON. Ви можете написати свій `baseQuery`, наприклад, на основі axios або з кастомною логікою (додавання токена, retry тощо) — але зазвичай `fetchBaseQuery` достатньо.

3. **`endpoints`** — функція, яка отримує `builder` і повертає об'єкт з описом усіх endpoints вашого API. Кожен endpoint — це або **query** (читання даних, GET), або **mutation** (зміна даних, POST/PATCH/DELETE).

4. **`builder.query<ResultType, ArgType>`** — описує query-endpoint. `ResultType` — тип даних, які поверне сервер; `ArgType` — тип аргументу, який приймає hook (у цьому прикладі `void`, бо `/trips` не потребує параметрів). Метод `query` повертає URL (відносно `baseUrl`) або об'єкт з `url`, `method`, `body` тощо.

5. **`useGetTripsQuery`** — автоматично згенерований hook. Назва складається з `use` + назва endpoint (з великої літери) + `Query`. Цей hook ви викликаєте в компоненті, і він **автоматично** запускає запит, кешує дані, надає `data`, `isLoading`, `error`.

### Підключення до store

RTK Query генерує reducer і middleware. Їх треба додати до Redux store:

```typescript
// src/store/index.ts
import { configureStore } from '@reduxjs/toolkit';
import { api } from '@/services/api';

export const store = configureStore({
  reducer: {
    [api.reducerPath]: api.reducer,
    // інші slice (напр. theme, user)
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(api.middleware),
});
```

**Middleware** потрібен, щоб RTK Query міг:

- автоматично виконувати refetch при invalidation;
- скасовувати запити, які вже не потрібні (наприклад, компонент розмонтувався);
- керувати lifecycle підписок на дані (якщо два компоненти підписані на один endpoint, запит виконається один раз, дані шаряться).

::warning
**Типова плутанина**  
Новачки іноді забувають додати `api.middleware` у store — і тоді RTK Query працює частково: hooks повертають дані, але автоматичний refetch і invalidation **не спрацьовують**. Якщо ви бачите, що дані не оновлюються після mutation, перевірте middleware.
::

### Використання в компоненті

```typescript
// src/screens/TripsScreen.tsx
import { useGetTripsQuery } from '@/services/api';
import { View, Text, ActivityIndicator } from 'react-native';

export function TripsScreen() {
  const { data, isLoading, error } = useGetTripsQuery();

  if (isLoading) {
    return <ActivityIndicator size="large" />;
  }

  if (error) {
    return <Text>Помилка завантаження</Text>;
  }

  return (
    <View>
      {data?.map((trip) => (
        <Text key={trip.id}>{trip.title}</Text>
      ))}
    </View>
  );
}
```

Зверніть увагу: **ви не писали жодного reducer**, не викликали `dispatch`, не створювали async thunk. Ви просто описали endpoint і викликали hook. RTK Query **автоматично**:

- запустив HTTP-запит при монтуванні компонента;
- поклав дані в Redux store (slice `api`);
- надав `isLoading = true` під час запиту;
- після отримання відповіді надав `data` і `isLoading = false`;
- якщо помилка — надав `error`.

Це і є головна перевага RTK Query: **менше коду, більше автоматизації**.

## Query endpoints: читання даних

Query-endpoint — це endpoint, який **читає** дані з сервера (зазвичай HTTP GET, але може бути й POST, якщо API так спроектовано). RTK Query кешує результат query і повертає його з кешу, якщо запит виконується повторно з тими самими аргументами.

### Endpoint з параметрами

Часто endpoint потребує аргументів. Наприклад, щоб отримати деталі конкретної поїздки, ви робите `GET /trips/:id`.

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  endpoints: (builder) => ({
    getTripById: builder.query<Trip, string>({
      query: (id) => `/trips/${id}`,
    }),
  }),
});

export const { useGetTripByIdQuery } = api;
```

Тепер `useGetTripByIdQuery` приймає аргумент:

```typescript
const { data: trip } = useGetTripByIdQuery('trip-123');
```

RTK Query **автоматично кешує** результат за ключем `['getTripById', 'trip-123']`. Якщо інший компонент викличе `useGetTripByIdQuery('trip-123')`, він отримає дані з кешу **миттєво**, без повторного запиту (якщо кеш ще актуальний).

### Query з об'єктом параметрів

Якщо аргументів кілька (наприклад, фільтри списку), передайте об'єкт:

```typescript
interface GetTripsArgs {
  status?: 'planned' | 'completed';
  limit?: number;
}

export const api = createApi({
  // ...
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], GetTripsArgs | void>({
      query: (args) => {
        const params = new URLSearchParams();
        if (args?.status) params.set('status', args.status);
        if (args?.limit) params.set('limit', String(args.limit));
        return `/trips?${params}`;
      },
    }),
  }),
});
```

Виклик:

```typescript
const { data } = useGetTripsQuery({ status: 'planned', limit: 20 });
```

RTK Query **серіалізує** об'єкт аргументів у рядок для ключа кешу (за замовчуванням через `JSON.stringify` з сортуванням ключів). Якщо ви викличете `useGetTripsQuery({ limit: 20, status: 'planned' })` (у іншому порядку), RTK Query **розпізнає**, що це той самий запит, і поверне дані з кешу.

### UI-стани hook

Hook `useGetTripsQuery` повертає об'єкт з кількома полями:

| Поле | Тип | Значення |
|------|-----|----------|
| `data` | `Trip[] \| undefined` | Дані з кешу або з сервера (якщо запит успішний) |
| `isLoading` | `boolean` | `true`, якщо це **перший** запит (кешу ще немає) і запит іще не завершився |
| `isFetching` | `boolean` | `true`, якщо запит іде **зараз** (навіть якщо кеш уже є — наприклад, refetch) |
| `isSuccess` | `boolean` | `true`, якщо запит завершився успішно і є `data` |
| `isError` | `boolean` | `true`, якщо запит завершився з помилкою |
| `error` | `FetchBaseQueryError \| SerializedError \| undefined` | Об'єкт помилки (якщо `isError = true`) |
| `refetch` | `() => void` | Функція, щоб вручну запустити запит знову (наприклад, при pull-to-refresh) |

**Різниця `isLoading` vs `isFetching`:**

- `isLoading` — користувач **вперше** бачить екран, даних ще немає. Зазвичай тут показують повноекранний spinner або skeleton.
- `isFetching` — запит іде, але дані **вже є** в кеші (можливо, застарілі). Зазвичай тут показують маленький індикатор «оновлюється», а старі дані лишаються на екрані.

Приклад UX:

```typescript
const { data, isLoading, isFetching, error, refetch } = useGetTripsQuery();

if (isLoading) {
  return <FullScreenSpinner />;
}

if (error) {
  return <ErrorBanner onRetry={refetch} />;
}

return (
  <View>
    {isFetching && <TopBanner>Оновлюється…</TopBanner>}
    <FlatList data={data} renderItem={...} />
  </View>
);
```

::tip
**Практична порада**  
Використовуйте `isLoading` для **першого завантаження** (skeleton), а `isFetching` для **фонового оновлення** (маленький індикатор). Це дає користувачу відчуття «застосунок швидкий, дані вже є, просто оновлюються», а не «кожен раз весь екран блокується спіннером».
::

## Mutation endpoints: зміна даних

Mutation-endpoint — це endpoint, який **змінює** дані на сервері (створення, оновлення, видалення). У REST API це зазвичай POST, PATCH, PUT, DELETE.

### Створення mutation

```typescript
interface CreateTripPayload {
  title: string;
  startDate: string;
}

export const api = createApi({
  // ...
  endpoints: (builder) => ({
    createTrip: builder.mutation<Trip, CreateTripPayload>({
      query: (payload) => ({
        url: '/trips',
        method: 'POST',
        body: payload,
      }),
    }),
  }),
});

export const { useCreateTripMutation } = api;
```

**Різниця з query:**

- `builder.mutation` замість `builder.query`;
- hook називається `useCreateTripMutation` (не `Query`, а `Mutation`);
- hook **не запускає** запит автоматично при монтуванні компонента. Ви отримуєте функцію `trigger`, яку викликаєте вручну (наприклад, при натисканні кнопки).

### Використання в компоненті

```typescript
import { useCreateTripMutation } from '@/services/api';
import { Button } from 'react-native';

export function CreateTripButton() {
  const [createTrip, { isLoading, isSuccess, error }] = useCreateTripMutation();

  const handlePress = async () => {
    try {
      const newTrip = await createTrip({
        title: 'Поїздка до Львова',
        startDate: '2026-09-01',
      }).unwrap();
      console.log('Створено поїздку:', newTrip);
    } catch (err) {
      console.error('Помилка:', err);
    }
  };

  return (
    <Button title="Створити поїздку" onPress={handlePress} disabled={isLoading} />
  );
}
```

**Що тут відбувається:**

1. `useCreateTripMutation()` повертає tuple: `[trigger, result]`.
2. `trigger` — функція, яка приймає payload (`CreateTripPayload`) і запускає HTTP-запит. Вона повертає Promise з методом `.unwrap()`, який «розгортає» результат або кидає помилку (як звичайний Promise).
3. `result` — об'єкт зі станами `isLoading`, `isSuccess`, `isError`, `error`, `data`.

**Чому `.unwrap()`?**  
За замовчуванням `trigger` повертає Promise, який **не відхиляється** (reject) при помилці — він завжди resolve з об'єктом `{ data?, error? }`. Це зручно для Redux-логіки, але в async/await незручно. Метод `.unwrap()` перетворює це на звичайний Promise: resolve з `data` при успіху, reject з `error` при помилці.

### Відміна попереднього запиту

Якщо користувач швидко натискає кнопку кілька разів, RTK Query **не скасовує** попередні запити автоматично (на відміну від query, де повторний виклик з тими самими аргументами просто поверне кеш). Кожен виклик `trigger` створює новий запит.

Щоб уникнути дублювання, зазвичай **відключають кнопку** під час `isLoading`:

```typescript
<Button disabled={isLoading} />
```

Або використовують `fixedCacheKey` (детально пізніше).

## Система тегів: декларативна invalidation

Уявіть, що ви створили нову поїздку через `createTrip` mutation. Сервер прийняв дані, повернув об'єкт новоствореної поїздки. Але на екрані списку поїздок досі **старі** дані — бо коли ви завантажували список раніше, нової поїздки ще не було, і RTK Query закешував той список. Як «сказати» RTK Query, що кеш списку **застарів** і треба запитати сервер знову?

Ручний спосіб (без тегів): викликати `refetch()` у компоненті списку. Але це незручно — треба пам'ятати, які запити треба оновити після якої mutation. Якщо mutation відбувається на іншому екрані, ви маєте прокидати callback або слухати Redux action.

**RTK Query пропонує декларативний механізм: теги (tags).** Ви «мітите» кожен query і mutation тегами, які описують, які дані вони **надають** (provides) і які дані вони **визнають застарілими** (invalidates). RTK Query **автоматично** виконає refetch усіх query, кеш яких було визнано застарілим.


### Як працюють теги

Теги — це **рядки** (або об'єкти з `type` і `id`), які ви задаєте у двох місцях:

1. **`providesTags`** у query — «цей query надає дані з такими тегами». Наприклад, список поїздок надає тег `'Trip'` (або `{ type: 'Trip', id: 'LIST' }`).
2. **`invalidatesTags`** у mutation — «ця mutation визнає застарілими дані з такими тегами». Наприклад, створення поїздки визнає застарілим тег `'Trip'`.

Коли ви викликаєте mutation з `invalidatesTags: ['Trip']`, RTK Query:

- знаходить усі query, які мають `providesTags: ['Trip']`;
- визнає їхній кеш застарілим;
- якщо є **активні підписки** на ці query (тобто компонент змонтований і викликав відповідний hook), RTK Query автоматично **запускає refetch**.


### Приклад: список і створення

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  tagTypes: ['Trip'], // 1. Оголосити типи тегів
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      providesTags: ['Trip'], // 2. Query надає тег 'Trip'
    }),
    createTrip: builder.mutation<Trip, CreateTripPayload>({
      query: (payload) => ({
        url: '/trips',
        method: 'POST',
        body: payload,
      }),
      invalidatesTags: ['Trip'], // 3. Mutation визнає 'Trip' застарілим
    }),
  }),
});
```

**Що відбувається покроково:**

1. Користувач відкриває екран списку поїздок. Компонент викликає `useGetTripsQuery()`. RTK Query виконує `GET /trips`, кешує результат і **мітить цей кеш** тегом `'Trip'`.
2. Користувач натискає «Створити поїздку», заповнює форму, натискає «Зберегти». Компонент викликає `createTrip(payload)`. RTK Query виконує `POST /trips`.
3. Коли POST успішний, RTK Query бачить `invalidatesTags: ['Trip']` і **визнає застарілим** увесь кеш, який має тег `'Trip'`.
4. Якщо екран списку досі відкритий (компонент змонтований і підписаний на `useGetTripsQuery`), RTK Query **автоматично** запускає `GET /trips` знову. Користувач бачить оновлений список з новою поїздкою — **без** ручного виклику `refetch`.


::note
**Головна думка**  
Теги — це «мітки» на кеші. Query каже: «я надаю дані з міткою X». Mutation каже: «я псую дані з міткою X». RTK Query автоматично оновлює всі query, чий кеш було «зіпсовано».
::

### Теги зі специфічним ID

Іноді треба визнавати застарілим не **весь** кеш типу `'Trip'`, а лише **конкретну** сутність. Наприклад, ви оновили назву поїздки `trip-123` — треба визнати застарілим кеш `getTripById('trip-123')`, але **не** треба перезапитувати весь список поїздок (бо він може бути великим).

Для цього використовують **теги з ID**:

```typescript
export const api = createApi({
  // ...
  tagTypes: ['Trip'],
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      providesTags: (result) =>
        result
          ? [
              ...result.map((trip) => ({ type: 'Trip' as const, id: trip.id })),
              { type: 'Trip', id: 'LIST' },
            ]
          : [{ type: 'Trip', id: 'LIST' }],
    }),
    getTripById: builder.query<Trip, string>({
      query: (id) => `/trips/${id}`,
      providesTags: (result, error, id) => [{ type: 'Trip', id }],
    }),
    updateTrip: builder.mutation<Trip, { id: string; title: string }>({
      query: ({ id, title }) => ({
        url: `/trips/${id}`,
        method: 'PATCH',
        body: { title },
      }),
      invalidatesTags: (result, error, { id }) => [{ type: 'Trip', id }],
    }),
  }),
});
```


**Розбір:**

1. **`getTrips`** надає:
   - Тег `{ type: 'Trip', id: 'LIST' }` — для списку як цілого.
   - По одному тегу `{ type: 'Trip', id: trip.id }` для кожної поїздки у списку. Це означає: «якщо хтось визнає застарілим конкретну поїздку, я **теж** мушу оновитися, бо можу містити цю поїздку».

2. **`getTripById`** надає тег `{ type: 'Trip', id }` — де `id` — аргумент query (наприклад, `'trip-123'`).

3. **`updateTrip`** визнає застарілим лише `{ type: 'Trip', id }` — конкретну поїздку, яку оновили.

**Сценарій:**

- Екран списку викликає `useGetTripsQuery()`. Кеш мітиться тегами `{ type: 'Trip', id: 'LIST' }`, `{ type: 'Trip', id: 'trip-123' }`, `{ type: 'Trip', id: 'trip-456' }` тощо.
- Екран деталей викликає `useGetTripByIdQuery('trip-123')`. Кеш мітиться тегом `{ type: 'Trip', id: 'trip-123' }`.
- Користувач на екрані деталей змінює назву. Виконується `updateTrip({ id: 'trip-123', title: 'Нова назва' })`. Mutation визнає застарілим тег `{ type: 'Trip', id: 'trip-123' }`.
- RTK Query **refetch** два query: `getTripById('trip-123')` (бо він прямо надає цей тег) **і** `getTrips` (бо він теж надає цей тег — адже список містить `trip-123`).

Якщо ви оновили `trip-789`, який **не** відображається у списку (наприклад, список показує лише перші 20 поїздок), RTK Query **не** буде refetch списку — бо список не надає тег `{ type: 'Trip', id: 'trip-789' }`.


::tip
**Практична порада**  
Якщо mutation **створює** нову сутність, зазвичай визнають застарілим тег `{ type: 'Trip', id: 'LIST' }` — щоб список оновився. Якщо mutation **оновлює** існуючу, визнають застарілим `{ type: 'Trip', id: specificId }` — щоб оновилися лише query, які стосуються цієї конкретної сутності. Якщо mutation **видаляє**, визнають застарілими обидва теги (і `LIST`, і `specificId`).
::

### Чому не перезапитувати весь список кожного разу?

Технічно можна просто писати `invalidatesTags: ['Trip']` (без ID) для будь-якої mutation — і RTK Query буде refetch весь список після кожної зміни. Це працює, але **неефективно**:

- Якщо список великий (1000 поїздок), ви щоразу завантажуєте всі 1000, навіть якщо змінилася лише одна.
- Якщо список з пагінацією (ви завантажили сторінку 1, потім сторінку 2), і ви оновили поїздку на сторінці 5 — навіщо refetch сторінки 1 і 2?

Теги з ID дають **гранулярний** контроль: оновлюєте лише те, що справді змінилося.

## Refetch при зміні lifecycle: focus і network

У веб-застосунку вкладка браузера зазвичай **завжди відкрита**. У мобільному застосунку користувач **часто** ховає застосунок у фон (перемикається на іншу програму, блокує екран) і повертається через хвилину, годину або день. За цей час дані на сервері могли змінитися. RTK Query надає механізми **автоматичного refetch** при поверненні застосунку на передній план або при відновленні мережі.

### Refetch on focus

Коли застосунок повертається з фону на передній план (наприклад, користувач розблокував телефон і знову відкрив застосунок), RTK Query може автоматично виконати refetch усіх активних query.

Це вмикається через опцію **`refetchOnFocus`** (за замовчуванням `false` глобально, але можна встановити `true` для окремих endpoints або глобально).

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  refetchOnFocus: true, // Глобально для всіх endpoints
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      // або локально для цього endpoint:
      // keepUnusedDataFor: 60, // (секунди)
    }),
  }),
});
```

**Як це працює під капотом:**

RTK Query підписується на події `AppState` (у React Native) або `focus`/`blur` вкладки (у вебі). Коли застосунок переходить у стан `active`, RTK Query перевіряє всі query, які мають активні підписки (тобто компонент змонтований), і якщо для них увімкнено `refetchOnFocus`, виконує refetch.


**Приклад життєвого сценарію:**

Користувач відкриває екран списку поїздок, бачить 5 поїздок. Потім перемикається на Telegram, читає повідомлення 10 хвилин. За цей час колега (з яким спільна поїздка) додав нове місце до поїздки через веб-інтерфейс. Користувач повертається до застосунку Nomad — і завдяки `refetchOnFocus` список **автоматично** оновлюється, показуючи нові дані. Без цієї опції користувач бачив би старі дані, поки не потягне список вниз (pull-to-refresh) вручну.

::warning
**Типова плутанина**  
`refetchOnFocus` спрацьовує **лише** якщо компонент **змонтований** і викликав hook. Якщо користувач перейшов на інший екран (компонент розмонтувався), а потім повернувся, RTK Query **не** виконає refetch автоматично при фокусі застосунку — бо підписки вже немає. Refetch відбудеться при **повторному виклику** hook (тобто при монтуванні компонента знову), якщо кеш застарів (див. `keepUnusedDataFor`).
::

### Refetch on reconnect

Подібна опція — **`refetchOnReconnect`** — для ситуації, коли мережа **зникла** й **з'явилася** знову. Наприклад, користувач увійшов у метро (втратив інтернет), вийшов на поверхню (інтернет повернувся). RTK Query може автоматично refetch усі query, які були активні під час втрати мережі.

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  refetchOnReconnect: true, // Глобально
  endpoints: (builder) => ({
    // ...
  }),
});
```


RTK Query слухає події `NetInfo` (у React Native) або браузерну подію `online`. Коли мережа з'являється знову, виконується refetch.

::tip
**Практична порада для mobile**  
Увімкніть обидві опції (`refetchOnFocus` і `refetchOnReconnect`) глобально або принаймні для критичних endpoints (списки, профіль). Це дає користувачу відчуття «застосунок завжди показує свіжі дані», навіть якщо він довго не оновлював екран вручну.
::

### `keepUnusedDataFor` — скільки тримати кеш без підписки

Коли компонент розмонтується (наприклад, користувач перейшов на інший екран), підписка на query зникає. RTK Query **не видаляє** кеш одразу — він зберігає його протягом `keepUnusedDataFor` секунд (за замовчуванням **60 секунд**). Якщо протягом цього часу компонент знову змонтується і викличе той самий hook, дані **миттєво** візьмуться з кешу, без нового запиту.

Якщо ж пройшло більше 60 секунд, кеш видаляється, і при наступному виклику hook виконається запит з нуля (з `isLoading = true`).

Ви можете налаштувати це глобально або для окремих endpoints:

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  keepUnusedDataFor: 300, // 5 хвилин глобально
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      keepUnusedDataFor: 120, // 2 хвилини для цього endpoint
    }),
  }),
});
```

**Життєвий сценарій:**

Користувач відкриває список поїздок (завантажується з сервера), переходить на екран деталей однієї поїздки (список розмонтувався), через 30 секунд повертається назад до списку. Завдяки `keepUnusedDataFor: 60` список **миттєво** з'являється з кешу, без spinner. Якщо ж користувач повернувся через 5 хвилин (більше 60 секунд), список завантажиться знову з сервера.

## Optimistic updates: миттєвий відгук без очікування сервера

Коли користувач натискає «Лайк» у соціальній мережі, іконка серця **миттєво** стає червоною — не чекаючи, поки сервер підтвердить операцію. Це називається **optimistic update** (оптимістичне оновлення): ми **припускаємо**, що сервер прийме зміну, і оновлюємо UI одразу. Якщо сервер поверне помилку, ми **відкочуємо** зміну назад.

RTK Query підтримує optimistic updates через механізм **`onQueryStarted`** — lifecycle-хук, який виконується **одразу після** запуску mutation, до того як прийшла відповідь від сервера.

### Приклад: optimistic створення поїздки

Уявіть, що користувач створює нову поїздку. Ми хочемо **одразу** додати її до списку в UI, не чекаючи відповіді від сервера. Якщо сервер повертає помилку, ми видалимо її зі списку назад.

```typescript
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  tagTypes: ['Trip'],
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      providesTags: [{ type: 'Trip', id: 'LIST' }],
    }),
    createTrip: builder.mutation<Trip, CreateTripPayload>({
      query: (payload) => ({
        url: '/trips',
        method: 'POST',
        body: payload,
      }),
      async onQueryStarted(payload, { dispatch, queryFulfilled }) {
        // 1. Створюємо тимчасовий ID для optimistic update
        const tempId = `temp-${Date.now()}`;
        const optimisticTrip: Trip = {
          id: tempId,
          title: payload.title,
          startDate: payload.startDate,
        };

        // 2. Оновлюємо кеш списку, додаючи нову поїздку
        const patchResult = dispatch(
          api.util.updateQueryData('getTrips', undefined, (draft) => {
            draft.push(optimisticTrip);
          })
        );

        try {
          // 3. Чекаємо на відповідь сервера
          const { data: createdTrip } = await queryFulfilled;

          // 4. Сервер повернув справжню поїздку з реальним ID
          //    Замінюємо тимчасову на реальну
          dispatch(
            api.util.updateQueryData('getTrips', undefined, (draft) => {
              const index = draft.findIndex((t) => t.id === tempId);
              if (index !== -1) {
                draft[index] = createdTrip;
              }
            })
          );
        } catch {
          // 5. Якщо помилка — відкочуємо optimistic update
          patchResult.undo();
        }
      },
      // Якщо не потрібен optimistic update, достатньо invalidatesTags:
      // invalidatesTags: [{ type: 'Trip', id: 'LIST' }],
    }),
  }),
});
```


**Розбір коду:**

1. **`onQueryStarted`** — функція, яка виконується **одразу після** запуску mutation (коли викликали `createTrip(payload)`, але HTTP-запит ще не завершився). Вона отримує два аргументи:
   - `payload` — дані, які передали в mutation.
   - Об'єкт з `dispatch`, `queryFulfilled` (Promise, який resolve, коли сервер відповість), `getCacheEntry` тощо.

2. **Створення тимчасового ID** — бо сервер поверне реальний ID (`uuid` тощо), але ми ще не знаємо його. Генеруємо тимчасовий (`temp-123456`), щоб React міг відрізнити цей елемент у списку (для `key`).

3. **`api.util.updateQueryData`** — RTK Query надає утиліту для **прямого** оновлення кешу конкретного query. Перший аргумент — назва endpoint (`'getTrips'`), другий — аргумент query (`undefined`, бо `getTrips` не має параметрів), третій — функція, яка отримує **draft** (Immer proxy) кешу і може його змінювати (через `push`, `splice` тощо, ніби це мутабельний масив).

4. **`dispatch(updateQueryData(...))`** повертає об'єкт з методом **`.undo()`**, який **відкочує** зміну. Ми зберігаємо його у `patchResult`.

5. **`await queryFulfilled`** — чекаємо на відповідь сервера. Якщо запит успішний, `queryFulfilled` resolve з `{ data }`. Якщо помилка, `queryFulfilled` reject.

6. Якщо успіх — замінюємо тимчасову поїздку (з `tempId`) на реальну (з ID від сервера). Якщо помилка — викликаємо `patchResult.undo()`, і кеш повертається до стану «до optimistic update».


**Що бачить користувач:**

1. Користувач натискає «Створити поїздку» → форма надсилається.
2. **Миттєво** (до відповіді сервера) нова поїздка з'являється у списку (з тимчасовим ID).
3. Через 100–500 мс сервер відповідає успішно → тимчасовий ID замінюється на реальний (користувач цього не помічає, бо візуально нічого не змінилося).
4. Якщо сервер повернув помилку (наприклад, валідація не пройшла) → поїздка **зникає** зі списку, показується повідомлення про помилку.

::note
**Головна думка**  
Optimistic updates роблять застосунок **швидшим на відчуття**. Користувач не чекає 500 мс на відповідь сервера — UI реагує миттєво. Це особливо важливо в мобільних мережах, де затримка може бути 200–1000 мс.
::

### Коли використовувати optimistic updates?

| Операція | Чи варто optimistic update? | Чому |
|----------|----------------------------|------|
| Лайк поста, додавання в обране | Так | Висока ймовірність успіху; користувач очікує миттєвого відгуку |
| Створення запису (поїздка, нотатка) | Так, якщо валідація проста | Якщо валідація складна (перевірка унікальності на сервері), краще чекати підтвердження |
| Видалення запису | Так, з обережністю | Якщо помилка, треба повернути запис назад і показати чітке повідомлення |
| Оплата, зміна пароля, критичні операції | Ні | Користувач має **бачити** підтвердження від сервера |


::warning
**Типова помилка**  
Якщо ви використовуєте optimistic update **і** `invalidatesTags` одночасно, може статися подвійний refetch: спочатку optimistic update додає елемент у кеш, потім `invalidatesTags` запускає refetch, і сервер повертає список **без** нового елемента (бо запит пішов раніше, ніж сервер встиг обробити mutation). Результат: нова поїздка «блимає» на екрані й зникає. **Рішення:** якщо робите optimistic update, **не** використовуйте `invalidatesTags` для того самого списку — оновлюйте кеш вручну через `updateQueryData`.
::

## Pagination: завантаження даних частинами

Якщо список великий (сотні або тисячі записів), завантажувати все одразу — неефективно. Замість цього використовують **pagination** (посторінкове завантаження): спочатку завантажуємо перші 20 записів, потім наступні 20 тощо.

RTK Query **не має вбудованого** механізму pagination (на відміну від TanStack Query з `useInfiniteQuery`), але ви можете реалізувати його вручну через `query` з параметрами і логіку «додавання» нових сторінок до кешу.

### Cursor-based pagination (приклад)

Припустімо, сервер підтримує cursor-based pagination: ви надсилаєте `GET /trips?cursor=abc123&limit=20`, сервер повертає масив записів + `nextCursor` (для наступної сторінки).

```typescript
interface TripsPage {
  trips: Trip[];
  nextCursor: string | null;
}

export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  endpoints: (builder) => ({
    getTripsPage: builder.query<TripsPage, string | void>({
      query: (cursor) => {
        const params = new URLSearchParams();
        if (cursor) params.set('cursor', cursor);
        params.set('limit', '20');
        return `/trips?${params}`;
      },
      // Merge нових даних у кеш (для infinite scroll)
      serializeQueryArgs: ({ endpointName }) => endpointName, // Один кеш для всіх сторінок
      merge: (currentCache, newItems) => {
        currentCache.trips.push(...newItems.trips);
        currentCache.nextCursor = newItems.nextCursor;
      },
      forceRefetch({ currentArg, previousArg }) {
        return currentArg !== previousArg;
      },
    }),
  }),
});
```


**Розбір:**

1. **`serializeQueryArgs`** — за замовчуванням RTK Query створює окремий кеш для кожного набору аргументів (якщо викликали `getTripsPage(undefined)` і `getTripsPage('cursor-123')`, це два різні кеші). Але для pagination ми хочемо **один** кеш, в який **додаємо** нові сторінки. Тому ми перевизначаємо `serializeQueryArgs`, щоб він повертав завжди одне й те саме значення (назву endpoint) — так усі сторінки потрапляють в один кеш.

2. **`merge`** — функція, яка **об'єднує** нові дані зі старими в кеші. `currentCache` — поточний стан кешу (перша сторінка), `newItems` — нові дані (друга сторінка). Ми додаємо нові поїздки до масиву `trips` і оновлюємо `nextCursor`.

3. **`forceRefetch`** — функція, яка вирішує, чи потрібно **запускати новий запит**, навіть якщо кеш уже є. Ми кажемо: «якщо аргумент змінився (новий cursor), запускай запит». Без цього RTK Query поверне кеш, а не виконає запит.

**Використання в компоненті:**

```typescript
import { useGetTripsPageQuery } from '@/services/api';
import { FlatList, Button } from 'react-native';
import { useState } from 'react';

export function TripsScreen() {
  const [cursor, setCursor] = useState<string | undefined>(undefined);
  const { data, isLoading, isFetching } = useGetTripsPageQuery(cursor);

  const loadMore = () => {
    if (data?.nextCursor) {
      setCursor(data.nextCursor);
    }
  };

  return (
    <FlatList
      data={data?.trips}
      renderItem={({ item }) => <TripCard trip={item} />}
      ListFooterComponent={
        isFetching ? (
          <ActivityIndicator />
        ) : data?.nextCursor ? (
          <Button title="Завантажити ще" onPress={loadMore} />
        ) : null
      }
    />
  );
}
```


**Що відбувається:**

1. При монтуванні компонента `cursor = undefined`. Викликається `useGetTripsPageQuery(undefined)` → запит `GET /trips?limit=20` → перша сторінка завантажується в кеш.
2. Користувач скролить до кінця списку, натискає «Завантажити ще». Викликається `setCursor(data.nextCursor)` (наприклад, `'cursor-abc'`).
3. Викликається `useGetTripsPageQuery('cursor-abc')` → запит `GET /trips?cursor=cursor-abc&limit=20` → друга сторінка завантажується.
4. Функція `merge` додає нові 20 поїздок до існуючого масиву в кеші → `data.trips` тепер містить 40 поїздок.
5. Користувач бачить оновлений список без перезавантаження перших 20.

::tip
**Альтернатива: TanStack Query**  
Якщо ваш застосунок **heavily** покладається на pagination (багато списків, infinite scroll), розгляньте **TanStack Query** (React Query) — у нього є вбудований `useInfiniteQuery` з автоматичним merge і `fetchNextPage`. RTK Query вимагає ручної реалізації через `merge` / `serializeQueryArgs`, що більш багатослівно. Ми розглянемо TanStack Query у статті 17.
::

### Offset-based pagination

Якщо сервер використовує offset/limit (`GET /trips?offset=0&limit=20`, потім `offset=20&limit=20`), логіка схожа, але замість `cursor` ви тримаєте `offset` у state і збільшуєте його на `limit` при кожній загрузці.

### Крок 3. Налаштування RTK Query API

::collapsible{title="src/services/todosApi.ts — повний код (розгорніть за потреби)"}

```typescript
// src/services/todosApi.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export interface Todo {
  id: number;
  userId: number;
  title: string;
  completed: boolean;
}

export interface CreateTodoPayload {
  title: string;
  userId: number;
}

export const todosApi = createApi({
  reducerPath: 'todosApi',
  baseQuery: fetchBaseQuery({ 
    baseUrl: 'https://jsonplaceholder.typicode.com' 
  }),
  tagTypes: ['Todo'],
  endpoints: (builder) => ({
    // Query: отримати список todos
    getTodos: builder.query<Todo[], void>({
      query: () => '/todos?_limit=20', // Обмежимо 20 записів для швидкості
      providesTags: (result) =>
        result
          ? [
              ...result.map(({ id }) => ({ type: 'Todo' as const, id })),
              { type: 'Todo', id: 'LIST' },
            ]
          : [{ type: 'Todo', id: 'LIST' }],
    }),

    // Mutation: створити todo
    createTodo: builder.mutation<Todo, CreateTodoPayload>({
      query: (payload) => ({
        url: '/todos',
        method: 'POST',
        body: payload,
      }),
      invalidatesTags: [{ type: 'Todo', id: 'LIST' }],
    }),

    // Mutation: видалити todo
    deleteTodo: builder.mutation<void, number>({
      query: (id) => ({
        url: `/todos/${id}`,
        method: 'DELETE',
      }),
      invalidatesTags: (result, error, id) => [{ type: 'Todo', id }],
    }),

    // Mutation: перемкнути статус completed
    toggleTodo: builder.mutation<Todo, { id: number; completed: boolean }>({
      query: ({ id, completed }) => ({
        url: `/todos/${id}`,
        method: 'PATCH',
        body: { completed },
      }),
      invalidatesTags: (result, error, { id }) => [{ type: 'Todo', id }],
    }),
  }),
});

export const {
  useGetTodosQuery,
  useCreateTodoMutation,
  useDeleteTodoMutation,
  useToggleTodoMutation,
} = todosApi;
```

::

**Пояснення:**

- **`getTodos`** надає теги для кожного todo (`{ type: 'Todo', id: 1 }`, `{ type: 'Todo', id: 2 }` тощо) **і** тег для списку як цілого (`{ type: 'Todo', id: 'LIST' }`).
- **`createTodo`** визнає застарілим `LIST` — щоб список оновився після створення.
- **`deleteTodo`** і **`toggleTodo`** визнають застарілим конкретний todo за ID — щоб оновилися query, які використовують цей todo (якщо є екран деталей todo, він теж оновиться).

::note
**JSONPlaceholder особливість**  
JSONPlaceholder — це **mock API**. Коли ви робите POST `/todos`, сервер **не зберігає** дані реально (при наступному GET їх не буде). Але він **імітує** успішну відповідь (повертає об'єкт з `id: 201`). Для навчання це ідеально — ви бачите, як працює RTK Query, без необхідності розгортати власний backend.
::

### Крок 9. Перевірка роботи

Запустіть застосунок:

```bash
npx expo start
```

**Що перевірити:**

1. **Список завантажується:** при відкритті застосунку ви бачите spinner, потім список з 20 todos (з JSONPlaceholder).
2. **Створення todo:** введіть текст у поле «Нове завдання», натисніть «Додати». Ви побачите Alert «Завдання створено!». Після цього список **автоматично** refetch (завдяки `invalidatesTags`) — і ви бачите, що запит пішов знову (можете відкрити Network tab у Expo DevTools або Flipper).  
   **Увага:** JSONPlaceholder **не зберігає** нові todos реально, тому при refetch ви побачите ті самі 20 записів, що були. Але це нормально для mock API — важливо, що механізм invalidation **спрацював**.
3. **Toggle todo:** натисніть на checkbox будь-якого todo. Іконка зміниться на ✓, текст перекреслиться. Mutation `toggleTodo` виконається, але JSONPlaceholder не зберігає зміни, тому при refetch todo повернеться до початкового стану. (Якщо хочете, щоб зміни «трималися» у кеші, додайте optimistic update — див. наступний крок.)
4. **Видалення todo:** натисніть смітник. Todo зникне зі списку (бо `invalidatesTags` визнає його застарілим і refetch поверне список без нього — хоча JSONPlaceholder не видаляє реально).
5. **Pull-to-refresh:** потягніть список вниз. Індикатор оновлення з'явиться, список refetch.
6. **Refetch on focus (опціонально):** згорніть застосунок (перейдіть на Home screen), почекайте 5 секунд, поверніться до застосунку. Якщо ви додали `refetchOnFocus: true` у `getTodos` endpoint, ви побачите, що список автоматично refetch (індикатор оновлення на мить з'явиться).

::tip
**Практична порада**  
Щоб побачити, що invalidation працює, відкрийте Redux DevTools (якщо підключені) або Flipper Network Inspector — ви побачите, що після mutation одразу йде новий GET-запит на `/todos`. Це і є автоматичний refetch завдяки тегам.
::


### Крок 10 (опціонально). Optimistic update для toggle

Якщо ви хочете, щоб checkbox реагував **миттєво** (без затримки на відповідь сервера), додайте optimistic update у `toggleTodo`:

```typescript
// У src/services/todosApi.ts, у toggleTodo mutation:
toggleTodo: builder.mutation<Todo, { id: number; completed: boolean }>({
  query: ({ id, completed }) => ({
    url: `/todos/${id}`,
    method: 'PATCH',
    body: { completed },
  }),
  async onQueryStarted({ id, completed }, { dispatch, queryFulfilled }) {
    // Optimistic update
    const patchResult = dispatch(
      todosApi.util.updateQueryData('getTodos', undefined, (draft) => {
        const todo = draft.find((t) => t.id === id);
        if (todo) {
          todo.completed = completed;
        }
      })
    );

    try {
      await queryFulfilled;
    } catch {
      patchResult.undo(); // Якщо помилка, відкочуємо зміну
    }
  },
  // Видаліть invalidatesTags, бо ми вручну оновлюємо кеш
}),
```

Тепер при натисканні на checkbox UI змінюється **миттєво**, без чекання на сервер. Якщо сервер поверне помилку (що малоймовірно для JSONPlaceholder, але можливо при втраті мережі), зміна відкотиться назад.

Ми створили повнофункціональний TODO-застосунок з RTK Query, який демонструє:

## Наскрізний проєкт «Nomad»

### Навіщо користувачу

У попередній статті ми навчили Nomad **зберігати** список поїздок у Redux store і **завантажувати** його з json-server через async thunk. Це працює, але вимагає багато ручного коду: ми самі керуємо станами `loading`, `error`, `items`, самі пишемо thunk, самі обробляємо `pending`/`fulfilled`/`rejected`.

У цій статті ми **переведемо** роботу з API на RTK Query. Це дасть:

- **Менше коду** — RTK Query автоматично генерує hooks і керує станами.
- **Автоматичне кешування** — якщо користувач повертається на екран списку, дані беруться з кешу миттєво (без spinner).
- **Invalidation через теги** — коли створимо нову поїздку, список автоматично оновиться без ручного `dispatch`.
- **Refetch on focus** — коли користувач повертається до застосунку після паузи, список автоматично оновлюється, якщо екран активний.

### Нитка проєкту

#### Уже є (з попередніх статей)

### Покрокові зміни

#### Крок 1. Створення RTK Query API

Створюємо файл `src/services/tripsApi.ts` (нова папка `services/` — загальноприйнята конвенція для RTK Query).

```typescript
// src/services/tripsApi.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import { Platform } from 'react-native';
import Constants from 'expo-constants';

import type { Trip, CreateTripPayload } from '@/features/trips/model/types';

/** Визначаємо baseURL залежно від платформи (Android Emulator / iOS Simulator / physical device) */
const getBaseUrl = (): string => {
  if (Platform.OS === 'android') {
    return 'http://10.0.2.2:3000';
  }

  const hostUri = Constants.expoConfig?.hostUri;
  if (hostUri) {
    const ip = hostUri.split(':').shift();
    if (ip) return `http://${ip}:3000`;
  }

  return 'http://localhost:3000';
};

export const tripsApi = createApi({
  reducerPath: 'tripsApi',
  baseQuery: fetchBaseQuery({
    baseUrl: getBaseUrl(),
    timeout: 8000,
  }),
  tagTypes: ['Trip'],
  refetchOnFocus: true,    // Автоматичний refetch при поверненні застосунку на передній план
  refetchOnReconnect: true, // Автоматичний refetch при відновленні мережі
  endpoints: (builder) => ({
    // Query: отримати список поїздок
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      providesTags: (result) =>
        result
          ? [
              ...result.map(({ id }) => ({ type: 'Trip' as const, id })),
              { type: 'Trip', id: 'LIST' },
            ]
          : [{ type: 'Trip', id: 'LIST' }],
    }),

    // Query: отримати одну поїздку за ID (для deep link / деталей)
    getTripById: builder.query<Trip, string>({
      query: (id) => `/trips/${id}`,
      providesTags: (result, error, id) => [{ type: 'Trip', id }],
    }),

    // Mutation: створити нову поїздку
    createTrip: builder.mutation<Trip, CreateTripPayload>({
      query: (payload) => ({
        url: '/trips',
        method: 'POST',
        body: payload,
      }),
      invalidatesTags: [{ type: 'Trip', id: 'LIST' }],
    }),
  }),
});

export const {
  useGetTripsQuery,
  useGetTripByIdQuery,
  useCreateTripMutation,
} = tripsApi;
```

**Пояснення:**

- Ми перенесли логіку `getBaseUrl()` з `client.ts` прямо в RTK Query (можна було б залишити окремо, але для простоти — в одному місці).
- `providesTags` для `getTrips` — кожна поїздка мітиться своїм ID **і** є загальний тег `LIST`.
- `createTrip` визнає застарілим `LIST` — щоб після створення список автоматично refetch.
- Увімкнули глобально `refetchOnFocus` і `refetchOnReconnect` — щоб дані завжди були свіжими.


#### Крок 2. Оновлення Redux store

Видаляємо старий `tripsSlice` і `fetchTripsThunk`, підключаємо RTK Query reducer і middleware.

```typescript
// src/store/index.ts
import { configureStore } from '@reduxjs/toolkit';
import { setupListeners } from '@reduxjs/toolkit/query';

import { tripsApi } from '@/services/tripsApi';

export const store = configureStore({
  reducer: {
    [tripsApi.reducerPath]: tripsApi.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(tripsApi.middleware),
});

// Увімкнення refetchOnFocus і refetchOnReconnect
setupListeners(store.dispatch);

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

**Зміни:**

- Видалили `tripsReducer` — тепер немає окремого slice для trips.
- Додали `tripsApi.reducer` під ключем `tripsApi.reducerPath`.
- Додали `tripsApi.middleware` — без нього не працюватимуть invalidation і refetch.
- Викликали `setupListeners(store.dispatch)` — це активує слухачів `AppState` і `NetInfo` для автоматичного refetch.

```typescript
// src/features/trips/ui/CreateTripForm.tsx (або де у вас форма)
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { useRouter } from 'expo-router';
import { Alert } from 'react-native';

import { useCreateTripMutation } from '@/services/tripsApi';
import { createTripSchema, type CreateTripFormData } from '../model/validation';
import type { CreateTripPayload } from '../model/types';

export function CreateTripForm() {
  const router = useRouter();
  const [createTrip, { isLoading }] = useCreateTripMutation();

  const { control, handleSubmit, formState: { errors } } = useForm<CreateTripFormData>({
    resolver: zodResolver(createTripSchema),
  });

  const onSubmit = async (data: CreateTripFormData) => {
    const payload: CreateTripPayload = {
      title: data.title,
      startDate: data.startDate,
      endDate: data.endDate || null,
      description: data.description || null,
    };

    try {
      await createTrip(payload).unwrap();
      Alert.alert('Успіх', 'Поїздку створено!');
      router.back(); // Повертаємося на екран списку
    } catch (error) {
      Alert.alert('Помилка', 'Не вдалося створити поїздку');
    }
  };

  return (
    <View>
      {/* Поля форми (Controller для title, startDate, endDate, description) */}
      <Button
        title={isLoading ? 'Створюємо...' : 'Зберегти'}
        onPress={handleSubmit(onSubmit)}
        disabled={isLoading}
      />
    </View>
  );
}
```

**Що змінилося:**

- Замість `dispatch(addTrip(newTrip))` викликаємо `createTrip(payload).unwrap()`.
- RTK Query **автоматично** надсилає POST-запит на сервер.
- Після успіху RTK Query **автоматично** визнає застарілим тег `{ type: 'Trip', id: 'LIST' }` → екран списку (якщо він активний) **автоматично** refetch і покаже нову поїздку.
- Нам **не треба** вручну оновлювати store або викликати `refetch` в іншому компоненті — RTK Query робить це сам через теги.

```typescript
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import { Platform } from 'react-native';
import Constants from 'expo-constants';

import type { Trip, CreateTripPayload } from '@/features/trips/model/types';

const getBaseUrl = (): string => {
  if (Platform.OS === 'android') {
    return 'http://10.0.2.2:3000';
  }

  const hostUri = Constants.expoConfig?.hostUri;
  if (hostUri) {
    const ip = hostUri.split(':').shift();
    if (ip) return `http://${ip}:3000`;
  }

  return 'http://localhost:3000';
};

export const tripsApi = createApi({
  reducerPath: 'tripsApi',
  baseQuery: fetchBaseQuery({
    baseUrl: getBaseUrl(),
    timeout: 8000,
  }),
  tagTypes: ['Trip'],
  refetchOnFocus: true,
  refetchOnReconnect: true,
  endpoints: (builder) => ({
    getTrips: builder.query<Trip[], void>({
      query: () => '/trips',
      providesTags: (result) =>
        result
          ? [
              ...result.map(({ id }) => ({ type: 'Trip' as const, id })),
              { type: 'Trip', id: 'LIST' },
            ]
          : [{ type: 'Trip', id: 'LIST' }],
    }),

    getTripById: builder.query<Trip, string>({
      query: (id) => `/trips/${id}`,
      providesTags: (result, error, id) => [{ type: 'Trip', id }],
    }),

    createTrip: builder.mutation<Trip, CreateTripPayload>({
      query: (payload) => ({
        url: '/trips',
        method: 'POST',
        body: payload,
      }),
      invalidatesTags: [{ type: 'Trip', id: 'LIST' }],
    }),
  }),
});

export const {
  useGetTripsQuery,
  useGetTripByIdQuery,
  useCreateTripMutation,
} = tripsApi;
```

```typescript
import { createContext, useContext, useState, useEffect, type ReactNode } from 'react';
import { useColorScheme } from 'react-native';

import { lightTheme, darkTheme, type Theme } from './tokens';

interface ThemeContextValue {
  theme: 'light' | 'dark' | 'system';
  colors: Theme['colors'];
  setTheme: (theme: 'light' | 'dark' | 'system') => void;
}

const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const systemScheme = useColorScheme();
  const [theme, setTheme] = useState<'light' | 'dark' | 'system'>('system');

  const activeScheme = theme === 'system' ? systemScheme || 'light' : theme;
  const colors = activeScheme === 'dark' ? darkTheme.colors : lightTheme.colors;

  return (
    <ThemeContext.Provider value={{ theme, colors, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const context = useContext(ThemeContext);
  if (!context) throw new Error('useTheme must be used within ThemeProvider');
  return context;
}
```

### Перевірка

Запустіть json-server і застосунок:

```bash
# Термінал 1: json-server
cd /path/to/nomad
npm run api

# Термінал 2: expo
npm start
```

**Що перевірити:**

1. **Автоматичне завантаження списку:**  
   Відкрийте екран «Поїздки». Ви побачите spinner, потім список з двох поїздок з `db.json`. RTK Query автоматично запустив `GET /trips` при монтуванні компонента.

2. **Кешування:**  
   Перейдіть на вкладку «Профіль», потім поверніться на «Поїздки». Список з'явиться **миттєво** (без spinner) — бо RTK Query взяв дані з кешу (кеш живе 60 секунд за замовчуванням).

3. **Створення поїздки + invalidation:**  
   Натисніть «Створити поїздку», заповніть форму, натисніть «Зберегти». Ви побачите Alert «Успіх», форма закриється. На екрані списку **автоматично** з'явиться нова поїздка — без ручного виклику `refetch`. Це спрацювала invalidation через тег `{ type: 'Trip', id: 'LIST' }`.

4. **Pull-to-refresh:**  
   Потягніть список вниз. Індикатор оновлення з'явиться, список refetch (ви побачите мерехтіння мережевого запиту в DevTools або Flipper).

5. **Refetch on focus (мобільний тест):**  
   Згорніть застосунок (Home screen на телефоні або Cmd+Shift+H в Simulator), почекайте 5 секунд, поверніться. Якщо екран «Поїздки» був активний, RTK Query автоматично refetch список (ви побачите короткий індикатор оновлення вгорі, якщо дані змінилися на сервері — вони оновляться).

6. **Обробка помилок:**  
   Зупиніть json-server (`Ctrl+C` в терміналі 1). Refetch список (pull-to-refresh). Ви побачите екран помилки з кнопкою «Спробувати знову». Запустіть json-server знову, натисніть кнопку — список завантажиться.

## Підсумок

У цій статті ми повністю перевели роботу з серверним state на RTK Query — офіційний інструмент Redux Toolkit для API-запитів. Ми розібрали:

- **`createApi`** і автоматичну генерацію hooks, reducer, middleware.
- **Query endpoints** (читання) і **mutation endpoints** (зміна даних).
- **Систему тегів** для декларативної invalidation — після mutation список автоматично оновлюється без ручного `refetch`.
- **Refetch on focus / reconnect** — застосунок завжди показує свіжі дані після повернення з фону або відновлення мережі.
- **Optimistic updates** — UI реагує миттєво, не чекаючи на сервер.
- **Pagination** — завантаження даних частинами з merge у один кеш.

Міні-проєкт TODO показав повний цикл: список, створення, toggle, видалення — все через RTK Query без ручних reducer і thunk. У Nomad ми замінили старий Redux slice на RTK Query, скоротивши код у кілька разів і отримавши автоматичне кешування, invalidation і refetch.

У наступній статті (17) ми розглянемо **альтернативний стек**: Zustand (для клієнтського state) + TanStack Query (для серверного state) — щоб ви могли порівняти два підходи й обрати той, що підходить вашому проєкту.

::tip
**Ключовий висновок**  
RTK Query — це не «магія», а **автоматизація** шаблонного коду, який ви писали б вручну: reducer для кешу, middleware для refetch, селектори для UI-станів, логіка invalidation. Ви описуєте **що** (які endpoints), а RTK Query генерує **як** (reducer, hooks, invalidation). Це дозволяє зосередитися на бізнес-логіці, а не на «сантехніці» state management.
::
