## Вступ: від білду до рук користувачів

Ви завершили розробку застосунку. Код працює бездоганно, дизайн відшліфований, тестування пройдено. Тепер настав момент істини — публікація у **App Store** (iOS) та **Google Play Store** (Android), де ваш застосунок стане доступним для мільйонів користувачів по всьому світу.

Публікація мобільного застосунку — це не просто натискання кнопки «Опублікувати». Це багатоетапний процес, що включає:

- Створення облікових записів розробника ($99/рік для Apple, $25 одноразово для Google)
- Підготовку маркетингових матеріалів (іконка, скріншоти, опис, відео-превью)
- Налаштування метаданих (категорія, вікові обмеження, ціна)
- Проходження модерації (App Review для iOS, автоматичний скан для Android)
- Управління версіями та оновленнями

Процес публікації в App Store та Google Play принципово відрізняється за філософією:

::card-group

::card{title="🍎 App Store (Apple)" icon="i-lucide-apple"}

**Філософія:** Жорсткий контроль якості через ручну модерацію.

- ✅ Кожен білд перевіряється людиною (App Review Team)
- ✅ Висока довіра користувачів до якості застосунків
- ⏱️ Модерація 24–72 години (іноді до 7 днів)
- ❌ Відхилення за порушення Guidelines (~40% при першій спробі)
- 💰 $99/рік за Developer Program

::

::card{title="🤖 Google Play (Android)" icon="i-lucide-smartphone"}

**Філософія:** Автоматизована модерація з ручною перевіркою вибіркових застосунків.

- ✅ Автоматичний скан на шкідливий код та політики
- ⏱️ Публікація 1–3 години (іноді миттєво)
- 🔍 Ручна перевірка лише підозрілих застосунків
- ❌ Відхилення рідше (~15%), але за серйозні порушення — permanent ban
- 💰 $25 одноразово за Developer Account

::

::

### Мета цієї лекції

Ця лекція проведе вас через **весь процес публікації** від створення облікового запису до отримання першого завантаження:

::steps

### Крок 1: Підготовка застосунку до релізу
Фінальні перевірки коду, оптимізація, створення production білду через EAS Build.

### Крок 2: Маркетингові матеріали
Іконка застосунку, скріншоти, опис, ключові слова, promotional відео.

### Крок 3: Створення облікових записів розробника
Реєстрація у Apple Developer Program та Google Play Console.

### Крок 4: Налаштування метаданих в App Store Connect
Заповнення інформації про застосунок, категорії, ціноутворення, доступність за регіонами.

### Крок 5: Налаштування метаданих у Google Play Console
Аналогічно для Android, але з особливостями платформи.

### Крок 6: Завантаження білдів
Upload IPA до App Store Connect, AAB до Google Play Console.

### Крок 7: Проходження модерації
Підготовка до App Review, типові причини відхилень, як відповідати на запити модераторів.

### Крок 8: Публікація та моніторинг
Запуск у production, відстеження установок, робота з відгуками користувачів.

::

## Передумови: що потрібно мати перед публікацією

Перед початком процесу публікації переконайтеся, що у вас є:

::field-group

::field{name="Production білди" type="required"}
Створені через EAS Build або локально: `.ipa` для iOS, `.aab` для Android. Детально розглянуто у лекції **29. EAS Build та профілі збірки**.
::

::field{name="Іконка застосунку" type="required"}
Квадратна іконка **1024×1024 пікселів** у форматі PNG без прозорості. Без заокруглених кутів (платформи додають їх автоматично).
::

::field{name="Скріншоти" type="required"}
Мінімум 2 скріншоти для кожної підтримуваної платформи. Вимоги до розмірів різні для iOS/Android (детально нижче).
::

::field{name="Опис застосунку" type="required"}
Короткий (до 80 символів) та повний (до 4000 символів) опис. Має відповідати функціоналу застосунку.
::

::field{name="Privacy Policy URL" type="required"}
Обов'язкова вимога обох платформ. Може бути розміщена на вашому сайті або через [privacypolicies.com](https://www.privacypolicies.com).
::

::field{name="Support URL або Email" type="required"}
Контактна інформація для користувачів. Apple вимагає URL, Google дозволяє email.
::

::field{name="Банківський рахунок (для платних застосунків)" type="optional"}
Для отримання виплат від продажів або in-app purchases. Налаштовується у Developer Console.
::

::field{name="Тестові облікові записи" type="recommended"}
Для App Review команди — доступ до застосунку якщо потрібна авторизація. Apple вимагає обов'язково.
::

::

::warning
**Типова помилка початківців:** Спроба подати на модерацію застосунок з placeholder-контентом (Lorem ipsum, тестові зображення, незавершений функціонал). Це призводить до миттєвого відхилення. Apple та Google вимагають **повністю готовий до використання продукт**.
::

## Крок 1: Фінальна підготовка застосунку

### 1.1. Чек-лист перед релізом

Перед створенням production білду пройдіть цей чек-лист:

::accordion

::accordion-item{label="✅ Функціональність повністю реалізована" icon="i-lucide-check-circle"}

- Всі екрани працюють без краш-помилок
- Навігація між екранами логічна та інтуїтивна
- Форми валідуються коректно
- API інтеграції працюють стабільно
- Push-нотифікації доставляються

::

::accordion-item{label="✅ Видалено тестові та дебаг-елементи" icon="i-lucide-check-circle"}

```typescript
// ❌ ВИДАЛИТИ перед релізом:
console.log('User data:', userData); // логи з sensitive даними
alert('TODO: implement this'); // незакінчені функції
<Button title="Test Crash" onPress={() => { throw new Error() }} />
```

Перевірте через глобальний пошук:
```bash
grep -r "console.log" src/
grep -r "TODO" src/
grep -r "FIXME" src/
grep -r "alert(" src/
```

::

::accordion-item{label="✅ Змінні оточення налаштовані для production" icon="i-lucide-check-circle"}

```typescript
// config.ts
const ENV = {
  development: {
    apiUrl: 'http://localhost:3000',
    enableLogging: true,
  },
  production: {
    apiUrl: 'https://api.myapp.com', // ← перевірте!
    enableLogging: false,
  },
};

export default __DEV__ ? ENV.development : ENV.production;
```

Перевірте `eas.json`:
```json
{
  "build": {
    "production": {
      "env": {
        "API_URL": "https://api.myapp.com",
        "STRIPE_PUBLIC_KEY": "pk_live_...", // не pk_test_!
      }
    }
  }
}
```

::

::accordion-item{label="✅ Версіонування налаштоване коректно" icon="i-lucide-check-circle"}

**app.json:**
```json
{
  "expo": {
    "version": "1.0.0", // Semantic versioning
    "ios": {
      "buildNumber": "1", // iOS Build Number (ціле число)
      "bundleIdentifier": "com.mycompany.myapp"
    },
    "android": {
      "versionCode": 1, // Android Version Code (ціле число)
      "package": "com.mycompany.myapp"
    }
  }
}
```

**Правила:**
- `version` — публічна версія (1.0.0, 1.0.1, 1.1.0)
- `buildNumber` / `versionCode` — **монотонно зростає** з кожним білдом (1, 2, 3, ...)
- При кожному оновленні хоча б одне з чисел має збільшитися

::

::accordion-item{label="✅ Іконка та splash screen налаштовані" icon="i-lucide-check-circle"}

**app.json:**
```json
{
  "expo": {
    "icon": "./assets/icon.png", // 1024x1024 px, без заокруглення
    "splash": {
      "image": "./assets/splash.png", // 1284x2778 px (iPhone 13 Pro Max)
      "resizeMode": "contain",
      "backgroundColor": "#ffffff"
    },
    "ios": {
      "icon": "./assets/icon-ios.png" // опціонально
    },
    "android": {
      "adaptiveIcon": {
        "foregroundImage": "./assets/adaptive-icon.png", // 1024x1024
        "backgroundColor": "#ffffff"
      }
    }
  }
}
```

::

::accordion-item{label="✅ Permissions (дозволи) оптимізовані" icon="i-lucide-check-circle"}

Видаліть невикористані дозволи:

**app.json (iOS):**
```json
{
  "ios": {
    "infoPlist": {
      "NSCameraUsageDescription": "Для завантаження фото профілю",
      "NSPhotoLibraryUsageDescription": "Для вибору фото з галереї",
      // Видаліть якщо не використовуєте:
      // "NSLocationWhenInUseUsageDescription": "..."
    }
  }
}
```

**app.json (Android):**
```json
{
  "android": {
    "permissions": [
      "CAMERA",
      "READ_EXTERNAL_STORAGE",
      "WRITE_EXTERNAL_STORAGE"
      // Не додавайте зайві дозволи!
    ]
  }
}
```

::

::accordion-item{label="✅ Розмір білду оптимізований" icon="i-lucide-check-circle"}

Типовий розмір:
- iOS: 20–50 MB (залежить від залежностей)
- Android: 15–30 MB (AAB автоматично оптимізується)

**Якщо білд > 100 MB:**

1. Перевірте великі залежності:
```bash
npx expo-doctor
npm ls --depth=0 # список всіх залежностей
```

2. Видаліть невикористані:
```bash
npm uninstall unused-package
```

3. Оптимізуйте зображення:
```bash
# Встановіть ImageOptim (macOS) або TinyPNG CLI
tinypng assets/**/*.png
```

4. Увімкніть Hermes (Android):
```json
{
  "android": {
    "jsEngine": "hermes" // швидший запуск + менший розмір
  }
}
```

::steps

### Тестуйте на різних версіях ОС
- iOS: мінімум iOS 13, 15, останню версію

### Перевірте landscape орієнтацію
Якщо застосунок підтримує — перевірте всі екрани у горизонтальному режимі

### Тестуйте повільний інтернет
Увімкніть Network Link Conditioner (iOS) або обмежте швидкість в Android

### Перевірте crash-free rate
Використовуйте аналітику (Sentry, Firebase Crashlytics) для відстеження крашів

::

## Крок 2: Підготовка маркетингових матеріалів

### 2.1. Іконка застосунку

Іконка — це **перше враження** користувача про ваш застосунок. Вона відображається на домашньому екрані, у результатах пошуку App Store/Play Store, у списку встановлених застосунків.

**Технічні вимоги:**

| Параметр | Вимога |
| :--- | :--- |
| **Розмір** | 1024×1024 пікселів (обидві платформи) |
| **Формат** | PNG (без прозорості для iOS, з прозорістю для Android) |
| **Колірний простір** | RGB (не CMYK) |
| **Кути** | Квадратна без заокруглення (платформи додають автоматично) |
| **Розмір файлу** | До 1 MB |

::warning
**Заборонено:**
- Текст менше 44pt (нечитабельний на маленьких іконках)
- Скріншоти UI застосунку (Apple вважає це Guideline порушенням)
- Фото реальних людей без письмового дозволу
- Логотипи сторонніх компаній (Apple, Android, тощо)
- Emoji або символи, захищені авторським правом
::

**Рекомендації дизайну:**

::card-group

::card{title="🎨 Простота" icon="i-lucide-minimize-2"}

Іконка має бути зрозумілою на екрані 60×60 пікселів. Один чіткий символ краще за складну композицію.

✅ Instagram (градієнт + камера)
❌ Детальна ілюстрація міста

::

::card{title="🌈 Контрастність" icon="i-lucide-palette"}

Висока контрастність між фоном і головним елементом. Уникайте світлих іконок на білому фоні.

✅ Telegram (синє небо + білий літак)
❌ Сірий текст на білому фоні

::

::card{title="🔲 Padding" icon="i-lucide-maximize-2"}

Залиште 10% padding від країв. iOS додає тінь, Android — adaptive icon mask.

✅ Елемент у центрі з відступами
❌ Елемент торкається країв

::

::card{title="📱 Тестування" icon="i-lucide-smartphone"}

Перевірте як виглядає іконка:
- На світлому та темному фоні (iOS Dark Mode)
- Поруч з іншими іконками на домашньому екрані
- У результатах пошуку App Store/Play Store

::

### 2.2. Скріншоти застосунку

Скріншоти — це **візуальна розповідь** про ваш застосунок. Користувачі приймають рішення про встановлення за 5–7 секунд перегляду сторінки у сторі.

**Вимоги Apple App Store:**

| Пристрій | Розмір (пікселі) | Обов'язковість |
| :--- | :--- | :--- |
| **iPhone 6.7"** (15 Pro Max) | 1290×2796 | ✅ Обов'язково |
| **iPhone 6.5"** (11 Pro Max) | 1284×2778 | Рекомендовано |
| **iPhone 5.5"** (8 Plus) | 1242×2208 | Опціонально |
| **iPad Pro 12.9"** (якщо підтримка) | 2048×2732 | Обов'язково для iPad |

**Кількість:** 2–10 скріншотів на кожен розмір.

**Вимоги Google Play Store:**

| Пристрій | Розмір (пікселі) | Обов'язковість |
| :--- | :--- | :--- |
| **Phone** | Мінімум 320px по короткій стороні | ✅ Обов'язково (2–8 шт) |
| **7" Tablet** | 1024×600 або більше | Рекомендовано |
| **10" Tablet** | 1280×800 або більше | Рекомендовано |

**Формат:** JPEG або PNG, до 8 MB на скріншот.

::tip
**Лайфхак для створення скріншотів:**

1. Запустіть застосунок на симуляторі з потрібним розміром екрану
2. Натисніть `Cmd + S` (iOS Simulator) або `Ctrl + S` (Android Emulator)
3. Скріншоти збережуться автоматично у правильному розмірі

Альтернатива — використовуйте [Screenshot](https://www.shotsnapp.com) для додавання рамок пристрою.
::

**Правила дизайну скріншотів:**

::steps

### Перший скріншот = заголовок
Це головний продаючий екран. Має показувати core value proposition.

**Приклад (застосунок для подорожей):**
> "Плануйте ідеальну подорож за 3 хвилини"

### Показуйте функціонал, а не пусті стани
Заповніть екрани реальними даними. Ніякого Lorem Ipsum.

✅ Екран з 10 подорожами та красивими фото
❌ "У вас поки немає подорожей"

### Додайте текстові описи
Короткі заголовки над кожним скріншотом пояснюють що відбувається.

**Шрифт:** Жирний, розмір 60–80pt, контрастний колір.

### Використовуйте послідовність (flow)
Скріншоти мають розповідати історію: Реєстрація → Головний екран → Основна функція → Результат.

### Локалізуйте для різних ринків
Якщо таргетуєте Україну та США — створіть окремі набори скріншотів українською та англійською.

::

**Інструменти для створення скріншотів:**

- [Figma Templates](https://www.figma.com/@appscreenshots) — готові шаблони
- [Fastlane Frameit](https://docs.fastlane.tools/actions/frameit/) — автоматичне додавання рамок
- [AppLaunchpad](https://theapplaunchpad.com) — генератор маркетингових скріншотів

### 2.3. Опис застосунку

### 2.4. Ключові слова (Keywords)

**App Store (iOS):**

Можна вказати до **100 символів** ключових слів (через кому без пробілів).

1. **Основні терміни:** назва категорії (travel, planner, trip)

- Назву застосунку

- Повний опис

**Структура відео:**

::steps

### Секунди 1–3: Hook (гачок)

"Завантажте зараз" з іконкою застосунку.

**Вимоги:**

- Розмір: 1024×500 пікселів
- Без тексту (Google накладає текст автоматично)

::tip

   - Can be deleted: Yes
   
✅ App interactions (analytics)

## Крок 7: Проходження модерації

### 7.1. App Review (Apple) — що перевіряють модератори?

Apple App Review — це команда людей, які вручну тестують ваш застосунок протягом 24–72 годин (іноді до 7 днів). Вони перевіряють:

::steps

### Функціональність
Всі екрани працюють, навігація логічна, немає crashів.

### Відповідність метаданим
Опис застосунку відповідає реальному функціоналу. Скріншоти показують актуальний UI.

### App Store Review Guidelines
2.8 тис+ правил у [developer.apple.com/app-store/review/guidelines](https://developer.apple.com/app-store/review/guidelines)

### Безпека
Немає шкідливого коду, private API, jailbreak detection exploitation.

### Privacy
Правильна декларація збору даних у App Privacy секції.

### Design
Відповідність Human Interface Guidelines (не обов'язково, але рекомендовано).

::

**Типові причини відхилення (Rejection reasons):**

::accordion

::accordion-item{label="❌ Guideline 2.1 - App Completeness" icon="i-lucide-x-circle"}

**Проблема:** Застосунок незавершений або містить placeholder-контент.

**Приклади:**
- "Coming soon" на деяких екранах
- Lorem ipsum текст
- Кнопки, що нічого не роблять
- "Under construction" повідомлення

**Рішення:** Видаліть або доповніть незавершені функції перед submission.

::

::accordion-item{label="❌ Guideline 2.3.10 - Accurate Metadata" icon="i-lucide-x-circle"}

**Проблема:** Скріншоти або опис не відповідають реальному застосунку.

**Приклади:**
- Скріншоти показують функції, яких немає у білді
- Опис обіцяє "AI-powered recommendations", але застосунок цього не робить
- Іконка змінена після submission (не збігається з білдом)

**Рішення:** Переконайтеся що всі маркетингові матеріали відповідають дійсності.

::

::accordion-item{label="❌ Guideline 4.2 - Minimum Functionality" icon="i-lucide-x-circle"}

**Проблема:** Застосунок не надає достатньої цінності або це просто обгортка над веб-сайтом.

**Приклади:**
- WebView з вашим сайтом без нативного функціоналу
- Застосунок робить лише одну просту дію (таймер, калькулятор tip)
- Дублікат існуючого застосунку без унікальних фіч

**Рішення:** Додайте унікальний нативний функціонал або не публікуйте як застосунок.

::

::accordion-item{label="❌ Guideline 5.1.1 - Data Collection and Storage" icon="i-lucide-x-circle"}

**Проблема:** Порушення Privacy Policy або невідповідність декларації App Privacy.

**Приклади:**
- Збираєте геолокацію, але не вказали у App Privacy
- Privacy Policy URL не працює (404 error)
- Немає можливості видалити акаунт та дані

**Рішення:** Оновіть App Privacy декларацію, перевірте Privacy Policy URL, додайте функцію видалення акаунту.

::

::accordion-item{label="❌ Guideline 2.1 - Performance: App Crashes" icon="i-lucide-x-circle"}

**Проблема:** Застосунок падає під час тестування модераторами.

**Приклади:**
- Crash при відсутності інтернету
- Crash при відмові у дозволі на геолокацію
- Crash при повороті екрану

**Рішення:** Тестуйте всі edge cases. Використовуйте Sentry або Crashlytics для відстеження крашів у реальному часі.

::

::

4. У **Resolution Center** напишіть відповідь модераторам:

- Поясніть архітектуру та призначення застосунку

**Типові запитання:**

### 7.4. Google Play Automated Review

Google використовує автоматизовану модерацію через машинне навчання:

**Що перевіряється автоматично:**

::steps

### Malware scan
Статичний аналіз APK/AAB на наявність шкідливого коду.

### Policy compliance
Автоматична перевірка SDK на порушення Privacy Policy.

### Content rating validation
Сканування на невідповідність заявленому віковому рейтингу.

### Trademark infringement
Перевірка назви та іконки на порушення торгових марок.

### SDK detection
Виявлення banned SDK (наприклад, реклама від заблокованих мереж).

::

**Типовий час модерації:**

- **80% застосунків:** Публікуються автоматично за 1–3 години
- **15% застосунків:** Ручна перевірка 1–3 дні (якщо виявлені підозрілі ознаки)
- **5% застосунків:** Відхилення (policy violation)

**Типові причини відхилення Google Play:**

::accordion

::accordion-item{label="❌ Malicious Behavior" icon="i-lucide-x-circle"}

**Проблема:** Виявлено шкідливий код або підозрілу поведінку.

**Приклади:**
- Збір SMS без явного дозволу користувача
- Приховане завантаження APK з інтернету
- Root exploit спроби

**Рішення:** Видаліть підозрілий код. Якщо це помилкове спрацювання — оскаржте через Appeal form.

::

::accordion-item{label="❌ Misleading Content" icon="i-lucide-x-circle"}

**Проблема:** Назва або опис вводять в оману.

**Приклади:**
- Назва містить "Official" без дозволу бренду
- Іконка копіює популярний застосунок
- Опис обіцяє функції, яких немає

**Рішення:** Змініть назву/іконку, оновіть опис.

::

::accordion-item{label="❌ Privacy Policy" icon="i-lucide-x-circle"}

**Проблема:** Відсутня або неправильна Privacy Policy.

**Приклади:**
- Privacy Policy URL повертає 404
- Політика не описує збір даних, заявлений у Data Safety
- Privacy Policy не оновлена 5+ років

**Рішення:** Опублікуйте актуальну Privacy Policy на вашому сайті.

::

::

### 7.5. Appeal (Оскарження відхилення)

Якщо вважаєте що відхилення помилкове:

**Apple:**
1. **Resolution Center** → **Appeal**
2. Поясніть чому вважаєте рішення неправильним (з доказами)
3. Очікування розгляду: 1–3 дні
4. Якщо appeal відхилено — рішення остаточне

**Google:**
1. **Play Console** → **Policy status** → **Appeal**
2. Заповніть форму з детальним поясненням
3. Очікування: 1–5 днів
4. Можна апелювати повторно якщо надали нові докази

::warning
**Не зловживайте Appeal!** Якщо відхилення справедливе, виправте проблему замість апеляції. Часті необґрунтовані appeal призводять до зниження довіри та повільнішої модерації у майбутньому.
::

### 8.1. Запуск у production

**Apple App Store:**

Після схвалення модерації (статус "Ready for Sale"):

::tabs
::tabs-item{label="Automatic Release"}

Застосунок автоматично публікується одразу після approval.

**Налаштування:** App Store → Version → Release → **Automatically release this version**

::

Ви контролюєте точний час публікації.

**Налаштування:** App Store → Version → Release → **Manually release this version**

Після approval натисніть **"Release this version"**

::
::tabs-item{label="Scheduled Release"}

Запланована публікація у конкретний день/час.

**Налаштування:** App Store → Version → Release → **Release on [date]**

::
::

**Google Play:**

Після завантаження білду:

1. **Navigation:** Release → Production → Review release
2. Перевірте всю інформацію
3. Натисніть **"Start rollout to Production"**
4. Оберіть стратегію rollout:

::tabs
::tabs-item{label="Full Rollout (100%)"}

Застосунок одразу доступний всім користувачам.

**Використання:** Якщо впевнені у якості білду (пройшов beta testing).

::
::tabs-item{label="Staged Rollout"}

Поступовий запуск:
- 5% користувачів → моніторинг 24 години
- 10% → моніторинг 24 години
- 20% → 50% → 100%

**Використання:** Для мінімізації ризику критичних багів.

**Налаштування:** Оберіть "Create staged rollout" → вкажіть % (5%, 10%, 20%, 50%)

::
::

::tip
**Рекомендація:** Для першого релізу використовуйте Staged Rollout 10% → 50% → 100%. Це дасть можливість виявити критичні баги на малій аудиторії та швидко відреагувати.
::

### 8.2. Моніторинг після публікації

**Перші 48 годин критичні.** Відстежуйте:

::card-group

::card{title="📊 Crash-free rate" icon="i-lucide-activity"}

Цільовий показник: **> 99%** (менше 1% користувачів мають краші)

**Інструменти:**
- **Sentry** — real-time crash tracking
- **Firebase Crashlytics** — безкоштовна альтернатива
- **App Store Connect Analytics** — вбудована статистика

**Дії при crash rate > 2%:**
1. Ідентифікуйте топ-3 crashy екрани
2. Виправте критичні баги
3. Створіть hotfix білд (version 1.0.1)
4. Submit для expedited review (Apple) або push hotfix (Android)

::

::card{title="⭐ Рейтинг та відгуки" icon="i-lucide-star"}

**Стратегія роботи з відгуками:**

✅ **Відповідайте на негативні відгуки** (1–2 зірки) протягом 24 годин
- Вибачтеся за незручності
- Запропонуйте вирішення або компенсацію
- Повідомте про виправлення у наступному оновленні

✅ **Дякуйте за позитивні відгуки** (4–5 зірок)

✅ **Не просіть "купити" 5-зірковий рейтинг** — це порушення Guidelines

**Коли просити відгук:**
- Після 3-го успішного використання core функції
- Не частіше 1 разу на 120 днів (Apple обмеження)
- Ніколи після негативного досвіду (помилка, краш)

::

::card{title="📈 Install/Uninstall rate" icon="i-lucide-trending-up"}

**Здорові показники:**

| Метрика | Цільове значення |
| :--- | :--- |
| **Day 1 retention** | > 40% (користувачі повертаються наступного дня) |
| **Day 7 retention** | > 20% |
| **Day 30 retention** | > 10% |
| **Uninstall rate** | < 5% протягом першого тижня |

**Якщо retention низький:**
- Перевірте onboarding (чи зрозуміло що робити?)
- Додайте push-нотифікації (нагадування про цінність)
- A/B тестуйте різні флоу

::

::card{title="🐛 Bug reports" icon="i-lucide-bug"}

**Канали збору:**
- Email підтримки (support@yourapp.com)
- In-app feedback форма
- Соціальні мережі (Twitter, Reddit)
- App Store / Google Play відгуки

**Пріоритизація:**

| Пріоритет | Критерії | Дії |
| :--- | :--- | :--- |
| **P0 (Critical)** | Блокує core функціонал, масові краші | Hotfix протягом 24 годин |
| **P1 (High)** | Важлива функція не працює | Виправлення у наступному релізі (1–2 тижні) |
| **P2 (Medium)** | Minor баг, не впливає на UX | Backlog |
| **P3 (Low)** | Косметичні проблеми | Nice-to-have |

::

### 8.3. Оновлення застосунку (Updates)

**Коли випускати оновлення:**

::steps

### Hotfix (1.0.1) — терміново
Критичні баги, що блокують функціонал. Випускаємо протягом 1–3 днів.

### Minor Update (1.1.0) — щомісяця
Нові фічі, покращення UX, виправлення накопичених багів.

### Major Update (2.0.0) — щороку
Великий редизайн, нова архітектура, breaking changes.

::

**Процес оновлення:**

1. Збільшіть версію у `app.json`:
```json
{
  "version": "1.0.1", // було 1.0.0
  "ios": { "buildNumber": "2" }, // було "1"
  "android": { "versionCode": 2 } // було 1
}
```

2. Створіть новий production білд:
```bash
eas build --platform all --profile production
```

3. Upload до App Store Connect / Google Play Console

4. Оновіть **"What's New"** (Release Notes):

**Приклад якісних Release Notes:**

```
🐛 Bug Fixes
- Fixed crash when opening trip details without internet
- Resolved issue with camera permissions on Android 14

✨ Improvements
- Faster loading of trip photos
- Better offline mode experience

📱 Under the hood
- Performance improvements
- Reduced app size by 15%
```

❌ **Поганий приклад:**
```
- Bug fixes
- Performance improvements
```

5. Submit for Review (Apple) або Rollout (Google)

### 8.4. Версіонування: best practices

**Semantic Versioning (рекомендовано):**

```
MAJOR.MINOR.PATCH

1.0.0 → Initial release
1.0.1 → Hotfix (bug fixes)
1.1.0 → New features
2.0.0 → Breaking changes / major redesign
```

**Build Number / Version Code:**

Завжди збільшується на 1 з кожним білдом (навіть якщо version не змінюється).

**Приклад еволюції:**

| Дата | Version | Build | Зміни |
| :--- | :--- | :--- | :--- |
| Dec 1 | 1.0.0 | 1 | Initial release |
| Dec 3 | 1.0.1 | 2 | Hotfix: crash fix |
| Dec 15 | 1.1.0 | 3 | New feature: offline mode |
| Jan 10 | 1.1.1 | 4 | Bug fix |
| Feb 1 | 2.0.0 | 5 | Major redesign |
