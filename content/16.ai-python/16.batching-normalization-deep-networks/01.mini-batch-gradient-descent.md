## Від теорії до практики — коли датасет не поміщається в пам'ять

У попередніх розділах ми побудували згорткові нейронні мережі, навчили їх розпізнавати зображення та досягли чудових результатів на датасетах MNIST та CIFAR-10. Але всі наші експерименти об'єднувала одна тиха передумова: **ми завантажували весь датасет у пам'ять одразу**. Це працювало, бо MNIST містить 60 000 зображень 28×28 пікселів (близько 180 МБ), а CIFAR-10 — 50 000 зображень 32×32×3 (близько 170 МБ). Такі обсяги легко вміщуються в оперативну пам'ять сучасного ноутбука.

Але уявіть, що ви працюєте над реальним промисловим проєктом:

::card-group

::card{title="🏥 Медична діагностика" icon="i-lucide-heart-pulse"}

Датасет рентгенівських знімків легень для виявлення пневмонії містить **500 000 зображень** у роздільності **2048×2048 пікселів**. Кожне зображення у форматі float32 займає:

::math-formula
2048 \times 2048 \times 1 \times 4 \text{ байти} = 16.8 \text{ МБ}
::

Весь датасет: **8.4 терабайти**. Навіть сервер з 256 ГБ RAM не впорається.

::

::card{title="🚗 Автономне водіння" icon="i-lucide-car"}

Навчальний датасет відеозаписів доріг містить **10 мільйонів кадрів** у роздільності **1920×1080×3** (Full HD). Один батч із 32 кадрів займає близько **750 МБ** у пам'яті GPU. Завантажити весь датасет фізично неможливо.

::

::card{title="🌐 Обробка природної мови" icon="i-lucide-globe"}

Корпус текстів Wikipedia англійською мовою містить **6.5 мільйонів статей**. Після токенізації та створення ембедінгів датасет займає **понад 50 ГБ**. Модель навчається днями, тому ефективне завантаження даних критичне для швидкості.

::

::

У всіх цих випадках неможливо завантажити датасет повністю. Більше того, навіть якщо б це було можливо, **це неефективно**. Сучасні GPU мають пам'ять 8-24 ГБ, а тренувальні датасети займають сотні гігабайт. Нам потрібен спосіб **поступово подавати дані в мережу невеликими порціями**, не втрачаючи при цьому ефективності навчання.

Саме це завдання розв'язує **Mini-batch Gradient Descent** (*міні-батч градієнтний спуск*) — золота середина між ідеалістичною теорією та суворою реальністю обмежених обчислювальних ресурсів.

::card-group

::card{title="🎯 Мета статті" icon="i-lucide-target"}

- Зрозуміти обмеження класичного градієнтного спуску для великих датасетів
- Опанувати три підходи до обчислення градієнта: Batch GD, Stochastic GD та Mini-batch GD
- Навчитися ефективно завантажувати дані через PyTorch `DataLoader`
- Дослідити вплив розміру батчу на швидкість навчання, стабільність та якість моделі
- Розібратися у термінології: epoch, iteration, batch та їх взаємозв'язку

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Batch Gradient Descent:** обчислення градієнта по всьому датасету одразу
- **Stochastic Gradient Descent (SGD):** оновлення ваг після кожного окремого прикладу
- **Mini-batch Gradient Descent:** компроміс — обчислення градієнта по невеликій групі прикладів
- **DataLoader:** клас PyTorch для ефективного завантаження даних батчами
- **Epoch:** один повний прохід через весь тренувальний датасет
- **Iteration:** одне оновлення ваг (одна обробка одного батчу)

## Нагадування: градієнтний спуск у теорії

Перш ніж перейти до практичних варіантів, згадаймо математичну суть алгоритму градієнтного спуску. Наша мета — мінімізувати функцію втрат :math-formula{tex="L(\mathbf{w})" inline}, яка вимірює помилку моделі з параметрами (вагами) :math-formula{tex="\mathbf{w}" inline}.

### Класична формула оновлення ваг

Градієнтний спуск ітеративно оновлює ваги, рухаючись у напрямку, протилежному градієнту:

::math-formula
\mathbf{w}_{t+1} = \mathbf{w}_t - \eta \nabla_{\mathbf{w}} L(\mathbf{w}_t)
::

Де:
- :math-formula{tex="\mathbf{w}_t" inline} — поточні ваги на кроці :math-formula{tex="t" inline}
- :math-formula{tex="\eta" inline} — швидкість навчання (*learning rate*)
- :math-formula{tex="\nabla_{\mathbf{w}} L" inline} — градієнт функції втрат по вагах

### Функція втрат для всього датасету

Якщо наш тренувальний датасет містить :math-formula{tex="N" inline} прикладів :math-formula{tex="\{(\mathbf{x}_1, y_1), (\mathbf{x}_2, y_2), \ldots, (\mathbf{x}_N, y_N)\}" inline}, то функція втрат — це **середня помилка по всіх прикладах**:

::math-formula
L(\mathbf{w}) = \frac{1}{N} \sum_{i=1}^{N} \ell(\mathbf{x}_i, y_i, \mathbf{w})
::

Де :math-formula{tex="\ell(\mathbf{x}_i, y_i, \mathbf{w})" inline} — втрати на одному прикладі (наприклад, Cross-Entropy для класифікації).

Градієнт цієї функції:

::math-formula
\nabla_{\mathbf{w}} L(\mathbf{w}) = \frac{1}{N} \sum_{i=1}^{N} \nabla_{\mathbf{w}} \ell(\mathbf{x}_i, y_i, \mathbf{w})
::

**Ключовий момент:** для обчислення градієнта нам потрібно **пропустити всі** :math-formula{tex="N" inline} **прикладів через мережу** (forward pass), обчислити втрати на кожному, а потім усереднити їхні градієнти (backward pass). Якщо :math-formula{tex="N = 1{,}000{,}000" inline}, це означає мільйон forward-backward проходів **для одного оновлення ваг**!


::note
**Інтуїція градієнта:**

Градієнт :math-formula{tex="\nabla_{\mathbf{w}} L" inline} — це вектор, що вказує напрямок **найшвидшого зростання** функції втрат. Віднімаючи градієнт від ваг, ми рухаємося у протилежному напрямку — до **мінімуму втрат**. Чим більший градієнт, тим крутіший «схил» і тим більший крок ми робимо.
::

## Три підходи до обчислення градієнта

Існує три фундаментально різних способи обчислення градієнта, кожен із яких має свої переваги та недоліки. Розглянемо їх детально.

### Підхід 1: Batch Gradient Descent (повний датасет)

**Ідея:** обчислюємо градієнт по **всьому датасету** одразу, як у формулі вище.

::plant-uml{alt="Batch Gradient Descent — обробка всього датасету за раз"}

```plantuml
@startuml
skinparam style plain
skinparam backgroundColor #FFFFFF
skinparam defaultFontName "Arial"

!define DATA_COLOR #DBEAFE
!define COMPUTE_COLOR #FEF3C7
!define UPDATE_COLOR #DCFCE7

rectangle "Тренувальний датасет\n(N = 1,000,000 прикладів)" as dataset #DATA_COLOR

rectangle "Обчислення градієнта\nпо ВСЬОМУ датасету" as compute #COMPUTE_COLOR {
  rectangle "Forward pass\nдля кожного x₁, x₂, ..., xₙ" as forward
  rectangle "Обчислення втрат\nℓ(x₁), ℓ(x₂), ..., ℓ(xₙ)" as loss
  rectangle "Backward pass\nусереднення градієнтів" as backward
}

rectangle "Оновлення ваг\nw ← w - η∇L" as update #UPDATE_COLOR

dataset -down-> compute
compute -down-> update
update -right-> dataset : Наступна ітерація

note right of compute
  ⏱️ Одне оновлення може
  займати хвилини або години
  для великих датасетів
end note

@enduml
```

::

**Алгоритм:**

::steps

### Крок 1. Завантажити весь датасет у пам'ять

Зчитати всі :math-formula{tex="N" inline} прикладів: :math-formula{tex="\{(\mathbf{x}_1, y_1), \ldots, (\mathbf{x}_N, y_N)\}" inline}.

### Крок 2. Forward pass по всіх прикладах

Пропустити кожен приклад через модель, отримати передбачення :math-formula{tex="\hat{y}_i = f(\mathbf{x}_i, \mathbf{w})" inline}.

### Крок 3. Обчислити середню втрату

::math-formula
L = \frac{1}{N} \sum_{i=1}^{N} \ell(\hat{y}_i, y_i)
::

### Крок 4. Backward pass — обчислити градієнт

::math-formula
\nabla_{\mathbf{w}} L = \frac{1}{N} \sum_{i=1}^{N} \nabla_{\mathbf{w}} \ell(\mathbf{x}_i, y_i, \mathbf{w})
::

### Крок 5. Оновити ваги

::math-formula
\mathbf{w} \leftarrow \mathbf{w} - \eta \nabla_{\mathbf{w}} L
::

### Крок 6. Повторити з кроку 2

Продовжувати, поки не досягнемо конвергенції.

::

**Переваги Batch GD:**

::card-group

::card{title="✅ Стабільна конвергенція" icon="i-lucide-trending-up"}

Градієнт обчислюється по всьому датасету, тому він **точний** і не шумний. Траєкторія оптимізації плавно рухається до мінімуму без хаотичних стрибків.

::

::card{title="✅ Детермінованість" icon="i-lucide-lock"}

Якщо запустити алгоритм двічі з однаковими початковими вагами та learning rate, отримаємо **ідентичний результат**. Це полегшує відтворюваність експериментів.

::

::card{title="✅ Ефективна векторизація" icon="i-lucide-zap"}

Сучасні бібліотеки (NumPy, PyTorch) оптимізовані для операцій над великими масивами. Обробка всього датасету одним тензором використовує SIMD-інструкції процесора та паралелізм GPU ефективніше, ніж окремі приклади.

::

::

**Недоліки Batch GD:**

::card-group

::card{title="❌ Вимагає всю пам'ять" icon="i-lucide-hard-drive"}

Весь датасет має поміститися в RAM або VRAM GPU. Для ImageNet (14 мільйонів зображень, близько **150 ГБ**) це нереально.

::

::card{title="❌ Повільні оновлення" icon="i-lucide-clock"}

Одне оновлення ваг вимагає обробки **всього датасету**. Для мільйона прикладів це може займати хвилини навіть на потужному GPU. Якщо модель застрягла в поганому локальному мінімумі, ми дізнаємося про це лише після наступного повного проходу.

::

::card{title="❌ Неможливість онлайн-навчання" icon="i-lucide-wifi-off"}

Якщо дані надходять поступово (наприклад, стрімінг відео або онлайн-реклама), неможливо почекати накопичення всього датасету перед навчанням.

::

::

::warning
**Для реальних задач:**

Batch Gradient Descent практично **ніколи не використовується** через обмеження пам'яті. Навіть для малих датасетів (MNIST, CIFAR-10) це неефективно, бо оновлення ваг відбуваються рідко.
::

### Підхід 2: Stochastic Gradient Descent (один приклад за раз)

**Ідея:** обчислюємо градієнт по **одному випадково обраному прикладу**, оновлюємо ваги, беремо наступний приклад.

Замість усереднення по всьому датасету, градієнт на кроці :math-formula{tex="t" inline} обчислюється лише для одного прикладу :math-formula{tex="(\mathbf{x}_t, y_t)" inline}:

::math-formula
\nabla_{\mathbf{w}} L_{\text{SGD}} \approx \nabla_{\mathbf{w}} \ell(\mathbf{x}_t, y_t, \mathbf{w})
::

Оновлення ваг:

::math-formula
\mathbf{w}_{t+1} = \mathbf{w}_t - \eta \nabla_{\mathbf{w}} \ell(\mathbf{x}_t, y_t, \mathbf{w}_t)
::

**Алгоритм SGD:**

::steps

### Крок 1. Перемішати датасет

Випадково змінити порядок прикладів, щоб уникнути систематичних зміщень.

### Крок 2. Взяти один приклад

Вибрати :math-formula{tex="(\mathbf{x}_i, y_i)" inline}.

### Крок 3. Forward pass для одного прикладу

::math-formula
\hat{y}_i = f(\mathbf{x}_i, \mathbf{w})
::

### Крок 4. Обчислити втрату

::math-formula
\ell_i = \ell(\hat{y}_i, y_i)
::

### Крок 5. Backward pass — градієнт для одного прикладу

::math-formula
\nabla_{\mathbf{w}} \ell_i
::

### Крок 6. Оновити ваги

::math-formula
\mathbf{w} \leftarrow \mathbf{w} - \eta \nabla_{\mathbf{w}} \ell_i
::

### Крок 7. Взяти наступний приклад

Повторити з кроку 2 для :math-formula{tex="\mathbf{x}_{i+1}" inline}.

::

**Переваги SGD:**

::card-group

::card{title="✅ Швидкі оновлення" icon="i-lucide-zap"}

Ваги оновлюються після **кожного прикладу**. Для датасету з 50 000 прикладів отримуємо 50 000 оновлень ваг за одну епоху, замість одного у Batch GD!

::

::card{title="✅ Мінімальні вимоги до пам'яті" icon="i-lucide-hard-drive-download"}

У пам'яті потрібен лише **один приклад** одночасно. Це дозволяє працювати з будь-якими датасетами.

::

::card{title="✅ Втеча з локальних мінімумів" icon="i-lucide-move"}

Шумний градієнт додає **стохастичність** до траєкторії оптимізації. Модель може «вистрибнути» з вузького локального мінімуму та знайти кращий глобальний.

::

::

**Недоліки SGD:**

::card-group

::card{title="❌ Шумна конвергенція" icon="i-lucide-activity"}

Градієнт одного прикладу — **погана апроксимація** справжнього градієнта по датасету. Траєкторія оптимізації хаотично стрибає навколо мінімуму, навіть після досягнення конвергенції.

::

::card{title="❌ Неефективна векторизація" icon="i-lucide-cpu"}

Обробка одного прикладу не використовує паралелізм GPU. Сучасні GPU мають тисячі ядер, але SGD завантажує лише одне. Це як використовувати Ferrari для поїздки до магазину за кутом.

::

::card{title="❌ Повільніше за годинником" icon="i-lucide-clock"}

Хоча SGD робить більше оновлень, **час виконання** може бути більшим через неефективність GPU. Обробити 1000 прикладів по одному повільніше, ніж батчем із 1000.


::

::tip
**Термінологія:**

У літературі термін «SGD» часто використовується для позначення будь-якого варіанта градієнтного спуску, включаючи Mini-batch. Коли кажуть «навчаємо з SGD», зазвичай мають на увазі Mini-batch GD з невеликим батчем (32-256).
::

### Підхід 3: Mini-batch Gradient Descent (золота середина)

**Ідея:** обчислюємо градієнт не по всьому датасету і не по одному прикладу, а по **невеликій групі прикладів** — міні-батчу (*mini-batch*).

Розіб'ємо датасет на :math-formula{tex="K" inline} міні-батчів розміром :math-formula{tex="B" inline} кожен. Градієнт на кроці :math-formula{tex="t" inline} обчислюється по батчу :math-formula{tex="\mathcal{B}_t = \{(\mathbf{x}_{t,1}, y_{t,1}), \ldots, (\mathbf{x}_{t,B}, y_{t,B})\}" inline}:

::math-formula
\nabla_{\mathbf{w}} L_{\text{mini-batch}} = \frac{1}{B} \sum_{i=1}^{B} \nabla_{\mathbf{w}} \ell(\mathbf{x}_{t,i}, y_{t,i}, \mathbf{w})
::

Оновлення ваг:

::math-formula
\mathbf{w}_{t+1} = \mathbf{w}_t - \eta \nabla_{\mathbf{w}} L_{\text{mini-batch}}
::

::plant-uml{alt="Mini-batch Gradient Descent — компроміс між Batch та SGD"}

```plantuml
@startuml
skinparam style plain
skinparam backgroundColor #FFFFFF
skinparam defaultFontName "Arial"

!define DATA_COLOR #DBEAFE
!define BATCH_COLOR #FEF3C7
!define COMPUTE_COLOR #DCFCE7

rectangle "Датасет\n(N = 50,000)" as dataset #DATA_COLOR

package "Розбиття на міні-батчі" as split {
  rectangle "Batch 1\n(B = 128)" as b1 #BATCH_COLOR
  rectangle "Batch 2\n(B = 128)" as b2 #BATCH_COLOR
  rectangle "..." as dots
  rectangle "Batch K\n(B = 128)" as bk #BATCH_COLOR
}

rectangle "Обчислення градієнта\nпо одному батчу" as compute #COMPUTE_COLOR

rectangle "Оновлення ваг\nw ← w - η∇L" as update

dataset -down-> split
b1 -down-> compute : Ітерація 1
compute -down-> update
update -right-> b2 : Ітерація 2
b2 -right-> compute
dots -right-> bk
bk -up-> dataset : Епоха завершена

note right of compute
  ⚡ Кожне оновлення — швидке
  📊 Градієнт — достатньо точний
  🎯 Ефективна векторизація GPU
end note

@enduml
```

::

**Типові розміри батчу:**

| Розмір батчу | Застосування | Пам'ять GPU | Характеристики |
|:-------------|:-------------|:------------|:---------------|
| **8-16** | Дуже великі зображення (медичні скани) | ~2-4 ГБ | Дуже шумний градієнт, повільна конвергенція |
| **32-64** | Стандарт для CNN на середніх зображеннях | ~4-8 ГБ | Баланс швидкості та якості |
| **128-256** | Популярний вибір для класифікації | ~8-16 ГБ | Швидка конвергенція, стабільний градієнт |
| **512-1024** | Великі датасети з малими входами (MNIST) | ~16+ ГБ | Максимальна швидкість, ризик перенавчання |

**Переваги Mini-batch GD:**

::card-group

::card{title="✅ Ефективна векторизація" icon="i-lucide-cpu"}

Батч із 128 прикладів завантажує GPU на ~70-90%. Операції матричного множення виконуються паралельно на тисячах ядер CUDA.

::

::card{title="✅ Стабільніший градієнт" icon="i-lucide-trending-up"}

Градієнт, усереднений по 128 прикладах, значно точніший за градієнт одного прикладу SGD. Траєкторія оптимізації плавніша, ніж у SGD, але швидша, ніж у Batch GD.

::

::card{title="✅ Помірні вимоги до пам'яті" icon="i-lucide-hard-drive"}

Потрібно зберігати лише один батч (~0.5-2 ГБ) замість усього датасету (~100 ГБ).

::

::card{title="✅ Регуляризаційний ефект" icon="i-lucide-shield"}

Невеликий шум у градієнті (через вибірковість батчу) діє як **імпліцитна регуляризація**, зменшуючи перенавчання. Це один із секретів успіху глибокого навчання.

::

::

**Недоліки Mini-batch GD:**

::card-group

::card{title="⚠️ Гіперпараметр batch size" icon="i-lucide-settings"}

Розмір батчу стає черговим гіперпараметром, який потрібно налаштовувати. Надто малий — шумно та повільно, надто великий — ризик перенавчання.

::

::card{title="⚠️ Залежність від апаратури" icon="i-lucide-server"}

Оптимальний batch size залежить від пам'яті GPU. На GTX 1060 (6 ГБ) можна використовувати batch_size=64, а на A100 (80 ГБ) — 512.

Практично **всі сучасні моделі** (ResNet, BERT, GPT, DALL-E) навчаються з Mini-batch Gradient Descent. Це оптимальний компроміс між швидкістю, пам'яттю та якістю.

# Функція втрат для логістичної регресії
def sigmoid(z):
    return 1 / (1 + np.exp(-np.clip(z, -500, 500)))

def compute_loss(X, y, w):
    """Cross-Entropy Loss"""
    z = X @ w
    predictions = sigmoid(z)
    epsilon = 1e-15  # для стабільності log
    loss = -np.mean(y * np.log(predictions + epsilon) + 
                    (1 - y) * np.log(1 - predictions + epsilon))
    return loss

def compute_gradient(X, y, w):
    """Градієнт Cross-Entropy"""
    z = X @ w
    predictions = sigmoid(z)
    gradient = X.T @ (predictions - y) / len(y)
    return gradient

# Додамо bias (стовпчик одиниць)
X_bias = np.c_[np.ones(len(X)), X]

# Створимо сітку ваг для візуалізації ландшафту втрат
w0_range = np.linspace(-3, 3, 100)
w1_range = np.linspace(-3, 3, 100)

Z = np.zeros_like(W0)

for i in range(W0.shape[0]):

        Z[i, j] = compute_loss(X_bias, y, w)

```python
def batch_gradient_descent(X, y, lr=0.5, epochs=50):
    """Batch GD: градієнт по всьому датасету"""
    w = np.array([0.0, -2.5, -2.5])  # Початкова точка
    trajectory = [w.copy()]
    
    for epoch in range(epochs):
        gradient = compute_gradient(X, y, w)
        w = w - lr * gradient
        trajectory.append(w.copy())
    
    return np.array(trajectory)

def stochastic_gradient_descent(X, y, lr=0.05, epochs=50):
    """SGD: градієнт по одному прикладу"""
    w = np.array([0.0, -2.5, -2.5])
    trajectory = [w.copy()]
    
    for epoch in range(epochs):
        # Перемішаємо дані
        indices = np.random.permutation(len(X))
        for i in indices:
            X_single = X[i:i+1]
            y_single = y[i:i+1]
            gradient = compute_gradient(X_single, y_single, w)
            w = w - lr * gradient
            if len(trajectory) < epochs * 10:  # Зберігаємо кожні 40 оновлень
                if i % 40 == 0:
                    trajectory.append(w.copy())
    
    return np.array(trajectory)

def mini_batch_gradient_descent(X, y, batch_size=32, lr=0.3, epochs=50):
    """Mini-batch GD: градієнт по невеликому батчу"""
    w = np.array([0.0, -2.5, -2.5])
    trajectory = [w.copy()]
    
    n_batches = len(X) // batch_size
    
    for epoch in range(epochs):
        indices = np.random.permutation(len(X))
        for i in range(n_batches):
            batch_indices = indices[i * batch_size : (i+1) * batch_size]
            X_batch = X[batch_indices]
            y_batch = y[batch_indices]
            gradient = compute_gradient(X_batch, y_batch, w)
            w = w - lr * gradient
            if epoch % 4 == 0:  # Зберігаємо кожну 4-ту епоху
                trajectory.append(w.copy())
    
    return np.array(trajectory)

# Запускаємо три алгоритми
traj_batch = batch_gradient_descent(X_bias, y, lr=0.5, epochs=50)
traj_sgd = stochastic_gradient_descent(X_bias, y, lr=0.05, epochs=50)
traj_minibatch = mini_batch_gradient_descent(X_bias, y, batch_size=32, lr=0.3, epochs=50)

print(f"Траєкторія Batch GD: {len(traj_batch)} точок")
print(f"Траєкторія SGD: {len(traj_sgd)} точок")
print(f"Траєкторія Mini-batch GD: {len(traj_minibatch)} точок")

## PyTorch DataLoader — ефективне завантаження даних

Тепер, коли ми розуміємо теорію Mini-batch GD, перейдемо до практичної реалізації у PyTorch. Клас `torch.utils.data.DataLoader` автоматизує розбиття датасету на батчі, перемішування та паралельне завантаження.

### Анатомія DataLoader

`DataLoader` приймає датасет (об'єкт класу `Dataset`) та створює ітератор, що повертає батчі даних. Основні параметри:

| Параметр | Тип | Опис |
|:---------|:----|:-----|
| `dataset` | `Dataset` | Об'єкт датасету (наприклад, `torchvision.datasets.MNIST`) |
| `batch_size` | `int` | Розмір батчу (кількість прикладів) |
| `shuffle` | `bool` | Перемішувати датасет перед кожною епохою (для train=True, для val/test=False) |
| `num_workers` | `int` | Кількість паралельних процесів для завантаження даних (0 = основний процес) |
| `pin_memory` | `bool` | Зберігати дані у pinned memory для швидшого копіювання на GPU |
| `drop_last` | `bool` | Відкинути останній неповний батч (якщо датасет не ділиться націло на batch_size) |

import torch.optim as optim

# Проста CNN модель
class SimpleCNN(nn.Module):
    def __init__(self):
        super(SimpleCNN, self).__init__()
        self.conv1 = nn.Conv2d(1, 32, kernel_size=3, padding=1)
        self.conv2 = nn.Conv2d(32, 64, kernel_size=3, padding=1)
        self.pool = nn.MaxPool2d(2, 2)
        self.fc1 = nn.Linear(64 * 7 * 7, 128)
        self.fc2 = nn.Linear(128, 10)
        self.relu = nn.ReLU()
    
    def forward(self, x):

        x = self.pool(x)  # 28x28 → 14x14
        x = self.relu(self.conv2(x))
        x = self.pool(x)  # 14x14 → 7x7
        x = x.view(x.size(0), -1)  # Flatten
        x = self.relu(self.fc1(x))
        x = self.fc2(x)
        return x

    for batch_idx, (images, labels) in enumerate(loader):
        # Перенесення даних на GPU
        images, labels = images.to(device), labels.to(device)
        
        # Forward pass
        outputs = model(images)
        loss = criterion(outputs, labels)
        
        # Backward pass та оптимізація
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
        
        # Статистика
        running_loss += loss.item()
        _, predicted = outputs.max(1)
        total += labels.size(0)
        correct += predicted.eq(labels).sum().item()
        
        # Виведення прогресу кожні 100 батчів
        if (batch_idx + 1) % 100 == 0:
            print(f"  Батч [{batch_idx+1}/{len(loader)}] | "
                  f"Loss: {running_loss / (batch_idx+1):.4f} | "
                  f"Acc: {100. * correct / total:.2f}%")
    
    epoch_loss = running_loss / len(loader)
    epoch_acc = 100. * correct / total
    return epoch_loss, epoch_acc

# Навчання 3 епохи
print("🚀 Початок навчання...\n")
for epoch in range(3):
    print(f"Епоха {epoch + 1}/3:")
    loss, acc = train_one_epoch(model, train_loader, criterion, optimizer, device)
    print(f"✅ Епоха завершена | Середня втрата: {loss:.4f} | Точність: {acc:.2f}%\n")

print("🎉 Навчання завершено!")
```

import time

def train_with_batch_size(batch_size, epochs=10):
    """Навчання моделі з заданим batch_size"""
    # DataLoader
    train_loader = DataLoader(
        train_dataset, 
        batch_size=batch_size,

    )

    criterion = nn.CrossEntropyLoss()
    optimizer = optim.SGD(model.parameters(), lr=0.01, momentum=0.9)

    history = {
        'train_loss': [],
        'train_acc': [],
        'epoch_time': []
    }
    
    print(f"\n📊 Навчання з batch_size={batch_size}")

            loss.backward()
            optimizer.step()

            total += labels.size(0)
            correct += predicted.eq(labels).sum().item()

## Термінологія: Epoch, Iteration, Batch

Тепер, коли ми розуміємо практичну роботу Mini-batch GD, формалізуймо ключову термінологію. Ці терміни **постійно** вживаються у літературі та коді, тому їх розуміння критичне.

::card-group

::card{title="📦 Batch (Батч)" icon="i-lucide-package"}

**Невелика група прикладів**, що обробляється за одну ітерацію. Типовий розмір: 32-256 прикладів.

**Приклад:** batch із 128 зображень = 128 рядків у тензорі `[128, 1, 28, 28]`.

::

::card{title="🔄 Iteration (Ітерація)" icon="i-lucide-repeat"}

**Одне оновлення ваг** після обробки одного батчу. 

**Формула:**  
::math-formula
\text{Iterations per epoch} = \left\lceil \frac{N}{\text{batch\_size}} \right\rceil
::

**Приклад:** датасет 60 000 прикладів, batch_size=128 → **469 ітерацій** на епоху.

::

::card{title="📅 Epoch (Епоха)" icon="i-lucide-calendar"}

**Один повний прохід** через весь тренувальний датасет. Після епохи кожен приклад було побачено рівно один раз.

**Приклад:** якщо навчаємо 10 епох, кожен приклад буде використаний для оновлення ваг 10 разів.

::

::

## Висновки та практичні рекомендації

Ми детально розібрали три підходи до градієнтного спуску та навчилися ефективно використовувати PyTorch DataLoader. Підіб'ємо підсумки:

::::accordion

:::accordion-item{label="❓ Який batch_size вибрати для нової задачі?" icon="i-lucide-help-circle"}

**Загальне правило:**

1. **Починайте з 32-128** — працює для 90% задач
2. **Експериментуйте:** збільшуйте batch_size, поки модель поміщається в GPU пам'ять
3. **Моніторьте validation loss:** якщо модель перенавчається, зменшіть batch_size (більший шум = краща регуляризація)

**Специфічні рекомендації:**

- **Малі зображення (28×28, 32×32):** 128-512
- **Середні зображення (224×224):** 32-128
- **Великі зображення (>512×512):** 8-32
- **NLP (довгі послідовності):** 16-64
- **Tabular data (XGBoost competitor):** 256-1024

:::

:::accordion-item{label="❓ Чому великий batch_size може погіршити генералізацію?" icon="i-lucide-help-circle"}

Дослідження показали (Keskar et al., 2017), що **надто великі батчі** призводять до конвергенції у **вузькі мінімуми** (*sharp minima*), які погано генералізуються на нові дані. 

**Інтуїція:** великий batch_size → дуже точний градієнт → модель «впевнено» йде у найближчий мінімум, навіть якщо він вузький. Малий batch_size → шумний градієнт → модель «блукає» та знаходить **широкі мінімуми** (*flat minima*), які стійкі до збурень.

**Рішення:** використовувати техніку **learning rate warm-up** та **збільшення LR пропорційно batch_size** (правило Гойала: LR × sqrt(batch_size_ratio)).

:::

:::accordion-item{label="❓ Що робити, якщо датасет не поміщається в RAM?" icon="i-lucide-help-circle"}

**Три стратегії:**

1. **Кастомний Dataset із ледачим завантаженням:**
   ```python
   class LazyImageDataset(Dataset):
       def __getitem__(self, idx):
           # Зчитуємо зображення з диска лише при запиті
           img = Image.open(self.image_paths[idx])
           return self.transform(img), self.labels[idx]
   ```

2. **Використання HDF5/Zarr:** зберігати дані у форматі, оптимізованому для швидкого доступу по індексах

3. **Стримінг з хмари:** AWS S3, Google Cloud Storage + streaming DataLoader

**PyTorch підтримує всі ці підходи через абстракцію `Dataset`!**

:::

:::accordion-item{label="❓ Як прискорити завантаження даних?" icon="i-lucide-help-circle"}

**Оптимізації:**

1. **Збільшити `num_workers`** (2-8 оптимально)
2. **Використати `pin_memory=True`** (прискорює копіювання CPU → GPU)
3. **Кешувати трансформації** (якщо augmentation повільна)
4. **Зберігати дані на SSD**, а не HDD (10x різниця швидкості)
5. **Попередньо обробити дані:** конвертувати всі зображення у .npy масиви замість .jpg (уникнути декодування)

**Профілювання:** використайте `torch.utils.bottleneck` для визначення вузьких місць.

:::

::::

::tip
**Золоте правило batch_size:**

Якщо GPU utilization < 70% (перевіряйте через `nvidia-smi`), збільшуйте batch_size. Якщо GPU memory overflow — зменшуйте. Збалансований batch_size завантажує GPU на 80-95%.
::
