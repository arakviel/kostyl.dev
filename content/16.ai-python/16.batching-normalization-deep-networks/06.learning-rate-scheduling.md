Саме тому фіксований learning rate **неефективний**:
- Початок навчання: можна було б їхати швидше → втрачаємо час
- Кінець навчання: їдемо занадто швидко → не можемо зупинитись у мінімумі

**Learning Rate Scheduling** — це систематичний підхід до зміни LR протягом навчання, що вирішує цю проблему.

## Фундамент — як learning rate впливає на оптимізацію

Перш ніж перейти до schedulers, згадаймо математику оптимізації та візуально зрозуміймо, як LR впливає на траєкторію руху до мінімуму.

### Оновлення ваг у градієнтному спуску

Базова формула SGD (Stochastic Gradient Descent):

::math-formula
\mathbf{w}_{t+1} = \mathbf{w}_t - \eta \nabla_{\mathbf{w}} L(\mathbf{w}_t)
::

Де:
- :math-formula{tex="\mathbf{w}_t" inline} — поточні ваги на кроці :math-formula{tex="t" inline}
- :math-formula{tex="\eta" inline} — **learning rate** (швидкість навчання)
- :math-formula{tex="\nabla_{\mathbf{w}} L" inline} — градієнт функції втрат

**Ключовий інсайт:** Learning rate :math-formula{tex="\eta" inline} — це **довжина кроку** у напрямку, протилежному градієнту. Чим більший :math-formula{tex="\eta" inline}, тим більший крок робимо за одну ітерацію.

### Три сценарії: занадто малий, оптимальний, занадто великий LR

Розглянемо просту квадратичну функцію втрат :math-formula{tex="L(w) = (w - 3)^2" inline} з мінімумом у точці :math-formula{tex="w^* = 3" inline}.

::jupyter-notebook{title="learning_rate_visualization.ipynb" kernel="Python 3.11 (ipykernel)"}

::jupyter-cell{type="markdown"}

### Візуалізація впливу learning rate

Запустимо градієнтний спуск з трьома різними LR та порівняємо траєкторії.

::

::jupyter-cell{executionCount="1" executionTime="0.92s"}

```python
import numpy as np
import matplotlib.pyplot as plt

# Проста квадратична функція: L(w) = (w - 3)²
def loss_fn(w):
    return (w - 3) ** 2

def gradient(w):
    return 2 * (w - 3)

# Градієнтний спуск з різними LR
def gradient_descent(w_init, lr, num_steps):
    trajectory = [w_init]
    w = w_init
    
    for _ in range(num_steps):
        grad = gradient(w)
        w = w - lr * grad
        trajectory.append(w)
    
    return np.array(trajectory)

# Три сценарії
w_init = 0.0
num_steps = 15

traj_small = gradient_descent(w_init, lr=0.1, num_steps=num_steps)    # Малий LR
traj_optimal = gradient_descent(w_init, lr=0.5, num_steps=num_steps)  # Оптимальний LR
traj_large = gradient_descent(w_init, lr=1.1, num_steps=num_steps)    # Занадто великий LR

# Візуалізація
fig, axes = plt.subplots(1, 3, figsize=(18, 5))

# Функція втрат
w_range = np.linspace(-1, 6, 200)
loss_range = loss_fn(w_range)

scenarios = [
    (traj_small, 0.1, 'Занадто малий LR = 0.1', '#3b82f6', axes[0]),
    (traj_optimal, 0.5, 'Оптимальний LR = 0.5', '#22c55e', axes[1]),
    (traj_large, 1.1, 'Занадто великий LR = 1.1', '#ef4444', axes[2])
]

for trajectory, lr, title, color, ax in scenarios:
    # Ландшафт втрат
    ax.plot(w_range, loss_range, 'k-', linewidth=1.5, alpha=0.3, label='Loss landscape')
    
    # Мінімум
    ax.plot(3, 0, 'g*', markersize=20, label='Глобальний мінімум', zorder=5)
    
    # Траєкторія оптимізації
    losses = loss_fn(trajectory)
    ax.plot(trajectory, losses, 'o-', color=color, linewidth=2.5, 
            markersize=6, alpha=0.8, label='Траєкторія GD')
    
    # Стартова точка
    ax.plot(trajectory[0], losses[0], 'ko', markersize=12, label='Старт', zorder=4)
    
    # Нумерація кроків
    for i in [0, 5, 10, min(14, len(trajectory)-1)]:
        if i < len(trajectory):
            ax.annotate(f'{i}', xy=(trajectory[i], losses[i]), 
                       xytext=(5, 5), textcoords='offset points', fontsize=9)
    
    ax.set_xlabel('Weight (w)', fontsize=12)
    ax.set_ylabel('Loss L(w)', fontsize=12)
    ax.set_title(title, fontsize=13, fontweight='bold')
    ax.legend(fontsize=9)
    ax.grid(alpha=0.3)
    ax.set_ylim([-1, 15])

plt.tight_layout()
plt.show()

# Виведення статистики
print("📊 Порівняння конвергенції:\n")
print(f"{'LR':<8} {'Кроків до w ≈ 3':<20} {'Фінальне w':<15} {'Фінальна втрата':<20} {'Статус'}")
print("-" * 85)

for traj, lr, desc, _, _ in scenarios:
    final_w = traj[-1]
    final_loss = loss_fn(final_w)
    
    # Скільки кроків потрібно, щоб досягти |w - 3| < 0.1
    converged_step = None
    for i, w in enumerate(traj):
        if abs(w - 3) < 0.1:
            converged_step = i
            break
    
    status = "✅ Сходиться" if converged_step else "❌ Не сходиться"
    steps_str = f"{converged_step}" if converged_step else "—"
    
    print(f"{lr:<8.1f} {steps_str:<20} {final_w:<15.4f} {final_loss:<20.6f} {status}")
```

**Інтерпретація результатів:**

- **LR = 0.1 (малий):** Модель повільно, але впевнено рухається до мінімуму. Потрібно 13 кроків. Фінальна втрата близька до нуля, але не ідеальна. **Проблема:** Навчання займе багато часу, особливо для глибоких мереж.

- **LR = 0.5 (оптимальний):** Швидка та стабільна конвергенція за 4 кроки. Фінальна втрата практично нульова. **Ідеальний баланс** між швидкістю та стабільністю.

- **LR = 1.1 (великий):** Катастрофа! Модель **перестрибує** через мінімум з кожним кроком, рухаючись все далі. Втрати **зростають** замість зменшення. Навчання нестабільне, градієнти можуть вибухнути (exploding gradients).

### Проблема у реальних нейронних мережах

У реальних глибоких мережах ландшафт втрат **набагато складніший** за просту квадратичну функцію:

::card-group

::card{title="🏔️ Нерівномірна кривизна" icon="i-lucide-mountain-snow"}

Різні напрямки у просторі параметрів мають різну "крутизну". У одному напрямку градієнт крутий (потрібен малий LR), в іншому — пологий (потрібен великий LR).

**Наслідок:** Один фіксований LR не може бути оптимальним для всіх напрямків.

::

::card{title="🎢 Сідлові точки та плато" icon="i-lucide-trending-up"}

Ландшафт містить **сідлові точки** (градієнт нульовий, але це не мінімум) та **плато** (майже нульовий градієнт на великій області). Модель "застряє" на плато, якщо LR занадто малий.

**Розв'язання:** Періодично збільшувати LR для "виштовхування" з плато (Warm Restarts).

::

::card{title="⏱️ Зміна кривизни протягом навчання" icon="i-lucide-clock"}

На початку навчання (далеко від мінімуму) ландшафт "грубий" — великі LR безпечні. Ближче до мінімуму ландшафт стає "делікатним" — потрібні малі LR для точного позиціонування.

**Висновок:** Оптимальний LR **змінюється** протягом навчання!

::

## Основні типи Learning Rate Schedulers

Тепер, розуміючи проблему фіксованого LR, розглянемо систематичні підходи до його зміни. PyTorch надає клас `torch.optim.lr_scheduler` з готовими реалізаціями популярних стратегій.

### 1. StepLR — зменшення кожні N епох

**Ідея:** Зменшувати learning rate на фактор :math-formula{tex="\gamma" inline} кожні :math-formula{tex="N" inline} епох.

::math-formula
\eta_t = \eta_0 \cdot \gamma^{\lfloor t / N \rfloor}
::

Де:
- :math-formula{tex="\eta_0" inline} — початковий learning rate
- :math-formula{tex="\gamma" inline} — множник зменшення (зазвичай 0.1 або 0.5)
- :math-formula{tex="N" inline} — крок (step_size), кількість епох між зменшеннями
- :math-formula{tex="t" inline} — поточна епоха

**Приклад:** :math-formula{tex="\eta_0 = 0.1, \gamma = 0.1, N = 30" inline}

| Епоха | Learning Rate | Пояснення |
|:------|:--------------|:----------|
| 0-29  | 0.1           | Початковий період |
| 30-59 | 0.01          | Після 30 епох: :math-formula{tex="0.1 \times 0.1 = 0.01" inline} |
| 60-89 | 0.001         | Після 60 епох: :math-formula{tex="0.01 \times 0.1 = 0.001" inline} |
| 90+   | 0.0001        | Після 90 епох: :math-formula{tex="0.001 \times 0.1 = 0.0001" inline} |

::jupyter-cell{executionCount="2"}

```python
import torch
import torch.optim as optim
import matplotlib.pyplot as plt

# Створимо dummy модель та optimizer для демонстрації
model = torch.nn.Linear(10, 1)
optimizer = optim.SGD(model.parameters(), lr=0.1, momentum=0.9)

# StepLR scheduler
scheduler = optim.lr_scheduler.StepLR(optimizer, step_size=30, gamma=0.1)

# Симуляція 100 епох
epochs = 100
lr_history_step = []

for epoch in range(epochs):
    lr_history_step.append(optimizer.param_groups[0]['lr'])
    
    # Імітація training step (не важливо для демонстрації scheduler)
    optimizer.step()
    
    # Оновлення LR
    scheduler.step()

# Візуалізація
plt.figure(figsize=(12, 5))
plt.plot(lr_history_step, linewidth=2.5, color='#3b82f6', label='StepLR')
plt.xlabel('Epoch', fontsize=12)
plt.ylabel('Learning Rate', fontsize=12)
plt.title('StepLR Scheduler (step_size=30, gamma=0.1)', fontsize=14, fontweight='bold')
plt.yscale('log')  # Логарифмічна шкала для кращої візуалізації
plt.grid(alpha=0.3)
plt.legend(fontsize=11)
plt.tight_layout()
plt.show()

print("📊 StepLR:")
print(f"├─ Епохи 0-29:   LR = {lr_history_step[0]:.4f}")
print(f"├─ Епохи 30-59:  LR = {lr_history_step[30]:.4f}")
print(f"├─ Епохи 60-89:  LR = {lr_history_step[60]:.4f}")
print(f"└─ Епохи 90-99:  LR = {lr_history_step[90]:.4f}")
```

### 2. MultiStepLR — зменшення у конкретні епохи

**Ідея:** Розширення StepLR — зменшуємо LR у заздалегідь визначені епохи (milestones).

::math-formula
\eta_t = \eta_0 \cdot \gamma^{\sum_{i} \mathbb{1}(t \geq m_i)}
::

### 4. CosineAnnealingLR — косинусоїдальне зменшення

**Ідея:** Зменшувати LR за косинусоїдою від :math-formula{tex="\eta_{\text{max}}" inline} до :math-formula{tex="\eta_{\text{min}}" inline} протягом :math-formula{tex="T_{\text{max}}" inline} епох.

::math-formula
\eta_t = \eta_{\text{min}} + \frac{1}{2}(\eta_{\text{max}} - \eta_{\text{min}})\left(1 + \cos\left(\frac{t}{T_{\text{max}}} \pi\right)\right)
::

Де:
- :math-formula{tex="\eta_{\text{max}}" inline} — початковий LR (0.1)
- :math-formula{tex="\eta_{\text{min}}" inline} — мінімальний LR (зазвичай 0 або 1e-6)
- :math-formula{tex="T_{\text{max}}" inline} — загальна кількість епох для одного циклу

**Візуальна інтуїція:** Уявіть половину косинусної хвилі, що плавно спускається від максимуму до мінімуму.

## Advanced техніки — Warm-up та Warm Restarts

Тепер розглянемо дві потужні advanced техніки, що використовуються у cutting-edge дослідженнях: **Learning Rate Warm-up** та **SGDR (Stochastic Gradient Descent with Warm Restarts)**.

### Learning Rate Warm-up — обережний старт

**Проблема:** На самому початку навчання ваги ініціалізовані випадково (навіть з He/Xavier initialization). Якщо одразу застосувати великий LR (наприклад, 0.1), градієнти можуть бути **нестабільними** та спричинити divergence, особливо для дуже глибоких мереж або великих batch sizes.

**Ідея Warm-up:** Починати з дуже малого LR (наприклад, 1e-5) та **поступово збільшувати** його до цільового значення (0.1) протягом перших :math-formula{tex="N" inline} епох або ітерацій.

**Математична реалізація (лінійний warm-up):**

::math-formula
\eta_t = \begin{cases}
\eta_{\text{min}} + t \cdot \frac{\eta_{\text{max}} - \eta_{\text{min}}}{T_{\text{warmup}}} & \text{якщо } t < T_{\text{warmup}} \\
\eta_{\text{max}} & \text{інакше}
\end{cases}
::

Де :math-formula{tex="T_{\text{warmup}}" inline} — кількість епох warm-up (зазвичай 5-10).

::jupyter-cell{executionCount="7"}

```python
# Реалізація Warm-up + CosineAnnealing вручну
class WarmupCosineScheduler:
    def __init__(self, optimizer, warmup_epochs, total_epochs, eta_min=1e-6, warmup_start_lr=1e-5):
        self.optimizer = optimizer
        self.warmup_epochs = warmup_epochs
        self.total_epochs = total_epochs
        self.eta_min = eta_min
        self.warmup_start_lr = warmup_start_lr
        self.base_lr = optimizer.param_groups[0]['lr']
        self.current_epoch = 0
    
    def step(self):
        if self.current_epoch < self.warmup_epochs:
            # Лінійний warm-up
            lr = self.warmup_start_lr + (self.base_lr - self.warmup_start_lr) * \
                 (self.current_epoch / self.warmup_epochs)
        else:
            # Cosine annealing після warm-up
            progress = (self.current_epoch - self.warmup_epochs) / \
                      (self.total_epochs - self.warmup_epochs)
            lr = self.eta_min + (self.base_lr - self.eta_min) * \
                 0.5 * (1 + np.cos(np.pi * progress))
        
        for param_group in self.optimizer.param_groups:
            param_group['lr'] = lr
        
        self.current_epoch += 1
        return lr

# Симуляція
```

### SGDR — Warm Restarts (Перезапуск Warm)

**Ідея:** Періодично **скидати LR до початкового значення** (restart), замість монотонного зменшення. Це дозволяє моделі "виштовхнутися" з локальних мінімумів та знайти кращі розв'язки.

**Метафора:** Уявіть кулю, що котиться долиною до ямки (локальний мінімум). Якщо періодично "підкидати" кулю вгору (restart LR), вона може перекотитися через гірку та знайти глибшу ямку (кращий глобальний мінімум).

**Математика (Cosine Annealing with Warm Restarts):**

::math-formula
\eta_t = \eta_{\text{min}} + \frac{1}{2}(\eta_{\text{max}} - \eta_{\text{min}})\left(1 + \cos\left(\frac{T_{\text{cur}}}{T_i} \pi\right)\right)
::

Де:
- :math-formula{tex="T_{\text{cur}}" inline} — кількість епох з моменту останнього restart
- :math-formula{tex="T_i" inline} — кількість епох до наступного restart

Кожен restart подвоює період: :math-formula{tex="T_i = T_0, 2T_0, 4T_0, 8T_0, \ldots" inline}

::jupyter-cell{executionCount="8"}

```python
# PyTorch CosineAnnealingWarmRestarts
optimizer = optim.SGD(model.parameters(), lr=0.1, momentum=0.9)
scheduler = optim.lr_scheduler.CosineAnnealingWarmRestarts(
    optimizer,
    T_0=10,      # Перший restart через 10 епох
    T_mult=2,    # Кожен наступний період подвоюється
    eta_min=1e-6
)

lr_history_sgdr = []
for epoch in range(150):  # Довше навчання для демонстрації
    lr_history_sgdr.append(optimizer.param_groups[0]['lr'])
    optimizer.step()
    scheduler.step()

# Візуалізація
plt.figure(figsize=(14, 6))
plt.plot(lr_history_sgdr, linewidth=2.5, color='#8b5cf6', label='SGDR (T_0=10, T_mult=2)')

# Позначимо restart точки
restart_epochs = [10, 30, 70]  # 10, 10+20, 10+20+40
for restart_epoch in restart_epochs:
    if restart_epoch < len(lr_history_sgdr):
        plt.axvline(x=restart_epoch, color='red', linestyle='--', alpha=0.5, linewidth=2)
        plt.text(restart_epoch, 0.12, f'Restart', ha='center', fontsize=10, rotation=90,
                bbox=dict(boxstyle='round', facecolor='wheat', alpha=0.5))

plt.xlabel('Epoch', fontsize=12)
plt.ylabel('Learning Rate', fontsize=12)
plt.title('SGDR (Warm Restarts) — періодичні стрибки LR', fontsize=14, fontweight='bold')
plt.grid(alpha=0.3)
plt.legend(fontsize=11)
plt.tight_layout()
plt.show()

print("📊 SGDR Warm Restarts:")
print(f"├─ Перший період (епохи 0-9): cosine decay")
print(f"├─ Restart на епосі 10: LR → 0.1")
print(f"├─ Другий період (епохи 10-29, довжина 20): cosine decay")
print(f"├─ Restart на епосі 30: LR → 0.1")
print(f"└─ Третій період (епохи 30-69, довжина 40): cosine decay")
```

### OneCycleLR — супер-конвергенція

**Ідея (від Leslie Smith, 2018):** Замість монотонного зменшення LR, використовуйте **один великий цикл**:
1. **Збільшення** LR від малого до максимального (50% часу)
2. **Зменшення** LR від максимального до мінімального (50% часу)

Це дозволяє досягти "super-convergence" — навчання у 5-10 разів швидше з тією ж accuracy!

::jupyter-cell{executionCount="9"}

```python
# OneCycleLR
optimizer = optim.SGD(model.parameters(), lr=0.1, momentum=0.9)

# Потрібно знати загальну кількість кроків (не епох!)
total_steps = 100 * 391  # 100 епох × 391 батч/епоха (CIFAR-10 з batch_size=128)

scheduler = optim.lr_scheduler.OneCycleLR(
    optimizer,
    max_lr=0.1,           # Максимальний LR у піку циклу
    total_steps=total_steps,
    pct_start=0.3,        # 30% часу — збільшення, 70% — зменшення
    anneal_strategy='cos', # Косинусоїдальна форма
    div_factor=25,        # Початковий LR = max_lr / 25 = 0.004
    final_div_factor=10000 # Фінальний LR = max_lr / 10000 = 0.00001
)

# Симуляція (кожен "epoch" тут — це насправді батч)
lr_history_onecycle = []
for step in range(1000):  # Симулюємо 1000 кроків
    lr_history_onecycle.append(optimizer.param_groups[0]['lr'])
    optimizer.step()
    scheduler.step()

# Візуалізація
plt.figure(figsize=(14, 6))
plt.plot(lr_history_onecycle, linewidth=2.5, color='#22c55e', label='OneCycleLR')
plt.axvline(x=300, color='orange', linestyle='--', alpha=0.5, linewidth=2, label='Пік (30%)')
plt.xlabel('Training Step (батч)', fontsize=12)
plt.ylabel('Learning Rate', fontsize=12)
plt.title('OneCycleLR — один великий цикл (super-convergence)', fontsize=14, fontweight='bold')
plt.grid(alpha=0.3)
plt.legend(fontsize=11)
plt.tight_layout()
plt.show()

print("📊 OneCycleLR:")
print(f"├─ Старт (крок 0):      LR = {lr_history_onecycle[0]:.6f}")
print(f"├─ Пік (крок 300):      LR = {lr_history_onecycle[300]:.6f}")
print(f"├─ Середина (крок 500): LR = {lr_history_onecycle[500]:.6f}")
print(f"└─ Фініш (крок 999):    LR = {lr_history_onecycle[999]:.6f}")
```

::jupyter-cell{executionCount="10"}

```python
import torch
import torch.nn as nn
import torch.optim as optim
from torch.utils.data import DataLoader
from torchvision import datasets, transforms
import time

# Підготовка даних
device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
print(f"🖥️ Пристрій: {device}\n")

transform_train = transforms.Compose([
    transforms.RandomCrop(32, padding=4),
    transforms.RandomHorizontalFlip(),
    transforms.ToTensor(),
    transforms.Normalize((0.4914, 0.4822, 0.4465), (0.2470, 0.2435, 0.2616))
])

transform_test = transforms.Compose([
    transforms.ToTensor(),
    transforms.Normalize((0.4914, 0.4822, 0.4465), (0.2470, 0.2435, 0.2616))
])

train_dataset = datasets.CIFAR10(root='./data', train=True, download=True, transform=transform_train)
test_dataset = datasets.CIFAR10(root='./data', train=False, download=True, transform=transform_test)

train_loader = DataLoader(train_dataset, batch_size=128, shuffle=True, num_workers=2)
test_loader = DataLoader(test_dataset, batch_size=128, shuffle=False, num_workers=2)

# Імпортуємо ResNet-18 (припускаємо, що ми реалізували його у попередній статті)
from torchvision import models
resnet18 = models.resnet18(num_classes=10)
# Адаптація для CIFAR-10: зменшимо початковий conv
resnet18.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
resnet18.maxpool = nn.Identity()  # Вимкнемо maxpool для малих зображень

def train_with_scheduler(model, scheduler_name, scheduler, num_epochs=100):
    """Тренування моделі з заданим scheduler"""
    model = model.to(device)
    criterion = nn.CrossEntropyLoss()
    optimizer = optim.SGD(model.parameters(), lr=0.1, momentum=0.9, weight_decay=5e-4)
    
    history = {'train_loss': [], 'train_acc': [], 'test_loss': [], 'test_acc': [], 'lr': []}
    
    print(f"\n🚀 Початок навчання: {scheduler_name}")
    print("=" * 80)
    start_time = time.time()
    
    best_acc = 0
    
    for epoch in range(1, num_epochs + 1):
        # Тренування
        model.train()
        running_loss = 0.0
        correct = 0
        total = 0
        
        for images, labels in train_loader:
            images, labels = images.to(device), labels.to(device)
            
            optimizer.zero_grad()
            outputs = model(images)
            loss = criterion(outputs, labels)
            loss.backward()
            optimizer.step()
            
            running_loss += loss.item() * images.size(0)
            _, predicted = outputs.max(1)
            total += labels.size(0)
            correct += predicted.eq(labels).sum().item()
        
        train_loss = running_loss / total
        train_acc = 100. * correct / total
        
        # Валідація
        model.eval()
        running_loss = 0.0
        correct = 0
        total = 0
        
        with torch.no_grad():
            for images, labels in test_loader:
                images, labels = images.to(device), labels.to(device)
                outputs = model(images)
                loss = criterion(outputs, labels)
                
                running_loss += loss.item() * images.size(0)
                _, predicted = outputs.max(1)
                total += labels.size(0)
                correct += predicted.eq(labels).sum().item()
        
        test_loss = running_loss / total
        test_acc = 100. * correct / total
        
        # Збереження історії
        history['train_loss'].append(train_loss)
        history['train_acc'].append(train_acc)
        history['test_loss'].append(test_loss)
        history['test_acc'].append(test_acc)
        history['lr'].append(optimizer.param_groups[0]['lr'])
        
        # Оновлення scheduler
        if scheduler_name == "ReduceLROnPlateau":
            scheduler.step(test_loss)
        elif scheduler is not None:
            scheduler.step()
        
        if test_acc > best_acc:
            best_acc = test_acc
        
        # Виведення прогресу
        if epoch % 20 == 0 or epoch == 1:
            print(f"Epoch {epoch:3d} | Train: {train_loss:.4f} / {train_acc:.2f}% | "
                  f"Test: {test_loss:.4f} / {test_acc:.2f}% | LR: {history['lr'][-1]:.6f}")
    
    elapsed = time.time() - start_time
    print("=" * 80)
    print(f"✅ Завершено за {elapsed/60:.1f} хв | Найкраща accuracy: {best_acc:.2f}%\n")
    
    return history

# Експеримент 1: Фіксований LR (baseline)
model_fixed = models.resnet18(num_classes=10)
model_fixed.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
model_fixed.maxpool = nn.Identity()

history_fixed = train_with_scheduler(model_fixed, "Fixed LR", scheduler=None, num_epochs=100)

# Експеримент 2: StepLR
model_step = models.resnet18(num_classes=10)
model_step.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
model_step.maxpool = nn.Identity()

optimizer_step = optim.SGD(model_step.parameters(), lr=0.1, momentum=0.9, weight_decay=5e-4)
scheduler_step = optim.lr_scheduler.StepLR(optimizer_step, step_size=30, gamma=0.1)

history_step = train_with_scheduler(model_step, "StepLR", scheduler_step, num_epochs=100)

# Експеримент 3: CosineAnnealingLR
model_cosine = models.resnet18(num_classes=10)
model_cosine.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
model_cosine.maxpool = nn.Identity()

optimizer_cosine = optim.SGD(model_cosine.parameters(), lr=0.1, momentum=0.9, weight_decay=5e-4)
scheduler_cosine = optim.lr_scheduler.CosineAnnealingLR(optimizer_cosine, T_max=100, eta_min=1e-6)

history_cosine = train_with_scheduler(model_cosine, "CosineAnnealingLR", scheduler_cosine, num_epochs=100)

# Експеримент 4: ReduceLROnPlateau
model_plateau = models.resnet18(num_classes=10)
model_plateau.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
model_plateau.maxpool = nn.Identity()

optimizer_plateau = optim.SGD(model_plateau.parameters(), lr=0.1, momentum=0.9, weight_decay=5e-4)
scheduler_plateau = optim.lr_scheduler.ReduceLROnPlateau(
    optimizer_plateau, mode='min', factor=0.1, patience=10, verbose=True
)

history_plateau = train_with_scheduler(model_plateau, "ReduceLROnPlateau", scheduler_plateau, num_epochs=100)

# Експеримент 5: Warm-up + CosineAnnealing
model_warmup = models.resnet18(num_classes=10)
model_warmup.conv1 = nn.Conv2d(3, 64, kernel_size=3, stride=1, padding=1, bias=False)
model_warmup.maxpool = nn.Identity()

optimizer_warmup = optim.SGD(model_warmup.parameters(), lr=0.1, momentum=0.9, weight_decay=5e-4)
scheduler_warmup = WarmupCosineScheduler(optimizer_warmup, warmup_epochs=5, total_epochs=100)

history_warmup = train_with_scheduler(model_warmup, "Warm-up + Cosine", scheduler_warmup, num_epochs=100)
```

:::accordion-item{label="❓ Чому Warm-up допоміг?" icon="i-lucide-help-circle"}

На початку навчання ваги випадкові (навіть після He initialization). Великий LR (0.1) може спричинити:
- Нестабільні градієнти у глибоких шарах
- "Шокування" BatchNorm статистики
- Ризик divergence у перші кілька епох

Warm-up (5 епох від 1e-5 до 0.1) дозволяє моделі "розігрітися":
- Ваги стабілізуються
- BatchNorm накопичує коректні running statistics
- Градієнти стають передбачуваними

Після цього cosine annealing забезпечує оптимальне зменшення LR.

:::

:::accordion-item{label="❓ Чому ReduceLROnPlateau не виграв?" icon="i-lucide-help-circle"}

Хоча ReduceLROnPlateau **адаптивний** і не потребує заздалегідь знати епохи для зменшення, він має два недоліки:

1. **Консерватизм:** `patience=10` означає, що scheduler чекає 10 епох **після** зупинки прогресу. За цей час модель марнує час, рухаючись занадто великими кроками біля мінімуму.

2. **Шум у val_loss:** Validation loss природно шумна (особливо для малих val sets). Scheduler може "пропустити" справжній plateau або спрацювати на випадковому сплеску.

**Висновок:** ReduceLROnPlateau добрий для **першого експерименту** з новою задачею, коли ви не знаєте, коли модель зупиниться. Але для фінального тренування краще використовувати Cosine з warm-up.

:::

## Практичні рекомендації — як обрати scheduler

Підсумуймо всі знання у практичний гід:

### Чек-лист вибору scheduler

::steps

### Крок 1. Оцініть свій сценарій

**Питання:** Чи це перший експеримент чи фінальне тренування?

- **Перший експеримент:** Використовуйте `ReduceLROnPlateau` (адаптивний, безпечний)
- **Фінальне тренування:** Використовуйте `CosineAnnealingLR` або `Warm-up + Cosine`

### Крок 2. Врахуйте тривалість навчання

| Епохи | Рекомендація |
|:------|:-------------|
| **<50** | `StepLR` з milestones=[25, 40] |
| **50-200** | `CosineAnnealingLR` (T_max=num_epochs) |
| **>200** | `ExponentialLR` (gamma=0.98) або `CosineAnnealingWarmRestarts` |

### Крок 3. Розгляньте розмір batch

- **Малий batch (<64):** Градієнти шумні → використовуйте консервативніший scheduler (StepLR)
- **Великий batch (>256):** Градієнти стабільні → використовуйте агресивніший (OneCycleLR)
- **Дуже великий batch (>1024):** **Обов'язковий warm-up** (5-10 епох)

### Крок 4. Специфіка архітектури

- **ResNet, DenseNet, EfficientNet:** `CosineAnnealingLR` (перевірений вибір)
- **Transformers (BERT, GPT):** `Warm-up + Linear Decay` або `Warm-up + Cosine`
- **RNN, LSTM:** `ReduceLROnPlateau` (важко передбачити конвергенцію)

::

### Коли НЕ використовувати scheduling

У деяких випадках фіксований LR насправді краще:

::card-group

::card{title="🔬 Transfer Learning з малим датасетом" icon="i-lucide-database"}

Якщо fine-tune pretrained модель на малому датасеті (<1000 зображень), використовуйте **малий фіксований LR** (1e-4 або 1e-5).

**Чому:** Pretrained ваги вже близькі до оптимуму, великий LR або aggressive scheduling можуть зруйнувати їх.

::

::card{title="⚡ Few-shot learning" icon="i-lucide-zap"}

У few-shot сценаріях (5-10 прикладів на клас) навчання триває 10-20 епох. Scheduling не встигає "розігрітися".

::

::card{title="🎯 Hyperparameter tuning" icon="i-lucide-settings"}

Коли шукаєте оптимальні hyperparameters (learning rate, weight decay, архітектура), спочатку використовуйте фіксований LR для швидких експериментів.
