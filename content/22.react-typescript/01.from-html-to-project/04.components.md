# Компоненти — будівельні блоки інтерфейсу

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Зрозуміти філософію компонентного підходу у React — розбиття UI на незалежні, переповторно використовувані частини.
- Опанувати створення функціональних компонентів із типізацією TypeScript.
- Навчитися передавати дані через props та правильно типізувати їх.
- Усвідомити принцип композиції компонентів через `children`.
- Застосовувати найкращі практики іменування, структурування та організації компонентів.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Компонент** (*component*) — функція, що повертає React Elements (JSX), описуючи частину UI.
- **Props** (*properties*) — незмінні дані, що передаються від батьківського компонента до дочірнього.
- **Композиція** (*composition*) — побудова складних компонентів із простих через вкладення та передачу `children`.
- **Деструктуризація** (*destructuring*) — витягування властивостей із об'єкта `props` для зручності.
- **Children** — спеціальний пропс, що містить вміст між відкриваючим та закриваючим тегами компонента.

::

## Філософія компонентів: Divide and Conquer

Уявіть собі будівництво будинку. Ви не створюєте монолітну структуру, де кожна цеглина унікальна. Натомість ви використовуєте **стандартизовані блоки**: цегли, вікна, двері, сходи. Кожен блок має чіткий призначення, його можна замінити або повторно використати у іншому місці.

React застосовує той самий принцип до UI. Замість одного величезного HTML-файлу ви розбиваєте інтерфейс на **компоненти** — самодостатні, переповторно використовувані частини, кожна з яких відповідає за свій шматок функціональності.

### Проблема монолітного коду

Розглянемо типовий веб-застосунок без компонентного підходу:

```html
<!-- index.html — 2000+ рядків HTML -->
<!DOCTYPE html>
<html>
<head>
  <title>Застосунок</title>
  <style>
    /* 500+ рядків CSS */
    .header { ... }
    .navigation { ... }
    .user-profile { ... }
    .sidebar { ... }
    .content { ... }
    .footer { ... }
  </style>
</head>
<body>
  <!-- Хедер -->
  <header class="header">
    <nav class="navigation">
      <a href="/">Головна</a>
      <a href="/about">Про нас</a>
      <!-- ... 50 рядків навігації -->
    </nav>
    <div class="user-profile">
      <img src="avatar.jpg" />
      <span id="username">Користувач</span>
      <!-- ... 30 рядків профілю -->
    </div>
  </header>

  <!-- Основний контент -->
  <div class="main-content">
    <aside class="sidebar">
      <!-- ... 200 рядків сайдбару -->
    </aside>
    <main class="content">
      <!-- ... 1000 рядків контенту -->
    </main>
  </div>

  <!-- Футер -->
  <footer class="footer">
    <!-- ... 100 рядків футера -->
  </footer>

  <script>
    // 1000+ рядків JavaScript
    document.getElementById('username').textContent = 'Іван';
    // ... десятки обробників подій
  </script>
</body>
</html>
```

**Проблеми цього підходу:**

1. **Складність читання:** Неможливо швидко зрозуміти структуру — усе змішано в одному файлі.
2. **Відсутність переповторного використання:** Якщо потрібен той самий профіль користувача на іншій сторінці — доведеться копіювати HTML та CSS.
3. **Конфлікти імен:** Класи `.user-profile`, `.button`, `.card` можуть випадково збігтися у різних частинах застосунку.
4. **Тестування:** Неможливо протестувати окремий шматок UI — усе зв'язано.
5. **Командна робота:** Кілька розробників не можуть працювати над одним файлом без конфліктів у Git.

### Компонентний підхід React

React пропонує розбити цей монолітний код на **самодостатні компоненти**:

```
App (кореневий компонент)
├── Header
│   ├── Navigation
│   │   ├── NavLink
│   │   ├── NavLink
│   │   └── NavLink
│   └── UserProfile
│       ├── Avatar
│       └── UserMenu
├── MainContent
│   ├── Sidebar
│   │   └── SidebarItem (x5)
│   └── Content
│       └── Article (x10)
└── Footer
    └── SocialLinks
```

Кожен компонент — це окремий файл із власною логікою, стилями та типізацією:

```
src/
├── components/
│   ├── Header/
│   │   ├── Header.tsx
│   │   ├── Header.css
│   │   └── Header.test.tsx
│   ├── Navigation/
│   │   ├── Navigation.tsx
│   │   └── Navigation.css
│   ├── UserProfile/
│   │   ├── UserProfile.tsx
│   │   └── UserProfile.css
│   └── ... (інші компоненти)
└── App.tsx
```

**Переваги:**

- **Модульність:** Кожен компонент — незалежна одиниця, яку можна розробляти, тестувати та документувати окремо.
- **Переповторне використання:** `<Button>`, `<Card>`, `<Modal>` можна використовувати скрізь у застосунку.
- **Ізоляція:** Зміни у `Header` не впливають на `Footer`.
- **Командна робота:** Різні розробники працюють над різними компонентами без конфліктів.

::note
**Аналогія з функціями у програмуванні:**

Компоненти у React — це як функції у звичайному програмуванні. Ви не пишете весь код в одній функції `main()` на 10,000 рядків. Замість цього ви розбиваєте логіку на окремі функції з чіткими обов'язками:

```js
function calculateTotal(items) { ... }
function validateEmail(email) { ... }
function formatDate(date) { ... }
```

Так само у React ви розбиваєте UI на компоненти з чіткими обов'язками:

```tsx
function Button(props) { ... }
function UserCard(props) { ... }
function Modal(props) { ... }
```

::

## Що таке компонент у React?

**Компонент** — це JavaScript-функція, яка приймає об'єкт `props` (властивості) та **повертає React Elements** (JSX), що описують, як повинна виглядати частина UI.

### Найпростіший компонент

```tsx
// src/components/Greeting.tsx
function Greeting() {
  return <h1>Привіт, світ!</h1>;
}

export default Greeting;
```

**Це вже повноцінний React-компонент!** Він:

1. **Називається з великої літери** (`Greeting`, не `greeting`) — це конвенція React.
2. **Повертає JSX** — опис того, що повинно бути на екрані.
3. **Експортується** — щоб інші компоненти могли його імпортувати.

### Використання компонента

```tsx
// src/App.tsx
import Greeting from './components/Greeting';

function App() {
  return (
    <div>
      <Greeting />
      <Greeting />
      <Greeting />
    </div>
  );
}

export default App;
```

**Результат у DOM:**

```html
<div>
  <h1>Привіт, світ!</h1>
  <h1>Привіт, світ!</h1>
  <h1>Привіт, світ!</h1>
</div>
```

::tip
**Компоненти — це звичайні функції:**

Під капотом `<Greeting />` перетворюється на виклик функції:

```js
// JSX
<Greeting />

// Трансформація
_jsx(Greeting, {})

// React викликає
const element = Greeting({});
```

React викликає вашу функцію та отримує React Elements, які потім перетворюються на реальний DOM.

::

### Іменування компонентів: PascalCase

**Правило:** Імена компонентів **завжди** починаються з великої літери.

```tsx
// ✅ ПРАВИЛЬНО — PascalCase
function UserProfile() { ... }
function NavBar() { ... }
function CardHeader() { ... }

// ❌ НЕПРАВИЛЬНО — camelCase
function userProfile() { ... }
function navBar() { ... }
```

**Чому це важливо?**

React розрізняє компоненти та HTML-теги за регістром першої літери:

- **Мала літера** (`<div>`, `<button>`) — React розуміє як HTML-тег.
- **Велика літера** (`<UserProfile>`, `<Button>`) — React розуміє як компонент.

```tsx
// <button> — HTML-тег
<button>Натисни</button>

// <Button> — React-компонент
<Button>Натисни</Button>
```

Якщо ви назвете компонент з малої літери, React спробує знайти HTML-тег із такою назвою:

```tsx
function greeting() {  // ❌ Мала літера!
  return <h1>Привіт</h1>;
}

// JSX
<greeting />

// React шукає HTML-тег <greeting>, а не викликає функцію
// Результат: <greeting></greeting> у DOM (невалідний HTML)
```

## Props: передача даних до компонентів

Компоненти стають корисними, коли ви можете **передавати їм дані**. Це робиться через **props** (*properties* — властивості).

### Базовий приклад: компонент із пропсами

```tsx
// src/components/Greeting.tsx
interface GreetingProps {
  name: string;
}

function Greeting(props: GreetingProps) {
  return <h1>Привіт, {props.name}!</h1>;
}

export default Greeting;
```

**Використання:**

```tsx
// src/App.tsx
import Greeting from './components/Greeting';

function App() {
  return (
    <div>
      <Greeting name="Олександр" />
      <Greeting name="Марія" />
      <Greeting name="Іван" />
    </div>
  );
}
```

**Результат у DOM:**

```html
<div>
  <h1>Привіт, Олександр!</h1>
  <h1>Привіт, Марія!</h1>
  <h1>Привіт, Іван!</h1>
</div>
```

::note
**Що відбувається під капотом:**

Коли ви пишете `<Greeting name="Олександр" />`, React викликає вашу функцію та передає пропси як об'єкт:

```js
Greeting({ name: "Олександр" })
```

Усі атрибути JSX-тегу збираються в один об'єкт `props`. Тому `props.name` дорівнює `"Олександр"`.

::

### Деструктуризація пропсів

Замість того, щоб кожного разу писати `props.name`, `props.age`, можна **деструктурувати** об'єкт `props` прямо у параметрах функції:

```tsx
// Без деструктуризації
function UserCard(props: { name: string; age: number; role: string }) {
  return (
    <div>
      <h2>{props.name}</h2>
      <p>Вік: {props.age}</p>
      <p>Роль: {props.role}</p>
    </div>
  );
}

// З деструктуризацією (рекомендований стиль)
function UserCard({ name, age, role }: { name: string; age: number; role: string }) {
  return (
    <div>
      <h2>{name}</h2>
      <p>Вік: {age}</p>
      <p>Роль: {role}</p>
    </div>
  );
}
```

**Переваги деструктуризації:**

- **Коротший код:** `name` замість `props.name`.
- **Явність:** Відразу видно, які пропси використовує компонент.
- **Автодоповнення:** TypeScript краще підказує властивості.

**Винесення типу у окремий інтерфейс:**

```tsx
interface UserCardProps {
  name: string;
  age: number;
  role: string;
}

function UserCard({ name, age, role }: UserCardProps) {
  return (
    <div>
      <h2>{name}</h2>
      <p>Вік: {age}</p>
      <p>Роль: {role}</p>
    </div>
  );
}
```

::tip
**Конвенція іменування типів пропсів:**

Називайте інтерфейс пропсів як `{ComponentName}Props`:

```tsx
interface ButtonProps { ... }
interface ModalProps { ... }
interface UserProfileProps { ... }
```

Це стандарт у React-спільноті, що полегшує навігацію по коду.

::



### Опціональні пропси

Не всі пропси обов'язкові. У TypeScript опціональні властивості позначаються знаком `?`:

```tsx
interface GreetingProps {
  name: string;
  age?: number;  // Опціональний пропс
  role?: string; // Опціональний пропс
}

function Greeting({ name, age, role }: GreetingProps) {
  return (
    <div>
      <h1>Привіт, {name}!</h1>
      {age && <p>Вік: {age}</p>}
      {role && <p>Роль: {role}</p>}
    </div>
  );
}

// Використання
<Greeting name="Олександр" />  {/* age та role не передані */}
<Greeting name="Марія" age={25} role="Designer" />
```

**Значення за замовчуванням:**

Якщо пропс не переданий, можна встановити значення за замовчуванням через деструктуризацію:

```tsx
interface ButtonProps {
  label: string;
  variant?: 'primary' | 'secondary';
  disabled?: boolean;
}

function Button({ label, variant = 'primary', disabled = false }: ButtonProps) {
  return (
    <button 
      className={`btn btn-${variant}`}
      disabled={disabled}
    >
      {label}
    </button>
  );
}

// Використання
<Button label="Зберегти" />  
// variant буде 'primary', disabled буде false

<Button label="Скасувати" variant="secondary" />
// variant буде 'secondary', disabled буде false
```

## Props є незмінними (immutable)

**Фундаментальне правило React:** компонент **ніколи не повинен змінювати свої пропси**.

```tsx
function UserCard({ name, age }: { name: string; age: number }) {
  // ❌ НЕПРАВИЛЬНО — спроба змінити props
  name = "Інше ім'я";  // TypeScript покаже помилку!
  
  return <div>{name}</div>;
}
```

**Чому props є read-only?**

1. **Однонаправлений потік даних:** Дані рухаються від батьківського компонента до дочірнього. Якщо дочірній змінить props, батьківський не дізнається про це — виникне неузгодженість стану.

2. **Передбачуваність:** React покладається на те, що props не змінюються під час рендерингу. Якщо ви змінюєте props, React не може ефективно визначити, що оновити.

3. **Чисті функції:** React-компоненти мають бути **чистими функціями** — вони повертають однаковий результат для однакових вхідних даних (props) без побічних ефектів.

::note
**Чисті функції у програмуванні:**

**Чиста функція** — це функція, яка:

1. **Повертає однаковий результат** для однакових аргументів.
2. **Не має побічних ефектів** — не змінює зовнішній стан, не викликає IO-операції, не змінює аргументи.

```js
// ✅ Чиста функція
function sum(a, b) {
  return a + b;
}

// ❌ Нечиста функція — змінює зовнішню змінну
let total = 0;
function addToTotal(value) {
  total += value;  // Побічний ефект!
  return total;
}

// ❌ Нечиста функція — змінює аргумент
function addItem(array, item) {
  array.push(item);  // Мутація аргумента!
  return array;
}
```

React-компоненти мають бути чистими відносно props:

```tsx
// ✅ Чистий компонент
function Greeting({ name }: { name: string }) {
  return <h1>Привіт, {name}!</h1>;
}

// ❌ Нечистий компонент — змінює props
function Greeting({ name }: { name: string }) {
  name = name.toUpperCase();  // Мутація!
  return <h1>Привіт, {name}!</h1>;
}
```

::

**Якщо потрібна локальна копія пропса:**

Використовуйте **локальний стан** (`useState`), про який ми детально поговоримо у наступних лекціях:

```tsx
import { useState } from 'react';

function EditableLabel({ initialValue }: { initialValue: string }) {
  // Створюємо локальну копію у стані
  const [value, setValue] = useState(initialValue);

  return (
    <input
      type="text"
      value={value}
      onChange={(e) => setValue(e.target.value)}
    />
  );
}
```

## Передача функцій через props

Props можуть містити не лише дані, а й **функції**. Це дозволяє дочірнім компонентам **комунікувати з батьківськими**.

### Приклад: кнопка з обробником події

```tsx
// src/components/Button.tsx
interface ButtonProps {
  label: string;
  onClick: () => void;  // Функція без параметрів, що не повертає значення
}

function Button({ label, onClick }: ButtonProps) {
  return (
    <button onClick={onClick} className="btn">
      {label}
    </button>
  );
}

export default Button;
```

**Використання:**

```tsx
// src/App.tsx
import { useState } from 'react';
import Button from './components/Button';

function App() {
  const [count, setCount] = useState(0);

  const handleIncrement = () => {
    setCount(count + 1);
  };

  const handleDecrement = () => {
    setCount(count - 1);
  };

  return (
    <div>
      <h1>Лічильник: {count}</h1>
      <Button label="Збільшити" onClick={handleIncrement} />
      <Button label="Зменшити" onClick={handleDecrement} />
    </div>
  );
}
```

**Що відбувається:**

1. Батьківський компонент `App` передає функцію `handleIncrement` через пропс `onClick`.
2. Дочірній компонент `Button` отримує цю функцію та викликає її при кліку на кнопку.
3. Виклик функції змінює стан у батьківському компоненті, що призводить до перерендерингу.

::tip
**Передача даних назад:**

Якщо дочірньому компоненту потрібно передати дані батьківському, функція у props може приймати параметри:

```tsx
interface SearchInputProps {
  onSearch: (query: string) => void;  // Функція приймає рядок
}

function SearchInput({ onSearch }: SearchInputProps) {
  const [value, setValue] = useState('');

  const handleSubmit = () => {
```

## Композиція через `children`

Одна з найпотужніших можливостей React — **композиція компонентів** через спеціальний пропс `children`.

### Що таке `children`?

**`children`** — це вміст між відкриваючим та закриваючим тегами компонента.

```tsx
<Card>
  <h2>Заголовок</h2>
  <p>Параграф</p>
</Card>
```

Усе, що знаходиться між `<Card>` та `</Card>`, автоматично передається як `props.children`.

### Створення контейнерних компонентів

```tsx
// src/components/Card.tsx
interface CardProps {
  children: React.ReactNode;  // Тип для children
}

function Card({ children }: CardProps) {
  return (
    <div className="card">
      {children}
    </div>
  );
}

export default Card;
```

**Використання:**

```tsx
import Card from './components/Card';

function App() {
  return (
    <div>
      <Card>
        <h2>Заголовок картки</h2>
        <p>Це вміст картки.</p>
        <button>Дія</button>
      </Card>

      <Card>
        <img src="photo.jpg" alt="Фото" />
        <p>Опис фото</p>
      </Card>

      <Card>
        <ul>
          <li>Пункт 1</li>
          <li>Пункт 2</li>
        </ul>
      </Card>
    </div>
  );
}
```

**Результат:** Кожна `<Card>` обгортає свій вміст у `<div className="card">`, додаючи стилі та структуру.

::note
**Тип `React.ReactNode`:**

`React.ReactNode` — це універсальний тип для всього, що може бути відрендерене React:

```ts
type ReactNode =
  | ReactElement       // JSX-елементи (<div>, <Component />)
  | string             // Текст
  | number             // Числа
  | boolean            // true/false (не рендеряться)
  | null               // Не рендериться
  | undefined          // Не рендериться
  | ReactNode[]        // Масив будь-чого з вищезгаданого
```

Використовуйте `React.ReactNode` для `children`, якщо компонент приймає будь-який контент.

::

### Композиція замість успадкування

У React **композиція переважає над успадкуванням** (*composition over inheritance*). Замість того, щоб створювати ієрархію класів через `extends`, ви комбінуєте компоненти.

**Антипатерн (успадкування у класових компонентах, застаріле):**

```tsx
// ❌ Застарілий підхід — успадкування
class BaseButton extends React.Component {
  render() {
    return <button>{this.props.label}</button>;
  }
}

class PrimaryButton extends BaseButton {
  render() {
    return <button className="primary">{this.props.label}</button>;
  }
}
```

**Сучасний підхід (композиція):**

```tsx
// ✅ Сучасний підхід — композиція
interface ButtonProps {
  children: React.ReactNode;
  variant?: 'primary' | 'secondary';
}

function Button({ children, variant = 'primary' }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`}>
      {children}
    </button>
  );
}

// Використання
<Button variant="primary">Зберегти</Button>
<Button variant="secondary">Скасувати</Button>
```

**Переваги композиції:**

- **Гнучкість:** Легко комбінувати різні компоненти.
- **Простота:** Немає складних ланцюгів успадкування.
- **Переповторне використання:** Компоненти незалежні один від одного.

## Іменовані слоти через комбінацію props

Іноді потрібно передати кілька незалежних фрагментів контенту у різні частини компонента. Це досягається через **комбінацію звичайних props та `children`**.

### Приклад: модальне вікно з header, body та footer

```tsx
// src/components/Modal.tsx
interface ModalProps {
  children: React.ReactNode;      // Основний контент (body)
  header: React.ReactNode;         // Заголовок
  footer?: React.ReactNode;        // Футер (опціонально)
  onClose: () => void;
}

function Modal({ children, header, footer, onClose }: ModalProps) {
  return (
    <div className="modal-overlay" onClick={onClose}>
      <div className="modal" onClick={(e) => e.stopPropagation()}>
        <div className="modal-header">
          {header}
          <button className="close-btn" onClick={onClose}>×</button>
        </div>
        
        <div className="modal-body">
          {children}
        </div>

        {footer && (
          <div className="modal-footer">
            {footer}
          </div>
        )}
      </div>
    </div>
  );
}

export default Modal;
```

**Використання:**

```tsx
import { useState } from 'react';
import Modal from './components/Modal';

function App() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(true)}>Відкрити модалку</button>

      {isOpen && (
        <Modal
          header={<h2>Підтвердження дії</h2>}
          footer={
            <>
              <button onClick={() => setIsOpen(false)}>Скасувати</button>
              <button onClick={() => alert('Підтверджено!')}>Підтвердити</button>
            </>
          }
          onClose={() => setIsOpen(false)}
        >
          <p>Ви впевнені, що хочете видалити цей елемент?</p>
          <p>Цю дію неможливо скасувати.</p>
        </Modal>
      )}
    </div>
  );
}
```

**Переваги підходу:**

- **Гнучкість:** Можна передати будь-який JSX у кожен слот.
- **Типобезпека:** TypeScript перевіряє, що ви передали всі обов'язкові пропси.
- **Читабельність:** Чітко видно, що саме передається у header, body та footer.

**Переваги розбиття на дрібні компоненти:**

1. **Переповторне використання:** `ProductRating` можна використати у інших місцях (у списках, на сторінці товару).
2. **Тестування:** Легше тестувати `ProductRating` окремо, ніж весь `ProductCard`.
3. **Підтримуваність:** Зміни у рейтингу торкаються лише `ProductRating`, а не всього `ProductCard`.
4. **Командна робота:** Різні розробники можуть працювати над різними компонентами.

::

::warning
**Коли НЕ варто розбивати на дрібні компоненти:**

Не створюйте компоненти заради компонентів. Якщо частина UI:

- Не переповторно використовується в інших місцях.
- Складається з 2-3 рядків JSX.
- Не має власної логіки.

...тоді залишайте її як частину батьківського компонента. **Над-інженерія** (*over-engineering*) шкодить так само, як і недо-інженерія.

**Приклад над-інженерії:**

```tsx
// ❌ Занадто дрібно
function ProductPriceLabel({ children }: { children: React.ReactNode }) {
  return <span className="price-label">{children}</span>;
}

function ProductPriceCurrency({ children }: { children: React.ReactNode }) {
  return <span className="currency">{children}</span>;
}

function ProductPrice({ amount }: { amount: number }) {
  return (
    <div>
      <ProductPriceLabel>{amount}</ProductPriceLabel>
      <ProductPriceCurrency>грн</ProductPriceCurrency>
    </div>
  );
}

// ✅ Достатньо просто
function ProductPrice({ amount }: { amount: number }) {
  return <div className="price">{amount} грн</div>;
}
```

### 1. Один компонент — одна відповідальність

```tsx
      <header>...</header>
```

## Підсумок

::card-group

::card{title="✅ Що ми опанували" icon="i-lucide-check-circle"}

- **Компонент** — це функція, що повертає JSX і описує частину UI.
- **Props** — незмінні дані, що передаються від батьківського компонента до дочірнього.
- **Композиція через `children`** дозволяє будувати складні компоненти з простих.
- **Деструктуризація props** робить код читабельнішим.
- **TypeScript типізація** забезпечує безпеку та автодоповнення.

::

::card{title="🔑 Ключові принципи" icon="i-lucide-key-round"}

- **Один компонент — одна відповідальність** (Single Responsibility Principle).
- **Композиція переважає над успадкуванням** (Composition over Inheritance).
- **Props є read-only** — ніколи не змінюйте їх.
- **Компоненти мають бути чистими функціями** відносно props.
- **Використовуйте унікальні `key`** у списках для ефективного reconciliation.

::

::

::tip
**Наступні кроки:**

У наступній лекції ми детально розглянемо **стан компонентів** (*state*) та хук `useState` — як зберігати та змінювати дані всередині компонентів, що призводить до їхнього перерендерингу.

## Запитання для самоперевірки

::::accordion

:::accordion-item{label="❓ Чому імена компонентів мають починатися з великої літери?" icon="i-lucide-help-circle"}

React розрізняє HTML-теги та компоненти за регістром першої літери:

- **Мала літера** (`<div>`, `<button>`) — React розуміє як HTML-тег.
- **Велика літера** (`<Button>`, `<UserCard>`) — React розуміє як компонент і викликає відповідну функцію.

Якщо ви назвете компонент з малої літери (`<button>`), React спробує знайти HTML-тег із такою назвою, а не викличе вашу функцію.

**Приклад:**

```tsx
function button() { return <div>Кнопка</div>; }  // ❌ Мала літера
<button />  // React шукає HTML-тег <button>, а не викликає функцію

function Button() { return <div>Кнопка</div>; }  // ✅ Велика літера
<Button />  // React викликає функцію Button()
```

:::

:::accordion-item{label="❓ Чи можна змінювати props всередині компонента?" icon="i-lucide-help-circle"}

**Ні**, props є **незмінними** (*immutable*) та **read-only**. Спроба змінити props порушує фундаментальний принцип React — однонаправлений потік даних (*unidirectional data flow*).

**Чому props є read-only:**

1. **Передбачуваність:** React покладається на те, що props не змінюються під час рендерингу.
2. **Ефективність:** React оптимізує reconciliation, припускаючи незмінність props.
3. **Чисті функції:** Компоненти мають бути чистими функціями — повертати однаковий результат для однакових вхідних даних.

**Якщо потрібна локальна копія:**

Використовуйте локальний стан через `useState`:

```tsx
function EditableLabel({ initialValue }: { initialValue: string }) {
  const [value, setValue] = useState(initialValue);
  
  return (
    <input 
      value={value} 
      onChange={(e) => setValue(e.target.value)} 
    />
  );
}
```

:::

:::accordion-item{label="❓ Що таке `children` і як його використовувати?" icon="i-lucide-help-circle"}

**`children`** — це спеціальний пропс, що містить вміст між відкриваючим та закриваючим тегами компонента.

**Приклад:**

```tsx
<Card>
  <h2>Заголовок</h2>
  <p>Контент</p>
</Card>
```

Усе між `<Card>` та `</Card>` передається як `props.children`.

**Реалізація компонента:**

```tsx
interface CardProps {
  children: React.ReactNode;
}

function Card({ children }: CardProps) {
  return <div className="card">{children}</div>;
}
```

**Тип `React.ReactNode`** охоплює все, що може бути відрендерено: JSX, рядки, числа, масиви, `null`, `undefined`.

:::

:::accordion-item{label="❓ Коли створювати новий компонент, а коли залишати код у існуючому?" icon="i-lucide-help-circle"}

**Створюйте новий компонент, якщо:**

1. **Частина UI переповторно використовується** у кількох місцях.
2. **Логіка складна** та заслуговує ізоляції (50+ рядків JSX).
3. **Потрібна окрема відповідальність** (Single Responsibility Principle).
4. **Потрібне окреме тестування** цієї частини UI.
5. **Потрібна окрема оптимізація** (наприклад, через `React.memo`).

**НЕ створюйте новий компонент, якщо:**

1. Частина UI складається з 2-3 рядків JSX без логіки.
2. Використовується лише в одному місці і не має власної відповідальності.
3. Не має власного стану або обробників подій.

**Приклад над-інженерії:**

```tsx
// ❌ Занадто дрібно — це просто <span>
function PriceLabel({ children }: { children: React.ReactNode }) {
  return <span className="price">{children}</span>;
}

// ✅ Достатньо залишити у батьківському компоненті
<span className="price">{price}</span>
```

:::

:::accordion-item{label="❓ Чи обов'язково типізувати props у TypeScript?" icon="i-lucide-help-circle"}

Технічно **не обов'язково** — TypeScript може вивести типи автоматично або можна використовувати `any`. Але **настійно рекомендується** для продакшн-коду.

**Переваги типізації props:**

1. **Виявлення помилок на етапі компіляції:** TypeScript покаже помилку, якщо ви передасте неправильний тип.
2. **Автодоповнення:** Редактор підказує доступні властивості.
3. **Документація:** Інтерфейс props є самодокументованим контрактом.
4. **Рефакторинг:** Зміна типу автоматично виявить всі місця, де потрібно оновити код.

**Порівняння:**

```tsx
// ❌ Без типізації — помилки виявляться у runtime
function Button(props) {
  return <button>{props.label}</button>;
}

<Button lable="Зберегти" />  // Typo! Помилка у runtime

// ✅ З типізацією — помилка на етапі компіляції
interface ButtonProps {
  label: string;
}

function Button({ label }: ButtonProps) {
  return <button>{label}</button>;
}

<Button lable="Зберегти" />  // TypeScript покаже помилку!
```
