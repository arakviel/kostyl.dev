# Можливо, вам не потрібен ефект: антипатерни та альтернативи

> 🔗 **Офіційний референс:** [Можливо, вам не потрібен ефект (You Might Not Need an Effect)](https://uk.react.dev/learn/you-might-not-need-an-effect)

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Розпізнавати типові антипатерни надмірного використання `useEffect`.
- Опанувати техніки усунення зайвих ефектів через обчислення під час рендеру.
- Навчитися скидати стан компонента через зміну ключа `key` без ефектів.
- Застосувати правильні місця для мережевих запитів та оновлень стану.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Антипатерн (*Anti-pattern*):** поширений спосіб написання коду, що здається правильним, але призводить до проблем.
- **Обчислювані значення (*Derived Values*):** дані, що можуть бути отримані з існуючого стану без додаткового зберігання.
- **Ключ компонента (*Component Key*):** спеціальний проп, зміна якого змушує React повністю перестворити компонент.
- **Каскадне оновлення (*Cascading Update*):** ситуація, коли одна зміна стану викликає ефект, що змінює інший стан.

::

## Чому надмірне використання ефектів є проблемою

Хук `useEffect` — це потужний інструмент для синхронізації компонентів із зовнішніми системами: мережевими API, браузерними подіями, таймерами. Проте багато розробників використовують його для речей, що не вимагають синхронізації з зовнішнім світом — просто для координації стану всередині React.

Це призводить до кількох системних проблем:

1. **Зайві рендери:** Ефект виконується **після** рендерингу, тому коли він змінює стан, компонент рендериться знову. Це створює каскад оновлень замість одного атомарного рендеру.
2. **Складність відстеження потоку даних:** Коли стан змінюється у багатьох місцях (у обробниках подій **та** в ефектах), стає важко зрозуміти, чому інтерфейс виглядає саме так.
3. **Проблеми з продуктивністю:** Кожен зайвий рендер — це додаткові обчислення, диференціювання віртуального DOM та можливі зміни реального DOM.
4. **Ускладнення тестування:** Логіка, розмазана між обробниками подій та ефектами, важче тестується ізольовано.

::note
**Золоте правило `useEffect`:**
Якщо ваш код не виходить за межі React (не звертається до DOM, мережі, таймерів, сторонніх бібліотек), швидше за все, вам не потрібен `useEffect`. Спочатку спробуйте вирішити задачу через звичайну логіку рендерингу або обробники подій.
::

## Антипатерн №1: Дублювання даних у стані через ефект

### ❌ Проблемний код: синхронізація через `useEffect`

Одна з найпоширеніших помилок — зберігати список у стані, а потім у `useEffect` обчислювати відфільтровану версію і зберігати її у другому стані:

```tsx
import { useState, useEffect } from "react";

interface Task {
  id: number;
  title: string;
  completed: boolean;
}

export function TaskListBad() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, title: "Вивчити React", completed: true },
    { id: 2, title: "Опанувати TypeScript", completed: false },
    { id: 3, title: "Побудувати проєкт", completed: false },
  ]);

  // ❌ Погано: обчислюємо відфільтровані задачі у окремому стані через ефект
  const [activeTasks, setActiveTasks] = useState<Task[]>([]);

  useEffect(() => {
    const filtered = tasks.filter((task) => !task.completed);
    setActiveTasks(filtered);
  }, [tasks]); // Ефект запускається при кожній зміні tasks

  return (
    <div>
      <h3>Активні задачі ({activeTasks.length})</h3>
      <ul>
        {activeTasks.map((task) => (
          <li key={task.id}>{task.title}</li>
        ))}
      </ul>
    </div>
  );
}
```

**Що тут не так:**

1. **Два рендери замість одного:** Коли `tasks` змінюється, React спочатку рендерить компонент з **застарілим** `activeTasks`, потім виконує ефект, оновлює `activeTasks` і запускає **другий рендер**.
2. **Дублювання джерела істини:** Тепер `activeTasks` — це копія даних, що може стати неконсистентною, якщо забути оновити її у всіх місцях.
3. **Зайва складність:** Лінтер вимагатиме додавання `tasks` у залежності, що створює відчуття «магічної синхронізації», хоча насправді це просте обчислення.

### ✅ Правильний підхід: обчислення під час рендеру

React **надзвичайно швидкий** у обчисленнях під час рендерингу. Фільтрація масиву з тисяч елементів займає мікросекунди — це не вимагає окремого стану:

```tsx
import { useState } from "react";

interface Task {
  id: number;
  title: string;
  completed: boolean;
}

export function TaskListGood() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, title: "Вивчити React", completed: true },
    { id: 2, title: "Опанувати TypeScript", completed: false },
    { id: 3, title: "Побудувати проєкт", completed: false },
  ]);

  // ✅ Правильно: обчислюємо на льоту під час рендерингу
  const activeTasks = tasks.filter((task) => !task.completed);

  return (
    <div>
      <h3>Активні задачі ({activeTasks.length})</h3>
      <ul>
        {activeTasks.map((task) => (
          <li key={task.id}>{task.title}</li>
        ))}
      </ul>
    </div>
  );
}
```

import { useState } from 'react';

interface Task {
  id: number;
  title: string;
  completed: boolean;
}

const initialTasks: Task[] = [
  { id: 1, title: 'Вивчити React', completed: true },
  { id: 2, title: 'Опанувати TypeScript', completed: false },
  { id: 3, title: 'Побудувати проєкт', completed: false },
  { id: 4, title: 'Написати тести', completed: false },
];

export default function App() {
  const [tasks, setTasks] = useState<Task[]>(initialTasks);
  const [newTaskTitle, setNewTaskTitle] = useState('');

  // ✅ Обчислюємо відфільтровані дані безпосередньо під час рендеру
  const activeTasks = tasks.filter(task => !task.completed);
  const completedTasks = tasks.filter(task => task.completed);

  const handleToggle = (id: number) => {
    setTasks(prev =>
      prev.map(task =>
        task.id === id ? { ...task, completed: !task.completed } : task
      )
    );
  };

  const handleAdd = () => {
    if (!newTaskTitle.trim()) return;
    
    setTasks(prev => [
      ...prev,
      { id: Date.now(), title: newTaskTitle, completed: false }
    ]);
    setNewTaskTitle('');
  };

  return (
    <div className="container">
      <div className="card">
        <h2>Список задач</h2>
        
        <div className="add-task">
          <input
            type="text"
            value={newTaskTitle}
            onChange={(e) => setNewTaskTitle(e.target.value)}
            onKeyDown={(e) => e.key === 'Enter' && handleAdd()}
            placeholder="Нова задача..."
            className="input"
          />
          <button onClick={handleAdd} className="btn">
            Додати
          </button>
        </div>

        <div className="stats">
          <div className="stat active">
            <span className="count">{activeTasks.length}</span>
            <span className="label">Активні</span>
          </div>
          <div className="stat completed">
            <span className="count">{completedTasks.length}</span>
            <span className="label">Завершені</span>
          </div>
        </div>

        <div className="tasks">
          {tasks.map(task => (
            <div key={task.id} className="task">
              <input
                type="checkbox"
                checked={task.completed}
                onChange={() => handleToggle(task.id)}
                className="checkbox"
              />
              <span className={task.completed ? 'task-title completed' : 'task-title'}>
                {task.title}
              </span>
            </div>
          ))}
        </div>

        <p className="hint">
          Фільтрація виконується на льоту без useEffect
        </p>
      </div>
    </div>
  );
}

**Чому це краще:**

- **Один рендер:** Коли `tasks` змінюється, відбувається лише один рендер із актуальними `activeTasks`.
- **Одне джерело істини:** `tasks` — єдине місце зберігання, всі інші дані обчислюються з нього.
- **Простіше тестування:** Логіка фільтрації може бути витягнута у чисту функцію та протестована окремо.

::tip
**Коли варто використовувати `useMemo`:**
Якщо фільтрація або трансформація займає помітний час (наприклад, сортування масиву з 10 000+ елементів за складним критерієм), оберніть обчислення у `useMemo`, щоб React кешував результат і пропускав повторні обчислення при рендерах, що не змінюють `tasks`:

```tsx
const activeTasks = useMemo(() => {
  return tasks.filter(task => !task.completed);
}, [tasks]);
```

Проте у 90% випадків обчислення настільки швидкі, що `useMemo` не потрібен і додає лише зайву складність.
::

## Антипатерн №2: Скидання стану при зміні пропса через ефект

### ❌ Проблемний код: синхронізація через `useEffect`

Типовий сценарій: у вас є форма редагування профілю, і коли користувач обирає іншого користувача зі списку, форма повинна показати дані нового користувача. Початківці часто пишуть такий код:

```tsx
import { useState, useEffect } from "react";

interface User {
  id: number;
  name: string;
  email: string;
}

interface ProfileFormProps {
  userId: number;
  users: User[];
}

export function ProfileFormBad({ userId, users }: ProfileFormProps) {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");

  // ❌ Погано: синхронізуємо стан форми через ефект при зміні userId
  useEffect(() => {
    const user = users.find((u) => u.id === userId);
    if (user) {
      setName(user.name);
      setEmail(user.email);
    }
  }, [userId, users]);

  return (
    <form>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <button type="submit">Зберегти</button>
    </form>
  );
}
```

**Проблеми цього підходу:**

1. **Каскадний рендер із застарілими даними:** Коли `userId` змінюється з `1` на `2`, React спочатку рендерить форму зі **старими** значеннями `name` та `email` (ті, що були для `userId: 1`), потім виконує ефект, оновлює стан і запускає другий рендер із новими даними. Користувач бачить мигтіння застарілих даних.
2. **Незграбна логіка:** Логіка ініціалізації форми розмазана між початковим станом та ефектом.
3. **Баг при редагуванні:** Якщо користувач почав редагувати форму для `userId: 1`, потім перемкнувся на `userId: 2` і повернувся до `userId: 1`, його незбережені зміни зникли, оскільки ефект скинув форму до вихідних даних.

### ✅ Правильний підхід: розділення компонентів через `key`

React має вбудований механізм для повного скидання стану компонента — зміна спеціального пропса `key`. Коли `key` змінюється, React **повністю видаляє** старий екземпляр компонента з DOM і створює новий з нуля, з чистим початковим станом:

```tsx
import { useState } from "react";

interface User {
  id: number;
  name: string;
  email: string;
}

interface ProfileFormProps {
  userId: number;
  users: User[];
}

function ProfileFormGood({ userId, users }: ProfileFormProps) {
  const user = users.find((u) => u.id === userId)!;
  
  // ✅ Початковий стан встановлюється один раз при монтуванні
  const [name, setName] = useState(user.name);
  const [email, setEmail] = useState(user.email);

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    console.log("Збереження:", { userId, name, email });
  };

  return (
    <form onSubmit={handleSubmit}>
      <label>
        Ім'я:
        <input value={name} onChange={(e) => setName(e.target.value)} />
      </label>
      <label>
        Email:
        <input value={email} onChange={(e) => setEmail(e.target.value)} />
      </label>
      <button type="submit">Зберегти</button>
    </form>
  );
}

// Батьківський компонент передає key={userId}
export function ProfileEditor() {
  const [selectedUserId, setSelectedUserId] = useState(1);
  
  const users: User[] = [
    { id: 1, name: "Олена Коваленко", email: "olena@example.com" },
    { id: 2, name: "Андрій Мельник", email: "andriy@example.com" },
    { id: 3, name: "Марія Шевченко", email: "maria@example.com" },
  ];

  return (
    <div>
      <select
        value={selectedUserId}
        onChange={(e) => setSelectedUserId(Number(e.target.value))}
      >
        {users.map((user) => (
          <option key={user.id} value={user.id}>
            {user.name}
          </option>
        ))}
      </select>

      {/* ✅ Зміна key повністю перестворює компонент без useEffect! */}
      <ProfileFormGood key={selectedUserId} userId={selectedUserId} users={users} />
    </div>
  );
}
```

import { useState } from 'react';

interface User {
  id: number;
  name: string;
  email: string;
  bio: string;
}

const users: User[] = [
  { id: 1, name: 'Олена Коваленко', email: 'olena@example.com', bio: 'Frontend-розробниця' },
  { id: 2, name: 'Андрій Мельник', email: 'andriy@example.com', bio: 'Backend-інженер' },
  { id: 3, name: 'Марія Шевченко', email: 'maria@example.com', bio: 'UX/UI дизайнерка' },
];

interface ProfileFormProps {
  userId: number;
}

function ProfileForm({ userId }: ProfileFormProps) {
  const user = users.find(u => u.id === userId)!;
  
  const [name, setName] = useState(user.name);
  const [email, setEmail] = useState(user.email);
  const [bio, setBio] = useState(user.bio);

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    alert(`Збережено профіль користувача #${userId}`);
  };

  return (
    <form onSubmit={handleSubmit} className="form">
      <div className="field">
        <label>Ім'я</label>
        <input
          type="text"
          value={name}
          onChange={(e) => setName(e.target.value)}
          className="input"
        />
      </div>
      
      <div className="field">
        <label>Email</label>
        <input
          type="email"
          value={email}
          onChange={(e) => setEmail(e.target.value)}
          className="input"
        />
      </div>
      
      <div className="field">
        <label>Про себе</label>
        <textarea
          value={bio}
          onChange={(e) => setBio(e.target.value)}
          className="textarea"
          rows={3}
        />
      </div>
      
      <button type="submit" className="btn">
        Зберегти зміни
      </button>
    </form>
  );
}

export default function App() {
  const [selectedUserId, setSelectedUserId] = useState(1);

  return (
    <div className="container">
      <div className="card">
        <h2>Редагування профілю</h2>
        
        <div className="selector">
          <label>Оберіть користувача:</label>
          <select
            value={selectedUserId}
            onChange={(e) => setSelectedUserId(Number(e.target.value))}
            className="select"
          >
            {users.map(user => (
              <option key={user.id} value={user.id}>
                {user.name}
              </option>
            ))}
          </select>
        </div>

        {/* key={selectedUserId} перестворює форму при зміні користувача */}
        <ProfileForm key={selectedUserId} userId={selectedUserId} />
        
        <p className="hint">
          Спробуйте змінити дані форми, потім оберіть іншого користувача — форма скинеться автоматично
        </p>
      </div>
    </div>
  );
}

Коли `key` змінюється, React трактує це як **інший компонент**, а не як той самий компонент із новими пропсами.

## Антипатерн №3: Мережеві запити у `useEffect` замість обробників подій

### ❌ Проблемний код: розділення логіки між обробником та ефектом

Ще один поширений антипатерн — встановлювати прапорець у обробнику події, а потім у `useEffect` реагувати на зміну цього прапорця:

```tsx
import { useState, useEffect } from "react";

export function ProductCardBad() {
  const [isInCart, setIsInCart] = useState(false);

  // ❌ Погано: робимо мережевий запит у ефекті
  useEffect(() => {
    if (isInCart) {
      fetch("/api/cart", {
        method: "POST",
        body: JSON.stringify({ productId: 123 }),
      });
    }
  }, [isInCart]);

  return (
    <button onClick={() => setIsInCart(true)}>
      Додати до кошика
    </button>
  );
}
```

**Проблеми:**

1. **Незрозумілий потік даних:** Читаючи код, складно зрозуміти, що натискання кнопки викликає мережевий запит.
2. **Зайвий рендер:** React спочатку рендерить компонент із `isInCart: true`, потім виконує ефект.
3. **Неправильна семантика:** `useEffect` призначений для синхронізації з зовнішніми системами, а не для обробки дій користувача.

### ✅ Правильний підхід: мережевий запит безпосередньо в обробнику

Мережеві запити у відповідь на дії користувача належать до **обробників подій**, а не до ефектів:

```tsx
import { useState } from "react";

export function ProductCardGood() {
  const [isInCart, setIsInCart] = useState(false);
  const [isLoading, setIsLoading] = useState(false);

  const handleAddToCart = async (): Promise<void> => {
    setIsLoading(true);

    try {
      await fetch("/api/cart", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ productId: 123 }),
      });

      setIsInCart(true);
    } catch (error) {
      console.error("Помилка додавання до кошика:", error);
      alert("Не вдалося додати товар до кошика");
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <button onClick={handleAddToCart} disabled={isInCart || isLoading}>
      {isLoading ? "Додавання..." : isInCart ? "У кошику ✓" : "Додати до кошика"}
    </button>
  );
}
```

**Переваги:**

- **Ясність:** Вся логіка обробки кліку зосереджена в одному місці.
- **Один рендер:** Стан оновлюється лише після успішної відповіді сервера.
- **Обробка помилок:** Логіка помилок природно вписується у `try-catch`.

## Антипатерн №4: Сповіщення батьківського компонента через ефект

### ❌ Проблемний код: виклик колбека в `useEffect`

Іноді дочірній компонент намагається повідомити батьківський про зміну стану через ефект:

```tsx
import { useState, useEffect } from "react";

interface SearchInputProps {
  onChange: (value: string) => void;
}

export function SearchInputBad({ onChange }: SearchInputProps) {
  const [query, setQuery] = useState("");

  // ❌ Погано: викликаємо колбек у ефекті
  useEffect(() => {
    onChange(query);
  }, [query, onChange]);

  return (
    <input
      value={query}
      onChange={(e) => setQuery(e.target.value)}
      placeholder="Пошук..."
    />
  );
}
```

**Проблеми:**

1. **Каскадне оновлення:** Спочатку `SearchInputBad` оновлює власний стан, рендериться, потім виконує ефект, який викликає `onChange`, що може змінити стан батьківського компонента і спричинити його рендер.
2. **Зайва складність:** Лінтер вимагає `onChange` у залежностях, що може призвести до проблем, якщо батьківський компонент передає нову функцію при кожному рендері.
3. **Непотрібний ефект:** Це не синхронізація з зовнішньою системою — це просто передача даних вгору.

### ✅ Правильний підхід: виклик колбека безпосередньо в обробнику

Дочірній компонент повинен викликати батьківський колбек **безпосередньо у відповідь на подію**, а не через ефект:

```tsx
import { useState } from "react";

interface SearchInputProps {
  onChange: (value: string) => void;
}

export function SearchInputGood({ onChange }: SearchInputProps) {
  const [query, setQuery] = useState("");

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>): void => {
    const newValue = e.target.value;
    setQuery(newValue);
    
    // ✅ Правильно: викликаємо колбек безпосередньо в обробнику
    onChange(newValue);
  };

  return (
    <input
      value={query}
      onChange={handleChange}
      placeholder="Пошук..."
    />
  );
}
```

**Або ще простіше — взагалі не зберігати локальний стан:**

```tsx
interface SearchInputProps {
  value: string;
  onChange: (value: string) => void;
}

export function SearchInputSimple({ value, onChange }: SearchInputProps) {
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.target.value)}
      placeholder="Пошук..."
    />
  );
}
```

Тепер батьківський компонент повністю контролює стан, а дочірній просто повідомляє про події. Це класичний патерн **контрольованого компонента** (*controlled component*).

**Вихідний код:**

```tsx
import { useState, useEffect } from "react";

interface Product {
  id: number;
  name: string;
  category: string;
  price: number;
}

const products: Product[] = [
  { id: 1, name: "Ноутбук", category: "Електроніка", price: 25000 },

  { id: 4, name: "Стіл", category: "Меблі", price: 8000 },
];

export function ProductListBad() {
  const [selectedCategory, setSelectedCategory] = useState("Всі");
  const [filteredProducts, setFilteredProducts] = useState<Product[]>(products);

  useEffect(() => {
    if (selectedCategory === "Всі") {
      setFilteredProducts(products);
    } else {
      setFilteredProducts(products.filter(p => p.category === selectedCategory));
    }
  }, [selectedCategory]);

  return (
    <div>
      <select value={selectedCategory} onChange={(e) => setSelectedCategory(e.target.value)}>
        <option>Всі</option>
        <option>Електроніка</option>

      <ul>
        {filteredProducts.map(product => (
          <li key={product.id}>{product.name} — {product.price} грн</li>
        ))}
      </ul>
    </div>
  );
}
```

3. **Один рендер:** Коли користувач змінює категорію, відбувається лише один рендер із актуальними даними.

Створіть компонент `Counter`, який приймає проп `initialValue` та відображає лічильник із кнопками збільшення/зменшення. Батьківський компонент повинен мати кнопку «Скинути», яка повністю перезапускає лічильник до початкового значення.

**Вимоги:**
- **Не використовуйте `useEffect`** для синхронізації стану з пропсом.
- Використайте патерн `key` для перестворення компонента при натисканні кнопки «Скинути».
- Батьківський компонент повинен генерувати новий ключ при кожному скиданні.

**Підказка:** Можна використовувати `Date.now()` або лічильник для генерації унікального ключа.

import { useState } from "react";

            border: "none",
            borderRadius: "8px",
            background: "#ef4444",
            color: "white",
            fontWeight: "600",
            cursor: "pointer",

        >
          −1
        </button>
        <button 
          onClick={() => setCount(count + 1)}
          style={{
            padding: "10px 20px",
            border: "none",
            borderRadius: "8px",
            background: "#22c55e",
            color: "white",
            fontWeight: "600",
            cursor: "pointer",
          }}
        >
          +1
        </button>
      </div>
    </div>
  );
}

export function CounterDemo() {
  const [resetKey, setResetKey] = useState(0);

  const handleReset = () => {
    // ✅ Генеруємо новий ключ, що змушує React перестворити Counter
    setResetKey(prev => prev + 1);

  return (
    <div>

      <Counter key={resetKey} initialValue={10} />

1. **Компонент `Counter`:** Зберігає власний стан `count`, ініціалізований з пропса `initialValue` при монтуванні.
2. **Батьківський компонент:** Зберігає `resetKey` — просте число, що збільшується при кожному скиданні.
3. **Механізм скидання:** Коли `resetKey` змінюється (наприклад, з `0` на `1`), React бачить, що `key` пропс змінився, і **повністю видаляє старий екземпляр** `<Counter key={0} />`, потім **створює новий** `<Counter key={1} />` з чистим початковим станом.
4. **Без `useEffect`:** Жодної синхронізації не потрібно — React сам керує життєвим циклом компонента через `key`.

::note
**Альтернативний підхід із `Date.now()`:**

```tsx
const [resetKey, setResetKey] = useState(Date.now());

const handleReset = () => {
  setResetKey(Date.now());
};
```

Це гарантує унікальність ключа навіть при швидких повторних натисканнях.

## Підсумок: контрольний список перевірки `useEffect`

Перш ніж писати `useEffect`, задайте собі ці запитання:

::steps

### Питання 1: Чи це синхронізація з зовнішньою системою?

Якщо ваш код не взаємодіє з DOM, мережею, таймерами, WebSocket або сторонніми бібліотеками, `useEffect` швидше за все не потрібен.

**Приклад:** Фільтрація списку — це **обчислення**, а не синхронізація.

### Питання 2: Чи можу я обчислити це під час рендерингу?

Якщо дані можна отримати з існуючого стану через просте перетворення, обчисліть їх під час рендеру або через `useMemo`.

**Приклад:** `const total = items.reduce((sum, item) => sum + item.price, 0);`

### Питання 3: Чи це реакція на подію користувача?

Мережеві запити, аналітика, логування та інші дії у відповідь на клік, сабміт форми або введення тексту належать до **обробників подій**, а не до ефектів.

**Приклад:** Відправка форми — це обробник `onSubmit`, а не `useEffect`.

### Питання 4: Чи можу я використовувати `key` замість ефекту?

Якщо вам потрібно скинути стан компонента при зміні пропса, спробуйте спочатку змінити `key` — це простіше і швидше.

**Приклад:** `<Form key={userId} ... />` автоматично скине форму без `useEffect`.

::

::warning
**Пам'ятайте:**
`useEffect` — це не «хук для всього підряд». Це спеціалізований інструмент для **синхронізації компонентів із зовнішніми системами**. Якщо ви використовуєте його для координації стану всередині React, швидше за все, існує простіший спосіб.
::
