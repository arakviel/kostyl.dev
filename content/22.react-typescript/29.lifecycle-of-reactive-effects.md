# Життєвий цикл реактивних ефектів: мислення процесами синхронізації

> 🔗 **Офіційний референс:** [Життєвий цикл реактивних ефектів (Lifecycle of Reactive Effects)](https://uk.react.dev/learn/lifecycle-of-reactive-effects)

::card-group

::card{title="🎯 Мета лекції" icon="i-lucide-target"}

- Зрозуміти різницю між життєвим циклом компонента та життєвим циклом ефекту.
- Опанувати концепцію початку та кінця синхронізації замість монтування/розмонтування.
- Навчитися визначати реактивні значення та правильно вказувати залежності.
- Застосувати правило `exhaustive-deps` для запобігання застарілим замиканням.

::

::card{title="🔑 Ключові терміни" icon="i-lucide-key"}

- **Реактивне значення (*Reactive Value*):** будь-яка змінна, оголошена всередині компонента, що може змінюватися між рендерами.
- **Застаріле замикання (*Stale Closure*):** ситуація, коли функція всередині ефекту читає застаріле значення реактивної змінної.
- **Exhaustive Dependencies:** правило лінтера, що вимагає включення всіх реактивних значень у масив залежностей.
- **Повторна синхронізація (*Re-synchronization*):** процес зупинки попереднього ефекту та запуску нового з актуальними даними.

::

## Компоненти мають життєвий цикл, але ефекти мають інший

У попередніх лекціях ми вивчили, що React-компоненти проходять через три фази:

1. **Монтування (*Mount*):** компонент з'являється на екрані вперше.
2. **Оновлення (*Update*):** компонент перерендерюється через зміну пропсів або стану.
3. **Розмонтування (*Unmount*):** компонент видаляється з DOM назавжди.

Початківці часто намагаються мислити про ефекти в тих самих категоріях: «цей ефект запускається при монтуванні», «цей — при оновленні», «цей — при розмонтуванні». Проте **це хибна ментальна модель**, яка призводить до багів.

::note
**Нова парадигма мислення:**
Ефект не думає категоріями «перший рендер чи п'ятий». Ефект вміє лише дві речі:
- **Почати синхронізацію** із зовнішньою системою (підключитися до сервера, підписатися на подію, запустити анімацію).
- **Припинити синхронізацію** (від'єднатися від сервера, відписатися від події, зупинити анімацію).

Кількість циклів початку/зупинки **залежить виключно від залежностей**, а не від кількості рендерів компонента.
::

## Життєвий цикл ефекту: початок і кінець синхронізації

Розглянемо компонент чату, що підключається до серверної кімнати:

```tsx
import { useEffect } from "react";

interface ChatRoomProps {
  roomId: string;
}

function createConnection(roomId: string) {
  return {
    connect() {
      console.log(`✅ Підключення до кімнати "${roomId}"`);
    },
    disconnect() {
      console.log(`❌ Відключення від кімнати "${roomId}"`);
    },
  };
}

export function ChatRoom({ roomId }: ChatRoomProps) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();

    return () => {
      connection.disconnect();
    };
  }, [roomId]);

  return <h3>Ласкаво просимо до кімнати: {roomId}</h3>;
}
```

**Що відбувається при зміні `roomId` з `"general"` на `"travel"`:**

1. React рендерить компонент із новим `roomId: "travel"`.
2. React бачить, що значення `roomId` у масиві залежностей змінилося.
3. React **спочатку викликає функцію очищення попереднього ефекту** із старим `roomId: "general"`:
   ```
   ❌ Відключення від кімнати "general"
   ```
4. React **потім виконує новий ефект** із актуальним `roomId: "travel"`:
   ```
   ✅ Підключення до кімнати "travel"
   ```

## Реактивні значення: що повинно бути у залежностях

**Реактивне значення** (*reactive value*) — це будь-яка змінна, оголошена всередині тіла компонента, яка може змінюватися між рендерами. Це включає:

- **Пропси:** `props.userId`, `props.theme`, тощо.
- **Стан:** змінні, повернуті з `useState`.
- **Локальні змінні:** будь-яка змінна, обчислена з пропсів або стану.

```tsx
function ChatRoom({ roomId, serverUrl }: { roomId: string; serverUrl: string }) {
  const [isConnected, setIsConnected] = useState(false);
  
  // roomId, serverUrl, isConnected — всі реактивні!
  const connectionStatus = isConnected ? "підключено" : "відключено";
  
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    setIsConnected(true);

    return () => {
      connection.disconnect();
      setIsConnected(false);
    };
  }, [roomId, serverUrl]); // Обидва пропси обов'язкові!

  return <p>Статус: {connectionStatus}</p>;
}
```

::warning
**Що не є реактивним значенням:**

- **Константи та змінні поза компонентом:** Якщо змінна оголошена за межами тіла функції компонента, вона не змінюється між рендерами і не потребує включення у залежності.
- **Рефи (`useRef`):** Об'єкт рефа стабільний між рендерами, тому `.current` можна читати в ефекті без додавання до залежностей (проте зміна `.current` **не перезапускає** ефект).
- **Функції-сеттери стану:** `setCount`, `setIsConnected` тощо завжди стабільні і не потребують включення.

```tsx
// ✅ Ці значення не є реактивними:
const API_URL = "https://api.example.com"; // Поза компонентом
const timeoutRef = useRef<number | null>(null); // Реф
const [count, setCount] = useState(0); // setCount стабільна

useEffect(() => {
  // Можна використовувати без додавання до залежностей
  fetch(API_URL);
  timeoutRef.current = setTimeout(() => {}, 1000);
  setCount(10);
}, []);
```

## Правило вичерпних залежностей (Exhaustive Dependencies Rule)

ESLint має спеціальне правило для React — `react-hooks/exhaustive-deps`, яке аналізує код всередині `useEffect` та перевіряє, чи всі реактивні значення присутні у масиві залежностей. Це правило запобігає одній із найпоширеніших категорій багів у React: **застарілим замиканням** (*stale closures*).

### Застаріле замикання: приклад бага

```tsx
import { useState, useEffect } from "react";

export function CounterBug() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const intervalId = setInterval(() => {
      // ❌ БАГ: count завжди буде 0, оскільки замикання захопило початкове значення
      console.log(`Поточний лічильник: ${count}`);
    }, 1000);

    return () => clearInterval(intervalId);
  }, []); // Порожній масив — ефект виконується лише один раз

  return (
    <div>
      <p>Лічильник: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

**Що тут не так:**

1. Ефект запускається один раз при монтуванні, коли `count === 0`.
2. Колбек `setInterval` захоплює значення `count` у замиканні — воно «заморожується» на `0`.
3. Навіть коли користувач збільшує лічильник до `5`, інтервал продовжує виводити `Поточний лічильник: 0`.

::

### Виправлення через додавання залежності

```tsx
import { useState, useEffect } from "react";

export function CounterFixed() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const intervalId = setInterval(() => {
      // ✅ Тепер count завжди актуальне
      console.log(`Поточний лічильник: ${count}`);
    }, 1000);

    return () => clearInterval(intervalId);
  }, [count]); // Додали count у залежності

  return (
    <div>
      <p>Лічильник: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

**Проте це рішення має побічний ефект:**
Тепер ефект перезапускається **кожного разу**, коли `count` змінюється. Це означає, що інтервал скидається — якщо він мав вивести повідомлення через 500 мс, але `count` змінився раніше, інтервал зупиниться та запуститься знову з нульової мітки.

### Ідеальне рішення через функціональне оновлення

```tsx
import { useState, useEffect } from "react";

export function CounterBest() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const intervalId = setInterval(() => {
      // ✅ Використовуємо функціональну форму для читання актуального значення
      setCount((currentCount) => {
        console.log(`Поточний лічильник: ${currentCount}`);
        return currentCount; // Не змінюємо значення, лише читаємо
      });
    }, 1000);

    return () => clearInterval(intervalId);
  }, []); // Порожній масив — ефект виконується лише один раз

  return (
    <div>
      <p>Лічильник: {count}</p>
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
    </div>
  );
}
```

Тепер інтервал створюється лише один раз, але завжди читає актуальне значення `count` через функціональне оновлення стану.

::note
**Коли використовувати функціональне оновлення:**
Якщо ефект повинен читати актуальне значення стану, але **не повинен перезапускатися** при його зміні, використовуйте функціональну форму `setState((prev) => ...)`. Це дозволяє читати свіже значення без додавання його до залежностей.
::

## Лінтер `exhaustive-deps`: автоматичне виявлення помилок

Правило `react-hooks/exhaustive-deps` аналізує код ефекту та видає попередження, якщо:

1. **Забута залежність:** Ви читаєте реактивне значення всередині ефекту, але не додали його до масиву залежностей.
2. **Зайва залежність:** Ви додали у залежності значення, яке не є реактивним (константу поза компонентом).
3. **Нестабільна залежність:** Ви додали об'єкт або функцію, що створюється при кожному рендері.

### Приклад попередження лінтера

```tsx
function ChatRoom({ roomId }: { roomId: string }) {
  const [message, setMessage] = useState("");

  useEffect(() => {
    const connection = connectToChat(roomId);
    connection.send(message); // Читаємо message

    return () => connection.close();
  }, [roomId]); // ⚠️ React Hook useEffect has a missing dependency: 'message'

  return <input value={message} onChange={(e) => setMessage(e.target.value)} />;
}
```

**Що каже лінтер:**
```
React Hook useEffect has a missing dependency: 'message'.
Either include it or remove the dependency array.
```

**Два варіанти виправлення:**

1. **Додати `message` у залежності** (якщо ефект справді повинен перезапускатися при зміні повідомлення):
   ```tsx
   useEffect(() => {
     const connection = connectToChat(roomId);
     connection.send(message);
     return () => connection.close();
   }, [roomId, message]);
   ```

2. **Перемістити логіку в обробник події** (якщо відправка повинна відбуватися лише при натисканні кнопки, а не при кожній зміні):
   ```tsx
   const handleSend = () => {
     const connection = connectToChat(roomId);
     connection.send(message);
   };
   ```

::warning
**Ніколи не вимикайте лінтер через `eslint-disable`!**

```tsx
// ❌ ПОГАНО: ігнорування попередження лінтера
useEffect(() => {
  doSomething(value);
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, []);
```

Якщо лінтер скаржиться, це означає, що ваш код має **потенційний баг**. Замість вимикання правила, виправте код одним із способів:
- Додайте пропущені залежності.
- Винесіть статичний код за межі компонента.
- Використайте `useRef` для збереження нереактивних значень.
- Використайте функціональне оновлення стану.
::

## Порівняння залежностей: як React визначає зміни

React порівнює кожне значення у масиві залежностей із попереднім значенням за допомогою алгоритму `Object.is()`. Це строге порівняння, еквівалентне `===`, але з особливими випадками для `NaN` та `-0`.

```tsx
Object.is(5, 5);           // true
Object.is("hello", "hello"); // true
Object.is(true, false);    // false
Object.is({}, {});         // false (різні об'єкти!)
Object.is([], []);         // false (різні масиви!)
Object.is(NaN, NaN);       // true (відмінність від ===)
```

### Проблема нестабільних об'єктів та масивів

```tsx
function ProductList() {
  const [products, setProducts] = useState<Product[]>([]);

  useEffect(() => {
    // ❌ БАГ: options — новий об'єкт при кожному рендері!
    const options = { category: "electronics", sort: "price" };
    
    fetchProducts(options).then(setProducts);
  }, [options]); // ⚠️ options — нестабільна залежність

  // ...
}
```

**Проблема:** `options` створюється при кожному рендері. Навіть якщо його вміст (`{ category: "electronics", sort: "price" }`) однаковий, це **різні об'єкти в пам'яті**. `Object.is(prevOptions, options)` поверне `false`, і ефект запуститься знову, викликавши новий рендер → нескінченний цикл.

**Рішення 1: Винести об'єкт за межі компонента**

```tsx
// ✅ Об'єкт створюється один раз, стабільне посилання
const OPTIONS = { category: "electronics", sort: "price" };

function ProductList() {
  const [products, setProducts] = useState<Product[]>([]);

  useEffect(() => {
    fetchProducts(OPTIONS).then(setProducts);
  }, []); // Порожній масив — ефект виконується один раз
}
```

**Рішення 2: Використати `useMemo` для стабілізації об'єкта**

```tsx
function ProductList({ category }: { category: string }) {
  const [products, setProducts] = useState<Product[]>([]);

  // ✅ options перестворюється лише при зміні category
  const options = useMemo(() => ({
    category,
    sort: "price"
  }), [category]);

  useEffect(() => {
    fetchProducts(options).then(setProducts);
  }, [options]);
}
```

::tip
**Загальне правило:**
Якщо залежність — це об'єкт або масив, що створюється всередині компонента, використовуйте `useMemo` для стабілізації його посилання. Якщо залежність — це функція, використовуйте `useCallback`.
::

## Практичний приклад: чат із множинними залежностями

Розглянемо складніший сценарій — чат, що залежить від кімнати, URL сервера та теми для сповіщень:

```tsx
import { useState, useEffect } from "react";

interface ChatProps {
  roomId: string;
  serverUrl: string;
  theme: "light" | "dark";
}

function createConnection(serverUrl: string, roomId: string) {
  return {
    connect() {
      console.log(`✅ Підключення: ${serverUrl}/rooms/${roomId}`);
    },
    disconnect() {
      console.log(`❌ Відключення: ${serverUrl}/rooms/${roomId}`);
    },
    on(event: string, callback: () => void) {
      if (event === "message") {
        setTimeout(callback, 2000); // Симулюємо отримання повідомлення
      }
    },
  };
}

function showNotification(message: string, theme: "light" | "dark") {
  const bgColor = theme === "light" ? "#f0f0f0" : "#333";
  console.log(`🔔 [${theme} theme] ${message}`, `background: ${bgColor}`);
}

export function Chat({ roomId, serverUrl, theme }: ChatProps) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();

    connection.on("message", () => {
      showNotification(`Нове повідомлення у ${roomId}`, theme);
    });

    return () => {
      connection.disconnect();
    };
  }, [roomId, serverUrl, theme]); // Всі три значення реактивні!

  return (
    <div>
      <h3>Кімната: {roomId}</h3>
      <p>Сервер: {serverUrl}</p>
      <p>Тема: {theme}</p>
    </div>
  );
}
```

**Проблема цього коду:**
Якщо користувач просто перемикає тему з `"light"` на `"dark"`, чат **відключається від сервера та підключається знову**, хоча сокет-з'єднання не залежить від теми. Це зайва робота — ми розірвали з'єднання лише для того, щоб прочитати нове значення `theme` у колбеку сповіщень.

**Рішення:** У наступній лекції ми розглянемо техніки **розділення подій та ефектів**, що дозволяють читати актуальне значення `theme` без додавання його до залежностей ефекту.

:::accordion-item{label="📋 Завдання 1: Виправлення застарілого замикання" icon="i-lucide-clipboard-list"}

Наведений компонент містить баг застарілого замикання. Кнопка «Показати затримане повідомлення» показує значення `name` через 3 секунди, але завжди виводить застаріле значення, навіть якщо користувач змінив ім'я в інпуті.

**Вихідний код:**

```tsx
import { useState } from "react";

export function DelayedGreeting() {
  const [name, setName] = useState("Гість");

  const handleClick = () => {
    setTimeout(() => {
      // БАГ: name захоплено у замиканні при натисканні кнопки
      alert(`Привіт, ${name}!`);
    }, 3000);
  };

  return (
    <div>
      <input
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Введіть ім'я"
      />
      <button onClick={handleClick}>
        Показати затримане повідомлення (3 сек)
      </button>
    </div>
  );
}
```

**Завдання:** Виправте баг так, щоб `alert` завжди показував **актуальне** значення `name` на момент спрацювання таймера, а не на момент натискання кнопки.

**Підказка:** Використайте `useRef` для збереження актуального значення `name`.

:::

:::accordion-item{label="✅ Розв'язок завдання 1" icon="i-lucide-check-circle"}

```tsx
import { useState, useRef, useEffect } from "react";

export function DelayedGreetingFixed() {
  const [name, setName] = useState("Гість");
  const nameRef = useRef(name);

  // ✅ Синхронізуємо реф із актуальним значенням після кожного рендеру
  useEffect(() => {
    nameRef.current = name;
  }, [name]);

  const handleClick = () => {
    setTimeout(() => {
      // ✅ Читаємо актуальне значення з рефа
      alert(`Привіт, ${nameRef.current}!`);
    }, 3000);
  };

  return (
    <div>
      <input
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Введіть ім'я"
      />
      <button onClick={handleClick}>
        Показати затримане повідомлення (3 сек)
      </button>
      <p style={{ fontSize: "13px", color: "#64748b" }}>
        Натисніть кнопку, потім швидко змініть ім'я — повідомлення покаже нове значення
      </p>
    </div>
  );
}
```

**Покрокове пояснення:**

1. **Створення рефа:** `useRef(name)` створює об'єкт із властивістю `.current`, ініціалізованою початковим значенням `name`.
2. **Синхронізація рефа:** `useEffect` оновлює `nameRef.current` після кожного рендеру, коли `name` змінюється.
3. **Читання актуального значення:** Всередині `setTimeout` ми читаємо `nameRef.current`, що завжди містить найсвіжіше значення.
4. **Без залежностей у таймері:** Колбек `setTimeout` не захоплює `name` у замиканні — він лише читає реф, який завжди актуальний.

::note
**Альтернативне рішення без `useEffect`:**
Можна оновлювати реф безпосередньо в обробнику `onChange`:

```tsx
const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  const newName = e.target.value;
  setName(newName);
  nameRef.current = newName;
};
```

Проте використання `useEffect` є більш декларативним підходом і гарантує синхронізацію навіть якщо `name` змінюється з інших місць.
::

:::

:::accordion-item{label="📋 Завдання 2: Діагностика циклу ефектів" icon="i-lucide-clipboard-list"}

Наведений компонент має баг — він потрапляє у нескінченний цикл повторних рендерів. Проаналізуйте код та визначте, яка залежність викликає проблему.

**Вихідний код:**

```tsx
import { useState, useEffect } from "react";

interface User {
  id: number;
  name: string;
}

export function UserProfile() {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const fetchUser = async () => {
      const response = await fetch("/api/user/1");
      const data: User = await response.json();
      setUser(data);
    };

    fetchUser();
  }, [user]); // ⚠️ Тут криється проблема

  if (!user) {
    return <p>Завантаження...</p>;
  }

  return (
    <div>
      <h3>{user.name}</h3>
      <p>ID: {user.id}</p>
    </div>
  );
}
```

**Питання:**
1. Чому виникає нескінченний цикл?
2. Як виправити код?
3. Які залежності повинні бути у масиві?

:::

:::accordion-item{label="✅ Розв'язок завдання 2" icon="i-lucide-check-circle"}

**Аналіз проблеми:**

1. **Початковий стан:** `user === null`.
2. **Перший рендер:** React виконує ефект, завантажує дані, викликає `setUser(data)`.
3. **Другий рендер:** React рендерить компонент із новим `user`. Значення `user` у залежностях змінилося (`null` → `{id: 1, name: "..."}`) → React запускає ефект знову.
4. **Третій рендер:** Ефект знову завантажує дані, викликає `setUser` з новим об'єктом. Навіть якщо вміст однаковий, `Object.is(prevUser, newUser)` поверне `false` (різні об'єкти в пам'яті) → React запускає ефект знову.
5. **Нескінченний цикл:** Кроки 3-4 повторюються безкінечно.

**Правильне рішення:**

```tsx
import { useState, useEffect } from "react";

interface User {
  id: number;
  name: string;
}

export function UserProfileFixed() {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const fetchUser = async () => {
      const response = await fetch("/api/user/1");
      const data: User = await response.json();
      setUser(data);
    };

    fetchUser();
  }, []); // ✅ Порожній масив — завантажуємо дані лише один раз

  if (!user) {
    return <p>Завантаження...</p>;
  }

  return (
    <div>
      <h3>{user.name}</h3>
      <p>ID: {user.id}</p>
    </div>
  );
}
```

**Чому це працює:**

- **Порожній масив залежностей `[]`** означає, що ефект виконується лише один раз при монтуванні.
- Після завантаження даних та виклику `setUser`, компонент рендериться знову, але ефект більше не запускається.
- Дані завантажуються лише один раз, що є правильною поведінкою для початкового завантаження профілю.

**Коли `user` повинен бути у залежностях:**

Якщо ви хочете **перезавантажувати дані** при зміні ідентифікатора користувача:

```tsx
function UserProfile({ userId }: { userId: number }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const fetchUser = async () => {
      const response = await fetch(`/api/user/${userId}`);
      const data: User = await response.json();
      setUser(data);
    };

    fetchUser();
  }, [userId]); // ✅ userId — примітивне значення, безпечна залежність

  // ...
}
```

Тепер ефект перезапускається лише при зміні `userId` (наприклад, користувач перейшов до іншого профілю), а не при зміні самого об'єкта `user`.

:::

::::accordion

:::accordion-item{label="📋 Завдання 3: Виправлення нестабільної функції у залежностях" icon="i-lucide-clipboard-list"}

Компонент відправляє аналітичну подію на сервер при монтуванні, але потрапляє у нескінченний цикл через нестабільну залежність.

**Вихідний код:**

```tsx
import { useEffect } from "react";

interface AnalyticsProps {
  userId: number;
  page: string;
}

export function AnalyticsTracker({ userId, page }: AnalyticsProps) {
  const sendAnalytics = (event: string, data: object) => {
    console.log(`📊 Analytics: ${event}`, data);
    // У реальності тут був би fetch до сервера
  };

  useEffect(() => {
    sendAnalytics("page_view", { userId, page });
  }, [userId, page, sendAnalytics]); // ⚠️ sendAnalytics — нестабільна залежність

  return <p>Сторінка: {page}</p>;
}
```

**Завдання:** Виправте код так, щоб ефект не потрапляв у нескінченний цикл. Використайте одну з технік:
- Перенесення функції всередину ефекту
- Використання `useCallback`
- Винесення функції за межі компонента

:::

:::accordion-item{label="✅ Розв'язок завдання 3" icon="i-lucide-check-circle"}

**Рішення 1: Перенесення функції всередину ефекту**

```tsx
import { useEffect } from "react";

interface AnalyticsProps {
  userId: number;
  page: string;
}

export function AnalyticsTrackerFixed1({ userId, page }: AnalyticsProps) {
  useEffect(() => {
    // ✅ Функція оголошена всередині ефекту — не потрібна у залежностях
    const sendAnalytics = (event: string, data: object) => {
      console.log(`📊 Analytics: ${event}`, data);
    };

    sendAnalytics("page_view", { userId, page });
  }, [userId, page]); // Лише userId та page — примітивні значення

  return <p>Сторінка: {page}</p>;
}
```

**Рішення 2: Використання `useCallback` для стабілізації функції**

```tsx
import { useEffect, useCallback } from "react";

interface AnalyticsProps {
  userId: number;
  page: string;
}

export function AnalyticsTrackerFixed2({ userId, page }: AnalyticsProps) {
  // ✅ useCallback створює стабільну версію функції
  const sendAnalytics = useCallback((event: string, data: object) => {
    console.log(`📊 Analytics: ${event}`, data);
  }, []); // Порожній масив — функція ніколи не змінюється

  useEffect(() => {
    sendAnalytics("page_view", { userId, page });
  }, [userId, page, sendAnalytics]); // sendAnalytics тепер стабільна

  return <p>Сторінка: {page}</p>;
}
```

**Рішення 3: Винесення функції за межі компонента**

```tsx
import { useEffect } from "react";

interface AnalyticsProps {
  userId: number;
  page: string;
}

// ✅ Функція поза компонентом — стабільне посилання
function sendAnalytics(event: string, data: object) {
  console.log(`📊 Analytics: ${event}`, data);
}

export function AnalyticsTrackerFixed3({ userId, page }: AnalyticsProps) {
  useEffect(() => {
    sendAnalytics("page_view", { userId, page });
  }, [userId, page]); // sendAnalytics не є реактивною — не потрібна у залежностях

  return <p>Сторінка: {page}</p>;
}
```

**Яке рішення обрати:**

- **Рішення 1 (перенесення всередину):** Найпростіше, якщо функція потрібна лише у цьому ефекті.
- **Рішення 2 (`useCallback`):** Якщо функція використовується у кількох місцях (інші ефекти, обробники подій, передається як проп).
- **Рішення 3 (поза компонентом):** Якщо функція не потребує доступу до пропсів або стану компонента.

::tip
**Загальне правило:**
Якщо функція використовує пропси або стан, але **не повинна перезапускати ефект** при їх зміні, використовуйте `useCallback` із порожнім масивом залежностей або техніку рефів (як у завданні 1).
::

:::

## Підсумок: ключові принципи життєвого циклу ефектів

::card-group

::card{title="🔄 Цикл синхронізації" icon="i-lucide-refresh-cw"}

Ефект не думає про монтування/оновлення/розмонтування. Він вміє лише:
- **Почати синхронізацію** (setup)
- **Припинити синхронізацію** (cleanup)

Кількість циклів залежить від змін у залежностях.

::

::card{title="⚛️ Реактивні значення" icon="i-lucide-atom"}

Будь-яка змінна, оголошена всередині компонента, є реактивною:
- Пропси
- Стан
- Локальні змінні

Всі реактивні значення, прочитані в ефекті, **обов'язково** мають бути у залежностях.

::

::card{title="🔍 Правило exhaustive-deps" icon="i-lucide-search-check"}

Лінтер автоматично виявляє:
- Забуті залежності → застарілі замикання
- Нестабільні об'єкти/функції → нескінченні цикли

Ніколи не ігноруйте попередження — виправте код.

::

::card{title="🛠️ Техніки оптимізації" icon="i-lucide-wrench"}

Для уникнення зайвих перезапусків:
- Винесіть статичний код за межі компонента
- Використайте `useMemo` для об'єктів
- Використайте `useCallback` для функцій
- Використайте `useRef` для нереактивних значень

## Наступні кроки

У цій лекції ви опанували фундаментальні принципи життєвого циклу реактивних ефектів: як React порівнює залежності, чому виникають застарілі замикання, та як лінтер `exhaustive-deps` допомагає уникати багів.

- **Наступна лекція:** «Розділення подій та ефектів» — розглянемо складнішу проблему: як прочитати свіже значення стану **без** додавання його до залежностей через техніку рефів та експериментальний хук `useEffectEvent`.
- **Подальші теми:** видалення зайвих залежностей ефектів, кастомні хуки для інкапсуляції логіки синхронізації, розширені патерни роботи з асинхронними ефектами.

::tip
**Практична рекомендація:**
Перегляньте існуючий код свого проєкту та знайдіть усі місця, де:
1. Масив залежностей містить об'єкти або функції — можливо, вони створюються при кожному рендері.
2. Лінтер видає попередження про пропущені залежності — не ігноруйте їх, виправте через одну з технік цієї лекції.
3. Ефекти запускаються частіше, ніж потрібно — проаналізуйте залежності та оптимізуйте через `useMemo`/`useCallback`.
::
